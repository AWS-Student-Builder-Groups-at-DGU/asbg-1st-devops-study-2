## Day 16. Resource Requests & Limits

### 1. 필요한 이유
- 파드(컨테이너)는 실행에 **CPU, 메모리** 같은 리소스가 필요함
- request/limit을 **지정하지 않으면** 생기는 문제
  - 부하가 늘면 파드 하나가 **노드의 리소스를 전부 차지**할 수 있음
  - 노드 메모리가 바닥나면 **OOM Killer**가 돌면서 **다른 파드까지 죽음** → 노드 전체가 위험
- 지정하면: 한도를 넘은 **그 파드만** 죽고, 노드와 다른 파드는 안전함

### 2. requests vs limits

| | requests | limits |
|---|---|---|
| 의미 | **최소 보장량** (하한선) | **최대 사용량** (상한선) |
| 쓰이는 곳 | **스케줄러**가 파드를 둘 노드를 고를 때 기준 | 실행 중 사용량의 상한 |
| 넘으면? | - | CPU → **Throttling** (느려질 뿐 안 죽음)<br>메모리 → **OOMKilled** (컨테이너 종료) |

- 모든 노드가 꽉 차면 → 파드는 `Pending` (`Insufficient cpu` / `Insufficient memory`)

### 3. YAML 작성 위치
- 리소스는 **컨테이너 단위**로 지정 → `containers[]` 아래 `resources`

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: memory-demo
  namespace: mem-example       
spec:
  containers:
    - name: memory-demo-ctr
      image: polinux/stress    
      resources:
        requests:
          memory: "100Mi"
        limits:
          memory: "200Mi"
      command: ["stress"]
      args: ["--vm", "1", "--vm-bytes", "150M", "--vm-hang", "1"]   
```

### 4. 실습 결과 정리

| 케이스 | requests / limits | 실제 사용 | 결과 |
|---|---|---|---|
| 1 | 100Mi / 200Mi | 150M | ✅ `Running` (범위 안) |
| 2 | 50Mi / 100Mi | 250M | ❌ `OOMKilled` → `CrashLoopBackOff` (limit 초과) |
| 3 | 1000Gi / 1000Gi | 150M | ❌ `Pending` — `Insufficient memory` (요청량을 줄 노드가 없음) |

- **limit 초과 = 실행 중에 죽음 (OOMKilled)** / **request 과다 = 아예 스케줄링 안 됨 (Pending)**
- 원인 확인은 `kubectl describe pod` → `Last State: Terminated, Reason: OOMKilled` 또는 Events의 `Insufficient memory`

## Day 17. Autoscaling (HPA / VPA)

### 1. 스케일링
- **수요(부하)에 맞춰 서버나 워크로드의 양/크기를 바꾸는 것**
- 지금까지는 `replicas`를 직접 바꾸는 **수동 스케일링** → 수천 개 파드/노드 환경에선 불가능
- 그래서 CPU/메모리 사용률 등을 보고 **자동으로** 조절하는 Autoscaling이 필요

### 2. Horizontal vs Vertical

<img width="827" height="301" alt="image" src="https://github.com/user-attachments/assets/44ee3f26-50f9-4b6b-ab98-8284d0f205a5" />


<img width="857" height="363" alt="image" src="https://github.com/user-attachments/assets/85fa80a8-ec45-4c9e-be0b-5f7e5e50ae70" />


| | Horizontal (수평) | Vertical (수직) |
|---|---|---|
| 방식 | **개수**를 늘리고 줄임 | **크기** 를 키우고 줄임 |
| 용어 | Scale **Out** / Scale **In** | Scale **Up** / Scale **Down** |
| 예시 | 파드 1개 → 5개 | 파드 1 CPU → 10 CPU |
| 재시작 | 필요 없음 | **재시작 필요** (더 큰 파드로 교체) |
| 적합한 앱 | 다운타임 없어야 하는 서비스 | 약간의 다운타임/재시작을 견딜 수 있는 비핵심 서비스 |

- AWS Auto Scaling Group(EC2 개수 증가) = 수평 / 더 큰 인스턴스로 교체 = 수직

### 3. Autoscaling 도구 정리 

| | 워크로드 (Pod) | 인프라 (Node) |
|---|---|---|
| **Horizontal** | **HPA** (Horizontal Pod Autoscaler) | **Cluster Autoscaler** |
| **Vertical** | **VPA** (Vertical Pod Autoscaler) | **Node Auto-provisioning** |

- **HPA만 쿠버네티스에 기본 내장**
- VPA는 별도 프로젝트라 직접 설치해야 함
- Cluster Autoscaler, Node Auto-provisioning은 주로 **클라우드 매니지드 서비스**(EKS, AKS, GKE)에서 제공 → kind/minikube 같은 로컬 환경에선 노드를 늘릴 수 없음

**그 외**
- **이벤트 기반 스케일링**: 502 에러 급증 같은 이벤트를 기준으로 확장 → **KEDA** (CNCF 프로젝트)
- **스케줄(Cron) 기반 스케일링**: 정해진 시간에 확장/축소

## Day 18. Health Probes

### 1. Probe란?
- 대상을 주기적으로 **검사·모니터링해서 필요한 조치를 취하는 것**
- 목적: 앱이 실패하면 자동으로 복구(**self-healing**)되어 사용자가 영향을 받지 않게 함

### 2. 세 가지 Probe 

| Probe | 역할 | 실패하면? |
|---|---|---|
| **livenessProbe** | 앱이 **살아있는지** 확인 | 컨테이너 **재시작** |
| **readinessProbe** | 앱이 **트래픽을 받을 준비**가 됐는지 확인 | 재시작 ❌, **트래픽만 안 보냄** (Ready 0/1) |
| **startupProbe** | 시작이 느린(레거시) 앱이 **다 켜졌는지** 확인 | 성공하기 전까지 liveness/readiness가 **동작 안 함** |


### 3. 헬스 체크 방식 3가지

| 방식 | 필드 | 성공 조건 |
|---|---|---|
| 명령어 실행 | `exec` | 명령의 종료 코드가 `0` (0이 아니면 실패) |
| HTTP 요청 | `httpGet` | 성공 응답 코드 (2xx~3xx). 500 등은 실패 |
| TCP 연결 | `tcpSocket` | 지정한 포트로 연결이 열리면 성공 |

- 3가지 Probe 모두 이 3가지 방식 중 하나를 사용

### 4. Probe 주요 속성

| 속성 | 의미 | 기본값 |
|---|---|---|
| `initialDelaySeconds` | 컨테이너 시작 후 **첫 검사까지 대기** 시간 | 0 |
| `periodSeconds` | 검사 **간격** | 10 |
| `failureThreshold` | **연속 몇 번 실패**해야 실패로 볼지 | **3** |
| `successThreshold` | 몇 번 성공해야 성공으로 볼지 | **1** |

- 예) `initialDelaySeconds: 5`, `periodSeconds: 5` → 5초 기다린 뒤, 그 후로 5초마다 검사
- 한 번 실패했다고 바로 재시작하지 않음 → **3번 연속** 실패해야 재시작
- 직접 안 적어도 `kubectl get pod <이름> -o yaml`로 보면 기본값이 채워져 있음

### 5. YAML 예시
probe는 `containers[]` 아래에 위치

**exec**
```yaml
spec:
  containers:
    - name: liveness
      image: busybox
      args: ["/bin/sh", "-c", "touch /tmp/healthy; sleep 30; rm -f /tmp/healthy; sleep 600"]
      livenessProbe:
        exec:
          command: ["cat", "/tmp/healthy"]
        initialDelaySeconds: 3
        periodSeconds: 3
```
- 0~30초: 파일 있음 → 성공 / 30초 후 파일 삭제 → `cat` 실패(종료 코드 ≠ 0) → 재시작 반복

**httpGet**
```yaml
      livenessProbe:
        httpGet:
          path: /healthz
          port: 8080
        initialDelaySeconds: 3
        periodSeconds: 3
```
- 응답 500 → 재시작 반복 

**tcpSocket**
```yaml
      livenessProbe:
        tcpSocket:
          port: 8080
        initialDelaySeconds: 3
        periodSeconds: 3
```
- 앱이 8080에서 리스닝 + probe도 8080 → 정상 (RESTARTS 0)
- probe만 3000으로 바꾸면 → `dial tcp ...:3000: connect: connection refused` → 재시작

**readinessProbe** — liveness와 **같은 레벨**에 이름만 바꿔서 작성
```yaml
      livenessProbe:
        httpGet: { path: /healthz, port: 8080 }
        initialDelaySeconds: 3
        periodSeconds: 3
      readinessProbe:
        httpGet: { path: /healthz, port: 8080 }
        initialDelaySeconds: 15
        periodSeconds: 10
```
- readiness 실패 → STATUS는 `Running`이어도 **READY `0/1`** (트래픽 안 받음)
