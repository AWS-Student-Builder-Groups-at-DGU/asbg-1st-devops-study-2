### Q1.

Namespace를 `test`, `prod`처럼 나눠 두면 서로 다른 namespace에 있는 Pod끼리는 통신이 막히나요?

<details>
<summary>정답</summary>
<br>

**막히지 않는다.**

Namespace는 리소스와 이름의 범위를 나누는 **논리적인 구분**이다. 나누기만 해서는 네트워크가 차단되지 않는다. 실습에서도 다른 namespace의 Pod IP로 요청하면 응답이 왔다.

실제로 namespace 간 통신을 막으려면 **NetworkPolicy**를 따로 설정해야 한다.

</details>

#### Q1-1(꼬리질문).

같은 namespace에서는 `web`처럼 Service 이름만 써도 접근되는데, 다른 namespace에서 똑같이 부르면 실패합니다. 왜 그런가요?

<details>
<summary>정답</summary>

<br>

**Pod의 DNS 검색 설정 때문이다.**

Pod 안의 `/etc/resolv.conf`에는 자기 namespace가 첫 번째 검색 도메인으로 들어가 있다.

```
search demo.svc.cluster.local svc.cluster.local cluster.local
```

그래서 이름만 쓰면 **호출한 Pod의 namespace에서 먼저** 찾는다. 다른 namespace에 있는 Service는 찾지 못한다.

</details>

#### Q1-2(꼬리질문).

그럼 다른 namespace의 Service에는 어떻게 접근해야 하나요?

<details>
<summary>정답</summary>
<br>

**대상 Service가 있는 namespace**까지 적어 준다.

| 형태 | 예시 |
| --- | --- |
| FQDN | `web.default.svc.cluster.local` |
| 축약형 | `web.default` |

`web.default`까지만 써도 나머지 `svc.cluster.local`은 검색 도메인에서 붙기 때문에 동작한다.

주소에 넣는 namespace는 **호출하는 쪽이 아니라 대상 Service가 속한 쪽**이다. 호출하는 Pod의 namespace를 넣으면 같은 이유로 실패한다.

</details>

### Q2.

Pod에 Init 컨테이너가 두 개 있으면 어떤 순서로 실행되고, 앱 컨테이너는 언제 시작되나요? 그리고 Pod 상태가 `Init:1/2`에서 멈춰 있다면 무슨 뜻인가요?

<details>
<summary>정답</summary>
<br>

**1. 실행 순서**

Init 컨테이너는 **적힌 순서대로 하나씩** 실행된다. 앞의 Init이 **성공적으로 종료**되어야 다음 Init이 시작되고, **모든 Init이 성공 종료된 뒤에야** 앱 컨테이너가 시작된다.

```
init 1 실행 → 성공 종료 → init 2 실행 → 성공 종료 → 앱 컨테이너 시작
```

Init이 `Running`이라는 건 아직 작업 중이라는 뜻이다. 그동안 앱은 계속 기다린다.

**2. `Init:1/2`의 의미**

**Init 두 개 중 하나만 끝났고, 두 번째 Init이 아직 끝나지 않았다**는 뜻이다. 앱 컨테이너는 아직 시작하지 않았으므로 앱 로그를 봐도 원인이 나오지 않는다.

```bash
kubectl logs <Pod> -c <두 번째 init 이름>   # 멈춘 Init의 로그
kubectl describe pod <Pod>                  # 컨테이너별 상태 확인
```

</details>

### Q3.

이번 주에 DaemonSet, Job, CronJob을 배웠습니다. 이미 배운 Deployment까지 포함해 네 가지를 각각 어떤 기준으로 고르나요?

<details>
<summary>정답</summary>

<br>

**"얼마나, 어디에, 언제까지 실행하느냐"**로 나눈다.

| 리소스 | 고르는 기준 | 예시 |
| --- | --- | --- |
| **Deployment** | 정해진 개수를 계속 유지 | 웹 서버 |
| **DaemonSet** | 노드마다 하나씩 계속 실행 | 로그 수집기, 모니터링 에이전트, kube-proxy |
| **Job** | 끝나는 것이 목표 | 일회성 스크립트 |
| **CronJob** | 일정마다 Job 생성 | 정기 보고서, 백업 |

Deployment와 DaemonSet은 계속 실행되어야 하는 Pod를, Job과 CronJob은 작업을 마치고 끝나야 하는 Pod를 관리한다.

</details>

### Q4.

같은 Pod 안의 컨테이너끼리는 무엇을 공유하나요? 그리고 보조 컨테이너인 Init 컨테이너와 Sidecar 컨테이너는 실행 시점과 실행 기간이 어떻게 다른가요?

<details>
<summary>정답</summary>
<br>

**1. 공유하는 것 — 네트워크와 볼륨**

- 항상 **같은 노드**에 함께 배치된다
- **Pod IP를 하나 같이 쓰기 때문에** 서로 `localhost`로 통신할 수 있다
- **같은 볼륨을 마운트하면** 파일을 주고받을 수 있다

다만 파일시스템 자체는 컨테이너마다 따로다. 파일을 공유하려면 볼륨을 마운트해야 한다.

**2. Init과 Sidecar의 차이**

| | Init 컨테이너 | Sidecar 컨테이너 |
| --- | --- | --- |
| 실행 시점 | 앱보다 먼저 | 앱과 함께 |
| 실행 기간 | 작업 끝나면 종료 | 앱과 계속 실행 |
| 예시 | 의존 Service 대기 | 로그 수집·전송 |

최신 쿠버네티스에서는 `initContainers`에 `restartPolicy: Always`를 붙이면 공식 Sidecar로 동작한다. 강의에서는 개념만 다뤘다.

</details>

### Q5.

CronJob은 시간이 되면 Pod를 직접 만들어서 작업을 실행하나요? 그리고 Job은 "한 번 실행하고 끝나는 작업"이라고 배웠는데, 정확히 한 번만 실행된다고 봐도 될까요?

<details>
<summary>정답</summary>
<br>

**1. CronJob → Job → Pod**

CronJob은 Pod를 **직접 만들지 않는다.** 시간이 되면 **Job을 만들고, 그 Job이 Pod를 만들어** 작업을 실행한다.

```
CronJob  →  Job  →  Pod
 (일정)     (완료)    (실행)
```

Deployment가 ReplicaSet을 거쳐 Pod를 만드는 구조와 비슷하다. YAML에도 `jobTemplate` 안에 Pod의 `template`이 들어 있고, **실행할 때마다 새 Job과 새 Pod**가 생긴다.

**2. 정확히 한 번은 아니다**

"한 번 실행"은 **끝까지 성공시키는 게 목적**이라는 뜻이지, 실행 횟수를 보장한다는 뜻이 아니다. Job은 Pod가 실패하면 `backoffLimit`만큼 **새 Pod로 다시 시도**하므로 작업이 여러 번 실행될 수 있다.

`restartPolicy: Never`도 같은 Pod에서 컨테이너를 재시작하지 않는다는 뜻일 뿐, Job이 새 Pod로 재시도하는 것까지 막지는 않는다.

</details>
