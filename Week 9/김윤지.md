# Day 10. Namespace

> 하나의 클러스터 안에서 리소스와 이름의 범위를 나누는 단위

## 1. Namespace란?

Namespace는 하나의 클러스터 안에서 **리소스를 논리적으로 나누는 범위**입니다.

지금까지 namespace를 지정하지 않고 만든 Pod, Deployment, Service는 모두 `default`에 들어갔습니다. 테스트용과 운영용 리소스가 한곳에 섞이면, 테스트 Pod를 지우려다 운영 Pod를 지우는 실수가 생기기 쉽습니다.

**Namespace로 얻는 것**

| 목적             | 설명                                                                                 |
| ---------------- | ------------------------------------------------------------------------------------ |
| 리소스 구분      | `test`, `prod`처럼 환경이나 팀 단위로 나눠 관리                                      |
| 이름 범위 분리   | 같은 namespace 안에서는 이름이 겹치면 안 되지만, 다른 namespace에서는 같은 이름 가능 |
| 작업 대상 명확화 | 조회·생성·삭제할 때 어느 범위에서 작업하는지 `-n`으로 지정                           |
| 정책 적용 단위   | RBAC(권한), ResourceQuota(자원 총량), LimitRange(기본값·상한)를 namespace별로 적용   |

```
하나의 Kubernetes 클러스터
├─ kube-system : 쿠버네티스 시스템 리소스
├─ test        : 테스트용 Pod, Deployment, Service
└─ prod        : 운영용 Pod, Deployment, Service
```

→ **Namespace는 "논리적 구분"입니다.** 만든다고 해서 namespace 사이의 통신이나 권한이 자동으로 막히지 않습니다. 통신을 막으려면 NetworkPolicy, 권한을 나누려면 RBAC를 따로 설정해야 합니다. 이 차이는 4절 실습에서 직접 확인합니다.

모든 리소스가 namespace에 속하는 것도 아닙니다.

| 구분                 | 예시                                                              |
| -------------------- | ----------------------------------------------------------------- |
| Namespace에 속함     | Pod, Deployment, ReplicaSet, Service, ConfigMap, Secret           |
| 클러스터 전체에 속함 | Node, PersistentVolume, Namespace 자체, ClusterRole, StorageClass |

```bash
kubectl api-resources --namespaced=false   # namespace에 속하지 않는 리소스 종류 확인
```

## 2. 기본 Namespace 살펴보기

```bash
kubectl get ns                       # namespace 목록 (ns = namespaces 축약형)
kubectl get all -n kube-system       # kube-system의 주요 리소스 조회
kubectl get all -n default           # default의 주요 리소스 조회
```

| Namespace            | 용도                                                                        |
| -------------------- | --------------------------------------------------------------------------- |
| `default`            | namespace를 지정하지 않은 리소스가 들어가는 기본 영역                       |
| `kube-system`        | 쿠버네티스 시스템 리소스 (API 서버, etcd, 스케줄러, CoreDNS, kube-proxy 등) |
| `kube-public`        | 인증 없이 읽을 수 있는 공용 정보 영역                                       |
| `kube-node-lease`    | 노드의 생존 신호(heartbeat)를 담는 Lease 리소스                             |
| `local-path-storage` | kind 환경의 로컬 스토리지 프로비저너용. 모든 클러스터에 있지는 않음         |

`kube-system`을 따로 두는 이유도 같습니다. 핵심 구성 요소를 사용자 리소스와 섞지 않아 실수로 건드리지 않게 하기 위함입니다.

**조회 결과를 읽을 때 주의할 점**

- **`kube-system`에 있다고 모두 컨트롤 플레인 컴포넌트는 아닙니다.** kube-proxy는 각 노드에서 동작하는 노드 컴포넌트이고, CoreDNS는 클러스터 DNS 애드온입니다.
- **`kubectl get all`은 모든 리소스를 보여 주지 않습니다.** `kube-node-lease`에서 `get all` 결과가 비어 있어도 Lease는 있습니다. `kubectl get leases -n kube-node-lease`처럼 종류를 직접 지정해야 보입니다.
- `default`에 아무것도 만들지 않아도 `kubernetes`라는 ClusterIP Service가 보입니다. 클러스터 안에서 API 서버에 접근하기 위한 기본 Service입니다.

## 3. Namespace 만들기와 `n`

Namespace도 오브젝트이므로 YAML과 명령형 두 방식으로 만들 수 있습니다.

```yaml
# ns.yaml
apiVersion: v1 # 키는 apiVersion(V 대문자), 값 v1은 소문자
kind: Namespace
metadata:
  name: demo # spec 없이 이름만으로 충분
```

```bash
kubectl apply -f ns.yaml             # YAML로 생성
kubectl create ns demo               # 명령형으로 생성 (하나만 만들 때 가장 빠름)
kubectl delete ns demo               # 삭제: 안의 리소스도 모두 함께 삭제됨
```

- **`n`을 생략하면 어디서 작업할까?**

현재 context에 설정된 기본 namespace를 사용합니다. 따로 바꾸지 않았다면 `default`입니다.

```bash
kubectl create deployment nginx-demo --image=nginx -n demo   # demo에 생성
kubectl get deployments                                      # default를 조회 → nginx-demo가 안 보임
kubectl get deployments -n demo                              # demo를 조회해야 보임
kubectl get pods -A                                          # 모든 namespace 조회
kubectl config set-context --current --namespace=demo        # 기본 namespace를 demo로 변경
```

→ 만든 리소스가 안 보이면 생성 실패보다 **다른 namespace를 조회하고 있는지**부터 확인합니다. `get`뿐 아니라 `exec`, `scale`, `expose`도 모두 `-n`의 영향을 받습니다.

## 4. 실습: Namespace가 달라도 통신이 될까?

### 4-1. 실습 구성

`demo`와 `default`에 같은 nginx 앱을 하나씩 배포하고, 각각 Service를 붙여 양쪽에서 서로 요청해 봅니다.

```
Namespace: demo                         Namespace: default

svc-demo (ClusterIP)                    svc-test (ClusterIP)
   └─ nginx-demo Pod × 3                   └─ nginx-test Pod × 3
```

```bash
# 1) 각 namespace에 Deployment 생성
kubectl create deployment nginx-demo --image=nginx -n demo
kubectl create deployment nginx-test --image=nginx -n default

# 2) 복제본을 3개로 늘림
kubectl scale deployment nginx-demo --replicas=3 -n demo
kubectl scale deployment nginx-test --replicas=3 -n default

# 3) 각 Deployment 앞에 Service 생성 (--type 생략 시 ClusterIP)
kubectl expose deployment nginx-demo -n demo    --name=svc-demo --port=80 --target-port=80
kubectl expose deployment nginx-test -n default --name=svc-test --port=80 --target-port=80

# 4) Pod IP와 Service 확인
kubectl get pods -n demo -o wide     # Pod 이름·IP·노드
kubectl get svc -n default           # svc-test의 ClusterIP
```

| 옵션                    | 의미                        |
| ----------------------- | --------------------------- |
| `deployment nginx-demo` | 노출할 기존 Deployment      |
| `--name=svc-demo`       | 새로 만들 Service 이름      |
| `--port=80`             | Service가 받는 포트         |
| `--target-port=80`      | 요청을 전달할 컨테이너 포트 |

`nginx-demo`, `nginx-test`로 이름을 다르게 지었지만, namespace가 다르므로 같은 이름을 써도 됩니다. 클러스터 내부 통신만 확인하므로 NodePort나 LoadBalancer는 필요 없습니다.

### 4-2. IP로는 서로 닿는다

`demo`의 Pod에 들어가서 `default` Pod의 IP로 요청합니다.

```bash
kubectl exec -it '<demo-Pod이름>' -n demo -- sh   # demo Pod 안으로 들어가기
curl http://<default-Pod-IP>:80                  # (컨테이너 안) 반대편 nginx에 HTTP 요청
exit                                             # 로컬 터미널로 복귀
```

반대 방향(`default` → `demo`)도 같은 방식으로 nginx 환영 페이지가 돌아옵니다. Service의 ClusterIP로 요청해도 마찬가지입니다.

**→ Namespace는 네트워크 벽이 아닙니다.** 별도 NetworkPolicy가 없는 환경에서는 Pod IP와 Service IP가 namespace와 상관없이 클러스터 안에서 통합니다.

다만 Pod IP는 Pod가 교체되면 바뀌므로, 실제 서비스 주소로는 쓰지 않습니다. 그래서 다음 단계에서 Service 이름으로 접근해 봅니다.

cf. nginx 이미지에는 `ping`이 없을 수 있습니다. 또 `ping`은 네트워크 도달 여부만, `curl`은 실제 HTTP 응답까지 확인하므로 웹 서버를 점검할 때는 `curl`이 목적에 맞습니다.

### 4-3. Service 짧은 이름은 다른 Namespace에서 실패한다

```bash
kubectl exec -it '<demo-Pod이름>' -n demo -- sh
curl <http://svc-test>                 # (컨테이너 안) default의 Service를 이름만으로 요청
# curl: (6) Could not resolve host: svc-test
```

IP로는 됐는데 이름으로는 실패합니다. `Could not resolve host`는 **이름을 IP로 바꾸는 DNS 단계에서 실패**했다는 뜻입니다. 대상에 연결한 뒤 권한을 거부당한 것이 아닙니다.

원인은 Pod의 DNS 설정에 있습니다.

```bash
cat /etc/resolv.conf                 # (컨테이너 안) DNS 서버와 검색 도메인 확인
```

```
# demo Pod의 예시 (주소 등은 환경마다 다름)
search demo.svc.cluster.local svc.cluster.local cluster.local
```

`search`는 **"이름만 주면 뒤에 이 도메인을 차례로 붙여서 찾아본다"**는 뜻입니다. `demo`의 Pod가 `svc-test`를 찾으면 먼저 `svc-test.demo.svc.cluster.local`을 조회합니다. `demo`에는 `svc-test`가 없으므로 찾지 못합니다.

**→ Service의 짧은 이름은 "호출한 Pod의 namespace"에서 먼저 찾습니다.** 그래서 같은 namespace 안에서만 짧은 이름이 통합니다.

### 4-4. 다른 Namespace는 대상 Namespace까지 적는다

이름을 끝까지 적은 주소를 **FQDN (Fully Qualified Domain Name)**이라고 합니다.

```
<Service이름>.<Namespace>.svc.cluster.local

svc-test.default.svc.cluster.local
   │       │     │       └─ 클러스터 도메인 (설정에 따라 다를 수 있음)
   │       │     └─ Service 영역
   │       └─ 대상 Service가 있는 namespace
   └─ Service 이름
```

```bash
curl <http://svc-test.default.svc.cluster.local>   # (demo Pod 안) default의 Service
curl <http://svc-demo.demo.svc.cluster.local>      # (default Pod 안) demo의 Service
```

두 방향 모두 응답이 돌아옵니다.

**→ 주소에 넣는 namespace는 호출하는 쪽이 아니라 대상 Service가 속한 쪽입니다.** `default` Pod에서 `svc-demo.default...`로 요청하면 같은 이유로 실패합니다.

`svc-test.default`처럼 namespace까지만 적어도 동작합니다. 나머지 `svc.cluster.local`은 `search` 목록에서 붙기 때문입니다.

### 4-5. 실습 결과 정리

| 접근 방식                                   | 같은 Namespace | 다른 Namespace    |
| ------------------------------------------- | -------------- | ----------------- |
| Pod IP / Service IP                         | O              | O                 |
| Service 짧은 이름 (`svc-test`)              | O              | X (DNS 해석 실패) |
| `svc-test.default`                          | O              | O                 |
| FQDN (`svc-test.default.svc.cluster.local`) | O              | O                 |

## 5. 중요 개념 정리

- **Namespace는 논리적 분리이지 네트워크 차단이 아닙니다.** 차단하려면 NetworkPolicy가 필요합니다.
- **IP는 클러스터 범위, Service 짧은 이름은 namespace 범위입니다.**
- **`n`을 생략하면 현재 context의 기본 namespace**(보통 `default`)에서 작업합니다.
- **Namespace를 삭제하면 안의 리소스가 모두 함께 삭제됩니다.**
- 리소스 이름에는 `_`를 쓸 수 없습니다. 소문자, 숫자, 만 사용합니다 (`svc_test` X, `svc-test` O).

| 증상                                 | 먼저 확인할 것                                    |
| ------------------------------------ | ------------------------------------------------- |
| 만든 Deployment가 조회되지 않음      | 생성한 namespace와 조회한 namespace가 같은지      |
| `exec`할 Pod를 찾지 못함             | Pod 이름과 `-n` 값                                |
| IP로는 되는데 Service 이름으로 안 됨 | 대상 namespace를 주소에 넣었는지                  |
| FQDN으로도 실패                      | DNS 해석 실패인지, 해석 후 연결 실패인지부터 구분 |

# Day 11. Multi-container Pod와 Init Container

> 하나의 Pod 안에서 컨테이너의 역할과 시작 순서를 나누는 방식

## 1. Multi-container Pod란?

지금까지는 Pod 하나에 컨테이너 하나만 넣었습니다. 하지만 Pod 안에는 **메인 앱을 돕는 보조 컨테이너**를 함께 넣을 수 있습니다.

| 종류           | 실행 시점           | 실행 기간          | 예시                                     |
| -------------- | ------------------- | ------------------ | ---------------------------------------- |
| 앱 컨테이너    | Init이 모두 끝난 뒤 | 계속               | nginx, 실제 애플리케이션                 |
| Init Container | 앱보다 먼저         | 작업 후 **종료**   | Service·DB 준비 대기, 설정 파일 다운로드 |
| Sidecar        | 앱과 함께           | 앱과 **계속** 실행 | 로그 수집·전송, 프록시                   |

**같은 Pod 안의 컨테이너가 공유하는 것**

- **노드**: 항상 같은 노드에 함께 배치됩니다.
- **네트워크**: 같은 Pod IP를 쓰므로 서로 `localhost`로 통신할 수 있습니다.
- **볼륨**: 같은 볼륨을 마운트하면 파일을 주고받을 수 있습니다.

cf. 컨테이너마다 파일시스템은 따로입니다. 볼륨을 마운트해야 파일을 공유합니다. 환경변수(`env`)도 컨테이너별 설정이라 한 컨테이너에 넣었다고 다른 컨테이너에 생기지 않습니다.

## 2. Init Container의 실행 규칙

앱이 의존하는 대상(DB, 다른 Service)이 준비되기 전에 앱이 시작되면 오류가 납니다. Init Container는 이 준비 작업을 앱과 분리해, **앱 시작 전에 반드시 끝나도록** 만듭니다.

```
Pod 생성
  ↓
init 1 실행 → 성공 종료
  ↓
init 2 실행 → 성공 종료
  ↓
앱 컨테이너 시작
```

- 여러 개면 **적힌 순서대로 하나씩** 실행됩니다.
- 앞의 init이 **성공 종료**해야 다음 init이 시작됩니다.
- 실패하면 성공할 때까지 재시도하고, 그동안 앱은 시작되지 않습니다.
- Init이 `Running`이라는 건 "아직 작업 중"이라는 뜻입니다. 앱 시작 조건은 **완료(Completed)**입니다.

cf. 일반 Init은 이미 끝나서 종료된 상태입니다. 앱 컨테이너만 재시작될 때 Init이 같이 다시 실행되는 것은 아닙니다. Pod 자체가 새로 만들어지면 Init도 처음부터 다시 실행됩니다.

cf. 최신 쿠버네티스에는 공식 Sidecar 문법이 있습니다. `initContainers`에 넣고 `restartPolicy: Always`를 붙이면 종료되지 않고 앱과 함께 계속 실행됩니다. 이번 실습은 일반 Init만 다룹니다.

```yaml
initContainers:
  - name: log-sidecar
    image: busybox
    restartPolicy: Always # 이 한 줄로 Sidecar가 됨
    command: ["sh", "-c", "tail -F /var/log/app.log"]
```

## 3. 실습 전에: env, command, args

실습 Pod는 BusyBox 이미지를 씁니다. BusyBox는 셸과 기본 리눅스 도구만 담은 작은 이미지로, 대기 스크립트나 간단한 명령을 실행할 때 자주 씁니다.

### 3-1. 실행할 일이 없으면 컨테이너는 끝난다

BusyBox를 명령 없이 띄우면 실행할 작업이 없어 곧바로 종료됩니다. Pod의 기본 `restartPolicy`가 `Always`이므로 다시 실행 → 또 종료를 반복하고, 재시작 간격이 늘어나면서 `CrashLoopBackOff`가 됩니다.

**→ 컨테이너는 주 프로세스가 살아 있는 동안만 실행됩니다.** 실습에서는 `sleep 3600`으로 1시간 동안 살려 둡니다.

### 3-2. command와 args

| 필드      | 의미                    | Docker 대응           |
| --------- | ----------------------- | --------------------- |
| `command` | 실행할 프로그램         | `ENTRYPOINT`를 덮어씀 |
| `args`    | 그 프로그램에 넘길 인자 | `CMD`를 덮어씀        |

```yaml
# 방식 1. 나눠 쓰기
command: ["sh", "-c"]
args: ["echo The app is running && sleep 3600"]

# 방식 2. 한 목록에 합치기 (위와 같은 의미)
command: ["sh", "-c", "echo The app is running && sleep 3600"]
```

- `sh -c '문자열'`: 셸을 열어 뒤의 문자열을 명령으로 실행합니다.
- `&&`: 앞 명령이 성공하면 뒤 명령을 실행합니다.

→ `until`, `;`, `&&` 같은 문법을 해석하는 것은 쿠버네티스가 아니라 `sh`입니다. 셸 문법을 쓰려면 `sh -c`로 셸을 명시해야 합니다.

### 3-3. env

컨테이너 안에서 쓸 환경변수입니다. 목록이므로 `- name / value` 쌍을 여러 개 넣을 수 있습니다.

```yaml
env:
  - name: FIRST_NAME
    value: "Piyush"
```

## 4. 실습 ①: Service가 생길 때까지 기다리는 Init

### 4-1. YAML

앱 시작 전에 `myservice`라는 Service의 DNS 이름이 조회되는지 확인하는 Init을 넣습니다.

```yaml
# pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: my-app
  labels:
    app: my-app
spec:
  containers: # 메인 앱 컨테이너
    - name: my-app-container
      image: busybox:1.28
      env:
        - name: FIRST_NAME
          value: "Piyush"
      command: ["sh", "-c", "echo The app is running && sleep 3600"]
  initContainers: # containers와 같은 레벨, C는 대문자
    - name: init-myservice
      image: busybox:1.28
      command: ["sh", "-c"]
      args:
        - "until nslookup myservice.default.svc.cluster.local; do echo waiting for service to be up; sleep 2; done"
```

**Init 명령 해석**

```bash
until nslookup myservice.default.svc.cluster.local   # 이 이름이 조회될 때까지
do echo waiting for service to be up; sleep 2        # 메시지 출력, 2초 대기, 반복
done                                                 # 조회 성공 → 반복 종료 → init 정상 종료
```

- Day 10에서 배운 FQDN 형식(`<Service>.<Namespace>.svc.cluster.local`)을 그대로 씁니다.
- YAML에서 `containers`가 먼저 적혀 있어도 실행은 Init이 먼저입니다.
- `busybox:1.28`을 쓰는 이유: 최신 BusyBox는 `nslookup` 동작이 불안정한 경우가 있어 공식 문서 예제도 1.28을 씁니다.

### 4-2. `Init:0/1`은 "Init이 실행 중인데 아직 못 끝났다"는 뜻이다

```bash
kubectl create -f pod.yaml           # Pod 생성
kubectl get pod my-app               # STATUS: Init:0/1, READY: 0/1
```

| 표시        | 의미                                                    |
| ----------- | ------------------------------------------------------- |
| `Init:0/1`  | Init 1개 중 완료된 것 0개                               |
| `READY 0/1` | **앱 컨테이너** 1개 중 준비된 것 0개 (Init은 세지 않음) |

`Init:0/1`만 보고 Init이 아예 시작하지 않았다고 판단하면 안 됩니다. 어디서 멈췄는지는 `describe`와 `logs`로 확인합니다.

```bash
kubectl describe pod my-app                  # init-myservice: Running / 앱: PodInitializing
kubectl logs my-app -c init-myservice        # Init 컨테이너의 로그만 보기
# nslookup: can't resolve 'myservice.default.svc.cluster.local'
# waiting for service to be up
```

컨테이너가 여러 개인 Pod에서는 `-c <컨테이너 이름>`으로 대상을 고릅니다. Pod 이름이 아니라 컨테이너의 `name`을 넣습니다.

**→ 앱이 안 뜰 때 앱 로그만 보면 원인을 놓칩니다.** 앱은 시작조차 안 했으므로, 막고 있는 Init의 로그를 봐야 "myservice를 기다리는 중"이라는 원인이 보입니다.

### 4-3. Pod가 아니라 Service 이름이 생겨야 통과한다

먼저 nginx Deployment만 만듭니다.

```bash
kubectl create deployment nginx-deploy --image=nginx   # nginx Pod 생성
kubectl get pods                                       # nginx는 Running, my-app은 여전히 Init:0/1
```

nginx가 떠도 Init은 계속 기다립니다. Init이 확인하는 조건은 **Pod의 존재가 아니라 `myservice`라는 Service 이름의 DNS 조회**이기 때문입니다.

이제 그 이름으로 Service를 만듭니다.

```bash
kubectl expose deployment nginx-deploy --name=myservice --port=80   # init이 기다리던 이름
kubectl get pod my-app -w            # 상태 변화를 실시간 관찰 (Ctrl+C로 종료)
```

```
Init:0/1  →  PodInitializing  →  Running
```

```bash
kubectl logs my-app -c init-myservice      # 마지막에 myservice의 DNS 응답이 찍힘
kubectl logs my-app -c my-app-container    # The app is running
```

**→ Init은 "내가 적어 둔 조건"만 확인합니다.** 무엇을 기다리는지는 스크립트가 정합니다.

cf. `nslookup` 성공은 **이름이 IP로 해석됐다**는 뜻일 뿐입니다. ClusterIP Service는 뒤의 앱이 아직 요청을 못 받아도 DNS 조회는 성공할 수 있습니다. 실제 DB 접속이나 HTTP 응답까지 보장하려면 그 조건을 직접 검사해야 합니다.

### 4-4. 환경변수는 해당 컨테이너 안에서 확인한다

```bash
kubectl exec my-app -c my-app-container -- printenv FIRST_NAME   # Piyush
kubectl exec -it my-app -c my-app-container -- sh                # 셸로 들어가서
echo "$FIRST_NAME"                                               # (컨테이너 안) 값 확인
```

- `kubectl exec`는 SSH 접속이 아니라 **실행 중인 컨테이너 안에서 명령을 실행**하는 기능입니다.
- 이미 종료된 Init에는 `exec`할 수 없습니다. 끝난 Init은 `logs`와 `describe`로 확인합니다.

## 5. 실습 ②: Init을 하나 더 추가하기

이번에는 `myservice`뿐 아니라 `mydb` Service도 있어야 앱이 시작되도록 Init을 하나 더 넣습니다.

```yaml
# pod.yaml의 initContainers 부분만 교체
initContainers:
  - name: init-myservice
    image: busybox:1.28
    command: ["sh", "-c"]
    args:
      - "until nslookup myservice.default.svc.cluster.local; do echo waiting for service to be up; sleep 2; done"
  - name: init-mydb
    image: busybox:1.28
    command: ["sh", "-c"]
    args:
      - "until nslookup mydb.default.svc.cluster.local; do echo waiting for database service to be up; sleep 2; done"
```

### 5-1. 실행 중인 Pod에는 컨테이너를 추가할 수 없다

```bash
kubectl apply -f pod.yaml
# The Pod "my-app" is invalid: spec: Forbidden: pod updates may not change fields other than ...
```

`apply`는 생성과 변경에 쓰는 명령이지만, Pod의 모든 필드를 바꿀 수 있는 것은 아닙니다. 컨테이너나 Init을 추가·삭제하는 변경은 거부됩니다.

```bash
kubectl delete pod my-app            # 실습용 단독 Pod 삭제
kubectl apply -f pod.yaml            # 수정한 설정으로 새로 생성
```

**→ Pod는 만든 뒤 구성을 바꿀 수 없는 경우가 많아 "삭제 후 재생성"이 기본입니다.** 실무에서 Pod를 직접 만들지 않고 Deployment로 관리하는 이유이기도 합니다. Deployment는 템플릿이 바뀌면 새 Pod로 교체해 줍니다.

### 5-2. `Init:1/2` — Init은 하나씩 순서대로 통과한다

```bash
kubectl get pod my-app               # STATUS: Init:1/2
kubectl logs my-app -c init-mydb     # waiting for database service to be up
```

```
init-myservice → myservice 이미 있음 → 완료
init-mydb      → mydb 없음          → 대기 중
앱 컨테이너    → 대기
```

`myservice`는 앞에서 만들어 두었으므로 첫 번째 Init은 바로 통과하고, 두 번째에서 멈춥니다.

### 5-3. mydb Service를 만들면 앱이 시작된다

```bash
kubectl create deployment mydb --image=redis                 # Redis Deployment
kubectl expose deployment mydb --name=mydb --port=6379       # 두 번째 init이 기다리는 Service
kubectl get pod my-app -w                                    # Init:1/2 → PodInitializing → Running
```

Deployment와 Service의 이름이 둘 다 `mydb`여도 됩니다. **리소스 종류가 다르면 같은 이름을 쓸 수 있습니다.**

| 단계              | STATUS            | 의미                                |
| ----------------- | ----------------- | ----------------------------------- |
| Pod 생성 직후     | `Init:0/2`        | Init 2개 중 0개 완료                |
| myservice 확인 후 | `Init:1/2`        | 첫 번째 완료, 두 번째 대기          |
| mydb 생성 후      | `PodInitializing` | Init 모두 완료, 앱 컨테이너 준비 중 |
| 최종              | `Running`         | 앱 컨테이너 실행                    |

**→ 준비 조건을 Init 하나에 하나씩 나누면, STATUS의 숫자만 보고도 몇 번째 조건에서 막혔는지 알 수 있습니다.**

## 6. 중요 개념 정리

- **Init은 순서대로, 모두 성공해야** 앱 컨테이너가 시작됩니다.
- **`READY`는 앱 컨테이너만 셉니다.** Init은 `Init:N/M`으로 따로 표시됩니다.
- *컨테이너가 여러 개면 `logs`, `exec`에 `c 컨테이너이름`*을 붙입니다.
- **Pod의 컨테이너 구성은 만든 뒤 바꿀 수 없어** 삭제 후 재생성해야 합니다.
- `nslookup` 성공은 이름 해석 성공일 뿐, 대상 앱의 정상 동작까지 보장하지 않습니다.

| 증상                            | 원인                             | 확인·해결                        |
| ------------------------------- | -------------------------------- | -------------------------------- |
| BusyBox가 `CrashLoopBackOff`    | 실행할 작업 없이 프로세스 종료   | `command`에 `sleep` 추가         |
| `Init:0/1`에서 멈춤             | Init의 조건이 충족되지 않음      | `describe`, `logs -c <init이름>` |
| nginx는 떴는데 Init이 계속 대기 | 조건은 Pod가 아니라 Service 이름 | Service 이름·namespace 확인      |
| `apply`로 Init 추가 실패        | Pod에 허용되지 않는 변경         | 삭제 후 재생성                   |
| 끝난 Init에 `exec` 실패         | 실행 중인 컨테이너가 아님        | `logs`, `describe`로 확인        |

# Day 12. DaemonSet, Job, CronJob

> 노드마다 하나씩 띄우는 DaemonSet, 끝나는 것이 목표인 Job, 정해진 시간마다 Job을 만드는 CronJob

## 1. DaemonSet이 필요한 이유

Deployment에서 `replicas: 3`은 "Pod 3개를 유지한다"는 뜻이지 "노드마다 하나씩"이라는 뜻이 아닙니다. 스케줄러가 한 노드에 두 개를 놓을 수도 있습니다.

그런데 노드의 로그나 지표를 모으는 프로그램은 **각 노드에 하나씩** 있어야 합니다. 개수만 맞춰서는 수집기가 없는 노드가 생길 수 있습니다.

DaemonSet은 **배치 조건을 만족하는 노드마다 Pod를 하나씩** 실행하도록 관리합니다.

```
DaemonSet
├─ Node A → Pod 1개
├─ Node B → Pod 1개
└─ Node C → Pod 1개
```

| 구분            | Deployment / ReplicaSet        | DaemonSet                              |
| --------------- | ------------------------------ | -------------------------------------- |
| 개수 기준       | `replicas`에 적은 전체 개수    | 대상 노드마다 1개                      |
| `replicas` 필드 | 있음                           | **없음**                               |
| 노드 추가 시    | Pod 수는 그대로                | 새 노드에 Pod 자동 생성                |
| 노드 삭제 시    | 다른 노드에 다시 채움          | 그 노드의 Pod도 함께 정리              |
| 대표 용도       | 웹 앱처럼 개수가 중요한 서비스 | 노드별 모니터링·로그·네트워크 에이전트 |

**DaemonSet을 쓰는 대표 사례**

| 사례               | 노드마다 필요한 이유                                      |
| ------------------ | --------------------------------------------------------- |
| 모니터링 에이전트  | 각 노드의 CPU·메모리 지표 수집 (예: node-exporter)        |
| 로그 수집 에이전트 | 각 노드의 로그를 외부(ELK, Splunk 등)로 전송              |
| kube-proxy         | 각 노드에서 Service 네트워크 규칙을 구현                  |
| CNI 노드 에이전트  | 각 노드의 Pod 네트워크 설정 (Calico, Flannel, kindnet 등) |

cf. kube-proxy는 컨트롤 플레인 컴포넌트가 아니라 **모든 노드에서 동작하는 노드 컴포넌트**입니다. 그래서 DaemonSet으로 배포됩니다.

## 2. YAML: Deployment에서 두 군데만 바꾼다

```yaml
# ds.yaml
apiVersion: apps/v1
kind: DaemonSet # ① kind 변경
metadata:
  name: ds
spec: # ② replicas 없음
  selector:
    matchLabels:
      app: ds-demo
  template:
    metadata:
      labels:
        app: ds-demo # selector와 일치해야 함
    spec:
      containers:
        - name: nginx
          image: nginx # 배치 방식 확인용. 실제 로그 수집 기능은 없음
          ports:
            - containerPort: 80
```

DaemonSet은 `kubectl create` 명령이 없습니다. Deployment YAML을 뽑아서 고치는 것이 가장 빠릅니다.

```bash
kubectl create deploy ds --image=nginx --dry-run=client -o yaml > ds.yaml
# kind: DaemonSet으로 바꾸고 replicas, strategy, status 줄 삭제
```

## 3. 실습: 노드 3개 클러스터에 DaemonSet 배포

실습 클러스터는 control-plane 1개 + worker 2개입니다.

```bash
kubectl apply -f ds.yaml                            # DaemonSet 생성
kubectl get ds                                      # DESIRED·CURRENT·READY 확인
kubectl get pods -l app=ds-demo -o wide             # 어느 노드에 배치됐는지 확인
```

### 3-1. 노드는 3개인데 Pod는 2개만 생긴다

Pod는 worker 2개에만 생기고 control-plane에는 생기지 않습니다.

**원인은 control-plane 노드의 Taint입니다.**

| 개념       | 의미                                                  |
| ---------- | ----------------------------------------------------- |
| Taint      | 노드에 붙여 "조건이 맞지 않는 Pod는 오지 마라"고 표시 |
| Toleration | Pod에 붙여 "그 Taint를 견딜 수 있다"고 표시           |

```
control-plane → Taint 있음, ds Pod는 Toleration 없음 → 배치 안 됨
worker-1      → 배치 가능                            → Pod 1개
worker-2      → 배치 가능                            → Pod 1개
```

**→ DaemonSet은 "모든 노드에 무조건 하나"가 아니라 "배치 조건을 만족하는 노드마다 하나"입니다.** control-plane에도 띄우려면 Pod 템플릿에 해당 Toleration을 추가해야 합니다. Taint와 Toleration은 이후 강의에서 자세히 다룹니다.

### 3-2. 지운 Pod는 같은 노드에 새로 생긴다

```bash
kubectl delete pod '<ds-Pod이름>'                    # DaemonSet Pod 하나 삭제
kubectl get pods -l app=ds-demo -o wide             # 같은 노드에 새 이름의 Pod 생성
kubectl describe pod '<새-ds-Pod이름>'               # Controlled By: DaemonSet/ds
```

노드는 여전히 대상인데 Pod가 없어졌으므로 DaemonSet 컨트롤러가 새 Pod를 만듭니다. 이전 Pod를 되살리는 것이 아니라 새 Pod로 채웁니다.

**→ DaemonSet도 Deployment처럼 "원하는 상태"를 계속 맞추는 컨트롤러입니다.** 다른 점은 기준이 "개수"가 아니라 "노드"라는 것입니다.

cf. Deployment가 만든 Pod의 `Controlled By`에는 Deployment가 아니라 **ReplicaSet**이 나옵니다 (`Deployment → ReplicaSet → Pod`). DaemonSet은 Pod를 직접 관리합니다.

### 3-3. 시스템 DaemonSet은 control-plane에도 있다

```bash
kubectl get ds -A                    # 모든 namespace의 DaemonSet (-A는 대문자)
kubectl get ds -n kube-system        # kube-proxy, kindnet
```

```
NAME         DESIRED   CURRENT   READY   ...
kindnet      3         3         3
kube-proxy   3         3         3
```

내가 만든 DaemonSet은 2개인데 `kube-proxy`, `kindnet`은 3개입니다. 이들은 control-plane의 Taint를 견디는 **Toleration을 갖고 있기** 때문입니다. 네트워크 규칙은 control-plane 노드에도 필요하니까요.

| 항목      | 의미                         |
| --------- | ---------------------------- |
| `DESIRED` | Pod가 있어야 할 대상 노드 수 |
| `CURRENT` | 실제로 Pod가 생성된 노드 수  |
| `READY`   | Pod가 준비 상태인 노드 수    |

`DESIRED`는 맞는데 `READY`가 부족하면 이미지 다운로드·실행 오류 등 Pod 상태를 따로 확인합니다.

노드가 1개인 클러스터로 context를 바꿔 보면 `kube-proxy`, `kindnet`의 `DESIRED`가 1로 나옵니다. **DESIRED는 정해진 숫자가 아니라 대상 노드 수를 따라갑니다.**

```bash
kubectl config get-contexts          # context 목록
kubectl config use-context <이름>    # 대상 클러스터 전환 → 비교 후 반드시 원래 context로 복귀
```

## 4. Job: 끝나는 것이 목표인 작업

Deployment와 DaemonSet은 계속 실행되어야 하는 Pod를 관리합니다. 반대로 설치 스크립트, 데이터 적재, 마이그레이션처럼 **작업을 마치고 정상 종료하는 것**이 목표인 경우에는 Job을 씁니다.

Job은 Pod가 작업을 **성공적으로 완료(exit code 0)**할 때까지 관리하고, 실패하면 정해진 횟수만큼 재시도합니다.

```yaml
# job.yaml (개념 확인용 보충 예제)
apiVersion: batch/v1
kind: Job
metadata:
  name: hello-once
spec:
  backoffLimit: 4 # 실패 시 최대 재시도 횟수 (기본 6)
  template:
    spec:
      containers:
        - name: hello
          image: busybox:1.28
          command: ["sh", "-c", "echo Job finished"]
      restartPolicy: Never # Job은 Never 또는 OnFailure만 가능
```

```bash
kubectl apply -f job.yaml               # Job 생성
kubectl get jobs                        # COMPLETIONS 1/1 확인
kubectl logs job/hello-once             # Job finished
kubectl create job my-job --image=busybox -- echo hello   # 명령형 생성
```

| 필드           | 의미                             |
| -------------- | -------------------------------- |
| `completions`  | 총 몇 번 성공해야 완료인가       |
| `parallelism`  | 동시에 몇 개 Pod를 실행할 것인가 |
| `backoffLimit` | 실패 시 최대 재시도 횟수         |

**주의할 점**

- Job의 Pod에는 `restartPolicy: Always`를 쓸 수 없습니다. 끝나야 하는 작업을 계속 재시작하면 안 되기 때문입니다.
- "한 번 실행"은 목적을 말하는 것이지, 프로세스가 물리적으로 딱 한 번만 실행된다는 보장은 아닙니다. 실패하면 재시도로 여러 번 실행될 수 있습니다.
- `Never`는 같은 Pod 안에서 컨테이너를 재시작하지 않는다는 뜻입니다. Job 컨트롤러가 **새 Pod**로 재시도하는 것까지 막지는 않습니다.

## 5. CronJob: 정해진 시간마다 Job을 만든다

CronJob은 **일정에 맞춰 Job을 만드는 리소스**입니다. 리눅스의 `cron`과 같은 개념으로, 정기 리포트, 오래된 로그 정리, 정기 백업에 씁니다.

```
CronJob ──(정해진 시간마다)──> Job ──> Pod
```

CronJob은 Pod를 직접 만들지 않습니다. 일정은 CronJob이, 작업 완료는 Job이 맡습니다. `Deployment → ReplicaSet → Pod`처럼 역할이 나뉜 구조입니다.

```yaml
# cronjob.yaml (공식 문서 예제)
apiVersion: batch/v1
kind: CronJob
metadata:
  name: hello
spec:
  schedule: "* * * * *" # 매분 실행
  jobTemplate: # 시간이 되면 이 Job을 만든다
    spec:
      template: # Job이 이 Pod를 만든다
        spec:
          containers:
            - name: hello
              image: busybox:1.28
              command:
                [
                  "/bin/sh",
                  "-c",
                  "date; echo Hello from the Kubernetes cluster",
                ]
          restartPolicy: OnFailure
```

YAML은 바깥에서 안쪽으로 **CronJob → `jobTemplate`(Job 설계도) → `template`(Pod 설계도) → `containers`** 순서로 읽습니다.

```bash
kubectl apply -f cronjob.yaml           # CronJob 생성
kubectl get cronjobs                    # 일정 확인
kubectl get jobs                        # 매분 hello-<숫자> 형태의 Job이 생김
kubectl logs job/'<생성된-Job이름>'      # 해당 회차의 출력
kubectl create cronjob hello --image=busybox:1.28 --schedule="*/1 * * * *" -- date   # 명령형 생성
```

생성되는 Job과 Pod에는 이름 뒤에 문자열이 붙습니다. 같은 Pod를 매번 다시 쓰는 것이 아니라 **회차마다 새 Job과 Pod**가 만들어집니다.

## 6. cron 표현식 읽기

```
분 시 일 월 요일(0~6, 0=일요일, 6=토요일)
* * * * *
```

**첫 필드는 초가 아니라 분입니다.** `*`는 "모든 값", `*/n`은 "n 간격"입니다.

**토요일 실행을 특정 시각까지 좁혀 보기**

| 표현식        | 의미                             |
| ------------- | -------------------------------- |
| `* * * * 6`   | 토요일 하루 종일 매분            |
| `* 23 * * 6`  | 토요일 23:00~23:59 동안 **매분** |
| `0 23 * * 6`  | 매주 토요일 23:00 한 번          |
| `45 23 * * 6` | 매주 토요일 23:45 한 번          |

**→ 어떤 필드를 `*`로 남기면 그 단위로 반복됩니다.** "토요일 23시에 한 번"을 원하면서 `* 23 * * 6`이라고 쓰면 60번 실행됩니다. 한 번만 실행하려면 분을 `0`처럼 고정해야 합니다.

**간격 실행**

| 표현식         | 의미                |
| -------------- | ------------------- |
| `* * * * *`    | 매분                |
| `*/5 * * * *`  | 매시 0, 5, 10, …분  |
| `*/10 * * * *` | 매시 0, 10, 20, …분 |
| `0 9 1 * *`    | 매월 1일 09:00      |

- `/5`는 작업이 끝난 뒤부터 5분을 세는 것이 아니라 **시계의 분 값**에 맞춰 실행합니다. 헷갈리면 crontab.guru에서 표현식을 검증할 수 있습니다.

## 7. 워크로드 선택 정리

| 리소스     | 실행 방식               | 끝나는가? | 고르는 기준                   |
| ---------- | ----------------------- | --------- | ----------------------------- |
| Deployment | 정해진 개수를 계속 유지 | X         | 몇 개가 떠 있어야 하는가      |
| DaemonSet  | 대상 노드마다 계속 유지 | X         | 노드마다 있어야 하는가        |
| Job        | 성공 완료까지 실행      | O         | 끝나는 작업인가               |
| CronJob    | 일정마다 Job 생성       | 매번 O    | 정해진 시간에 반복해야 하는가 |

## 8. 중요 개념 정리

- **DaemonSet = 대상 노드마다 1개.** `replicas`가 없고, 노드 수에 따라 Pod 수가 바뀝니다.
- **control-plane에는 Taint가 있어** Toleration이 없는 DaemonSet Pod는 배치되지 않습니다.
- **Job/CronJob의 Pod는 `restartPolicy`를 `Never` 또는 `OnFailure`로** 씁니다.
- **CronJob → Job → Pod** 순서로 만들어집니다.
- **cron의 첫 필드는 분**이고, 로 남긴 필드는 그 단위로 반복됩니다.
- Job·CronJob의 비중은 CKAD가 더 크지만, 워크로드 기본 개념이므로 명령형 생성 방법 정도는 익혀 둡니다. 시험 범위는 응시 시점의 공식 커리큘럼으로 확인합니다.
