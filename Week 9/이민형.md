# Day 10. Namespace

> 하나의 클러스터를 논리적으로 나누는 "방" 개념

## 1. Namespace란?

클러스터를 하나의 건물이라고 하면, Namespace는 그 안의 **방**입니다.
건물(클러스터)은 하나지만, 방(Namespace)을 나눠서 리소스를 따로 관리합니다.

- 리소스를 만들 때 Namespace를 지정하지 않으면 자동으로 `default`에 들어갑니다.
- 지금까지 실습에서 만든 Pod, Deployment, Service는 전부 `default`에 있었던 것입니다.

## 2. 왜 필요한가?

<img width="2288" height="1444" alt="image" src="https://github.com/user-attachments/assets/1e7a15ff-2b77-4d6c-8b12-45f51b8d684b" />

**1) 실수 방지**
모든 리소스가 한 곳에 있으면, 테스트용 Pod를 지우려다 운영용 Pod를 지우는 사고가 나기 쉽습니다.
Namespace를 나누면 작업할 때 반드시 대상 Namespace를 지정해야 하므로 이런 실수가 줄어듭니다.

**2) 권한 분리**
Namespace 단위로 RBAC(권한)를 줄 수 있습니다.
예: "개발팀은 `test`만 수정 가능, `prod`는 읽기만 가능"

**3) 환경 분리**
`test`, `prod`처럼 용도별로 나눠 운영합니다.

**4) 이름 중복 허용**
같은 Namespace 안에서는 이름이 겹치면 안 되지만, 다른 Namespace라면 같은 이름을 써도 됩니다.
예: `demo`에도 `nginx`, `default`에도 `nginx` 가능

## 3. 기본으로 생성되는 Namespace

클러스터를 만들면 쿠버네티스가 스스로 몇 개를 만듭니다.

| Namespace | 역할 |
|---|---|
| `default` | Namespace를 지정하지 않은 리소스가 들어가는 곳 |
| `kube-system` | 쿠버네티스 핵심 구성요소가 들어있는 곳 (apiserver, etcd, scheduler, controller-manager, kube-proxy, coredns 등) |
| `kube-public` | 인증 없이도 읽을 수 있는 공용 공간 |
| `kube-node-lease` | 각 노드가 "나 살아있다"는 신호(heartbeat)를 남기는 곳 |
| `local-path-storage` | kind 클러스터에만 있는 스토리지용 공간 |

> `kube-system`을 따로 분리해두는 이유도 같습니다. 핵심 구성요소를 실수로 건드리지 않게 하기 위함입니다.

## 4. Namespace에 속하는 것 vs 속하지 않는 것

모든 리소스가 Namespace 안에 들어가는 것은 아닙니다.

| 구분 | 예시 |
|---|---|
| Namespace에 속함 | Pod, Deployment, ReplicaSet, Service, ConfigMap, Secret |
| 클러스터 전체에 속함 | Node, PersistentVolume, Namespace 자체, ClusterRole, StorageClass |

> 노드는 건물의 "땅"이라서 특정 방에 속하지 않는다고 이해하면 쉽습니다.

## 5. Namespace 간 통신 원리 (핵심)

<img width="2496" height="1396" alt="image" src="https://github.com/user-attachments/assets/2a0e18fa-ac1e-49cc-952f-a55a4a42ed84" />

강의 실습의 결론은 아래 표 하나로 정리됩니다.

| 접근 방식 | 같은 Namespace | 다른 Namespace |
|---|---|---|
| IP 주소 | O | O |
| Service 이름 (예: `svc-test`) | O | X |
| FQDN (예: `svc-test.default.svc.cluster.local`) | O | O |

### 5-1. IP는 클러스터 전체에서 통한다

Pod IP, Service IP는 Namespace와 상관없이 클러스터 어디서든 접근됩니다.
즉, **Namespace는 네트워크 벽이 아닙니다.**

하지만 Pod IP는 Pod가 재시작되면 바뀌기 때문에 실제로는 IP 대신 Service 이름을 사용합니다.

### 5-2. Service 이름은 같은 Namespace 안에서만 통한다

이유는 Pod 안의 DNS 설정 파일(`/etc/resolv.conf`) 때문입니다.

`demo` Namespace의 Pod라면 이 파일에 다음과 같은 줄이 있습니다.

```
search demo.svc.cluster.local svc.cluster.local cluster.local
```

`search`의 의미는 **"이름만 주면 뒤에 이걸 자동으로 붙여서 찾아본다"** 입니다.

그래서 `demo`의 Pod에서 `svc-test`를 찾으면:
1. `svc-test.demo.svc.cluster.local` 을 먼저 찾음
2. `demo`에는 `svc-test`가 없으므로 실패

즉, 이름만 쓰면 **항상 내 Namespace부터** 찾기 때문에 다른 Namespace의 Service는 못 찾습니다.

### 5-3. 다른 Namespace는 FQDN으로 접근한다

FQDN(Fully Qualified Domain Name)은 "주소를 끝까지 다 적은 이름"입니다.

```
<서비스이름>.<네임스페이스>.svc.cluster.local
```

| 부분 | 의미 |
|---|---|
| `svc-test` | Service 이름 |
| `default` | 그 Service가 있는 Namespace |
| `svc` | Service라는 뜻 |
| `cluster.local` | 클러스터 기본 도메인 |

> 비유: 같은 집 안에서는 "엄마"라고 부르면 되지만, 다른 집 사람을 부르려면 "OO동 OO호 엄마"라고 주소를 붙여야 합니다.

`svc-test.default`까지만 써도 동작합니다. 나머지 `svc.cluster.local`은 `search` 목록에서 자동으로 붙기 때문입니다.

## 6. 중요 개념 정리

- **Namespace는 논리적 분리이지 네트워크 차단이 아닙니다.**
  다른 Namespace 간 통신을 실제로 막으려면 **NetworkPolicy**가 필요합니다. (시험 빈출)
- **IP는 클러스터 범위, Service 이름(호스트명)은 Namespace 범위입니다.**
- **Namespace를 삭제하면 그 안의 모든 리소스가 함께 삭제됩니다.**
- Namespace 단위로 걸 수 있는 정책: **RBAC**(권한), **ResourceQuota**(자원 총량 제한), **LimitRange**(Pod별 자원 기본값/상한)

## 7. 꼭 알아야 할 명령어

```bash
kubectl get ns                      # Namespace 목록
kubectl create ns demo              # 생성 (명령형, 시험에서 가장 빠름)
kubectl get pods -n demo            # 특정 Namespace 조회
kubectl get pods -A                 # 모든 Namespace 조회
kubectl config set-context --current --namespace=demo   # 기본 Namespace 변경
kubectl api-resources --namespaced=false                # Namespace에 속하지 않는 리소스 목록
```

> `-n`은 `--namespace`의 줄임말입니다.
> 시험 문제에 Namespace가 지정되어 있으면 반드시 `-n`을 붙여야 합니다. 빼먹으면 `default`에 생성되어 감점됩니다.

## 8. 강의 내용 정정

- 강사가 Service 이름을 `svc_test`(언더스코어)로 만들었는데, 리소스 이름에는 **`_`를 쓸 수 없습니다.** 소문자, 숫자, `-`만 가능합니다.
- 강사가 "access denied"라고 표현한 부분은 권한 문제가 아니라 **DNS 이름 해석 실패**(`Could not resolve host`)입니다.
- coredns는 엄밀히는 control plane 구성요소가 아니라 **애드온**입니다. `kube-system`에 함께 있을 뿐입니다.
- YAML에서 대문자 V는 키 이름 `apiVersion`의 V입니다. 값 `v1`은 **소문자**입니다.

# Day 11. Multi-Container Pod

> 하나의 Pod 안에 여러 컨테이너를 넣어 역할을 나누는 방식

## 1. Multi-Container Pod란?

지금까지는 Pod 하나에 컨테이너 하나(예: nginx)만 넣었습니다.
하지만 Pod 안에는 **메인 앱 컨테이너를 돕는 보조 컨테이너**를 함께 넣을 수 있습니다.

> 비유: 가게(Pod)에 사장님(앱 컨테이너) 혼자 있는 게 아니라, 문 열기 전 청소하는 사람(Init)과 영업 중 옆에서 돕는 직원(Sidecar)이 함께 있는 구조입니다.

## 2. 보조 컨테이너의 종류

<img width="1208" height="1164" alt="image" src="https://github.com/user-attachments/assets/51ef1495-2bef-4388-bc10-ff97f79f62c1" />

### 2-1. Init Container (초기화 컨테이너)

- 앱 컨테이너보다 **먼저 실행**되어 준비 작업을 합니다.
- 자기 일을 **끝내고 종료되어야** 앱 컨테이너가 시작됩니다.
- 여러 개가 있으면 **적힌 순서대로 하나씩** 실행되고, **전부 성공해야** 앱 컨테이너가 시작됩니다.
- 하나라도 실패하면 성공할 때까지 재시도합니다.

**사용 예시**
- DB나 다른 Service가 준비될 때까지 기다리기 (이번 강의 실습)
- 설정 파일 미리 다운로드하기
- 권한, 디렉터리 준비하기

### 2-2. Sidecar Container (보조 컨테이너)

- 앱 컨테이너와 **처음부터 끝까지 함께 실행**됩니다.
- 앱에 데이터를 넣어주거나, 앱이 만든 결과물(로그 등)을 가져가 처리합니다.
- Helper Container라고도 부릅니다.

**사용 예시**
- 앱 로그를 수집해서 외부로 전송
- 프록시(서비스 메시의 Envoy 등)

### 비교

| 구분 | Init Container | Sidecar Container |
|---|---|---|
| 실행 시점 | 앱보다 먼저 | 앱과 동시에 |
| 실행 기간 | 작업 끝나면 종료 | 앱과 계속 함께 실행 |
| 목적 | 사전 준비 | 실행 중 보조 |

## 3. Pod 안 컨테이너끼리 공유하는 것

같은 Pod 안의 컨테이너들은 아래를 공유합니다.

- **네트워크**: 같은 IP를 쓰므로 서로 `localhost`로 통신 가능
- **스토리지(Volume)**: 같은 볼륨을 마운트하면 파일 공유 가능
- **Pod에 할당된 자원(CPU, 메모리)**

## 4. command와 args

컨테이너가 시작될 때 실행할 명령을 지정합니다.

| 필드 | 의미 | Docker에서 대응 |
|---|---|---|
| `command` | 실행할 프로그램 | `ENTRYPOINT` 덮어씀 |
| `args` | 그 프로그램에 넘길 인자 | `CMD` 덮어씀 |

`sh -c '명령'`은 "쉘을 열어서 뒤의 문자열을 명령으로 실행하라"는 뜻입니다.

아래 두 방식은 **같은 의미**입니다.

```yaml
# 방식 1. 나눠서 쓰기
command: ['sh', '-c']
args: ['echo hello && sleep 3600']

# 방식 2. 한 줄로 합치기
command: ['sh', '-c', 'echo hello && sleep 3600']
```

## 5. 환경 변수 (env)

컨테이너 안에서 사용할 변수를 지정합니다. 리스트이므로 여러 개 넣을 수 있습니다.

```yaml
env:
- name: FIRSTNAME
  value: "hello"
```

## 6. 실습 YAML 구조

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: myapp
  labels:
    name: myapp-pod
spec:
  containers:                    # 메인 앱 컨테이너
  - name: myapp-container
    image: busybox:1.28
    command: ['sh', '-c', 'echo The app is running! && sleep 3600']
    env:
    - name: FIRSTNAME
      value: "hello"
  initContainers:                # containers와 같은 레벨, C는 대문자
  - name: init-myservice
    image: busybox:1.28
    command: ['sh', '-c']
    args: ['until nslookup myservice.default.svc.cluster.local; do echo waiting for myservice; sleep 2; done']
  - name: init-mydb
    image: busybox:1.28
    command: ['sh', '-c']
    args: ['until nslookup mydb.default.svc.cluster.local; do echo waiting for mydb; sleep 2; done']
```

**Init Container 명령 해석**

```
until nslookup myservice.default.svc.cluster.local   # 이 이름이 조회될 때까지
do echo waiting...; sleep 2                          # 메시지 찍고 2초 쉬고 반복
done                                                 # 조회되면 반복 종료 → 컨테이너 종료
```

즉, **`myservice`라는 Service가 생길 때까지 기다리는** Init Container입니다.
FQDN 형식은 Day 10에서 배운 `<서비스>.<네임스페이스>.svc.cluster.local` 입니다.

## 7. 실습 흐름과 상태 변화

| 단계 | `kubectl get pod` STATUS | 의미 |
|---|---|---|
| Pod 생성 직후 | `Init:0/2` | Init 2개 중 0개 완료 |
| myservice 생성 후 | `Init:1/2` | 첫 번째 Init 완료, 두 번째 대기 |
| mydb 생성 후 | `PodInitializing` | Init 전부 완료, 앱 컨테이너 준비 중 |
| 최종 | `Running` | 앱 컨테이너 실행 |

Service를 만드는 명령:

```bash
kubectl create deploy nginx-deploy --image=nginx --port=80
kubectl expose deploy nginx-deploy --name=myservice --port=80

kubectl create deploy mydb --image=redis --port=6379
kubectl expose deploy mydb --name=mydb --port=6379
```

> Deployment와 Service는 서로 다른 종류의 리소스라서 같은 이름(`mydb`)을 써도 됩니다.

## 8. 자주 쓰는 확인 명령

```bash
kubectl get pod -w                          # 상태 변화를 실시간으로 보기
kubectl describe pod myapp                  # 어디서 막혔는지 확인
kubectl logs myapp -c init-myservice        # 특정 컨테이너 로그 (-c 로 지정)
kubectl exec -it myapp -- printenv          # 환경 변수 확인
kubectl exec -it myapp -c myapp-container -- sh   # 특정 컨테이너 접속
```

> Pod 안에 컨테이너가 여러 개면 `logs`, `exec`에서 **`-c 컨테이너이름`** 으로 어느 컨테이너인지 지정해야 합니다.

## 9. 중요 개념 정리

- **busybox는 할 일이 끝나면 바로 종료되는 이미지**입니다. command 없이 띄우면 계속 종료되고 재시작되어 `CrashLoopBackOff`가 됩니다. 그래서 `sleep 3600`으로 살려둡니다.
- **Pod는 만든 뒤 컨테이너를 추가하거나 삭제할 수 없습니다.** 바꾸려면 삭제 후 다시 생성해야 합니다.
- **Init Container는 순서대로, 전부 성공해야** 앱 컨테이너가 시작됩니다.
- `READY 0/1`의 숫자는 **앱 컨테이너만** 셉니다. Init Container는 포함되지 않습니다.

## 10. 강의 내용 정정

- **최신 Sidecar 문법 (시험 중요)**
  강사는 Sidecar를 개념으로만 설명했지만, 현재 쿠버네티스에는 공식 Sidecar 문법이 있습니다.
  `initContainers`에 넣고 **`restartPolicy: Always`** 를 붙이면 Sidecar가 됩니다. 이 경우 종료되지 않고 앱과 함께 계속 실행됩니다.

```yaml
  initContainers:
  - name: log-sidecar
    image: busybox
    restartPolicy: Always
    command: ['sh', '-c', 'tail -F /var/log/app.log']
```

- 강사가 "앱 컨테이너가 멈추면 Init Container도 같이 내려간다"고 했는데, Init Container는 **이미 끝나서 종료된 상태**입니다. Pod가 처음부터 다시 시작될 때 Init Container도 다시 실행되는 것입니다.
- busybox는 쿠버네티스가 만든 이미지가 아니라 **Docker Hub 공식 이미지**입니다.
- `kubectl exec`는 SSH가 아니라 **컨테이너 안에서 명령을 실행**하는 기능입니다.
- 실습에서 `busybox:1.28`을 쓰는 이유: 최신 busybox는 `nslookup` 동작이 불안정한 경우가 있어서, 쿠버네티스 공식 문서 예제도 1.28을 사용합니다.
- 강사가 YAML에서 따옴표 하나를 잘못 넣어 에러가 났습니다. 에러 메시지의 줄 번호는 **실제 위치와 1~2줄 차이가 날 수 있으니** 주변 줄도 함께 확인해야 합니다.

# Day 12. DaemonSet, CronJob, Job

> 모든 노드에 하나씩 띄우는 DaemonSet, 정해진 시간에 실행하는 CronJob, 한 번 실행하고 끝나는 Job

## 1. DaemonSet

### 1-1. DaemonSet이란?

<img width="2292" height="1400" alt="image" src="https://github.com/user-attachments/assets/3df7c6f5-c43a-40fe-9c6e-36854dd4a4b3" />

**모든 노드에 Pod를 딱 하나씩** 띄워주는 리소스입니다.

Deployment와 비교하면 차이가 명확합니다.

| 구분 | Deployment / ReplicaSet | DaemonSet |
|---|---|---|
| 개수 결정 | `replicas`에 적은 숫자만큼 | 노드 수만큼 (노드당 1개) |
| 배치 위치 | 스케줄러가 알아서 분산 | 모든 노드에 하나씩 |
| `replicas` 필드 | 있음 | **없음** |

> 비유: Deployment는 "직원 3명 뽑아서 아무 지점에나 배치", DaemonSet은 "모든 지점에 경비원 1명씩 배치"입니다.

### 1-2. 노드 변화에 자동 반응

- **노드 추가** → 새 노드에 Pod 자동 생성
- **노드 삭제** → 그 노드의 Pod도 함께 삭제
- **Pod 삭제** → 컨트롤러가 즉시 다시 생성

### 1-3. 언제 쓰는가?

"모든 노드에서 항상 돌아야 하는 것"에 사용합니다.

- **모니터링 에이전트**: 각 노드의 CPU, 메모리 등 지표 수집
- **로그 수집 에이전트**: 각 노드의 로그를 외부(ELK, Splunk 등)로 전송
- **kube-proxy**: 각 노드의 네트워크 규칙 관리
- **CNI 플러그인**: Calico, Flannel, kindnet 등 Pod 네트워크 담당

### 1-4. YAML 구조

Deployment YAML에서 **`kind`만 바꾸고 `replicas`를 지우면** 됩니다.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: nginx-ds
spec:
  selector:
    matchLabels:
      env: demo
  template:
    metadata:
      labels:
        env: demo
    spec:
      containers:
      - name: nginx
        image: nginx
        ports:
        - containerPort: 80
```

### 1-5. 노드가 3개인데 Pod가 2개만 뜨는 이유

Control Plane 노드에는 **Taint(얼룩)** 가 걸려 있어서, 일반 워크로드는 올라가지 못합니다.
그래서 Worker 노드 2개에만 Pod가 생성됩니다.

반면 `kube-proxy`, `kindnet`은 Control Plane 노드에도 떠 있습니다.
이들은 Taint를 견딜 수 있는 **Toleration** 을 가지고 있기 때문입니다. (Taint/Toleration은 다음 강의에서 자세히 다룹니다)

### 1-6. 확인 명령

```bash
kubectl get ds                    # default 네임스페이스
kubectl get ds -A                 # 모든 네임스페이스 (-A 는 대문자)
kubectl get ds -n kube-system     # kube-proxy, kindnet 확인
```

출력 예시:

```
NAME         DESIRED   CURRENT   READY   ...
kube-proxy   3         3         3
```

DESIRED 숫자가 곧 노드 수입니다. 노드가 1개인 클러스터라면 1로 나옵니다.

`kubectl describe pod`로 보면 `Controlled By: DaemonSet/...` 으로 표시됩니다.

## 2. CronJob

### 2-1. CronJob이란?

<img width="2856" height="764" alt="image" src="https://github.com/user-attachments/assets/997c92e4-1740-4ac4-8d4f-0aa738f063c4" />

**정해진 시간마다 반복 실행**하는 작업입니다. 리눅스의 `cron`과 같은 개념입니다.

**사용 예시**
- 매일/매주/매월 리포트 생성
- 오래된 로그 정리
- 정기 백업

### 2-2. Cron 문법

```
┌───────── 분 (0~59)
│ ┌─────── 시 (0~23)
│ │ ┌───── 일 (1~31)
│ │ │ ┌─── 월 (1~12)
│ │ │ │ ┌─ 요일 (0~6, 0=일요일, 6=토요일)
│ │ │ │ │
* * * * *
```

`*`는 "모든 값", `*/n`은 "n마다"라는 뜻입니다.

| 표현 | 의미 |
|---|---|
| `* * * * *` | 매 분 |
| `*/5 * * * *` | 5분마다 |
| `0 23 * * 6` | 매주 토요일 23:00 |
| `45 23 * * 6` | 매주 토요일 23:45 |
| `0 9 1 * *` | 매월 1일 09:00 |

> 헷갈리면 "분 시 일 월 요일" 순서만 기억하면 됩니다. 사이트 crontab.guru 에서 검증할 수 있습니다.

### 2-3. YAML 구조

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: hello
spec:
  schedule: "* * * * *"
  jobTemplate:              # 시간이 되면 이 Job을 만든다
    spec:
      template:             # Job이 이 Pod를 만든다
        spec:
          containers:
          - name: hello
            image: busybox:1.28
            command: ['sh', '-c', 'date; echo Hello from Kubernetes']
          restartPolicy: OnFailure
```

## 3. Job

### 3-1. Job이란?

**한 번 실행하고 완료되면 끝나는** 작업입니다. 시간 예약이 없다는 점만 CronJob과 다릅니다.

**사용 예시**
- 설치 스크립트, 초기 데이터 적재
- 일회성 배치 작업

### 3-2. 주요 필드

| 필드 | 의미 |
|---|---|
| `completions` | 총 몇 번 성공해야 완료인가 |
| `parallelism` | 동시에 몇 개 Pod를 돌릴 것인가 |
| `backoffLimit` | 실패 시 최대 재시도 횟수 (기본 6) |

## 4. 세 리소스의 관계

```
CronJob ──(정해진 시간마다)──> Job ──> Pod
```

CronJob은 직접 Pod를 만들지 않고 **Job을 만들고, Job이 Pod를 만듭니다.**
Deployment → ReplicaSet → Pod 구조와 같은 원리입니다.

| 구분 | 실행 방식 | 끝나는가? |
|---|---|---|
| Deployment | 계속 실행 | X |
| DaemonSet | 노드마다 계속 실행 | X |
| Job | 한 번 실행 | O |
| CronJob | 정해진 시간마다 Job 생성 | 매번 O |

## 5. 명령형 생성 (시험 팁)

```bash
# Job
kubectl create job my-job --image=busybox -- echo hello

# CronJob
kubectl create cronjob hello --image=busybox:1.28 --schedule="*/1 * * * *" -- date
```

> **DaemonSet은 `kubectl create` 명령이 없습니다.**
> Deployment YAML을 뽑아서 수정하는 것이 가장 빠릅니다.
>
> ```bash
> kubectl create deploy nginx-ds --image=nginx --dry-run=client -o yaml > ds.yaml
> ```
> 이후 `kind: DaemonSet`으로 바꾸고, `replicas`, `strategy`, `status` 줄을 지웁니다.

## 6. 중요 개념 정리

- **DaemonSet = 노드당 1개.** `replicas` 필드가 없습니다.
- **Control Plane 노드에는 Taint가 있어** 일반 DaemonSet Pod가 올라가지 않습니다.
- **Job/CronJob의 Pod는 `restartPolicy`를 `Never` 또는 `OnFailure`로** 써야 합니다. `Always`는 허용되지 않습니다. (끝나야 하는 작업이기 때문)
- CronJob → Job → Pod 순서로 만들어집니다.

## 7. 강의 내용 정정

- **kube-proxy는 Control Plane 구성요소가 아닙니다.** 모든 노드에서 동작하는 **노드 구성요소**입니다. 그래서 DaemonSet으로 배포되는 것입니다.
- 강의 초반 "이전 영상에서 DaemonSet을 봤다"는 말은 **ReplicaSet**의 말실수입니다.
- 강의에서 예로 든 **Weave Net은 개발이 중단**되었습니다. 현재는 Calico, Flannel, Cilium이 주로 쓰입니다.
- 강사는 Job/CronJob이 CKA에서 중요하지 않다고 했지만, 워크로드 기본 개념으로 나올 수 있으니 **명령형 생성 방법 정도는** 익혀두는 것이 좋습니다.
