
## Day 10. 네임스페이스 (Namespace)

### 1. 네임스페이스란?
- 클러스터 안에서 리소스를 나눠주는 **논리적 격리 단위**
- 네임스페이스를 지정하지 않고 만든 리소스는 모두 `default` 네임스페이스에 생성됨
- 왜 쓰나?
  - **실수 방지**: 작업할 네임스페이스를 명시해야 하므로 엉뚱한 리소스를 지우거나 수정할 위험이 줄어듦
  - **권한 분리**: 네임스페이스마다 RBAC 권한을 다르게 줄 수 있음
  - **환경 분리**: test / prod 같은 환경을 나눠 접근 레벨, 보안, 격리를 확보
- 네임스페이스가 다르면 **같은 이름의 오브젝트**도 만들 수 있음

### 2. 기본 네임스페이스

| 네임스페이스 | 용도 |
|---|---|
| `default` | 네임스페이스를 지정하지 않았을 때 기본으로 쓰이는 공간 |
| `kube-system` | 컨트롤 플레인 컴포넌트가 실행되는 곳 (CoreDNS, etcd, kube-apiserver, controller-manager, kube-scheduler, kube-proxy, kindnet 등) |
| `kube-public` | 공개용 리소스 (기본적으로 비어 있음) |
| `kube-node-lease` | 노드 하트비트(Lease) 정보 |

> `kube-system`의 `kube-dns` 서비스가 클러스터 내부에서 **이름 → IP 해석(DNS)** 을 맡음

### 3. 네임스페이스 생성 / 조회 / 삭제

**선언형 (YAML)** — `apiVersion`, `kind`, `metadata` 세 필드면 충분 (`spec` 없음)
```yaml
apiVersion: v1    
kind: Namespace     
metadata:
  name: demo
```
```bash
kubectl apply -f ns.yaml
```

**명령형** — 훨씬 빠르기 때문에 시험에서 유용
```bash
kubectl create ns demo
```
### 4. 특정 네임스페이스에서 작업하기
`default`가 아닌 네임스페이스에서 **조회, 생성, 삭제, exec** 등을 할 때는 항상 `-n`을 붙여야 함
```bash
kubectl create deploy nginx-demo --image=nginx -n demo
kubectl get deploy -n demo
```
### 5. 네임스페이스 간 통신 실습

**실습 구성**
| 네임스페이스 | Deployment | Service |
|---|---|---|
| `demo` | nginx-demo (replicas 3) | svc-demo |
| `default` | nginx-test (replicas 3) | svc-test |

**결과**

| 접근 방식 | 같은 네임스페이스 | 다른 네임스페이스 |
|---|---|---|
| 파드 IP로 `curl` | ✅ | ✅ |
| 서비스 이름만 사용 (`curl svc-test`) | ✅ | ❌ `could not resolve host` |
| FQDN 사용 | ✅ | ✅ |

<img width="785" height="563" alt="image" src="https://github.com/user-attachments/assets/b906404a-2a69-4e09-a908-c7b573c2a44b" />


**FQDN 형식**
```
<서비스명>.<네임스페이스명>.svc.cluster.local
```
```bash
# demo 네임스페이스의 파드 안에서
curl svc-test.default.svc.cluster.local

# default 네임스페이스의 파드 안에서
curl svc-demo.demo.svc.cluster.local
```
- 파드 안의 `/etc/resolv.conf`에는 **자기 네임스페이스 기준의 search 도메인**이 설정되어 있음. 그래서 서비스 이름만 쓰면 같은 네임스페이스에서만 찾을 수 있음

## Day 11. 멀티 컨테이너 파드

### 1. 멀티 컨테이너 파드의 구성
하나의 파드 안에 **앱 컨테이너**와 이를 돕는 **추가 컨테이너**를 함께 둘 수 있음

| 종류 | 설명 |
|---|---|
| **App 컨테이너** | 메인 애플리케이션 (예: nginx) |
| **Init 컨테이너** | 앱 컨테이너보다 **먼저 실행**되어 사전 작업을 함. 끝나야(완료) 앱 컨테이너가 시작됨 (예: db, 다른 service의 준비 여부 확인)|
| **Sidecar 컨테이너** | 앱 컨테이너와 **나란히 계속 실행**되며 입력을 넣어주거나 출력을 가져감 (예: 로그 수집) |

- 파드에 할당된 **CPU, 메모리, 스토리지는 파드 안의 모든 컨테이너가 공유**


### 2. command / args
- `command`: 컨테이너에서 실행할 명령어 (Docker의 ENTRYPOINT에 해당)
- `args`: 명령어에 넘길 인자 (Docker의 CMD에 해당)

```yaml
# 방식 1: command와 args를 나눠서 작성
command: ['sh', '-c']
args: ['until nslookup myservice.default.svc.cluster.local; do echo waiting for service to be up; sleep 2; done;']

# 방식 2: command에 한꺼번에 작성
command: ['sh', '-c', 'echo The app is running && sleep 3600']
```

### 3. 실습 흐름과 상태 변화

| 단계 | 한 일 | `kubectl get pods` STATUS |
|---|---|---|
| 1 | init 컨테이너 1개로 파드 생성 (myservice 없음) | `Init:0/1` (READY 0/1, Pending) |
| 2 | `kubectl create deploy nginx-deploy --image=nginx --port=80` | 그대로 `Init:0/1` (서비스가 아직 없음) |
| 3 | `kubectl expose deploy nginx-deploy --name=myservice --port=80` | `PodInitializing` → `Running` |
| 4 | init 컨테이너를 2개로 늘려 다시 생성 (mydb 없음) | `Init:1/2` |
| 5 | `kubectl create deploy mydb --image=redis`<br>`kubectl expose deploy mydb --name=mydb --port=6379` | `PodInitializing` → `Running` |

## Day 12. DaemonSet / Job / CronJob

### 1. DaemonSet

<img width="910" height="683" alt="image" src="https://github.com/user-attachments/assets/0868513c-c330-4083-95ad-bddcbde59f75" />


**Deployment와의 차이**
| | Deployment / ReplicaSet | DaemonSet |
|---|---|---|
| 파드 수 | `replicas`에 지정한 개수 | **노드마다 1개** (노드 수 = 파드 수) |
| `replicas` 필드 | 필요 | **없음** |
| 노드가 추가될 때 | 변화 없음 | 새 노드에 **자동으로 파드 생성** |
| 노드가 삭제될 때 | 다른 노드로 다시 스케줄링 | 그 노드의 파드도 **함께 삭제** |

- 파드를 지워도 컨트롤러가 감지해서 **바로 다시 생성** (Deployment와 동일)

**대표 사용 사례**
- **모니터링 에이전트**: 모든 노드에서 메트릭을 수집
- **로깅 에이전트**: 노드와 앱 로그를 Splunk, ELK 같은 외부 시스템으로 전송
- **kube-proxy**: 모든 노드에서 동작해야 네트워크 규칙을 관리할 수 있음
- **네트워크 CNI 플러그인**: WeaveNet, Flannel, Calico, kindnet 등

**매니페스트 (ds.yaml)** 
```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: nginx-ds
  labels:
    env: demo
spec:
  # replicas 필드 없음
  selector:
    matchLabels:
      env: demo
  template:
    metadata:
      labels:
        env: demo
    spec:
      containers:
        - name: nginx
          image: nginx
          ports:
            - containerPort: 80
```

**노드가 3개인데 파드가 2개만 뜨는 이유**
- **컨트롤 플레인 노드에 Taint(테인트)가 걸려 있어서** 일반 워크로드는 스케줄링되지 않음
- 그래서 워커 노드 2개에만 배포됨 (Taint와 Toleration은 다음 강의에서 자세히 다룸)
- 반면 `kube-proxy`와 `kindnet` 데몬셋은 Toleration이 있어서 3개 노드 모두에 배포됨


### 2. Cron Syntax
```
┌───────── 분 (0 - 59)
│ ┌─────── 시 (0 - 23)
│ │ ┌───── 일 (1 - 31)
│ │ │ ┌─── 월 (1 - 12)
│ │ │ │ ┌─ 요일 (0 - 6, 0 = 일요일, 6 = 토요일)
│ │ │ │ │
* * * * *
```

| 표현식 | 의미 |
|---|---|
| `* * * * *` | 매 1분마다 (`*/1 * * * *`와 같음) |
| `*/5 * * * *` | 5분마다 |
| `*/10 * * * *` | 10분마다 |
| `* * * * 6` | 매주 토요일 (하루 종일 1분마다) |
| `* 23 * * 6` | 매주 토요일 23시대 (23:00~23:59 동안 1분마다) |
| `45 23 * * 6` | 매주 토요일 23:45에 한 번 |

### 3. CronJob
- 크론 구문으로 정한 **시간이나 간격마다 반복 실행**되는 잡
- 사용 예: 일간/주간/월간 리포트 생성, 오래된 로그 정리 같은 주기적인 작업

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: hello
spec:
  schedule: "*/1 * * * *"            # 1분마다
  jobTemplate:
    spec:
      template:
        spec:
          containers:
            - name: hello
              image: busybox:1.28
              command: ['/bin/sh', '-c', 'date; echo Hello from the Kubernetes cluster']
          restartPolicy: OnFailure
```

### 4. Job
- CronJob과 비슷하지만 **딱 한 번 실행하고 `Completed` 상태로 끝남**
- 사용 예: 설치 스크립트 실행, 클러스터 프로비저닝 자동화 파이프라인에서 하는 일회성 작업

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: one-time-job
spec:
  template:
    spec:
      containers:
        - name: job
          image: busybox:1.28
          command: ['sh', '-c', 'echo running one-time task']
      restartPolicy: Never
```
