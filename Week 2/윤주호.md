
## 2.1 쿠버네티스란?
 
- **쿠버네티스(Kubernetes, k8s)** = 컨테이너화된 애플리케이션의 배포·확장·관리를 자동화하는 플랫폼
- 이런 부류의 도구 = **컨테이너 오케스트레이션 엔진(Container Orchestration Engine)**
**도커 단독의 한계**
 
- 도커는 **호스트 1대** 범위만 관리
- 서버 N대에 걸친 컨테이너 배치·복구·트래픽 분산은 범위 밖
- → 여러 노드를 단일 리소스 풀로 묶는 상위 레이어 필요

**기본 구성**
 
| 용어 | 의미 |
|---|---|
| 노드(Node) | 컨테이너가 실제 기동되는 물리/가상 머신 |
| 마스터(Master) = 컨트롤 플레인 | 노드들을 관리·제어하는 주체 |
 

 
## 2.2 쿠버네티스의 역사
 
- 뿌리 = 구글 사내 컨테이너 클러스터 관리 시스템 **Borg**
- **2014.06** 오픈소스 공개
- **2015.07** v1.0 릴리스 → 동시에 **CNCF(Cloud Native Computing Foundation)** 로 이관 (리눅스 재단 산하)
- CNCF 이관 = 구글 단독 소유가 아닌 중립 거버넌스 확보 → 벤더 종속 우려 해소가 표준화의 결정적 요인
**CNCF 프로젝트 성숙도 3단계**
 
```
Sandbox → Incubating → Graduated
                          ↑ 쿠버네티스 (최상위)
```
 
**관리형 서비스 등장 **
 
- Google **GKE** 
- Microsoft **AKS** 
- AWS **EKS** 
 

## 2.3 쿠버네티스를 사용하면 무엇을 할 수 있을까?
 
**전체 기능 조망**
 
| 기능 | 요약 |
|---|---|
| 여러 노드 관리 | 다수 노드를 클러스터로 통합 |
| 컨테이너 스케줄링 | 배치 위치 자동 결정 |
| 롤링 업데이트 | 무중단 버전 교체 |
| 스케일링/오토스케일링 | 부하 기반 레플리카 자동 증감 |
| 컨테이너 모니터링 | 프로세스 상태 지속 감시 |
| 자동화된 복구 | 장애 시 자동 재배포 |
| 로드밸런싱 | 레플리카 간 트래픽 분산 |
| 데이터 관리 | 설정/시크릿/영구 데이터 |
| 워크로드 관리 | 배치·상시실행 등 유형별 지원 |
| 로그 관리 | 컨테이너 로그 수집/전달 |
| 선언적 관리(IaC) | 매니페스트로 원하는 상태 정의 |
| 에코시스템 확장 | CRD/오퍼레이터 |
 
---
 
### 2.3.1 선언적 코드를 사용한 관리 (IaC)
 
- YAML/JSON **매니페스트**로 "원하는 상태(Desired State)" 정의 → 실제 상태를 자동 수렴
- 기존 IaC(AWS CloudFormation, OpenStack Heat)의 사상을 컨테이너 워크로드에 적용
```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
        - name: nginx
          image: nginx:1.25
```
 
 
### 2.3.2 스케일링 / 오토스케일링
 
- 동일 이미지 기반 **레플리카(Replica)** 다중 배포 → 부하 분산 + 다중화
- 부하에 따라 레플리카 수 자동 증감
---
 
### 2.3.3 스케줄링
 
- 컨테이너를 **어느 노드에 배치할지** 결정하는 단계
- 기본 동작: 지정 없으면 CPU/메모리 여유 기준 자동 배치 → 사용자가 배치 위치를 직접 관리할 필요 없음
- 노드 자체의 자동 증감 = **Cluster Autoscaler**
---
 
### 2.3.4 리소스 관리
 
- 컨테이너별 CPU·메모리 요구량 선언 → 노드 잔여 자원 기준 자동 배치
- 리소스 사용량이 스케줄링·오토스케일링의 판단 근거
---
 
### 2.3.5 자동화된 복구 (Self-healing)
 
- 컨테이너 프로세스 표준 감시 → 정지 감지 시 자동 재배포
- 노드 장애·축출 시 다른 정상 노드로 이동 복구
- 프로세스 감시 외 헬스체크 방식: **HTTP / TCP / 셸 스크립트 실행**
---
 
### 2.3.6 로드밸런싱과 서비스 디스커버리
 
- 조건에 맞는 컨테이너 그룹에 엔드포인트 할당
- 컨테이너 확장·장애·롤링 업데이트 시 **자동 등록/해제** 
- 서비스 디스커버리 가능
#### 서비스 디스커버리
- 파드는 재생성마다 IP가 바뀜 → 직접 IP 참조 불가
- Service가 안정적 접근점(고정 이름/가상 IP) 제공 → 앱끼리 이름으로 상호 참조
---
 
### 2.3.7 데이터 관리
 
- 클러스터 상태 저장소 = **etcd** (분산 key-value 스토어, 이중화 가능)
- 컨테이너가 사용하는 설정 파일, 인증 정보 등의 데이터를 저장하는 구조 포함

---
 
## 2.4 정리
 
- 컨테이너를 서비스 환경에서 운영하려면 컨테이너 + 주변 리소스를 다루는 복잡한 기능이 필요
- 과거: CloudFormation, 로드밸런서 수동 구성, 자체 배포 스크립트로 개별 구현
- 현재: 쿠버네티스가 **사전 구현된 자동화 기능**으로 일괄 제공
- 컨테이너의 이동성·경량성을 살려 개발 속도와 배포 자동화를 동시에 달성
