> 요약) 도커는 컨테이너 `하나`를 잘 굴리는 도구, 쿠버네티스는 여러 서버에 흩어진 컨테이너 `무리`를 대신 굴려주는 도구

---

## 1. 쿠버네티스란

> 컨테이너화된 애플리케이션의 배포/확장/운영을 자동화하는 플랫폼
>
> = **컨테이너 오케스트레이션 엔진(Container Orchestration Engine)**

**왜 필요한가?** 도커만으로는 부족하기 때문

- 도커는 **도커가 설치된 호스트 1대** 안에서만 동작함
- 여러 대의 호스트를 동시에 다루거나 중앙에서 통합/관리할 수 없음
- 서버가 늘어나는 순간 `어느 서버에 띄울지, 죽으면 누가 살릴지, 트래픽은 어디로 보낼지`를 전부 사람이 처리해야 함

→ 이 반복 노동을 대신 해주는 것이 오케스트레이션 엔진

| 용어                      | 설명                                                              |
| ------------------------- | ----------------------------------------------------------------- |
| 오케스트레이션            | 여러 컨테이너의 배치, 기동, 감시, 연결을 지휘(orchestrate)하는 것 |
| 쿠버네티스 노드(Node)     | 실제로 컨테이너가 기동되는 물리 머신 또는 가상 머신 (= 일꾼)      |
| 쿠버네티스 마스터(Master) | 노드들을 관리하고 명령을 내리는 두뇌 (= 지휘자)                   |
| 컨테이너 런타임           | 컨테이너를 실제로 실행하는 엔진 (도커, containerd, cri-o 등)      |

cf. 경쟁자와 표준화

- 다른 오케스트레이션 엔진: **도커 스웜(Docker Swarm)**, **아파치 메소스(Apache Mesos)**
- 하지만 실제 서비스 환경에서 가장 많이 쓰이는 건 쿠버네티스 (표준)

cf. 런타임에 종속되지 않음

- 쿠버네티스가 쓸 수 있는 컨테이너 런타임은 도커만이 아님 → containerd, cri-o 등도 가능
- 즉 **쿠버네티스 = 도커 전용이 아님**. 도커는 선택지 중 하나일 뿐

## 2. 쿠버네티스의 역사

**Borg → 오픈 소스 → CNCF**

- 현재는 CNCF가 호스트로서 커뮤니티를 주도하며 개발도 진행
- 쿠버네티스는 소프트웨어 품질뿐 아니라 **프로젝트 활성도, 운영 프로세스의 명확성**까지 인정받아 Sandbox(초기 단계), Incubating(인큐베이팅/성장 중), Graduated 프로젝트 성숙도 중 Graduated로 분류됨
- cf. Graduated = '졸업'이지만, CNCF가 호스트를 하지 않는다는 의미는 x

### 관리형(Managed) 서비스 출시

| GCP가 **GKE**(구 Google Container Engine) 제공 시작   |
| ----------------------------------------------------- |
| Azure가 **AKS**(구 Azure Container Service) 출시      |
| AWS가 **EKS**(Amazon Elastic Kubernetes Service) 출시 |

- 한동안은 GKE 외에 선택지가 없었으나, 이후 **3대 클라우드가 모두 관리형 쿠버네티스를 보유**
- 대형 클라우드 사업자가 전부 밀어주는 순간 표준 지위가 굳어짐

## 3. 컨테이너를 서비스 환경에서 쓸 때 생기는 과제 (쿠버네티스를 사용하면 무엇을 할 수 있을까?)

> 컨테이너 = 어떤 애플리케이션을 실행하도록 빌드된 컨테이너 이미지를 기반으로 기동된 워크로드

도커로 배포는 쉽게 되지만, **서비스 환경**에 올리는 순간 아래 문제들이 따라옴

- 여러 쿠버네티스 노드 관리
- 컨테이너 스케줄링
- 롤링 업데이트
- 스케일링 / 오토 스케일링
- 컨테이너 모니터링
- 자동화된 복구
- 서비스 디스커버리
- 로드 밸런싱
- 데이터 관리
- 워크로드 관리
- 로그 관리
- 선언적 코드를 사용한 관리
- 그 외 에코시스템과의 연계 및 확장

→ 아래 항목들은 **이 과제들을 쿠버네티스가 어떻게 해결하는지**에 대한 답

---

## 4. 선언적 코드를 사용한 관리 (IaC)

> **명령형**: "이거 해, 그다음 저거 해" (절차를 지시)
>
> **선언형**: "결과가 이 상태가 되게 해" (원하는 상태만 기술)

- 쿠버네티스는 **YAML 또는 JSON**으로 작성한 선언적 코드(**매니페스트**)로 컨테이너와 주변 리소스를 관리 → **IaC(Infrastructure as Code)** 구현
- 사람이 절차를 밟는 게 아니라, 쿠버네티스가 매니페스트에 적힌 상태를 계속 맞추려고 함

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-deployment
spec:
  replicas: 3 # "3개 띄워라"가 아니라 "3개인 상태를 유지해라"
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
        - name: nginx-container
          image: nginx:1.16
```

- 컨테이너 이전의 가상화 시대에도 비슷한 시도는 있었음 → **AWS CloudFormation**, **OpenStack Heat**
- 쿠버네티스는 그에 준하는 것을 컨테이너 시대에 맞춰 제공

## 5. 스케일링 / 오토 스케일링

- 여러 노드를 묶어 **쿠버네티스 클러스터**를 구성
- 같은 이미지 기반의 컨테이너를 여러 개(**레플리카**) 배포 → **부하 분산 + 다중화 구조**가 자연스럽게 만들어짐
- 부하에 따라 레플리카 수를 **자동으로 늘리거나 줄임** (오토 스케일링)

## 6. 스케줄링

> **스케줄링** = 컨테이너를 "어느 노드에 배치할지" 결정하는 단계

- **어피니티(Affinity)** / **안티 어피니티(Anti-Affinity)** 로 배치 조건을 제어
- 워크로드 특징 또는 노드 성능을 기준으로 배치 가능
  - ex) '디스크 I/O가 많은' 컨테이너 → '디스크가 SSD인' 노드에 배치
- GCP/AWS/OpenStack 위에 클러스터를 구축한 경우, 노드에 **가용 영역(Availability Zone)** 등을 식별하는 정보가 자동 부여됨 → **멀티존 분산 배치**가 쉬움

> ![alt text](/images/yoonji_image1.png)

## 7. 리소스 관리

- 특별한 배치 지정이 없으면 각 노드의 **CPU/메모리 여유 상태**에 따라 알아서 스케줄링됨
- 즉 사용자가 `어느 노드에 넣을지`를 **관리할 필요가 없음**
- **클러스터 오토 스케일링**: 리소스 사용 상태에 따라 **노드 자체도** 자동으로 추가/삭제됨

> ![alt text](/images/yoonji_image2.png)

---

## 8. 자동화된 복구 (Self-healing)

> 다중화(fault tolerant) 관점에서 쿠버네티스의 핵심 컨셉 중 하나

- 컨테이너 프로세스를 **표준으로 모니터링** → 프로세스 정지를 감지하면 다시 스케줄링해서 **자동 재배포**
- 클러스터 노드에 장애가 발생하거나 노드를 축출한 경우, 그 노드의 컨테이너가 사라져도 **서비스에 영향 없이 자동 복구**
- 복구 실행 조건은 프로세스 감시 외에도 설정 가능
  - **HTTP / TCP 요청**, **셸 스크립트**로 헬스 체크 성공 여부 판단

> ![alt text](/images/yoonji_image3.png)

## 9. 로드 밸런싱과 서비스 디스커버리

**문제**: 여러 대로 나뉜 애플리케이션을 사용자에게는 `하나`로 보여줘야 함 → 목적지가 되는 **엔드포인트**가 필요

- 기존 VM 환경: 로드 밸런서를 만들고 → VM들을 등록하고 → LB 주소를 엔드포인트로 할당 (전부 수동)
- 쿠버네티스: **서비스(Service)** 와 **인그레스(Ingress)** 가 로드 밸런서 역할을 제공
  - 사전에 정의한 조건과 일치하는 컨테이너 그룹으로 라우팅되는 엔드포인트를 할당

**자동으로 처리되는 것들**

- 컨테이너 확장 시 **엔드포인트에 자동 등록/삭제**
- 컨테이너 장애 시 **자동 분리**
- 롤링 업데이트 시 필요한 **사전 분리 작업**

→ 높은 서비스 레벨을 유지하면서 엔드포인트 관리를 쿠버네티스에 위임 가능

### 서비스 디스커버리

- 컨테이너로 시스템을 만들면 보통 기능별로 쪼갠 **마이크로서비스 아키텍처**를 택하게 됨
- 이때 각 마이크로서비스가 **서로를 어떻게 찾을 것인가**가 문제
- 서비스에 디스커버리 기능이 있어, 각 마이크로서비스가 정의된 여러 매니페스트만으로 **시스템 전체를 쉽게 연계**할 수 있음

## 10. 데이터 관리

- 백엔드 데이터 스토어로 **etcd**를 채용
- etcd 자체도 클러스터를 구성해 **이중화 가능** → 컨테이너·서비스의 매니페스트도 이중화 구조로 저장
- 컨테이너가 사용하는 **설정 파일이나 인증 정보**를 저장하는 구조도 보유
  - ex) 컨테이너 공통 설정, 애플리케이션이 쓰는 DB 인증 정보 등을 **안전하고 이중화된 상태로 마스터에서 집중 관리**

## 11. 에코시스템과의 연계

쿠버네티스는 단독 플랫폼으로도 쓰지만, 외부 에코시스템과의 연계가 활발함

| 미들웨어      | 역할                                              |
| ------------- | ------------------------------------------------- |
| Ansible       | 쿠버네티스에 컨테이너 배포                        |
| Apache Ignite | 서비스 디스커버리를 활용한 클러스터 생성·스케일링 |
| Fluentd       | 컨테이너 로그 전송                                |
| GitLab        | CI/CD 도구들과 쿠버네티스의 통합                  |
| Jenkins       | 잡(Job) 실행 시 실행용 컨테이너를 배포            |
| OpenStack     | 클라우드 사업자와 연계한 쿠버네티스 구축          |
| Prometheus    | 쿠버네티스 모니터링                               |
| Spark         | 잡을 쿠버네티스에서 네이티브로 실행 (YARN 대체)   |
| Spinnaker     | 컨테이너 배포                                     |
| Kubeflow      | ML 플랫폼 배포                                    |
| Rook          | 분산 파일 시스템 배포                             |
| Vitess        | MySQL 클러스터 배포                               |

- 또한 쿠버네티스는 **기능을 확장할 수 있는 여러 구조**를 가짐
- 자체 기능을 추가하거나, **쿠버네티스 자체를 프레임워크 삼아 자체 플랫폼을 구현**하는 것도 가능

## 12. 정리

- 도커 컨테이너를 **서비스 환경**에서 쓰려면 컨테이너와 그 주변 리소스를 관리하는 복잡한 기능이 필요함
- 쿠버네티스를 쓰면 **이미 개발된 자동화 기능**을 그대로 가져다 쓸 수 있음
- 기존 VM 환경에서 전체 시스템 자동 배포를 구현하려면?
  - AWS CloudFormation을 쓰거나 → 로드 밸런서 구조를 직접 만들거나 → 업데이트 구조를 계속 수정해야 했음
- 쿠버네티스는 **컨테이너의 이동성과 경량화**를 활용해 빠른 개발 + 배포 자동화를 구현
- +) 자체 제작한 배포 스크립트 등을 쿠버네티스와 그 주변 에코시스템에서 **공통으로 재사용**할 수 있다는 것도 큰 장점
