# 3장 쿠버네티스 환경 선택

## 3.1 쿠버네티스 환경의 종류

쿠버네티스 클러스터를 구성하는 방법은 크게 세 가지다.

- **로컬 쿠버네티스**: 물리 머신 한 대에 구축하여 사용
- **쿠버네티스 구축 도구**: 도구를 사용하여 온프레미스/클라우드에 클러스터를 구축
- **관리형 쿠버네티스 서비스**: 퍼블릭 클라우드의 관리형 서비스로 제공하는 클러스터 사용

### 환경별 용도

- 로컬 쿠버네티스: 네트워크 연결 없이 바로 확인 가능. 개인 테스트/개발 환경에 적합. 이중화가 없어 서비스 환경에는 부적합
- 스테이징 및 서비스 환경: 구축 도구나 관리형 서비스 사용 권장
  - 관리형 서비스: 이미 사용 가능한 환경이 있다면 사용
  - 구축 도구: 온프레미스 배포, 세밀한 커스터마이즈가 필요한 경우

### 환경 간 호환성

- 일부 기능은 환경에 따라 사용 불가 (외부 로드 밸런서와의 연계, 동적 영구 볼륨 프로비저닝 등)
- 기본적으로는 어떤 환경에서도 동일하게 동작
- 이유: CNCF의 **쿠버네티스 적합성 인증 프로그램**(Certified Kubernetes Conformance Program)을 각 환경이 준수
  - 클러스터 기능 동작의 일관성과 이식성 보장

### 이 장에서 소개하는 환경

| 분류 | 도구 |
|---|---|
| 로컬 쿠버네티스 | 미니큐브(Minikube), Docker Desktop for Mac/Windows, kind |
| 구축 도구 | 큐브어드민(kubeadm), 랜처(Rancher) |
| 관리형 서비스 | GKE, AKS, EKS |

> 위 방법으로 구축한 환경은 모두 Certified Kubernetes Distribution/Platform이다.
> 4장 이후 기능 소개는 GKE 기준으로 집필됐지만 대부분 다른 환경에서도 동일하게 사용 가능하다.

## 3.2 로컬 쿠버네티스

- 물리 머신에서 손쉽게 쿠버네티스를 테스트하는 방법
- 한 대에 올인원 구성이라 **이중화가 보장되지 않음**
- 일부 사용 불가능한 기능 존재

### 3.2.1 미니큐브(Minikube)

- 물리 머신에 로컬 쿠버네티스를 쉽게 구축하는 도구
- 쿠버네티스의 SIG-Cluster-Lifecycle 분과회에서 개발
- **단일 노드 구성**이라 여러 대가 필요한 기능은 사용 불가
- 하이퍼바이저가 필요하며 OS별로 사전 설치 필요

| OS | 하이퍼바이저 |
|---|---|
| macOS | 도커/하이퍼킷 드라이버/VirtualBox/Parallels/VMware Fusion/Podman 중 하나 |
| Linux | 도커/VirtualBox/Podman/KVM/베어메탈(systemd-based) 중 하나 |
| Windows | 도커/VirtualBox/Hyper-V 중 하나 |

미니큐브는 하이퍼바이저에 맞는 드라이버를 지정하면 자동으로 호스트가 되는 컨테이너나 가상 머신을 생성하고 그 환경에 쿠버네티스를 설치한다. 구축한 클러스터는 kubectl로 조작한다.

#### 설치 (macOS + 홈브류)

```bash
# 홈브류 설치
/usr/bin/ruby -e "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/master/install)"

# 하이퍼킷 설치
brew update
brew install hyperkit

# 미니큐브 설치
brew install minikube
minikube version   # v1.18.1
```

#### 기동

```bash
# 하이퍼킷 드라이버, 쿠버네티스 버전 지정하여 기동
minikube start --driver=hyperkit --kubernetes-version v1.18.15

# 상태 확인
minikube status
# host: Running / kubelet: Running / apiserver: Running / kubeconfig: Configured

# 컨텍스트 전환
kubectl config use-context minikube

# 노드 확인 (가상 머신 미니큐브가 노드로 인식됨)
kubectl get nodes
# minikube  Ready  master  11m  v1.18.15

# 클러스터 삭제
minikube delete
```

- `minikube tunnel` 명령으로 ClusterIP 서비스에 연결 가능
- **Addon 기능**으로 이스티오(Istio) 등 설치 가능

### 3.2.2 Docker Desktop for Mac / Windows

- 버전 18.06.0 CE부터 로컬 머신에서 쿠버네티스 사용 가능
- **쿠버네티스 버전 지정 불가** (특정 버전이 필요한 경우 주의)
- 설치 후 Preference에서 쿠버네티스 활성화 필요 (배포에 약 5분 소요)

```bash
# 컨텍스트 변경
kubectl config use-context docker-desktop

# 노드 확인 (도커 호스트가 노드로 인식됨)
kubectl get nodes
# docker-desktop  Ready  master  2m44s  v1.16.6-beta.0

# 구성 요소도 컨테이너로 기동됨 (Show system containers 활성화 시 확인 가능)
docker container ls --format 'table {{.Image}}\t{{.Command}}' | grep -v pause
# kube-apiserver, kube-scheduler, etcd, coredns 등 확인
```

### 3.2.3 kind (Kubernetes in Docker)

- 쿠버네티스 자체 개발을 위한 도구, SIG-Testing 분과회에서 개발
- 도커 컨테이너 여러 개를 쿠버네티스 노드로 사용하여 **멀티 노드 클러스터** 구축
- 로컬에서 멀티 노드 클러스터를 구축할 때 가장 좋은 선택

<img width="1448" height="1086" alt="image" src="https://github.com/user-attachments/assets/761b97b1-f9bc-485f-b993-7af7f14a9a6b" />

```bash
# 설치
brew install kind
kind version   # v0.10.0
```

#### 클러스터 구성 (kind.yaml)

마스터 3대 + 워커 3대 예시. 노드 이미지는 도커 허브의 kindest Organization에서 관리.

```yaml
apiVersion: kind.x-k8s.io/v1alpha4
kind: Cluster
nodes:
- role: control-plane
  image: kindest/node:v1.18.15
- role: control-plane
  image: kindest/node:v1.18.15
- role: control-plane
  image: kindest/node:v1.18.15
- role: worker
  image: kindest/node:v1.18.15
- role: worker
  image: kindest/node:v1.18.15
- role: worker
  image: kindest/node:v1.18.15
```

#### 클러스터 기동/삭제

```bash
# 기동 (Docker Desktop의 도커 환경이 기동 중이어야 함)
kind create cluster --config kind.yaml --name kindcluster

# 컨텍스트 전환
kubectl config use-context kind-kindcluster

# 노드 확인
kubectl get nodes
# kindcluster-control-plane   Ready  master
# kindcluster-control-plane2  Ready  master
# kindcluster-control-plane3  Ready  master
# kindcluster-worker          Ready  <none>
# kindcluster-worker2         Ready  <none>
# kindcluster-worker3         Ready  <none>

# 삭제
kind delete cluster --name kindcluster
```

- 호스트에서 `docker container ls` 하면 노드 대수만큼의 컨테이너 확인 가능
- **마스터 이중화를 위해 HAProxy 컨테이너가 자동으로 생성됨** (kindcluster-external-load-balancer)

#### kind 심화

- 내부에서 kubeadm을 사용해 구축
- `kubeadmConfigPatches`, `kubeadmConfigPatchesJson6902`로 설정 패치 적용 가능
- 알파 기능 활성화 클러스터 구축 예 (kind-alpha.yaml):

```yaml
apiVersion: kind.x-k8s.io/v1alpha4
kind: Cluster
kubeadmConfigPatches:
- |
  apiVersion: kubeadm.k8s.io/v1beta2
  kind: ClusterConfiguration
  metadata:
    name: config
  apiServer:
    extraArgs:
      "feature-gates": "EphemeralContainers=true,HPAScaleToZero=true,TTLAfterFinished=true,ServiceTopology=true,ImmutableEphemeralVolumes=true"
```

- `extraPortMapping` 설정으로 로컬 머신에서 내부 컨테이너로의 통신 확보 가능
- kindest/node 이미지는 모든 버전이 공개되지는 않음. 미공개 버전은 amsy810/kind-node 이미지 참고

> **column: FeatureGates**
> 쿠버네티스 기능을 활성화/비활성화하는 방법. 베타 이상 기능은 기본 활성화, 알파 기능은 명시적으로 활성화 필요. 새 기능 추가 여부는 FeatureGates 확인으로 파악 가능.

## 3.3 쿠버네티스 구축 도구

구축 도구를 사용하여 여러 노드의 쿠버네티스 클러스터를 구축하는 방법.

### 3.3.1 쿠버네티스 서비스 수준 목표(SLO)

SIG-Scalability 분과회가 쿠버네티스 확장성을 논의하며 SLI(Service Level Indicator)/SLO(Service Level Objective)를 정의.

- **API 응답 시간**
  - 단일 객체의 변경 API 요청: 지난 5분 동안 99%가 1초 내에 돌아올 것 (일부 제외)
  - 비스트리밍 API 요청: 지난 5분 동안 99%가 아래 초 이내 (일부 제외)
    - 특정 리소스: 1초 / 네임스페이스 전체: 5초 / 클러스터 전체: 30초
- **파드 기동 시간**
  - 지난 5분 동안 99%가 5초 이내 기동 (이미지 다운로드, Init Container 처리 시간 제외)

#### 표 3-2 SLO를 충족하는 클러스터 최대 사이즈

| 항목 | 네임스페이스 단위 상한 | 클러스터 전체 상한 |
|---|---|---|
| 노드 수 | - | 5,000 노드 이하 |
| 클러스터 내 총 파드 수 | 3,000 파드 이하 | 150,000 파드 이하 |
| 1 노드당 파드 수 | - | 110 파드 또는 (코어 수 × 10) 중 낮은 쪽 |
| 서비스 수 | 5,000 이하 | 10,000 이하 |

- 이 이상 규모도 가능하지만 서비스 수준이 떨어질 수 있음
- 관리형 서비스는 파드 네트워크 구성 제약으로 파드 수 제한이 다를 수 있음
- 관리형 서비스는 마스터 노드 스케일 업이 자동. 구축 도구 사용 시 마스터 인스턴스 사이즈를 직접 정해야 함 (kube-up 스크립트의 GCP/AWS 인스턴스 사이즈 기준 참고 가능)

### 3.3.2 큐브어드민(kubeadm)

- 쿠버네티스 공식 구축 도구. 쿠버네티스 1.13(2018년 12월)에 GA
- 예제: Ubuntu 18.04 머신 여러 대로 멀티 노드 클러스터 구성

#### 사전 준비 (모든 노드)

```bash
# 필요한 의존 패키지 설치
sudo apt update && sudo apt install -y apt-transport-https curl

# 저장소 등록 및 업데이트
curl -s https://packages.cloud.google.com/apt/doc/apt-key.gpg | sudo apt-key add -
cat << EOF | sudo tee /etc/apt/sources.list.d/kubernetes.list
deb http://apt.kubernetes.io/ kubernetes-xenial main
EOF
sudo apt update

# 쿠버네티스 관련 패키지 설치
sudo apt install -y kubelet=1.18.15-00 kubeadm=1.18.15-00 kubectl=1.18.15-00 docker.io

# 버전 고정
sudo apt-mark hold kubelet kubeadm kubectl docker.io

# 오버레이 네트워크용 커널 파라미터 변경
cat << EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-ip6tables = 1
net.bridge.bridge-nf-call-iptables = 1
net.ipv4.ip_forward = 1
EOF
sudo sysctl --system
```

#### 마스터 노드 구축

- `--pod-network-cidr`: 클러스터 내부 네트워크(파드 네트워크)용. 플라넬 사용을 위한 설정
- **swap 비활성화 필수**: 일시적으로는 `sudo swapoff -a`, 영구적으로는 /etc/fstab의 swap 행 주석 처리

```bash
# kubeadm 초기화 (마스터 구축)
sudo kubeadm init \
--kubernetes-version=1.18.15 \
--pod-network-cidr=172.31.0.0/16

# 성공 시 워커 노드에서 실행할 join 명령어가 출력됨

# 인증용 파일 복사 (kubectl 사용 준비)
mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config
```

#### 워커 노드 조인

```bash
# 노드가 될 머신에서 실행 (마스터 구축 시 출력된 명령어)
sudo kubeadm join 172.31.2.189:6443 --token zpn5s6.jcx9h6k3a78znd3p \
--discovery-token-ca-cert-hash sha256:983f234b2c7641e817205f16270547ccc1da2a5360aac2abb767b2352ada464e
```

여기까지 하면 프로세스는 모두 기동 중이지만, **서로 다른 노드에 배포된 파드 간 통신이 안 되는 상태**라 아직 멀티 노드 클러스터라 하기 부족함.

### 3.3.4 랜처(Rancher)

- Rancher Labs가 개발하는 오픈 소스 컨테이너 플랫폼
- 1.X는 다양한 오케스트레이션 도구 지원, 2.0(2018년 5월 출시)부터 쿠버네티스 중심

#### 랜처 2.0 주요 기능 (버전 2.3 기준)

- 여러 클러스터의 통합 관리
- 클러스터를 다양한 플랫폼에 배포 (AWS, OpenStack, VMware 등)
- 기존 클러스터를 랜처로 관리 (클러스터 임포트, 온프레미스 포함)
- 멀티 클러스터 앱(Multi-cluster App): 여러 클러스터에 애플리케이션 배포
- 중앙 집중적 인증, 모니터링, 웹 UI
- 풍부한 애플리케이션 카탈로그
- 이스티오(Istio)와의 통합/연계

#### 구조

- 중앙에서 **랜처 서버**를 기동하고, 랜처 서버를 통해 클러스터를 구축·관리
- 클라우드 프로바이더 환경에도 랜처 서버가 프로바이더 API를 사용해 구축/관리 가능

## 3.4 퍼블릭 클라우드 관리형 쿠버네티스 서비스

영구 볼륨, 로드 밸런서와의 연계 등을 쉽게 사용할 수 있도록 기능 제공.

### 3.4.1 GKE (Google Kubernetes Engine)

- 가장 먼저 출시된 관리형 쿠버네티스 서비스 (2015년 8월 GA)
- Borg 기반 노하우로 만들어져 관리 편의 기능 다수
  - 릴리스 채널, 노드 자동 업데이트, 노드 자동 복구, 노드 자동 프로비저닝 등

#### 특징

- 노드로 GCE(Google Compute Engine) 사용
- **선점형 인스턴스(Preemptible Instance)**: 가동 시간 24시간 제한의 저비용 인스턴스를 노드로 사용 가능
  - 비용 절감 가능하나 노드가 정지될 수 있음. 서비스 구성을 잘 해두면 인스턴스 재생성 시 자동 복구 가능
  - 선점형만으로 구성하면 24시간 후 모든 노드가 동시 정지될 수 있음 → 랜덤으로 서서히 노드를 교체하는 preemptible-killer 검토
- **노드 자동 복구(Node Auto Repair)**: 인스턴스 장애 시 노드 재생성
- GCP 기능과 통합: Cloud Logging(구 Stackdriver) 기본 연계, HTTP 로드 밸런서(인그레스), GPU 사용 가능
- **노드 풀(NodePool)**: 노드에 레이블을 부여해 그룹핑
  - 'vCPU 많은 노드', '메모리 많은 노드' 등 성능이 다른 노드를 배치하고 스케줄링 시 배포 제약 조건으로 활용
  - 워크로드 분리, 노드 종류별 규모 제어 가능. 현재 다른 관리형 서비스에서도 제공

#### 구축

```bash
# Google Cloud SDK 설치
curl https://sdk.cloud.google.com | bash
exec -l $SHELL

# gcloud CLI 인증
gcloud init

# 사용 가능한 쿠버네티스 버전 확인 (asia-northeast3 = 서울 리전)
gcloud container get-server-config --zone asia-northeast3-a
# channels: RAPID / REGULAR / STABLE, validMasterVersions, validNodeVersions 출력

# GKE 클러스터 'k8s' 생성
gcloud container clusters create k8s \
--cluster-version 1.18.16-gke.2100 \  # validMasterVersions에 있는 버전 지정
--zone asia-northeast3-a \
--num-nodes 3

# "Kubernetes Engine API is not enabled" 에러 시
# → 에러 메시지 마지막의 URL에서 GCP 프로젝트의 Kubernetes Engine API 활성화

# 인증 정보는 ~/.kube/config에 자동 저장됨. 다시 가져오려면:
gcloud container clusters get-credentials k8s --zone asia-northeast3-a

# IAM 사용자에게 클러스터 관리자 권한 설정
GCP_USER=`gcloud config get-value core/account`
kubectl create --save-config clusterrolebinding iam-cluster-admin-binding \
--clusterrole=cluster-admin \
--user=${GCP_USER}

# 클러스터 삭제
gcloud container clusters delete k8s --zone asia-northeast3-a
```

- 구글 클라우드 콘솔의 자체 대시보드로도 관리 가능

### 3.4.2 AKS (Azure Kubernetes Service)

- Microsoft Azure의 관리형 쿠버네티스 서비스 (2018년 6월 GA)

#### 특징

- Azure Active Directory를 쿠버네티스 RBAC과 연계
- **버추얼 쿠버렛(Virtual Kubelet)**: 클러스터 리소스 부족 시 Azure Container Instances(ACI)로 버스팅(bursting)
  - 클러스터 스케일 아웃이 아니라 ACI 버스팅이라 파드를 몇 초 안에 기동. 버스팅 전까지 비용 없음

#### 구축

```bash
# Azure CLI 설치 및 인증
pip install paramiko
brew install azure-cli   # macOS
az login

# 사용 가능한 쿠버네티스 버전 확인
az aks get-versions -l koreasouth

# 리소스 그룹 생성
az group create --name k8srg --location koreasouth

# service principal 생성
az ad sp create-for-rbac --skip-assignment --name myAKSClusterServicePrincipal
# appId, password 출력됨

# AKS 클러스터 'k8s' 생성 (리소스 그룹 사용)
az aks create \
--name k8s \
--kubernetes-version 1.18.14 \
--node-count 3 \
--resource-group k8srg \
--generate-ssh-keys \
--service-principal <appId> \
--client-secret <password>

# 인증 정보 가져오기
az aks get-credentials --name k8s --resource-group k8srg

# 쿠버네티스 대시보드 표시
az aks browse --name k8s --resource-group k8srg

# 클러스터 삭제
az aks delete --name k8s --resource-group k8srg
```

### 3.4.3 EKS (Elastic Kubernetes Service)

- AWS re:invent 2017 발표, 2018년 6월 GA

#### 특징

- IAM과 쿠버네티스 사용자를 연결하여 IAM 기반 권한 관리
- 파드 네트워크와 AWS VPC 서브넷이 직접 연결 → 가상 머신에서 컨테이너로 직접 통신 가능
- CloudWatch Logs, CloudTrail 연계 로깅 등 AWS 서비스 통합 기대
- 노드: AWS 제공 AMI로 생성한 EC2 인스턴스 (Packer로 커스텀 AMI 생성 가능)
- 운용 부하 절감: **Managed Nodegroups**(워커 노드 관리를 AWS에 위임), **EKS on Fargate**
  - 단, 집필 시점 기준 클러스터 내부 DNS, CNI, 인그레스 컨트롤러 등은 관리되지 않음

#### 구축 (eksctl)

- AWS CLI + CloudFormation 방식은 커스터마이즈에 좋지만 복잡
- 여기서는 Amazon과 Waveworks가 개발한 오픈 소스 **eksctl** 사용

```bash
# AWS Credential 생성
vi ~/.aws/credentials
# [default]
# aws_access_key_id=XXXX
# aws_secret_access_key=XXXX

# eksctl 설치
curl --silent --location \
"https://github.com/weaveworks/eksctl/releases/latest/download/eksctl_$(uname -s)_amd64.tar.gz" | tar xz -C /tmp
sudo mv /tmp/eksctl /usr/local/bin

# EKS 클러스터 'k8s' 생성 (명령어 하나로 기동)
eksctl create cluster \
--name k8s \
--version 1.18 \
--region ap-northeast-2 \
--nodes 3 \
--managed   # Managed Nodegroups 활성화

# 인증 정보 가져오기
eksctl utils write-kubeconfig --cluster k8s

# 클러스터 삭제
eksctl delete cluster --name k8s --region ap-northeast-2
```

- eksctl 없이 생성하는 문서도 별도 존재. EKS는 깃허브에 로드맵 문서 공개 중

## 3.5 쿠버네티스 플레이그라운드

- 도커에서 제공하는 웹 기반 쿠버네티스 테스트 환경
- 최대 다섯 대 인스턴스 기동, 화면에 표시되는 순서대로 kubeadm을 사용해 클러스터 구축
- 짧게는 1분 정도에 환경 구축 가능
- **연속 사용 시간 제한(최대 4시간)**, 기능 제한 있음

## 3.6 정리

쿠버네티스 환경 구성 방법 세 가지:

- **로컬 쿠버네티스**: 물리 머신 한 대에 구축
- **쿠버네티스 구축 도구**: 도구로 온프레미스/클라우드에 구축
- **관리형 쿠버네티스 서비스**: 퍼블릭 클라우드 관리형 서비스 사용

플랫폼 종류(퍼블릭/프라이빗 클라우드), 환경 용도(개발/스테이징/서비스)에 맞게 선택.

- 인증 프로그램을 통해 인증받은 환경이라면 동작 일관성은 보장되지만 환경별 기능 차이 존재
- 개발/스테이징/서비스 환경은 가능하면 같은 환경 권장
- **최소한 스테이징과 서비스 환경은 같은 환경에서 운용할 것**
