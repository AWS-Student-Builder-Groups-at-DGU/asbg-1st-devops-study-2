# 5장. 워크로드 API 카테고리

『쿠버네티스 완벽 가이드』 5주차 정리 — 민성

4장에서 쿠버네티스 리소스가 다섯 카테고리로 나뉜다고 했는데, 5장은 그중 첫 번째인 워크로드 API 카테고리를 자세히 다룬다. 클러스터 위에서 컨테이너를 기동하기 위한 리소스들이고, 사용자가 직접 다루는 것은 여덟 가지다.

---

## 5.1 워크로드 API 카테고리 개요

사용자가 직접 사용하는 워크로드 리소스 여덟 가지는 다음과 같다.

파드, 레플리케이션 컨트롤러, 레플리카셋, 디플로이먼트, 데몬셋, 스테이트풀셋, 잡, 크론잡

핵심은 이 리소스들이 파드를 최소 단위로 하고, 그것을 관리하는 상위 리소스가 있는 부모 자식 관계로 되어 있다는 점이다. 예를 들어 디플로이먼트는 레플리카셋을 관리하고, 레플리카셋은 파드를 관리한다.

```
Tier 1          Tier 2                    Tier 3
파드    ←    레플리케이션 컨트롤러
파드    ←    레플리카셋           ←    디플로이먼트
파드    ←    데몬셋
파드    ←    스테이트풀셋
파드    ←    잡                   ←    크론잡
```

이 계층 구조를 이해하면 나머지 내용이 훨씬 쉬워진다.

## 5.2 파드

워크로드 리소스의 최소 단위다. 파드는 하나 이상의 컨테이너로 구성되며, 같은 파드에 포함된 컨테이너끼리는 네트워크적으로 격리되어 있지 않고 IP 주소를 공유한다.

즉 컨테이너가 두 개 들어 있는 파드를 만들면 두 컨테이너는 같은 IP를 가지고, 서로 localhost로 통신할 수 있다. 파드 내부에서 네트워크 네임스페이스를 공유하기 때문이다.

대부분의 경우 하나의 파드에 하나의 컨테이너를 두지만, 메인 컨테이너를 지원하는 서브 컨테이너를 함께 넣기도 한다. 서브 컨테이너의 예로는 로그 수집 역할을 하는 컨테이너, 설정값을 동적으로 변경시키는 컨테이너, 로컬 캐시용 컨테이너, SSL용 컨테이너 등이 있다.

주의할 점은 nginx 컨테이너와 redis 컨테이너처럼 메인 컨테이너 성격의 것을 하나의 파드 안에 두는 구성은 추천하지 않는다는 것이다. 개별 파드의 이동이 어려워지고 복잡해지기 때문이다.

### 5.2.1 파드 디자인 패턴

| 종류 | 개요 |
| --- | --- |
| 사이드카 패턴 | 메인 컨테이너에 기능을 추가한다 |
| 앰배서더 패턴 | 외부 시스템과의 통신을 중계한다 |
| 어댑터 패턴 | 외부 접속을 위한 인터페이스를 제공한다 |

보조적인 역할을 하는 서브 컨테이너를 통틀어 사이드카라고 부르는 경우도 있다.

사이드카 패턴은 메인 컨테이너 외에 보조 기능을 추가하는 서브 컨테이너를 포함하는 패턴이다. 특정 변경 사항을 감지해 동적으로 설정을 변경하는 컨테이너, 깃 저장소와 로컬 스토리지를 동기화하는 컨테이너, 애플리케이션 로그 파일을 오브젝트 스토리지로 전송하는 컨테이너 같은 구성이 자주 사용된다. 파드는 데이터 영역을 공유할 수 있기 때문에 대부분 데이터와 설정에 관련된 패턴이라 할 수 있다.

### 파드 기타 설정

```yaml
spec:
  containers:
  - name: nginx-container
    image: nginx:1.16
    workingDir: /tmp        # 프로세스 실행 디렉터리 지정
```

workingDir을 설정하면 컨테이너 안에서 프로세스가 실행되는 디렉터리가 바뀐다.

```bash
kubectl exec -it sample-pod -- pwd          # /
kubectl exec -it sample-workingdir -- pwd   # /tmp
```

## 5.3 레플리카셋 / 레플리케이션 컨트롤러

지정한 수의 파드를 유지하는 리소스다. 레플리케이션 컨트롤러는 구버전이고 지금은 레플리카셋을 쓴다.

```bash
kubectl get replicasets -o wide
# NAME       DESIRED  CURRENT  READY  AGE  CONTAINERS        IMAGES       SELECTOR
# sample-rs  3        3        3      11s  nginx-container   nginx:1.16   app=sample-app
```

레플리카셋은 레이블로 관리 대상 파드를 판별한다. 위 예에서는 `app=sample-app` 레이블이 붙은 파드를 세 개 유지한다.

```bash
kubectl get pods -l app=sample-app -o wide
```

파드가 각각 다른 노드에 흩어져 생성되기 때문에, 노드에 장애가 발생하더라도 서비스에 미치는 영향을 최소화할 수 있다. 레플리카셋이 생성하는 파드는 `레플리카셋 이름-임의의 문자열` 형태로 명명된다.

### 5.3.2 파드 정지와 자동화된 복구

레플리카셋은 노드나 파드에 장애가 발생하면 지정한 파드 수를 유지하려고 다른 노드에서 파드를 기동시킨다. 이것이 쿠버네티스의 핵심 개념 중 하나인 자동화된 복구(self-healing)다.

파드 하나를 강제로 삭제해보면 즉시 새 파드가 생성되는 것을 확인할 수 있다.

## 5.4 디플로이먼트

레플리카셋을 관리하는 상위 리소스로, 실무에서 가장 많이 쓰는 워크로드 리소스다. 파드나 레플리카셋을 직접 만들기보다 처음부터 디플로이먼트로 만드는 것이 좋다.

### 업데이트 동작

```bash
# 컨테이너 이미지 업데이트
kubectl set image deployment sample-deployment nginx-container=nginx:1.17 --record

# 업데이트 상태 확인
kubectl rollout status deployment sample-deployment
```

업데이트하면 레플리카셋이 새로 생성되고, 거기에 연결되는 형태로 파드가 다시 생성된다. 이때 내부적으로 롤링 업데이트가 이루어지므로 실제 서비스에는 영향이 없다.

```bash
kubectl get replicasets
# sample-deployment-5988b689cb  3  3  3  2m31s   # 신규 레플리카셋
# sample-deployment-7bf986f9cf  0  0  0  6m31s   # 이전 레플리카셋
```

이전 레플리카셋이 남아 있기 때문에 롤백이 가능하다. 업데이트를 반복하면 신규 레플리카셋이 계속 늘어난다.

### RollingUpdate 설정

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0   # 동시에 정지 가능한 최대 파드 수
      maxSurge: 1         # 동시에 생성 가능한 최대 파드 수
  replicas: 3
```

maxUnavailable=0 / maxSurge=1 설정이면 추가 레플리카를 먼저 늘린 뒤 기존 파드를 정지시키는 방식으로 파드를 이동시킨다. 즉 가용 파드 수가 절대 줄지 않는다.

```bash
kubectl get replicasets --watch   # 리소스 상태 변화를 계속 출력
```

## 5.5 데몬셋

각 노드에 파드를 하나씩 배포하는 리소스다. 로그 수집기나 모니터링 에이전트, CNI 플러그인처럼 모든 노드에 반드시 하나씩 떠야 하는 워크로드에 사용한다.

### 업데이트 전략

OnDelete: 파드가 정지되어 다시 생성되기 전까지는 업데이트되지 않는다. 운영상 정지하면 안 되는 파드거나 업데이트가 급하지 않을 때 쓰지만, 이전 버전이 장기간 사용된다는 점에 주의해야 한다. 임의의 시점에 업데이트하려면 파드를 수동으로 삭제하고 자동화된 복구로 새 파드를 생성해야 한다.

```bash
kubectl delete pod sample-ds-ondelete-xxxxx
```

RollingUpdate: 데몬셋도 롤링 업데이트가 가능하다. 다만 하나의 노드에 동일한 파드를 여러 개 생성할 수 없으므로 디플로이먼트와 달리 maxSurge를 설정할 수 없다. maxUnavailable만 지정한다.

```yaml
spec:
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 2   # 기본값 1, 0으로 지정 불가
```

## 5.6 스테이트풀셋

영속성 데이터를 가진 워크로드에 사용하는 리소스다. 데이터베이스처럼 각 파드가 고유한 상태와 저장소를 가져야 하는 경우에 쓴다.

### 디플로이먼트와의 차이

스테이트풀셋에는 영속성 데이터가 있으므로 디플로이먼트와 달리 추가 파드를 생성해서 롤링 업데이트를 할 수 없다. maxUnavailable을 지정할 수도 없어서, 파드마다 Ready 상태인지를 확인하고 하나씩 업데이트한다. `spec.podManagementPolicy`가 Parallel로 설정되어 있어도 병렬로 처리되지 않고 파드 하나씩 업데이트가 이루어진다.

### partition

스테이트풀셋의 RollingUpdate에서는 partition이라는 값을 설정할 수 있다.

```yaml
spec:
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 3
  replicas: 5
```

partition을 설정하면 전체 파드 중 어떤 파드까지 업데이트할지를 지정할 수 있다. 위 예에서 partition=3이면 인덱스 0, 1, 2번 파드는 업데이트되지 않고 3, 4번만 업데이트된다.

이 설정을 쓰면 전체에 영향을 주지 않고 부분적으로 업데이트를 적용하고 확인할 수 있어 안전한 업데이트가 가능하다. 카나리 배포와 비슷한 개념이다. 또 OnDelete와 달리 수동으로 재기동한 경우에도 partition 값보다 작은 인덱스를 가진 파드는 업데이트되지 않는다.

정리하며 (개별연구와 연결)

이번 장 내용이 개별연구에서 다룬 것들과 직접 이어지는 부분이 많았다.

데몬셋이 특히 그렇다. Cilium 에이전트가 모든 노드에 하나씩 떠 있어야 하는 이유가 바로 데몬셋이기 때문이다. cilium-config ConfigMap을 수정한 뒤 에이전트를 재시작해야 했던 것도, 데몬셋의 기본 업데이트 전략과 관련이 있다. OnDelete였다면 파드를 직접 지워야 반영되고, RollingUpdate라도 maxSurge를 못 쓰기 때문에 노드별로 순차 교체된다.

kube-proxy도 마찬가지로 데몬셋이라, 앞서 엔드포인트 전파 지연을 이야기할 때 나왔던 "각 노드의 kube-proxy가 규칙을 갱신한다"는 구조가 여기서 설명된다.

레플리카셋의 자동화된 복구는 2장에서 개념으로만 봤던 self-healing이 실제로 어떤 리소스에 의해 구현되는지를 보여준다. 파드를 지워도 다시 살아나는 것은 파드 자체의 기능이 아니라 레플리카셋이 하는 일이다.
