> **요약)** 워크로드 API 카테고리 = 컨테이너를 어떻게 띄우고, 몇 개를 유지하고, 어떻게 갈아끼우는지
>
> → 파드가 최소 단위이고, 그 위에 관리자 리소스가 층층이 얹힘
> → 디플로이먼트 → 레플리카셋 → 파드 라는 부모-자식 관계

---

## 5.1 워크로드 API 카테고리 개요

4장에서 본 다섯 카테고리 중 **컨테이너 실행에 관련된 리소스**가 워크로드 API 카테고리

| 종류                           | 개요                                                    |
| ------------------------------ | ------------------------------------------------------- |
| 워크로드 API 카테고리          | 컨테이너 실행에 관련된 리소스                           |
| 서비스 API 카테고리            | 컨테이너를 외부에 공개하는 엔드포인트를 제공하는 리소스 |
| 컨피그 & 스토리지 API 카테고리 | 설정/기밀 정보/영구 볼륨 등에 관련된 리소스             |
| 클러스터 API 카테고리          | 보안이나 쿼터 등에 관련된 리소스                        |
| 메타데이터 API 카테고리        | 클러스터 내부의 다른 리소스를 관리하기 위한 리소스      |

내부용을 제외하고 사용자가 직접 쓰는 워크로드 리소스는 총 **8가지**

- 파드 / 레플리케이션 컨트롤러 / 레플리카셋 / 디플로이먼트
- 데몬셋 / 스테이트풀셋 / 잡 / 크론잡

**왜 이렇게 많은가?**

> 각 리소스가 병렬로 놓인 게 아니라 파드를 최소 단위로 하고 그것을 관리하는 상위 리소스가 있는 부모-자식 관계이기 때문

```
Tier 1              Tier 2                      Tier 3
파드   <-- 관리 --   레플리케이션 컨트롤러
파드   <-- 관리 --   레플리카셋       <-- 관리 -- 디플로이먼트
파드   <-- 관리 --   데몬셋
파드   <-- 관리 --   스테이트풀셋
파드   <-- 관리 --   잡              <-- 관리 -- 크론잡
                                     → 오른쪽으로 갈수록 상위 리소스
```

→ 디플로이먼트는 레플리카셋을 관리하고, 레플리카셋은 파드를 관리함

## 5.2 파드

> 워크로드 리소스의 **최소 단위**. 한 개 이상의 컨테이너로 구성됨
>
> = **Pod**

핵심은 **같은 파드에 포함된 컨테이너끼리는 네트워크적으로 격리되어 있지 않고 IP 주소를 공유한다**는 점
컨테이너가 두 개 든 파드를 만들면 두 컨테이너는 같은 IP를 가지며, 서로 localhost로 통신할 수 있음

**대부분은 파드 하나에 컨테이너 하나**지만, 메인 컨테이너를 지원하는 서브 컨테이너를 같이 넣을 수 있음

- 로그 수집 역할 컨테이너
- 설정값을 동적으로 변경시키는 컨테이너
- 로컬 캐시용 컨테이너, SSL용 컨테이너

주의) nginx 컨테이너와 redis 컨테이너처럼 메인 컨테이너 여러 개를 하나의 파드에 두는 구성은 추천하지 x. 개별 파드의 이동(스케일링·재배치)이 어려워지고 복잡해지기 때문

### 5.2.1 파드 디자인 패턴

| 종류                              | 개요                                   |
| --------------------------------- | -------------------------------------- |
| 사이드카 패턴(sidecar pattern)    | 메인 컨테이너에 기능을 추가한다        |
| 앰배서더 패턴(ambassador pattern) | 외부 시스템과의 통신을 중계한다        |
| 어댑터 패턴(adapter pattern)      | 외부 접속을 위한 인터페이스를 제공한다 |

cf. 이렇게 셋으로 구분하지만, **보조 역할을 하는 서브 컨테이너를 통틀어 ’사이드카’라고 부르는 경우도 있다함**

> **사이드카 패턴:** 메인 컨테이너 외에 보조 기능을 추가하는 서브 컨테이너를 포함하는 패턴

- 애플리케이션 ← Config Updater (변경 감지 → 설정의 동적 변경)
- 애플리케이션 ↔︎ 공유 볼륨 ↔︎ Git Syncer (깃 저장소 내용과 동기화)
- 애플리케이션 → 공유 볼륨 → S3 Transfer (로그를 오브젝트 스토리지로 전송)

→ 파드는 데이터 영역을 공유할 수 있으므로, 대부분 **데이터와 설정에 관련된 패턴**

> **앰배서더 패턴:** 메인 컨테이너가 외부 시스템과 접속할 때 대리로 중계해주는 서브 컨테이너를 포함하는 패턴

- 애플리케이션 → (localhost 경유) → CloudSQL Proxy → CloudSQL
- 애플리케이션 → (localhost 경유) → Redis Proxy → 샤딩된 Redis

왜 필요한가? 앰배서더 없이 메인 컨테이너가 직접 샤딩된 DB 하나를 골라 접속하면 DB와의 결합도가 강해짐

앰배서더를 쓰면 메인 컨테이너는 항상 localhost만 바라보고 중계는 앰배서더가 하므로 느슨한 결합 유지

→ 단일 DB를 쓰는 개발 환경과 분산 DB를 쓰는 서비스 환경 양쪽에서 애플리케이션 변경 없이 동작함

> **어댑터 패턴:** 서로 다른 데이터 형식을 변환해주는 컨테이너를 포함하는 패턴

- MySQL(자체 형식으로 메트릭 제공) ↔︎ MySQL Exporter(Prometheus 형식으로 변환)
- Redis(자체 형식으로 메트릭 제공) ↔︎ Redis Exporter(Prometheus 형식으로 변환)

왜 필요한가? 프로메테우스는 정의된 형식으로 메트릭을 수집해야 하는데 대부분의 미들웨어는 프로메테우스 메트릭 형식을 지원하지 않음

어댑터 컨테이너가 외부 요청에 맞게 데이터 형식을 변환해 반환, 이 경우도 메인 ↔︎ 어댑터 간에는 localhost로 접속함

### 5.2.2 파드 생성

nginx:1.16 이미지 컨테이너 하나를 기동하고 80/TCP를 바인드하는 단순한 파드

```yaml
# sample-pod.yaml 파드 예제
apiVersion: v1
kind: Pod
metadata:
name: sample-pod
spec:
containers:
  -name: nginx-container
  image: nginx:1.16
```

```bash
# 파드 생성
$ kubectl apply -f sample-pod.yaml
pod/sample-pod created

# 파드 목록 표시
$ kubectl get pods
NAME         READY   STATUS    RESTARTS   AGE
sample-pod   1/1     Running   0          5h53m

# 더 상세한 리소스 정보(IP, 배치된 노드까지) 표시
$ kubectl get pods --output wide
NAME         READY   STATUS    RESTARTS   AGE     IP         NODE
sample-pod   1/1     Running   0          5h53m   10.0.2.7   gke-k8s-default-pool-be722c17-mnpv
```

### 5.2.3 두 개의 컨테이너를 포함한 파드 생성

```yaml
# 두 개의 컨테이너를 가진 파드 예제 (sample-2pod.yaml)
apiVersion: v1
kind: Pod
metadata:
name: sample-2pod
spec:
containers:
-name: nginx-container   # 80/TCP 바인드
image: nginx:1.16
-name: redis-container   # 6379/TCP 바인드
image: redis:3.2
```

```bash
# 두 개의 컨테이너를 포함한 파드 생성
$ kubectl apply -f sample-2pod.yaml
pod/sample-2pod created

# READY가 2/2 → 파드 안에서 컨테이너 두 개가 모두 기동됨
$ kubectl get pods
NAME          READY   STATUS    RESTARTS   AGE
sample-2pod   2/2     Running   0          2m8s
```

**그럼 두 컨테이너가 같은 포트를 쓰면?** → 파드 내 포트 충돌

```yaml
# 같은 포트를 사용하는 두 개의 컨테이너를 가진 파드 예제(sample-2pod-fail.yaml)
apiVersion: v1
kind: Pod
metadata:
name: sample-2pod-fail
spec:
containers:
-name: nginx-container-112
image: nginx:1.16          # 80/TCP
-name: nginx-container-113
image: nginx:1.17          # 80/TCP → 충돌
```

```bash
# 포트 충돌이 있는 파드 생성 => 생성 자체는 됨
$ kubectl apply -f sample-2pod-fail.yaml
pod/sample-2pod-fail created

# 파드 상태가 에러임을 확인 (READY 1/2, STATUS Error)
$ kubectl get pods
NAME               READY   STATUS   RESTARTS   AGE
sample-2pod-fail   1/2     Error    1          18s

# 여러 컨테이너가 있는 경우 -c로 특정 컨테이너의 로그 지정
$ kubectl logs sample-2pod-fail -c nginx-container-113
nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)
```

**주의)** 파드는 네트워크 네임스페이스를 공유하므로 일반 VM에서 80/TCP를 바인드하는 서비스를 둘 이상 못 띄우는 것과 같음

파드 내에서 containerPort가 충돌하지 않도록 해야 함, 매니페스트 검증 단계가 아니라 **기동 시점에 에러**로 드러난다는 점이 함정

### 5.2.4 컨테이너 로그인과 명령어 실행

kubectl exec는 실제 SSH가 아니고,

가상 터미널을 생성(-t)하고 표준 입력을 패스 스루(-i)하면서 셸을 실행해 로그인한 것처럼 보이게 하는 것

```bash
# 컨테이너에서 /bin/bash 실행 (로그인처럼 사용)
$ kubectl exec -it sample-pod -- /bin/bash
root@sample-pod:/#

# 컨테이너 내부에서 IP 주소 확인
root@sample-pod:/$ ip a | grep "inet "
    inet 127.0.0.1/8 scope host lo
    inet 10.0.2.7/32 scope global eth0

# 컨테이너 내부에서 바인드(listen)하는 포트 확인
root@sample-pod:/$ ss -napt | grep LISTEN
LISTEN 0  511  0.0.0.0:80  0.0.0.0:*  users:(("nginx",pid=1,fd=6))

# 로그인하지 않고 단발 명령 실행
$ kubectl exec -it sample-pod -- /bin/ls

# 다수의 컨테이너를 포함한 파드는 -c로 대상 컨테이너 지정
$ kubectl exec -it sample-2pod -c nginx-container -- /bin/ls

# 옵션을 포함한 명령어 실행 (-- 뒤는 컨테이너로 전달됨)
$ kubectl exec -it sample-pod -- /bin/ls --all --classify

# 파이프 등 특정 문자열을 포함한 경우는 셸로 감싸서 실행
$ kubectl exec -it sample-pod -- /bin/bash -c "ls --all --classify | grep lib"
```

### 5.2.5 ENTRYPOINT 명령/CMD 명령과 command/args

도커 파일의 ENTRYPOINT / CMD를 쿠버네티스는 다른 이름으로 부름

| 도커       | 쿠버네티스 | 지정 위치                 |
| ---------- | ---------- | ------------------------- |
| ENTRYPOINT | command    | spec.containers[].command |
| CMD        | args       | spec.containers[].args    |

주의) CMD 명령이 command에 해당하지 x

```yaml
# ENTRYPOINT 명령과 CMD 명령을 덮어 쓰기 하는 파드 예제(sample-entrypoint.yaml)
apiVersion: v1
kind: Pod
metadata:
name: sample-entrypoint
spec:
containers:
-name: nginx-container-112
image: nginx:1.16
command:["/bin/sleep"]   # ENTRYPOINT 명령으로 대체
args:["3600"]            # CMD 명령으로 대체
```

→ kubectl exec로 들어가 보면 nginx 대신 sleep이 실행되고 있음

### 5.2.6 파드명 제한

파드명은 **호스트명 규약**을 따라야 함

- 이용 가능한 문자는 영문 소문자와 숫자
- 이용 가능한 기호는 또는 `.`
- 시작과 끝은 영문 소문자

```yaml
# 파드명 규칙을 위반한 파드 예제
metadata:
name: sample_podname_fail # 언더바(_) 사용불가
```

```bash
# 호스트명 규약에 따르지 않은 파드명 → 생성 실패
$ kubectl apply -f sample-podname-fail.yaml
The Pod "sample_podname_fail" is invalid: metadata.name: Invalid value:
"sample_podname_fail": a DNS-1123 subdomain must consist of lower case
alphanumeric characters, '-' or '.', and must start and end with an
alphanumeric character
```

### 5.2.7 호스트의 네트워크 구성을 사용한 파드 기동

파드에 할당되는 IP는 노드의 호스트 IP와 범위가 달라 **외부에서 볼 수 없는 IP**

spec.hostNetwork: true를 켜면 호스트에서 프로세스를 기동하는 것과 같은 네트워크 구성(IP 주소, DNS 설정, host 설정 등)으로 파드를 기동할 수 있음

```yaml
# 호스트의 네트워크 구성을 사용하는 예제(sample-hostnetwork.yaml)
apiVersion: v1
kind: Pod
metadata:
name: sample-hostnetwork
spec:
hostNetwork:true
containers:
-name: nginx-container
image: nginx:1.16
```

```bash
# 파드의 IP 주소 확인 → 노드와 같은 10.178.x.x 대역
$ kubectl get pod sample-hostnetwork -o wide
NAME                 READY  STATUS   RESTARTS  AGE  IP            NODE
sample-hostnetwork   1/1    Running  0         3s   10.178.0.63   gke-k8s-default-pool-be722c17-mnpv

# 파드가 기동 중인 노드의 IP 주소 확인 → 위와 동일함을 대조
$ kubectl get node gke-k8s-default-pool-be722c17-mnpv -o wide

# 파드의 호스트명 확인 → 노드명이 그대로 나온다
$ kubectl exec -it sample-hostnetwork -- hostname
gke-k8s-default-pool-be722c17-mnpv
```

교재 예시 클러스터에서 일반 파드는 `10.0.0.0/14`, 노드는 `10.178.0.0/16` 범위이며 이 네트워크 간에는 통신할 수 X, 그 외 네트워크 설정도 모두 호스트 것이 상속됨

**주의)** 기본적으로 사용하지 않음. 노드의 IP를 그대로 쓰므로 포트 번호 충돌이 발생함. 외부 공개가 목적이면 6장의 NodePort 서비스로 해결할 수 있는지 먼저 검토,

쓸 만한 경우는 에지(Edge) 환경이나 호스트 측 네트워크를 감시·제어하는 특수 애플리케이션 정도가 있음

### 5.2.8 파드 DNS 설정과 서비스 디스커버리

DNS 서버에 관한 설정은 `spec.dnsPolicy`에 지정함

| 설정값                  | 개요                                                                       |
| ----------------------- | -------------------------------------------------------------------------- |
| ClusterFirst(기본값)    | 클러스터 내부 DNS에 질의하여 해석되지 않으면 업스트림(upstream)에 질의한다 |
| None                    | 파드 정의 내에서 정적으로 설정한다                                         |
| Default                 | 파드가 기동하는 쿠버네티스 노드의 `/etc/resolv.conf`를 상속받는다          |
| ClusterFirstWithHostNet | ClusterFirst의 동작과 같다(hostNetwork 사용 시 설정)                       |

cf. Default가 기본값이 아님. 기본값은 `ClusterFirst`

> **ClusterFirst(기본값):** 클러스터 내부 DNS로 이름을 해석 (7장의 서비스 디스커버리·클러스터 내부 로드 밸런싱을 쓰기 위한 설정)

```yaml
# 파드 예제(sample-dnspolicy-clusterfirst.yaml)
spec:
dnsPolicy: ClusterFirst
```

```bash
# 컨테이너 내부의 DNS 설정 파일 표시 → 클러스터 내부 DNS(10.3.240.10)를 바라봄
$ kubectl exec -it sample-dnspolicy-clusterfirst -- cat /etc/resolv.conf
nameserver 10.3.240.10
search default.svc.cluster.local svc.cluster.local cluster.local ...

# 위 IP의 정체 확인 — kube-system의 kube-dns 서비스
$ kubectl get services -n kube-system
NAME       TYPE        CLUSTER-IP    EXTERNAL-IP   PORT(S)         AGE
kube-dns   ClusterIP   10.3.240.10   <none>        53/UDP,53/TCP   3d15h
```

**None:** 클러스터 외부 DNS를 참조하고 싶을 때. `dnsPolicy: None`으로 두고 `dnsConfig`에 직접 작성

```yaml
# 정적으로 설정하여 외부 DNS 서버를 사용하는 파드 예제(sample-dnspolicy-none.yaml)
spec:
dnsPolicy: None
dnsConfig:
nameservers:
-8.8.8.8
-8.8.4.4
searches:
- example.com
options:
-name: ndots
value:"5"
```

주의) 정적으로 외부 DNS만 설정하면 클러스터 내부 DNS를 사용한 서비스 디스커버리를 쓸 수 없게 됨

Default: 노드의 DNS 설정을 그대로 상속받음. 마찬가지로 클러스터 내부 DNS 기반 서비스 디스커버리를 할 수 없게 되므로 주의

ClusterFirstWithHostNet: hostNetwork를 쓰면서 클러스터 내부 DNS도 참조하고 싶을 때

```yaml
# hostNetwork 사용 시 클러스터 내부의 DNS를 사용하는 파드 예제
spec:
dnsPolicy: ClusterFirstWithHostNet
hostNetwork:true
```

주의) hostNetwork를 쓰는 경우 기본값 `ClusterFirst` 설정은 무시되고 노드의 네트워크 설정(DNS 포함)이 사용됨 →그래서 명시적으로 `ClusterFirstWithHostNet`을 지정해야 함

```bash
# 앞서 만든 sample-hostnetwork 파드와 경합하므로 남아 있다면 삭제
$ kubectl delete pod sample-hostnetwork
pod "sample-hostnetwork" deleted
```

### 5.2.9 정적 호스트명 해석 설정: /etc/hosts

리눅스는 DNS 해석 전에 `/etc/hosts`로 정적 해석을 함. 쿠버네티스에서는 `spec.hostAliases`로 파드 내부 모든 컨테이너의 `/etc/hosts`를 변경할 수 있음

```yaml
# /etc/hosts에 정적 호스트명 해석을 설정하는 파드 예제
spec:
containers:
  -name: nginx-container
  image: nginx:1.16
  hostAliases: -ip:8.8.8.8
  hostnames:
    - google-dns
    - google-public-dns
```

```bash
# 컨테이너 내부의 /etc/hosts 확인 → 맨 아래에 HostAliases 항목이 추가됨
$ kubectl exec -it sample-hostaliases -- cat /etc/hosts
# Kubernetes-managed hosts file.
127.0.0.1       localhost
10.0.2.13       sample-hostaliases
# Entries added by HostAliases.
8.8.8.8         google-dns      google-public-dns
```

### 5.2.10 작업 디렉터리 설정

컨테이너 애플리케이션의 작업 디렉터리는 도커 파일의 `WORKDIR` 설정을 따르지만, `spec.containers[].workingDir`로 **덮어쓸 수 있음**

```yaml
# 작업 디렉터리를 변경한 파드 예제
spec:
containers:
  -name: nginx-container
  image: nginx:1.16
  workingDir: /tmp
```

```bash
# workingDir 미지정 → 루트
$ kubectl exec -it sample-pod -- pwd
/
# workingDir: /tmp로 지정
$ kubectl exec -it sample-workingdir -- pwd
/tmp
```

**언제 쓰나?**

→ 7장의 볼륨 기능으로 스크립트가 담긴 볼륨을 마운트한 뒤, **그 디렉터리로 이동해서 실행하고 싶을 때**

## 5.3 레플리카셋/레플리케이션 컨트롤러

> 파드의 레플리카를 생성하고 **지정한 파드 수를 유지**하는 리소스
>
> = **ReplicaSet / ReplicationController**

**둘의 관계**: 원래 이름이 레플리케이션 컨트롤러였고, 이후 레플리카셋으로 이름이 바뀌면서 일부 기능이 추가, 레플리케이션 컨트롤러는 앞으로 사용하지 않는 추세이므로 기본적으로 레플리카셋을 쓴다고 함

### 5.3.1 레플리카셋 생성

```yaml
# 레플리카셋 예제(sample-rs.yaml)
apiVersion: apps/v1
kind: ReplicaSet
metadata:
name: sample-rs
spec:
replicas:3              # 유지할 파드 수
selector:                # 어떤 레이블의 파드를 셀 것인가
matchLabels:
app: sample-app
template:                # 복제할 파드 정의(Pod Template)
metadata:
labels:
app: sample-app
spec:
containers:
-name: nginx-container
image: nginx:1.16
```

```bash
# 레플리카셋 생성
$ kubectl apply -f sample-rs.yaml
replicaset.apps/sample-rs created

# 레플리카셋 확인 (DESIRED/CURRENT/READY와 셀렉터가 보인다)
$ kubectl get replicasets -o wide
NAME        DESIRED  CURRENT  READY  AGE  CONTAINERS       IMAGES       SELECTOR
sample-rs   3        3        3      11s  nginx-container  nginx:1.16   app=sample-app

# 레플리카셋이 파드 관리에 사용하는 레이블을 지정해 파드 목록 표시
$ kubectl get pods -l app=sample-app -o wide
```

→ 배포된 노드를 보면 **파드가 각각 다른 노드에 흩어져 생성**되어 있어, 노드 장애가 나도 서비스 영향이 최소화됨

레플리카셋이 만드는 파드는 **`레플리카셋 이름 - 임의의 문자열`** 로 지어짐 (예: `sample-rs-cnvm5`)

### 5.3.2 파드 정지와 자동화된 복구

노드나 파드에 장애가 생기면 레플리카셋이 **다른 노드에서 파드를 기동시켜 지정한 수를 유지함**.

⇒ **자동화된 복구(self-healing)**

```bash
# 파드 정지(삭제) - 실제 기동 중인 파드명을 지정
$ kubectl delete pod sample-rs-9f9kr
pod "sample-rs-9f9kr" deleted

# 다시 확인하면 즉시 새 파드(sample-rs-hfxbl)가 생성되어 있다
$ kubectl get pods -o wide

# 레플리카셋의 파드 수 증감 이력 확인 (Events에 SuccessfulCreate가 쌓인다)
$ kubectl describe replicaset sample-rs
```

### 5.3.3 레플리카셋과 레이블

레플리카셋은 파드를 *“이름”*으로 세지 않음. 특정 레이블을 가진 파드 수를 계산하는 형태로 모니터링함

- 레플리카 수가 부족하면 → `spec.template`으로 파드를 생성
- 레플리카 수가 많으면 → 레이블이 일치하는 파드 중 하나를 삭제

어떤 레이블을 셀지는 `spec.selector.matchLabels`에 지정

**함정 1) 셀렉터와 파드 템플릿 레이블이 불일치하면?**

```yaml
# 셀렉터와 파드 Template 레이블이 일치하지 않는 레플리카셋 예제(sample-rs-fail.yaml)
spec:
replicas:3
selector:
matchLabels:
app: sample-app          # 세는 대상
template:
metadata:
labels:
app: sample-app-fail   # 만들어지는 파드의 레이블 → 불일치
```

```bash
# 레이블 불일치 상태로 생성 → 생성 단계에서 에러
$ kubectl apply -f sample-rs-fail.yaml
The ReplicaSet "sample-rs-fail" is invalid: spec.template.metadata.labels:
Invalid value: map[string]string{"app":"sample-app-fail"}:
`selector` does not match template `labels`
```

→ 만약 이 에러가 없었다면 레플리카 수를 채우려고 파드가 무한히 계속 생성되었을 것임. (만든 파드가 셀렉터에 잡히지 않으니 카운트가 영원히 안 오르기 때문)

**함정 2) 같은 레이블을 가진 파드를 레플리카셋 밖에서 만들면?**

```yaml
# 레플리카셋의 셀렉터와 일치하는 레이블을 가진 파드 예제
apiVersion: v1
kind: Pod
metadata:
name: sample-rs-pod
labels:
app: sample-app # sample-rs의 셀렉터와 동일
spec:
containers:
  -name: nginx-container
  image: nginx:1.17
```

```bash
# 레이블 sample-app의 레플리카 수가 3인 레플리카셋 생성(이미 있으면 생략)
$ kubectl apply -f sample-rs.yaml
# 같은 레이블을 가진 파드를 별도로 생성
$ kubectl apply -f sample-rs-pod.yaml

# -L 옵션으로 각 파드의 레이블도 함께 표시
$ kubectl get pods -L app
NAME               READY  STATUS       RESTARTS  AGE  APP
sample-rs-ccj9l    1/1    Running      0         24m  sample-app
sample-rs-gs98r    1/1    Running      0         24m  sample-app
sample-rs-hfxbl    1/1    Running      0         15m  sample-app
sample-rs-pod      0/1    Terminating  0         1s   sample-app   # 초과분으로 판단되어 정지
```

**주의)** 레플리카셋이 **초과 생성으로 판단해 네 개 중 하나를 정지**시킴. 이 예제에서는 마지막에 만든 파드가 삭제됐지만, **상황에 따라 기존 파드가 삭제될 수도 있으므로 주의** 필요!

→ 쿠버네티스 동작이 익숙해질 때까지 **레이블은 유니크하게** 붙이기, 하나의 리소스에 여러 레이블을 부여할 수 있으니 4장처럼 규칙을 정해 써야함

```yaml
labels:
env: dev
codename: system_a
role: web-front
```

### 5.3.4 레플리카셋과 스케일링

파드 수를 바꾸는 방법 2가지

| 방법                     | 명령             | 평가                                                                                                 |
| ------------------------ | ---------------- | ---------------------------------------------------------------------------------------------------- |
| 매니페스트 수정 후 apply | kubectl apply -f | **IaC 구현을 위해 이 방법을 쓰기**                                                                   |
| scale 명령어             | kubectl scale    | 즉석 스케일, 레플리카셋 외 레플리케이션 컨트롤러/디플로이먼트/스테이트풀셋/잡/크론잡에서도 사용 가능 |

```bash
# (1) 레플리카 수를 3에서 4로 변경한 매니페스트를 apply
# macOS(BSD sed)에서는 -e가 -i의 백업 확장자로 소비되어 `...yaml-e` 잔여 파일이 생긴다
#   → macOS: sed -i '' -e 's|...|...|' <파일>
$ sed -i -e 's|replicas: 3|replicas: 4|' sample-rs.yaml
$ kubectl apply -f sample-rs.yaml
replicaset.apps/sample-rs configured

# (2) scale 명령어로 레플리카 수를 5로 변경
$ kubectl scale replicaset sample-rs --replicas 5
replicaset.apps/sample-rs scaled

# 결과 확인
$ kubectl get replicasets
NAME        DESIRED  CURRENT  READY  AGE
sample-rs   5        5        5      29m
```

### 5.3.5 일치성 기준 조건과 집합성 기준 조건

| 조건                        | 개요                                                      |
| --------------------------- | --------------------------------------------------------- |
| 일치성 기준(equality-based) | 조건부에 일치/불일치(=, !=) 조건 지정                     |
| 집합성 기준(set-based)      | 일치/불일치 조건 + 집합(in, notin, exists) 조건 지정 가능 |

- 레플리케이션 컨트롤러는 **일치성 기준만** 가능 (예: `app=sample-app`)
- 레플리카셋은 **집합성 기준**까지 써서 유연한 제어가 가능 (예: `env In [development,staging]`)
- `In`에 해당하는 연산자는 **스케줄링 조건에서 쓸 때 수치 비교도 가능**

cf. 이 조건 지정은 레플리카셋뿐 아니라 **스케줄링할 때도** 쓰임

## 5.4 디플로이먼트

> **여러 레플리카셋을 관리**하여 롤링 업데이트나 롤백 등을 구현하는 리소스
>
> = **Deployment**

**왜 필요한가?** 파드로만 배포하면 장애 시 자동 재생성이 안 되고, 레플리카셋으로만 배포하면 **롤링 업데이트 기능을 쓸 수 없음**

→ **파드 하나만 기동하더라도 디플로이먼트 사용을 권장.** 쿠버네티스에서 가장 권장하는 컨테이너 기동 방법

**롤링 업데이트 동작 순서**

1. 신규 레플리카셋을 생성
2. 신규 레플리카셋의 레플리카 수(파드 수)를 단계적으로 늘림
3. 이전 레플리카셋의 레플리카 수(파드 수)를 단계적으로 줄임
4. (2, 3을 반복)
5. 이전 레플리카셋은 레플리카 수를 0으로 유지

→ **이전 레플리카셋이 삭제되지 않고 0인 채로 남기 때문에 롤백이 가능함**

### 5.4.1 디플로이먼트 생성

```yaml
# 디플로이먼트 예제
apiVersion: apps/v1
kind: Deployment
metadata:
name: sample-deployment
spec:
replicas:3
selector:
matchLabels:
app: sample-app
template:
metadata:
labels:
app: sample-app
spec:
containers:
-name: nginx-container
image: nginx:1.16
```

```bash
# --record: 어떤 명령어로 업데이트했는지 이력을 저장
# ㄴ> 동작은 하나, 현재 버전에선 deprecated 경고가 뜨긴함
$ kubectl apply -f sample-deployment.yaml --record
deployment.apps/sample-deployment created

# 디플로이먼트 확인
$ kubectl get deployments
NAME                READY  UP-TO-DATE  AVAILABLE  AGE
sample-deployment   3/3    3           3          2m5s

# 레플리카셋 확인 - 디플로이먼트명-해시 로 자동 생성되어 있다
$ kubectl get replicasets
NAME                           DESIRED  CURRENT  READY  AGE
sample-deployment-7bf986f9cf   3        3        3      2m19s

# 파드 확인 - 레플리카셋명-임의문자열
$ kubectl get pods
NAME                                 READY  STATUS   RESTARTS  AGE
sample-deployment-7bf986f9cf-t2xl2   1/1    Running  0         2m56s
```

→ **이름만 봐도 디플로이먼트 → 레플리카셋 → 파드의 생성 관계**를 알 수 있음

이력은 각 레플리카셋의 metadata.annotations에 저장됨

| 어노테이션                        | 내용                             |
| --------------------------------- | -------------------------------- |
| kubernetes.io/change-cause        | --record로 저장된 실행 명령어    |
| deployment.kubernetes.io/revision | 현재 레플리카셋의 수정 버전 번호 |

**cf.** `--record`는 실제로 많이 쓰지 않음. 서비스 환경 운영에서 `kubectl rollout`을 쓰는 경우가 거의 없기 때문

**업데이트해 보기**

```bash
# 컨테이너 이미지 업데이트 (매니페스트 수정 후 apply해도 동일)
$ kubectl set image deployment sample-deployment nginx-container=nginx:1.17 --record
deployment.apps/sample-deployment image updated

# 업데이트 진행 상태 확인
$ kubectl rollout status deployment sample-deployment
Waiting for deployment "sample-deployment" rollout to finish: 2 out of 3 new replicas have been updated...
deployment "sample-deployment" successfully rolled out

# 레플리카셋 확인 — 신규는 3, 이전은 0으로 남아 있다
$ kubectl get replicasets
NAME                           DESIRED  CURRENT  READY  AGE
sample-deployment-5988b689cb   3        3        3      2m31s   # 신규
sample-deployment-7bf986f9cf   0        0        0      6m31s   # 이전
```

→ 내부적으로 롤링 업데이트가 되므로 **실제 서비스에는 영향이 없음**

### 5.4.2 디플로이먼트 업데이트(레플리카셋이 생성되는) 조건

**모든 변경이 새 레플리카셋을 만들지는 않음**

- **레플리카 수 변경은 포함되지 않는다** - 새 레플리카셋이 생기지 않는다
- **`spec.template`에 변경이 있을 때만** 레플리카셋을 신규 생성하고 롤링 업데이트를 한다

작동 원리: spec.template 아래의 해시값(**파드 템플릿 해시, Pod Template Hash**)을 계산하고, 이 값을 pod-template-hash 레이블로 관리함

```bash
# 레플리카셋 상태를 YAML로 출력하면 셀렉터에 pod-template-hash가 들어 있다
$ kubectl get replicasets sample-deployment-5988b689cb -o yaml
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
      pod-template-hash: 5988b689cb
```

**주의)** 수작업으로 이미지를 **이전 버전으로 되돌려 해시값이 동일해진 경우에는 레플리카셋을 신규 생성하지 않고 기존 레플리카셋을 재사용함**

### 5.4.3 변경 롤백

**롤백의 실체는 “현재 사용 중인 레플리카셋의 전환”,** 이전 레플리카셋이 레플리카 수 0으로 남아 있으므로, 그 수를 되돌리면 그대로 롤백이 됨

```bash
# 변경 이력 확인 (CHANGE-CAUSE는 --record를 썼을 때만 채워진다)
$ kubectl rollout history deployment sample-deployment
REVISION  CHANGE-CAUSE
1         kubectl apply --filename=sample-deployment.yaml --record=true
2         kubectl set image deployment sample-deployment nginx-container=nginx:1.17 --record=true

# 특정 수정 버전의 상세 정보 확인
$ kubectl rollout history deployment sample-deployment --revision 1

# 버전 번호를 지정하여 롤백
$ kubectl rollout undo deployment sample-deployment --to-revision 1
deployment.apps/sample-deployment rolled back

# 바로 이전 버전으로 롤백(기본값 --to-revision 0)
$ kubectl rollout undo deployment sample-deployment
deployment.apps/sample-deployment rolled back

# 롤백 후 - 이전 레플리카셋의 파드가 다시 기동됨
$ kubectl get replicasets
NAME                           DESIRED  CURRENT  READY  AGE
sample-deployment-5988b689cb   0        0        0      31m   # 신규(비워짐)
sample-deployment-7bf986f9cf   3        3        3      35m   # 이전(복귀)
```

**주**의) 실제 환경에서는 롤백 기능을 쓰는 경우가 많지 않다고 함. CI/CD 파이프라인에서는 `kubectl rollout`보다 이전 매니페스트를 다시 `kubectl apply`하는 쪽이 호환성 면에서 더 좋기 때문,

이때 `spec.template`을 같은 내용으로 되돌리면 `pod-template-hash`가 같아지므로, rollout과 똑같이 기존 레플리카셋의 파드가 기동됨

### 5.4.4 디플로이먼트 변경 일시 중지

업데이트를 하더라도 바로 적용되지 않기를 원할 때 사용

```bash
# 업데이트 일시 정지
$ kubectl rollout pause deployment sample-deployment
deployment.apps/sample-deployment paused

# pause 상태에서 이미지를 바꿔도 반영되지 않고 대기 상태가 된다
$ kubectl set image deployment sample-deployment nginx-container=nginx:1.16
$ kubectl rollout status deployment sample-deployment
Waiting for deployment "sample-deployment" rollout to finish: 0 out of 3 new replicas have been updated...

# pause 상태에서는 롤백도 되지 않는다
$ kubectl rollout undo deployment sample-deployment
error: you cannot rollback a paused deployment; resume it first with
'kubectl rollout resume deployment/sample-deployment' and try again

# 일시 정지 해제
$ kubectl rollout resume deployment sample-deployment
deployment.apps/sample-deployment resumed
```

주의) pause 상태에서는 업데이트도 롤백도 막힘

### 5.4.5 디플로이먼트 업데이트 전략

spec.strategy.type으로 지정하며 기본값은 RollingUpdate

| 전략          | 동작                             | 다운타임   | 추가 리소스 | 지정 가능 항목           |
| ------------- | -------------------------------- | ---------- | ----------- | ------------------------ |
| Recreate      | 모든 파드를 한 번 삭제 후 재생성 | **발생함** | 사용 안 함  | type 외에 없음           |
| RollingUpdate | 단계적으로 교체                  | 없음       | 설정에 따름 | maxUnavailable, maxSurge |

**Recreate:** 기존 레플리카셋의 레플리카 수를 0으로 하고 리소스를 반환한 뒤, 신규 레플리카셋을 만들고 늘림

```yaml
# Recreate 업데이트 전략의 디플로이먼트 예제
spec:
strategy:
type: Recreate
replicas:3
```

```bash
# 레플리카셋 목록을 계속 관찰 (--watch)
$ kubectl get replicasets --watch
# → 몇 초 동안 파드가 전혀 존재하지 않는 구간이 나타난다
```

- **장점**: 클러스터에 현재 동작 중인 레플리카 수만큼만 리소스가 있어도 업데이트할 수 있고, 일괄 업데이트라 전환이 빠름
- 주의) 대략 몇 초 정도 파드가 존재하지 않으므로 일시적으로 서비스 중단이 발생

**RollingUpdate:** spec.strategy.rollingUpdate 아래에 설정 (type은 지정하지 않아도 O)

| 파라미터       | 의미                                             |
| -------------- | ------------------------------------------------ |
| maxUnavailable | 업데이트 중에 동시에 정지 가능한 최대 파드 수    |
| maxSurge       | 업데이트 중에 동시에 생성할 수 있는 최대 파드 수 |

```yaml
# RollingUpdate 업데이트 전략 디플로이먼트 예제(sample-deployment-rollingupdate.yaml)
spec:
strategy:
type: RollingUpdate
rollingUpdate:
maxUnavailable:0   # 정지되는 파드 없음 → 가용성 우선
maxSurge:1         # 한 개씩 더 만들어 가며 교체
replicas:3
```

- maxUnavailable=0 / maxSurge=1 → maxSurge 수만큼 레플리카를 더 늘려 놓고 파드를 이동시킨다(리소스 여유 필요, 무중단)
- maxUnavailable=1 / maxSurge=0 → maxUnavailable 수만큼 레플리카를 줄인 후 파드를 이동시킨다(추가 리소스 불필요, 순간 용량 감소)

**주의)** `maxUnavailable`과 `maxSurge`를 모두 0으로 설정할 수는 없음. 둘 다 0이면 파드를 늘릴 수도 줄일 수도 없어 업데이트가 진행되지 않음

백분율로도 지정할 수 있고, 지정하지 않을 경우 기본값은 각각 25%

```yaml
rollingUpdate:
maxUnavailable: 25%
maxSurge: 25%
```

### 5.4.6 상세 업데이트 파라미터

Recreate/RollingUpdate 양쪽에서 쓸 수 있으며 모두 디플로이먼트의 `spec` 아래에 설정

| 파라미터                | 의미                                                                                       |
| ----------------------- | ------------------------------------------------------------------------------------------ |
| minReadySeconds         | 파드가 Ready가 된 다음부터 기동 완료(= 다음 파드 교체 가능)로 판단하기까지의 최소 시간(초) |
| revisionHistoryLimit    | 디플로이먼트가 유지할 레플리카셋 수 = 롤백이 가능한 이력 수                                |
| progressDeadlineSeconds | Recreate/RollingUpdate 처리 타임아웃 시간(초). 경과하면 자동으로 롤백                      |

```yaml
# 업데이트 상세 파라미터를 설정한 디플로이먼트 예제
spec:
minReadySeconds:0
revisionHistoryLimit:2
progressDeadlineSeconds:3600
replicas:3
```

주의) `revisionHistoryLimit`을 너무 작게 잡으면 되돌아갈 수 있는 버전이 그만큼 사라짐

### 5.4.7 디플로이먼트 스케일링

레플리카셋과 같은 방법

```bash
# 레플리카 수를 3에서 4로 변경한 매니페스트를 apply
# macOS(BSD sed)에서는 -e가 -i의 백업 확장자로 소비되어 `...yaml-e` 잔여 파일이 생긴다
#   → macOS: sed -i '' -e 's|...|...|' <파일>
$ sed -i -e 's|replicas: 3|replicas: 4|' sample-deployment.yaml
$ kubectl apply -f sample-deployment.yaml
deployment.apps/sample-deployment configured

# kubectl scale 명령어를 사용한 스케일링
$ kubectl scale deployment sample-deployment --replicas=5
deployment.apps/sample-deployment scaled
```

cf. 역시 레플리카 수만 바꾸는 것은 `spec.template` 변경이 아니므로 새 레플리카셋이 생기지 않음

### 5.4.8 매니페스트를 사용하지 않고 디플로이먼트 생성

```bash
# 매니페스트 없이 명령어로 디플로이먼트를 생성
$ kubectl create deployment sample-deployment-by-cli --image nginx:1.16
deployment.apps/sample-deployment-by-cli created
```

기본 레이블은 `app: sample-deployment-by-cli`와 파드 템플릿 구조에서 계산되는 `pod-template-hash`가 부여됨

**주의)** 충돌 위험성이 낮아 **이미지 확인 등 간단한 작업 용도**로는 괜찮지만, **서비스 환경에서는 매니페스트를 사용할 것**
