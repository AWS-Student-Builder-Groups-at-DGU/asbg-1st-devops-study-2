# 5장 워크로드 API 카테고리

## 5.1 워크로드 API 카테고리 개요

쿠버네티스 리소스는 크게 다섯 가지 카테고리로 분류된다.

| 종류 | 개요 |
|---|---|
| 워크로드 API 카테고리 | 컨테이너 실행에 관련된 리소스 |
| 서비스 API 카테고리 | 컨테이너를 외부에 공개하는 엔드포인트를 제공하는 리소스 |
| 컨피그 & 스토리지 API 카테고리 | 설정/기밀 정보/영구 볼륨 등에 관련된 리소스 |
| 클러스터 API 카테고리 | 보안이나 쿼터 등에 관련된 리소스 |
| 메타데이터 API 카테고리 | 클러스터 내부의 다른 리소스를 관리하기 위한 리소스 |

워크로드 API 카테고리는 클러스터에 컨테이너를 기동시키기 위해 사용되는 리소스다. 사용자가 직접 사용하는 리소스는 총 여덟 가지다.

- 파드
- 레플리케이션 컨트롤러
- 레플리카셋
- 디플로이먼트
- 데몬셋
- 스테이트풀셋
- 잡
- 크론잡

각 리소스는 파드를 최소 단위로 하여 그것을 관리하는 상위 리소스가 있는 부모 자식 관계로 되어 있다.

- 디플로이먼트 → 레플리카셋 → 파드
- 크론잡 → 잡 → 파드

## 5.2 파드

워크로드 리소스의 최소 단위. 한 개 이상의 컨테이너로 구성되며, 같은 파드에 포함된 컨테이너끼리는 네트워크적으로 격리되어 있지 않고 IP 주소를 공유한다. 따라서 파드 내부의 컨테이너는 서로 localhost로 통신할 수 있다.

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/a30a3621-5e13-4e83-9ab4-9bb66259887f" />

- 대부분 하나의 파드에 하나의 컨테이너를 가지지만, 메인 컨테이너를 지원하는 서브 컨테이너를 포함할 수 있다
- 서브 컨테이너 예시: 프록시 역할 컨테이너, 설정값 동적 변경 컨테이너, 로컬 캐시용 컨테이너, SSL용 컨테이너
- nginx와 redis 같은 메인 컨테이너 두 개를 하나의 파드에 두는 구성은 개별 파드의 이동이 어려워지므로 비추천

### 5.2.1 파드 디자인 패턴

보조 역할을 하는 서브 컨테이너를 통틀어 사이드카라고 부르기도 한다.

| 종류 | 개요 |
|---|---|
| 사이드카 패턴(sidecar pattern) | 메인 컨테이너에 기능을 추가한다 |
| 앰배서더 패턴(ambassador pattern) | 외부 시스템과의 통신을 중계한다 |
| 어댑터 패턴(adapter pattern) | 외부 접속을 위한 인터페이스를 제공한다 |

#### 사이드카 패턴

메인 컨테이너에 보조 기능을 추가하는 서브 컨테이너를 포함하는 패턴. 파드는 데이터 영역을 공유할 수 있어 대부분 데이터와 설정에 관련된 패턴이다.

자주 사용되는 구성

- 특정 변경 사항을 감지해 동적으로 설정을 변경하는 컨테이너
- 깃 저장소와 로컬 스토리지를 동기화하는 컨테이너
- 애플리케이션의 로그 파일을 오브젝트 스토리지로 전송하는 컨테이너

<img width="512" height="768" alt="image" src="https://github.com/user-attachments/assets/6093520c-1e55-4c70-8cc9-2271c9d7da25" />

#### 앰배서더 패턴

메인 컨테이너가 외부 시스템과 접속할 때 대리로 중계해주는 서브 컨테이너(앰배서더 컨테이너)를 포함한 패턴.

- 메인 컨테이너는 항상 localhost를 지정해 앰배서더 컨테이너로만 접속
- 앰배서더 컨테이너가 여러 목적지로 중계하여 느슨한 결합 유지
- 단일 DB를 쓰는 개발 환경과 분산 DB를 쓰는 서비스 환경 모두에서 애플리케이션 변경 없이 사용 가능

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/4984009d-6400-43d1-8046-4d5d918f54a9" />

#### 어댑터 패턴

서로 다른 데이터 형식을 변환해주는 컨테이너(어댑터 컨테이너)를 포함하는 패턴.

- 대부분의 미들웨어는 프로메테우스 메트릭 형식을 지원하지 않음
- 어댑터 컨테이너가 외부 요청에 맞는 데이터 형식으로 변환해 반환 (예: MySQL Exporter, Redis Exporter)
- 메인 컨테이너와 어댑터 컨테이너 간에도 localhost로 접속

### 5.2.2 파드 생성

파드는 매니페스트(yaml)를 작성하고 `kubectl apply -f`로 생성한다.

```yaml
# sample-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-pod
spec:
  containers:
    - name: nginx-container
      image: nginx:1.16
```

- `kubectl get pods`로 파드 목록 확인
- `--output wide` 옵션으로 IP, NODE 등 상세 정보 확인

### 5.2.3 두 개의 컨테이너를 포함한 파드 생성

`spec.containers`에 여러 컨테이너를 나열하면 하나의 파드에 여러 컨테이너를 기동할 수 있다. 정상 기동 시 READY가 2/2로 표시된다.

포트 충돌 주의

- 파드 내 컨테이너는 IP 주소를 공유하므로 같은 포트 번호를 사용할 수 없다
- 두 컨테이너가 모두 80/TCP를 바인드하면 하나만 기동하고 Error 상태가 된다 (Address already in use)
- 일반 VM에서 같은 포트를 바인드하는 서비스를 두 개 못 띄우는 것과 같은 원리로, 파드 내에서 containerPort가 충돌하지 않도록 해야 한다

<img width="1448" height="1086" alt="image" src="https://github.com/user-attachments/assets/457e02a3-ff76-42f7-a0b8-0619a5954363" />

### 5.2.4 컨테이너 로그인과 명령어 실행

실제 SSH 로그인이 아니라, 가상 터미널을 생성(-t)하고 표준 입력을 패스 스루(-i)하면서 셸을 실행하면 로그인한 것과 같은 상태가 된다.

```bash
# 컨테이너에서 /bin/bash 실행
$ kubectl exec -it sample-pod -- /bin/bash

# 여러 컨테이너가 있는 파드는 -c로 컨테이너 지정
$ kubectl exec -it sample-2pod -c nginx-container -- /bin/ls

# 파이프 등 특수 문자를 포함하면 bash -c로 감싸서 실행
$ kubectl exec -it sample-pod -- /bin/bash -c "ls --all | grep lib"
```

### 5.2.5 ENTRYPOINT 명령/CMD 명령과 command/args

쿠버네티스에서는 도커 용어와 다르게 부른다. CMD가 command에 해당하지 않는다는 점에 주의.

| 도커 | 쿠버네티스 |
|---|---|
| ENTRYPOINT | spec.containers[].command |
| CMD | spec.containers[].args |

command와 args를 지정하면 도커 이미지의 ENTRYPOINT와 CMD를 덮어 쓸 수 있다.

```yaml
spec:
  containers:
    - name: nginx-container-112
      image: nginx:1.16
      command: ["/bin/sleep"]  # ENTRYPOINT 대체
      args: ["3600"]           # CMD 대체
```

### 5.2.6 파드명 제한

파드명은 RFC1123 호스트명 규약을 따른다.

- 이용 가능한 문자는 영문 소문자와 숫자
- 이용 가능한 기호는 '-' 또는 '.'
- 시작과 끝은 영문 소문자

언더바('_')를 포함하면 파드 생성에 실패한다.

### 5.2.7 호스트의 네트워크 구성을 사용한 파드 기동

파드에 할당되는 IP는 노드의 호스트 IP와 범위가 다른, 외부에서 볼 수 없는 IP다. `spec.hostNetwork: true`를 설정하면 호스트상에서 프로세스를 기동하는 것과 같은 네트워크 구성(IP 주소, DNS 설정, host 설정 등)으로 파드를 기동할 수 있다.

- 노드의 IP를 그대로 사용하므로 포트 충돌 위험이 있어 기본적으로 사용하지 않음
- 외부 공개는 NodePort 서비스(6장) 등으로 해결 가능한지 먼저 검토
- 에지 환경, 호스트 네트워크 감시/제어 같은 특수한 용도에서만 사용
- hostNetwork 파드의 호스트명은 노드명이 되고, DNS 설정도 호스트의 것을 상속

### 5.2.8 파드 DNS 설정과 서비스 디스커버리

DNS 설정은 파드 정의의 `spec.dnsPolicy`에 설정한다.

| 설정값 | 개요 |
|---|---|
| ClusterFirst(기본값) | 클러스터 내부 DNS에 질의하여 해석되지 않으면 업스트림에 질의 |
| None | 파드 정의 내에서 정적으로 설정 |
| Default | 파드가 기동하는 노드의 /etc/resolv.conf를 상속 |
| ClusterFirstWithHostNet | ClusterFirst와 동일 동작(hostNetwork 사용 시 설정) |

#### ClusterFirst(기본값)

클러스터 내부 DNS에 먼저 질의하고, 해석 안 되는 도메인은 업스트림 DNS 서버에 질의한다. 서비스 디스커버리와 클러스터 내부 로드 밸런싱에 사용된다.

#### None

클러스터 외부 DNS 서버만 참조하는 경우. dnsConfig에 nameservers, searches, options를 직접 작성한다. 클러스터 내부 DNS를 사용한 서비스 디스커버리는 사용 불가하므로 주의.

```yaml
spec:
  dnsPolicy: None
  dnsConfig:
    nameservers:
      - 8.8.8.8
      - 8.8.4.4
    searches:
      - example.com
    options:
      - name: ndots
        value: "5"
```

#### Default

노드의 DNS 설정을 그대로 상속. dnsPolicy의 기본값은 Default가 아니라 ClusterFirst이므로 주의. 이 경우도 클러스터 내부 서비스 디스커버리는 불가.

#### ClusterFirstWithHostNet

hostNetwork를 사용하면 기본값 ClusterFirst가 무시되고 노드의 네트워크 설정(DNS 포함)이 사용된다. hostNetwork 파드에서 클러스터 내부 DNS를 참조하려면 명시적으로 ClusterFirstWithHostNet을 지정한다.

### 5.2.9 정적 호스트명 해석 설정: /etc/hosts

리눅스는 DNS 해석 전에 /etc/hosts로 정적 호스트명을 해석한다. `spec.hostAliases`로 파드 내부 모든 컨테이너의 /etc/hosts를 변경할 수 있다.

```yaml
spec:
  containers:
    - name: nginx-container
      image: nginx:1.16
  hostAliases:
    - ip: 8.8.8.8
      hostnames:
        - google-dns
        - google-public-dns
```

### 5.2.10 작업 디렉터리 설정

작업 디렉터리는 도커 파일의 WORKDIR 설정을 따르지만 `spec.containers[].workingDir`로 덮어 쓸 수 있다. 볼륨을 마운트한 뒤 스크립트가 배치된 디렉터리에서 실행하고 싶은 경우 등에 사용한다.

```yaml
spec:
  containers:
    - name: nginx-container
      image: nginx:1.16
      workingDir: /tmp
```

## 5.3 레플리카셋/레플리케이션 컨트롤러

레플리카셋(ReplicaSet)/레플리케이션 컨트롤러(ReplicationController)는 파드의 레플리카를 생성하고 지정한 파드 수를 유지하는 리소스다.

- 원래 이름은 레플리케이션 컨트롤러였으나 레플리카셋으로 변경되며 일부 기능이 추가됨
- 레플리케이션 컨트롤러는 사용하지 않는 추세이므로 기본적으로 레플리카셋을 사용

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/0dd3b7c2-f731-467d-82ac-1793df3b5903" />

### 5.3.1 레플리카셋 생성

- `spec.replicas`에 유지할 파드 수를 지정
- `spec.template`에 복제할 파드 정의(Pod Template)를 기술
- `spec.selector.matchLabels`로 관리 대상 파드의 레이블을 지정

```yaml
# sample-rs.yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: sample-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
        - name: nginx-container
          image: nginx:1.16
```

- 생성된 파드는 각각 다른 노드에 흩어져 배치되므로 노드 장애 시 서비스 영향을 최소화할 수 있다
- 레플리카셋이 생성하는 파드는 '레플리카셋 이름-임의의 문자열'로 명명된다 (예: sample-rs-cnvm5)

### 5.3.2 파드 정지와 자동화된 복구

노드나 파드에 장애가 발생하면 지정한 파드 수를 유지하기 위해 다른 노드에서 파드를 기동시킨다. 쿠버네티스의 중요한 콘셉트 중 하나인 '자동화된 복구(self-healing)' 기능이다.

- 파드를 삭제해도 즉시 레플리카셋에 의해 새 파드가 생성된다
- 파드 수 증감 이력은 `kubectl describe rs`로 확인 가능

### 5.3.3 레플리카셋과 레이블

레플리카셋은 특정 레이블을 가진 파드 수를 계산하는 방식으로 파드를 모니터링하며 수를 조정한다.

- 레플리카 수 부족: `spec.template`로 파드 생성
- 레플리카 수 초과: 레이블이 일치하는 파드 중 하나를 삭제

계산 대상 레이블은 `spec.selector`에 지정한다.

```yaml
selector:
  matchLabels:
    app: sample-app
```

주의할 케이스

- `spec.selector`와 `spec.template.metadata.labels`의 레이블이 불일치하면 에러가 발생해 생성 불가 (`selector does not match template labels`). 에러가 없다면 레플리카 수를 늘리려고 파드를 무한 생성하게 되기 때문
- 같은 레이블을 가진 파드를 레플리카셋 밖에서 별도로 생성하면, 레플리카셋은 파드를 초과 생성한 것으로 판단해 파드 중 하나를 정지시킨다. 이때 기존 파드가 삭제될 수도 있으므로 주의
- 따라서 쿠버네티스에 익숙해질 때까지 레이블은 유니크하게 붙이는 것이 좋다. 하나의 리소스에 여러 레이블을 규칙을 정해 부여하는 방식 권장 (예: env, codename, role)

### 5.3.4 레플리카셋과 스케일링

파드 수를 변경하는 방법은 두 가지다.

| 방법 | 특징 |
|---|---|
| 매니페스트 수정 후 kubectl apply -f | IaC(Infrastructure as Code) 구현 관점에서 권장되는 방법 |
| kubectl scale 명령어 | 레플리카셋 외에 레플리케이션 컨트롤러/디플로이먼트/스테이트풀셋/잡/크론잡에서도 사용 가능 |

```bash
$ kubectl scale replicaset sample-rs --replicas 5
```

### 5.3.5 일치성 기준 조건과 집합성 기준 조건

레플리케이션 컨트롤러는 일치성 기준(equality-based) 셀렉터였지만, 레플리카셋은 더 강화된 집합성 기준(set-based) 셀렉터로 유연한 제어가 가능하다. 이 조건 지정은 스케줄링에도 사용된다.

| 조건 | 개요 |
|---|---|
| 일치성 기준 | 일치 불일치(=, !=) 조건 지정 |
| 집합성 기준 | 일치 불일치(=, !=) 조건에 더해 집합(in, notin, exists) 조건 지정 가능 |

- 일치성 기준 예: `app=sample-app`
- 집합성 기준 예: `env In [development,staging]`
- In 연산자는 스케줄링 조건에서 수치 비교도 가능
- 집합성 기준 지정 방법(matchExpressions)은 12장에서 상세 설명

## 5.4 디플로이먼트

디플로이먼트(Deployment)는 여러 레플리카셋을 관리하여 롤링 업데이트나 롤백 등을 구현하는 리소스다. 디플로이먼트가 레플리카셋을 관리하고 레플리카셋이 파드를 관리하는 관계다.

롤링 업데이트 동작 순서

1. 신규 레플리카셋을 생성
2. 신규 레플리카셋의 레플리카 수(파드 수)를 단계적으로 늘림
3. 이전 레플리카셋의 레플리카 수(파드 수)를 단계적으로 줄임
4. (2, 3을 반복)
5. 이전 레플리카셋은 레플리카 수를 0으로 유지

<img width="1672" height="941" alt="image" src="https://github.com/user-attachments/assets/561dea1a-4ef9-4573-8976-6e8305d35393" />

디플로이먼트를 사용해야 하는 이유

- 신규 레플리카셋에 컨테이너가 기동되었는지, 헬스 체크를 통과했는지 확인하면서 전환 진행
- 레플리카셋 이행 과정에서 파드 수를 상세히 지정 가능
- 파드로만 배포하면 장애 시 자동 재생성이 안 되고, 레플리카셋으로만 배포하면 롤링 업데이트 불가
- 하나의 파드만 기동하더라도 디플로이먼트 사용을 권장 (쿠버네티스에서 가장 권장하는 컨테이너 기동 방법)

### 5.4.1 디플로이먼트 생성

매니페스트 구조는 레플리카셋과 거의 동일하고 kind만 Deployment로 지정한다.

```yaml
# sample-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
        - name: nginx-container
          image: nginx:1.16
```

- 명명 규칙: 디플로이먼트 → 레플리카셋(디플로이먼트명-해시) → 파드(레플리카셋명-임의 문자열)
- `--record` 옵션으로 생성하면 어떤 명령을 실행했는지 이력이 저장됨. 이력은 레플리카셋의 `metadata.annotations[kubernetes.io/change-cause]`에, 수정 버전 번호는 `metadata.annotations[deployment.kubernetes.io/revision]`에 저장됨
- 서비스 환경에서 kubectl rollout을 쓰는 경우는 거의 없어 --record는 많이 사용하지 않음

<img width="1448" height="1086" alt="image" src="https://github.com/user-attachments/assets/77c00077-8862-4429-850f-dee434df9042" />

### 5.4.2 디플로이먼트 업데이트(레플리카셋이 생성되는) 조건

디플로이먼트에서 '변경'이 발생하면 신규 레플리카셋이 생성되고 롤링 업데이트가 실행된다.

- 레플리카 수 변경은 '변경'에 포함되지 않음. '생성된 파드의 내용 변경'(spec.template의 변경)이 필요
- 쿠버네티스는 spec.template 아래의 해시값(파드 템플릿 해시, Pod Template Hash)을 계산해 이 값을 레이블로 레플리카셋을 관리
- 이미지 등을 이전 버전으로 재변경하여 해시값이 동일해지면 신규 레플리카셋을 만들지 않고 기존 레플리카셋을 재사용

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/388e72bc-54a1-451d-9f00-79f607d67d29" />

### 5.4.3 변경 롤백

롤백 기능의 실체는 레플리카셋의 전환이다. 기존 레플리카셋은 레플리카 수 0인 상태로 남아 있으므로 레플리카 수를 되돌려 다시 사용할 수 있다.

```bash
# 변경 이력 확인 (--record 사용 시 CHANGE-CAUSE 표시, 미사용 시 <none>)
$ kubectl rollout history deployment sample-deployment

# 특정 수정 버전의 상세 정보
$ kubectl rollout history deployment sample-deployment --revision 1

# 버전을 지정하여 롤백
$ kubectl rollout undo deployment sample-deployment --to-revision 1

# 바로 이전 버전으로 롤백 (기본값 --to-revision 0)
$ kubectl rollout undo deployment sample-deployment
```

실제 환경에서는 롤백 기능을 사용하는 경우가 많지 않다

- CI/CD 파이프라인에서는 kubectl rollout보다 이전 매니페스트를 다시 kubectl apply로 적용하는 것이 호환성 면에서 더 좋음
- spec.template이 같은 내용으로 되돌아가면 pod-template-hash가 같으므로 rollout처럼 기존 레플리카셋의 파드가 기동됨

### 5.4.4 디플로이먼트 변경 일시 중지

업데이트가 즉시 적용되지 않기를 원하는 경우 일시 정지 구조를 사용할 수 있다.

```bash
# 업데이트 일시 정지
$ kubectl rollout pause deployment sample-deployment

# 일시 정지 해제
$ kubectl rollout resume deployment sample-deployment
```

- pause 상태에서는 업데이트가 즉시 반영되지 않고 대기 상태가 된다
- pause 상태에서는 롤백도 되지 않는다 (resume 후 롤백해야 함)

### 5.4.5 디플로이먼트 업데이트 전략

업데이트 전략은 `spec.strategy.type`으로 지정하며 기본값은 RollingUpdate다.

#### Recreate

모든 파드를 한 번 삭제하고 다시 파드를 생성한다.

- 장점: 추가 리소스를 사용하지 않고, 일괄 업데이트라 전환이 빠름
- 단점: 파드가 전혀 존재하지 않는 기간이 생겨 일시적인 서비스 중단(다운타임) 발생
- 동작: 기존 레플리카셋의 레플리카 수를 0으로 만들어 리소스 반환 → 신규 레플리카셋 생성 후 레플리카 수를 늘림
- type 이외에 지정할 수 있는 항목 없음

```yaml
spec:
  strategy:
    type: Recreate
```

<img width="1448" height="1086" alt="image" src="https://github.com/user-attachments/assets/d1b10649-d5a3-4208-a1d2-d8ffaeb29ca1" />

#### RollingUpdate

업데이트 중 동시 정지 가능한 최대 파드 수(maxUnavailable)와 동시 생성 가능한 최대 파드 수(maxSurge)를 설정해 업데이트 동작을 제어할 수 있다.

| 파라미터 | 개요 |
|---|---|
| maxUnavailable | 업데이트 중 동시에 정지 가능한 최대 파드 수 |
| maxSurge | 업데이트 중 동시에 생성할 수 있는 최대 파드 수 |

- maxUnavailable과 maxSurge를 모두 0으로 설정할 수는 없다
- maxUnavailable=0 / maxSurge=1: 추가 레플리카를 먼저 만든 뒤 파드를 이동 (리소스 초과 사용하되 가용성 유지)
- maxUnavailable=1 / maxSurge=0: 레플리카 수를 먼저 감소시킨 후 파드를 이동 (추가 리소스 사용 안 함)
- 백분율로도 지정 가능하며, 지정하지 않으면 기본값은 각각 25%

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
```

### 5.4.6 상세 업데이트 파라미터

Recreate나 RollingUpdate에서 함께 사용할 수 있는 파라미터. 모두 디플로이먼트의 spec 아래에 설정한다.

| 파라미터 | 개요 |
|---|---|
| minReadySeconds(최소 대기 시간) | 파드가 Ready 상태가 된 후 파드 기동이 완료되었다고 판단(다음 파드 교체 가능 판단)하기까지의 최소 시간(초) |
| revisionHistoryLimit(수정 버전 기록 제한) | 디플로이먼트가 유지할 레플리카셋 수 = 롤백 가능한 이력 수 |
| progressDeadlineSeconds(진행 기한 시간) | Recreate/RollingUpdate 처리 타임아웃 시간. 경과하면 자동으로 롤백 |

### 5.4.7 디플로이먼트 스케일링

레플리카셋과 같은 방법으로 `kubectl apply -f` 또는 `kubectl scale`을 사용해 스케일링할 수 있다.

### 5.4.8 매니페스트를 사용하지 않고 디플로이먼트 생성

`kubectl create deployment` 명령어로 매니페스트 없이 거의 동일한 디플로이먼트를 만들 수 있다.

```bash
$ kubectl create deployment sample-deployment-by-cli --image nginx:1.16
```

- 기본 레이블은 app: 디플로이먼트명, 파드 템플릿 구조에서 계산되는 pod-template-hash가 부여됨
- 충돌 위험성이 낮아 이미지 확인 등 간단한 작업 용도로 사용 가능
- 서비스 환경에서는 매니페스트를 사용할 것
