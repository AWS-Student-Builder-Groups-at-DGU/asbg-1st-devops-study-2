# 5장 워크로드 API 카테고리

## 사용자가 직접 사용하는 워크로드 리소스 8종

- 파드(Pod)
- 레플리케이션 컨트롤러(ReplicationController) — 레거시
- 레플리카셋(ReplicaSet)
- 디플로이먼트(Deployment)
- 데몬셋(DaemonSet)
- 스테이트풀셋(StatefulSet)
- 잡(Job)
- 크론잡(CronJob)

### 부모-자식 계층 구조 (Tier)

```
Tier 1          Tier 2                      Tier 3
─────────────────────────────────────────────────────────
파드   ←──   레플리케이션 컨트롤러
파드   ←──   레플리카셋            ←──   디플로이먼트
파드   ←──   데몬셋
파드   ←──   스테이트풀셋
파드   ←──   잡                    ←──   크론잡
                            
```
**파드가 최소 단위이고, 그것을 관리하는 상위 리소스가 겹겹이 쌓인다**
디플로이먼트 → 레플리카셋 → 파드. 


책임 분리 덕분에 디플로이먼트는 롤링 업데이트 로직만 신경 쓰면 되고, 파드가 죽었을 때의 복구는 레플리카셋이 알아서 합니다.

## 파드
워크로드 리소스의 최소 단위. **1개 이상의 컨테이너 묶음**

파드의 특징:

1. 같은 파드의 컨테이너끼리는 **네트워크적으로 격리되지 않고 IP 주소를 공유** 따라서 파드 내부의 컨테이너는 `localhost`로 통신한다.
2. 파드는 **원자적 스케줄링 단위**입니다.파드 안의 컨테이너들은 반드시 같은 노드에 배치됩니다. 절반만 다른 노드에 뜨는 일은 없습니다.
3. 파드는 **생명주기를 공유**합니다. 파드를 지우면 안의 컨테이너가 전부 사라집니다.


### 파드 디자인 패턴
파드 디자인 패턴은 크게 세 가지입니다. 보조 역할을 하는 서브 컨테이너를 통틀어 **사이드카**라고 부르는 경우도 많습니다.

| 종류 | 개요 |
|---|---|
| 사이드카 패턴 (sidecar) | 메인 컨테이너에 기능을 추가한다 |
| 앰배서더 패턴 (ambassador) | 외부 시스템과의 통신을 중계한다 |
| 어댑터 패턴 (adapter) | 외부 접속을 위한 인터페이스(형식)를 제공한다 |

#### 사이드카 패턴

메인 컨테이너 외에 보조 기능을 추가하는 서브 컨테이너를 함께 두는 패턴.

<img width="520" height="571" alt="image" src="https://github.com/user-attachments/assets/2066bc19-94c1-42e2-b315-3a1950f91bfe" />


예시:
- 설정 변경을 감시해 자동으로 반영하는 컨테이너
- 깃 저장소와 로컬 스토리지를 동기화하는 컨테이너
- 애플리케이션 로그 파일을 오브젝트 스토리지로 전송하는 컨테이너

#### 앰배서더 패턴

메인 컨테이너가 외부 시스템에 접속할 때 **대리로 중계**해주는 서브 컨테이너.

<img width="618" height="411" alt="image" src="https://github.com/user-attachments/assets/75faeaad-cda9-4aae-bcd6-72772e6109b4" />



- 앰배서더 없이: 애플리케이션이 샤딩된 DB 중 어느 노드에 붙을지 직접 알아야 함 → DB 토폴로지와 강하게 결합
- 앰배서더 있음: 애플리케이션은 항상 `localhost:3306`만 바라봄. 어느 목적지로 보낼지는 서브 컨테이너가 판단 → 느슨한 결합

결과적으로 **단일 DB를 쓰는 개발 환경과 분산 DB를 쓰는 운영 환경에서 애플리케이션 코드를 바꾸지 않아도 됩니다.**

#### 어댑터 패턴

서로 다른 **데이터 형식을 변환**해주는 컨테이너.

<img width="601" height="471" alt="image" src="https://github.com/user-attachments/assets/15fe8095-b25c-496e-b823-8b4343e924c4" />


프로메테우스는 정해진 형식의 메트릭만 수집할 수 있는데, 대부분의 미들웨어는 그 형식으로 메트릭을 내보내지 않습니다. Exporter 컨테이너를 붙여 형식을 변환하면 외부 요청 규격에 맞는 데이터를 반환할 수 있습니다. 이때도 메인 ↔ 어댑터 간 통신은 `localhost`입니다.

#### 안티패턴 — 메인 컨테이너 여러 개 넣기

책에서도 nginx와 redis를 한 파드에 넣지 말라고 경고합니다. 이유를 정리하면:

1. **개별 스케일링 불가**: nginx만 5개로 늘리고 싶어도 redis까지 5개가 됩니다.
2. **개별 배포 불가**: nginx 버전만 올려도 redis 컨테이너까지 재생성됩니다.
3. **리소스 산정 왜곡**: 파드 단위로 스케줄링되므로 CPU/메모리 요구가 합쳐집니다.
4. **장애 전파**: 파드가 죽으면 둘 다 죽습니다.

### 파드명 제한

파드명은 **RFC1123 호스트명 규약**을 따릅니다.

- 사용 가능한 문자: **영문 소문자**와 숫자
- 사용 가능한 기호: `-` 또는 `.`
- 시작과 끝은 영문 소문자 또는 숫자

```yaml
# 코드 5-5 sample-podname-fail.yaml — 언더바 사용
metadata:
  name: sample_podname_fail   # ✗ 언더바 불가
```

#### 파드명에 제한이 생기는 이유
- 파드/서비스 이름이 그대로 **클러스터 내부 DNS 레코드**가 되기 때문

| 규칙 | 적용 대상 | 최대 길이 | 특징 |
|---|---|---|---|
| **DNS-1123 subdomain** | Pod, ConfigMap, Secret, 노드, Deployment 이름 | 253자 | `.` 허용, 숫자로 시작 가능 |
| **DNS-1123 label** | 네임스페이스 | 63자 | `.` 불가 |
| **DNS-1035 label** | **Service 이름** | 63자 | **반드시 영문자로 시작** (숫자 시작 불가) |

### 호스트의 네트워크 구성을 사용한 파드 기동 (hostNetwork)

기본적으로 파드에 할당되는 IP는 노드의 호스트 IP와 대역이 달라 외부에서 볼 수 없습니다. `spec.hostNetwork: true`를 켜면 **호스트에서 프로세스를 띄운 것과 같은 네트워크 구성**(IP, DNS, host 설정)을 사용합니다.
```yaml
# 코드 5-6 sample-hostnetwork.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-hostnetwork
spec:
  hostNetwork: true
  containers:
  - name: nginx-container
    image: nginx:1.16
```

### 파드 DNS 설정

`spec.dnsPolicy`로 지정

| 설정값 | 개요 |
|---|---|
| `ClusterFirst` (기본값) | 클러스터 내부 DNS에 질의하고, 해석되지 않으면 업스트림(upstream)에 질의 |
| `None` | 파드 정의 내에서 정적으로 설정 (`dnsConfig` 필수) |
| `Default` | 파드가 기동하는 노드의 `/etc/resolv.conf`를 상속 |
| `ClusterFirstWithHostNet` | ClusterFirst와 동작이 같음 (hostNetwork 사용 시 지정) |

```yaml
# 코드 5-8
spec:
  dnsPolicy: None
  dnsConfig:
    nameservers:
      - 8.8.8.8
      - 8.8.4.4
    searches:
      - example.com
    options:
      - name: ndots
        value: "5"
```

## 레플리카셋 / 레플리케이션 컨트롤러

레플리카셋 → 파드

### 개념

레플리카셋(ReplicaSet) / 레플리케이션 컨트롤러(ReplicationController)는 **파드의 레플리카를 생성하고 지정한 파드 수를 유지**하는 리소스입니다.

<img width="517" height="272" alt="image" src="https://github.com/user-attachments/assets/f66a1704-f173-49c1-87ec-7e94239cc906" />


레플리카셋 생성

```yaml
# 코드 5-13 sample-rs.yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: sample-rs
spec:
  replicas: 3
  selector:                    #1 숫자를 세고자 하는 대상 파드
    matchLabels:
      app: sample-app
  template:                    #2 만드려는 파드
    metadata:
      labels:
        app: sample-app        #3 1, 2는 반드시 일치해야 함
    spec:
      containers:
        - name: nginx-container
          image: nginx:1.16
```

<img width="715" height="290" alt="image" src="https://github.com/user-attachments/assets/69dadea3-0dfe-4943-affe-488e465ca2a4" />


### 자동화된 복구
노드나 파드에 장애가 생기면 레플리카셋이 다른 노드에서 파드를 다시 기동시킵니다.

<img width="521" height="386" alt="image" src="https://github.com/user-attachments/assets/a425efc2-d71a-4717-8f37-b643782017fc" />


레플리카셋은 **특정 레이블을 가진 파드 수를 세는 방식**으로 모니터링합니다.

```
레플리카셋 (레플리카 수 = 3)
app: sample-app 레이블을 가진 파드를 검색
        ↓  ↓  ↓
[app: sample-app] [app: sample-app] [app: sample-app]   ← 계산 대상 (3개)
[app: test]       [app: demo]       [app: test]         ← 무시
```


### selector와 template.labels가 다르다면?

레플리카셋: "app: sample-app 파드가 여전히 0개네? 만들자"
  → 무한 생성 

**API 서버 검증 단계에서 막혀 쿠버네티스가 레플리카셋의 생성을 거부함**

### 동일한 레이블의 파드를 레플리카셋이 아닌 밖에서 생성한다면?

 
``` 코드 5-15 sample-rs-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-rs-pod
  labels:
    app: sample-app        # ← 레플리카셋의 셀렉터와 일치
spec:
  containers:
  - name: nginx-container
    image: nginx:1.17
```

<img width="739" height="455" alt="image" src="https://github.com/user-attachments/assets/8dc4a350-591a-43ac-b7ac-88db2c63d256" />


**레플리카셋은 레이블만 보고 세기 때문에 추가로 생성한 파드의 수만큼 파드를 삭제함** 

### 래플리카셋 수정 방법

2. kubectl apply -f sample-rs.yaml

## 디플로이먼트

### 개념

디플로이먼트(Deployment)는 **여러 레플리카셋을 관리하여 롤링 업데이트나 롤백을 구현**하는 리소스입니다.

```
디플로이먼트 → 레플리카셋 → 파드
```
<img width="837" height="350" alt="image" src="https://github.com/user-attachments/assets/8d6f91b2-9aa6-4d78-ada0-0b5f9de8ed9a" />


### 디플로이먼트 생성
```yaml
# 코드 5-16 sample-deployment.yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
        - name: nginx-container
          image: nginx:1.16
```

#### 새로운 레플리카가 생성되는 조건

**새로운 replicaset이 만들지는 spec.template의 내용으로 결정됨**

1. `spec.template` 아래의 내용으로 **해시값(Pod Template Hash)** 을 계산
2. 해시값과 동일한 레플리카셋이 없는 경우 → 신규 레플리카셋 생성
3. 해시값과 동일한 레플리카셋이 있는 경우 → 기존 레플리카셋 재사용

### 변경 롤백

디플로이먼트의 특정 버전으로 되돌리는 기능

1. 이력 확인
```bash
$ kubectl rollout history deployment sample-deployment
deployment.apps/sample-deployment
REVISION  CHANGE-CAUSE
1         kubectl apply --filename=sample-deployment.yaml --record=true
2         kubectl set image deployment sample-deployment nginx-container=nginx:1.17 --record=true
```
2. 롤백 실행
```bash
# 버전 번호를 지정하여 롤백
$ kubectl rollout undo deployment sample-deployment --to-revision 1
deployment.apps/sample-deployment rolled back
```
**만약 이전 버전의 레플리카셋이 삭제되었다면 해당 버전으로는 rollout undo를 이용해 되돌아 갈 수 없음**

**실제로는 rollout undo를 잘 사용하지 않고 이전 매니페스트를 다시 'kubectl apply'를 하는것이 더 권장됨**

#### 디플로이먼트 변경 일시 중지
```bash
kubectl rollout pause deployment sample-deployment
```
### 디플로이먼트 업데이트 방법
- Recreate
- RollingUpdate -기본값

#### Recreate 방식

**모든 파드를 한 번 삭제하고 다시 생성**

<img width="695" height="310" alt="image" src="https://github.com/user-attachments/assets/07dc592c-c38a-484d-a9e6-1f6e61ff20d8" />



- 단점: 파드가 존재하지 않는 시점이 존재하기 때문에 일시적으로 서비스 중단 발생
- 장점: 추가 리소스를 사용하지 않고, 전환이 빠름

- 두가지 버전이 공존하지 않음
#### Recreate를 써야 하는 경우

- **DB 스키마 마이그레이션이 하위 호환되지 않을 때** — 구/신 버전이 동시에 뜨면 데이터가 깨집니다.
- **싱글톤 워커** — 두 인스턴스가 동시에 돌면 안 되는 배치/스케줄러.

#### RollingUpdate
**일부 파드 생성, 삭제 반복**

<img width="701" height="287" alt="image" src="https://github.com/user-attachments/assets/4f2a03dd-f2e3-4be1-92b7-132541676073" />


| 파라미터 | 의미 |
|---|---|
| `maxUnavailable` | 업데이트 중에 동시에 **정지 가능한 최대 파드 수**  |
| `maxSurge` | 업데이트 중에 동시에 **생성 가능한 최대 파드 수** (원하는 수 초과분) |


**예시 1. maxUnavailable=0 / maxSurge=1 → 먼저 늘리고 나중에 줄임**
```
이전(3) ■■■   신규(0) ┈┈┈       총 3
   ↓ 신규를 1개 먼저 만듦
이전(3) ■■■   신규(1) ■         총 4  ← 리소스 초과 사용
   ↓ 준비되면 이전 1개 줄임
이전(2) ■■    신규(1) ■         총 3
   ↓ 반복
이전(2) ■■    신규(2) ■■        총 4
이전(1) ■     신규(2) ■■        총 3
이전(0) ┈┈┈   신규(3) ■■■       총 3
```
**특징**: 가용 파드가 기존에 설정한 파드 수 밑으로 안 내려감 → **무중단 보장.** 대신 배포 중 노드 리소스 초과 사용

**예시 2. maxUnavailable=1 / maxSurge=0 → 먼저 줄이고 나중에 늘림**
```
이전(3) ■■■   신규(0) ┈┈┈       총 3
   ↓ 이전 1개 먼저 죽임
이전(2) ■■    신규(0) ┈┈┈       총 2  ← 용량 부족 구간
   ↓ 신규 1개 생성
이전(2) ■■    신규(1) ■         총 3
이전(1) ■     신규(1) ■         총 2
이전(1) ■     신규(2) ■■        총 3
이전(0) ┈┈┈   신규(3) ■■■       총 3
```
**특징**: 추가 리소스가 전혀 필요 없음. 대신 배포 중 처리 용량이 최대 33% 감소 → 트래픽이 많으면 지연/에러 발생 가능.
### 디플로이먼트 상세 업데이트 파라미터

- **`minReadySeconds`** (최소 대기 시간, 초)
  - 파드가 Ready 상태가 된 다음부터 디플로이먼트가 "기동 완료"로 판단 하기까지의 최소 시간
- **`revisionHistoryLimit`** (수정 버전 기록 제한)
  - 디플로이먼트가 유지할 레플리카셋 수 = 롤백 가능한 이력 수
- **`progressDeadlineSeconds`** (진행 기한 시간, 초)
  - Recreate/RollingUpdate 처리 타임아웃 시간
  - 타임아웃이 경과하면 자동으로 롤백

### 디플로이먼트 스케일링 방법
레플리카셋과 마찬가지로 apply, scale 방법 존재 
- 방법1
1. 매니페스트 수정
2. kubectl apply -f ~~
- 방법2
1. kubectl scale deployment ~~ --replicas=5

**스케일링의 경우 spec.template의 변경이 아니므로 신규 레플리카셋이 생기지 않는다**

## 정리

### 세 리소스의 역할

| 리소스 | 하는 일 |
|---|---|
| 파드 | 컨테이너를 묶어서 띄운다 |
| 레플리카셋 | 레이블에 맞는 파드 수를 세며 파드 수를 조정한다 |
| 디플로이먼트 | 레플리카셋의 `replicas`를 조절한다 |

**각 계층은 바로 아래 계층에만 지시합니다.** 디플로이먼트는 파드를 직접 만들거나 지우지 않고, 레플리카셋의 숫자만 고쳐 씁니다. 단순한 컨트롤러를 쌓아 복잡한 동작을 만드는 것이 쿠버네티스의 설계 방식입니다.
