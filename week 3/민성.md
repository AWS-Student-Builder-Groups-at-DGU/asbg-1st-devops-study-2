# 3장. 쿠버네티스 환경 선택

> 『쿠버네티스 완벽 가이드』 3주차 정리 — 민성

2장에서 "왜 쿠버네티스가 필요한가"를 봤다면, 3장은 **"그래서 그 쿠버네티스를 어디에 어떻게 구축할 것인가"** 를 다룬다. 로컬 PC부터 퍼블릭 클라우드까지 선택지를 비교하고, 각 환경의 구축 방법을 소개하는 장이다.

---

## 3.1 쿠버네티스 환경의 종류

쿠버네티스 클러스터를 구성하는 방법은 크게 **세 가지**다.

| 방법 | 설명 | 주 용도 |
| --- | --- | --- |
| **로컬 쿠버네티스** | 물리 머신 한 대에 구축 | 개인 테스트/개발 |
| **쿠버네티스 구축 도구** | 도구로 온프레미스/클라우드에 클러스터 구축 | 온프레미스, 세밀한 커스터마이즈 |
| **관리형 쿠버네티스 서비스** | 퍼블릭 클라우드가 제공하는 클러스터 사용 | 스테이징/서비스 환경 |

**선택 가이드**
- **로컬 쿠버네티스**: 네트워크 연결 없이 바로 눈으로 확인 가능해 개인 테스트·개발에 적합. 하지만 **이중화가 안 되므로 서비스 환경으로 쓰면 안 된다.**
- **개발 부서가 공유하는 스테이징/서비스 환경**은 구축 도구나 관리형 서비스를 쓰는 게 좋다. 가능하면 개발 환경도 이 둘 중 하나로 맞춰 **서비스 환경과 동일하게** 구성하는 것이 이상적.
- 기본적으로는 **관리형 서비스**를 쓸 수 있으면 쓰고, **구축 도구**는 온프레미스 배포나 세밀한 커스터마이즈가 필요할 때 쓴다.

### 쿠버네티스 적합성 인증 프로그램 (Certified Kubernetes)
- 환경에 따라 일부 못 쓰는 기능(외부 로드밸런서 연계, 동적 영구 볼륨 프로비저닝 등)도 있지만, **기본적으로 어떤 쿠버네티스 환경에서도 동일하게 동작**한다.
- 이는 CNCF의 **쿠버네티스 적합성 인증 프로그램(Certified Kubernetes Conformance Program)** 덕분. **클러스터 기능 동작의 일관성과 이식성**을 보장하려고 만들어졌다.
- 각 환경 개발자는 이 인증을 먼저 준수한 뒤, 자기 플랫폼 특징을 살려 기능을 확장한다.

### 이 장에서 소개하는 환경
- **로컬 쿠버네티스**: 미니큐브(Minikube), Docker Desktop for Mac/Windows, **kind**(Kubernetes in Docker)
- **구축 도구**: **큐브어드민(kubeadm)**, 랜처(Rancher)
- **관리형 서비스**: **GKE**(Google), **AKS**(Azure), **EKS**(AWS)

> 참고: 4장 이후 설명은 **GKE 기준**으로 집필되었지만, 대부분의 기능은 다른 환경에서도 동일하게 쓸 수 있다.

## 3.2 로컬 쿠버네티스

물리 머신 한 대에서 손쉽게 쿠버네티스를 테스트하는 방법. **올인원 구성이라 이중화가 보장되지 않고, 일부 기능은 쓸 수 없다는 점**에 주의.

### 3.2.1 미니큐브 (Minikube)
- 쿠버네티스 **SIG-Cluster-Lifecycle** 분과회에서 만든, 로컬에 쿠버네티스를 쉽게 구축·실행하는 도구.
- **단일 노드 구성**이라 여러 대가 필요한 기능은 사용 불가.
- 로컬 가상 머신에 설치하므로 **하이퍼바이저가 필요**하다. OS별 지원 드라이버:
  - **macOS**: 도커 / 하이퍼킷(Hyperkit) / VirtualBox / Parallels / VMware Fusion / Podman 중 하나
  - **Linux**: 도커 / VirtualBox / Podman / KVM / 베어메탈(systemd-based) 중 하나
  - **Windows**: 도커 / VirtualBox / Hyper-V 중 하나
- 지정한 드라이버로 호스트가 될 컨테이너나 VM을 자동 생성하고 그 안에 쿠버네티스를 설치한다.
- 조작은 다른 방법과 동일하게 **kubectl** 사용 (kubectl은 4장에서 설명).

### 3.2.2 Docker Desktop for Mac / Windows
- 도커 데스크톱에 **쿠버네티스가 내장**되어 있어, 설정에서 체크만 하면 클러스터가 뜬다.
- 별도 하이퍼바이저 설치 없이 가장 간단하게 시작할 수 있는 방법. 역시 **단일 노드**.

### 3.2.3 kind (Kubernetes in Docker)
- 이름 그대로 **도커 컨테이너를 노드로 사용**해 쿠버네티스 클러스터를 만드는 도구.
- **멀티 노드 구성이 가능**한 것이 큰 장점 (미니큐브·Docker Desktop과의 차이).
- 설치: `brew install kind`
- 클러스터 구성을 **YAML 파일로 관리**한다. 예시(마스터 3대 + 워커 3대):
  ```yaml
  # kind.yaml
  apiVersion: kind.x-k8s.io/v1alpha4
  kind: Cluster
  nodes:
  - role: control-plane
    image: kindest/node:v1.18.15
  - role: control-plane
    image: kindest/node:v1.18.15
  - role: worker
    image: kindest/node:v1.18.15
  ```
- 클러스터 기동 (Docker Desktop의 도커 환경이 떠 있어야 함):
  ```bash
  kind create cluster --config kind.yaml --name kindcluster
  ```
- 실행하면 control-plane 기동 → CNI 설치 → StorageClass 설치 → 노드 join 순으로 자동 진행된다.
- 사용 이미지는 도커 허브의 **kindest** Organization에서 관리.

## 3.3 쿠버네티스 구축 도구

도구를 사용해 **여러 노드로 구성된 클러스터**를 직접 구축하는 방법. 온프레미스/클라우드 모두 가능.

### 3.3.1 쿠버네티스 서비스 수준 목표 (SLO)
**SIG-Scalability** 분과회가 쿠버네티스 확장성에 대한 **SLI(서비스 수준 지표)/SLO(서비스 수준 목표)** 를 정의하고 있다.

- **API 응답 시간**: 단일 객체 변경 API 요청은 지난 5분간 99%가 1초 이내 응답
  - 비스트리밍 API 요청 기준: 특정 리소스 1초 / 네임스페이스 전체 5초 / 클러스터 전체 30초
- **파드 기동 시간**: 지난 5분간 99%가 5초 이내 기동 (이미지 다운로드·Init Container 시간 제외)

**SLO를 충족하는 클러스터 최대 사이즈**

| 항목 | 네임스페이스 단위 상한 | 클러스터 전체 상한 |
| --- | --- | --- |
| 노드 수 | – | 5,000 노드 이하 |
| 총 파드 수 | 3,000 파드 이하 | 150,000 파드 이하 |
| 1 노드당 파드 수 | – | 110 파드 또는 (코어 수 × 10) 중 낮은 쪽 |
| 서비스 수 | 5,000 이하 | 10,000 이하 |

- 이 이상 규모도 만들 수는 있으나 **서비스 수준이 떨어질 수 있다.**
- 관리형 서비스는 파드의 네트워크 구성 제약 때문에 **파드 수 제한이 다를 수 있으니 주의.**
- 많은 관리형 서비스에서 **마스터 노드 스케일업은 자동**이지만, **구축 도구로 만들 경우 마스터 인스턴스 사이즈를 직접 정해야 한다.**

### 3.3.2 큐브어드민 (kubeadm)
쿠버네티스 공식 클러스터 구축 도구.

```bash
# 마스터 초기화 후 출력되는 인증 파일 설정
mkdir -p $HOME/.kube
sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
sudo chown $(id -u):$(id -g) $HOME/.kube/config

# 워커 노드에서 클러스터에 조인
sudo kubeadm join 172.31.2.189:6443 --token <토큰> \
  --discovery-token-ca-cert-hash sha256:<해시>
```
- 마스터 초기화가 성공하면 **노드에서 실행할 join 명령어가 출력**되고, 노드를 추가할 때마다 그 명령을 실행한다.
- kubectl 인증 파일은 `/etc/kubernetes/admin.conf`에 있다.
- **주의**: 여기까지만 하면 각 노드에 프로세스는 다 떴지만 **서로 다른 노드에 배포된 파드 간 통신이 안 되므로** 아직 완전한 멀티 노드 클러스터가 아니다. → CNI 설치 필요.

### 3.3.3 플라넬 (Flannel)
- 도커가 컨테이너에 할당하는 IP는 **호스트 외부에서 볼 수 없는 내부 IP**다. 그래서 그대로 두면 **노드 간 컨테이너 통신이 불가능**하다.
- 이를 해결하는 것이 **CNI 플러그인**이고, 플라넬은 그중 하나. (오버레이 네트워크로 노드 간 파드 통신을 가능하게 함)

### 3.3.4 랜처 (Rancher)
중앙 집중형 쿠버네티스 관리 플랫폼.
- 온프레미스 포함 **기존 클러스터를 랜처로 관리**(클러스터 임포트)
- 여러 클러스터에 앱 배포를 가능하게 하는 **멀티 클러스터 앱** 기능
- **중앙 집중적 인증, 모니터링, 웹 UI** 제공
- 풍부한 애플리케이션 카탈로그, **Istio와의 통합/연계**
- 랜처 서버를 중앙에서 띄우고, 관리자가 그 서버를 통해 클러스터를 구축·관리하는 구조. 클라우드 프로바이더 API도 활용한다.
  ```bash
  sudo docker run -d --restart=unless-stopped -p 80:80 -p 443:443 rancher/rancher:v2.3.5
  ```
- 실제 서비스에서 쓸 땐 **DB 이중화와 랜처 서버 HA 구성**을 고려해야 한다.

### 3.3.5 그 외 구축 도구
- **Kubespray** (Ansible 기반)
- **kube-aws** (CloudFormation 기반)
- **Terraform**, CloudFormation 형식 파일 출력 도구 등

## 3.4 퍼블릭 클라우드 관리형 쿠버네티스 서비스

클라우드 사업자가 마스터(컨트롤 플레인)를 대신 운영해주는 방식. 운영 부담이 가장 적다.

### GKE (Google Kubernetes Engine)
- 구글이 제공. 쿠버네티스의 본가 격이라 기능 반영이 빠르다.
- 버전은 **channel(RAPID/REGULAR/STABLE)** 로 관리된다.
  ```bash
  gcloud container clusters create k8s \
    --cluster-version 1.18.16-gke.2100 \
    --zone asia-northeast3-a \
    --num-nodes 3
  ```
- 인증 정보는 `~/.kube/config`에 자동 저장. 다시 가져오려면:
  ```bash
  gcloud container clusters get-credentials k8s --zone asia-northeast3-a
  ```
- `Kubernetes Engine API is not enabled` 에러가 나면 GCP 프로젝트에서 해당 API를 활성화해야 한다.

### AKS (Azure Kubernetes Service)
- **Azure Active Directory와 RBAC 연계** 기능 제공.
- 클러스터 자원이 부족할 때 **Virtual Kubelet으로 ACI(Azure Container Instances)에 버스팅**하는 기능이 특징. 클러스터를 스케일아웃하는 게 아니라 ACI로 넘기기 때문에 **파드를 몇 초 안에 기동**할 수 있고, **버스팅 전까지는 비용이 발생하지 않는다.**
  ```bash
  az group create --name k8srg --location koreasouth
  az aks create --name k8s --kubernetes-version 1.18.14 --node-count 3 ...
  ```

### EKS (Elastic Kubernetes Service)
- AWS 제공. 커스텀 AMI로 EC2를 만들어 노드로 쓸 수도 있다.
- 운용 부하를 줄이려면 **Managed Nodegroups**나 **EKS on Fargate**를 사용.
- **주의**: (집필 시점 기준) 클러스터 내부의 **DNS, CNI, Ingress Controller 등은 관리되지 않는다.**
- 보통 AWS CLI + CloudFormation으로 VPC·노드그룹 Stack을 만들지만 복잡해서, 아마존과 Weaveworks가 만든 **eksctl**을 쓰면 간단하다.
  ```bash
  eksctl create cluster --name k8s --version 1.18 \
    --region ap-northeast-2 --nodes 3 --managed

  eksctl utils write-kubeconfig --cluster k8s   # 인증 정보 가져오기
  eksctl delete cluster --name k8s --region ap-northeast-2
  ```

## 3.5 쿠버네티스 플레이그라운드
- 도커가 제공하는 **웹 화면에서 쿠버네티스를 테스트**할 수 있는 환경.
- 최대 **다섯 대의 인스턴스**를 띄우고, 화면 순서대로 kubeadm으로 클러스터를 구축해 사용.
- **1분 정도면 환경 구축**이 가능해 매우 편리하다.
- 단, **연속 사용 시간 제한(최대 4시간)** 과 기능 제약이 있으니 주의.

## 3.6 정리
- 쿠버네티스 환경은 크게 **로컬 쿠버네티스 / 구축 도구 / 관리형 서비스** 세 가지다.
- 퍼블릭·프라이빗 클라우드 같은 **플랫폼 종류**와 개발/스테이징/서비스 같은 **환경 용도**에 맞게 적절한 방법을 고르면 된다.
- 인증 프로그램을 통과한 환경이라면 기본 동작의 일관성은 보장되지만, **환경에 따라 기능 차이가 있을 수 있다.**
- 따라서 **개발/스테이징/서비스 환경은 가능하면 같은 환경에서 운용**하는 것이 좋고, **최소한 스테이징과 서비스 환경은 반드시 같은 환경**이어야 한다.
- 다음 4장부터는 실제 구축된 클러스터로 쿠버네티스의 개념과 사용법을 다룬다.

## 한 줄 요약
> **테스트는 로컬(미니큐브·Docker Desktop·kind), 직접 구축은 도구(kubeadm·Rancher), 실서비스는 관리형(GKE·AKS·EKS).** 인증 프로그램 덕에 어디서든 기본 동작은 같지만, 스테이징과 서비스 환경은 반드시 동일하게 맞춰라.
