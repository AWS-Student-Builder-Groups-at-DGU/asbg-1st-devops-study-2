# 3장 쿠버네티스 환경 선택

---

## 3.1 쿠버네티스 환경의 종류

클러스터를 구성하는 방법은 크게 세 가지.

| 방식 | 설명 | 적합한 용도 |
|---|---|---|
| 로컬 쿠버네티스 | 물리 머신 1대에 올인원 구축 | 개인 테스트 / 개발 |
| 쿠버네티스 구축 도구 | 온프레미스·클라우드에 직접 클러스터 구축 | 온프레미스 배포, 세밀한 커스터마이즈 |
| 관리형 쿠버네티스 서비스 | 퍼블릭 클라우드가 제공하는 클러스터 | 스테이징 / 서비스 (기본 선택지) |

**선택 기준**

- 로컬은 이중화가 안 되므로 서비스 환경에 사용하지 말 것.
- 가능하면 개발 환경도 구축 도구나 관리형 서비스를 써서 서비스 환경과 동일하게 맞추는 편이 좋다.
- 관리형을 쓸 수 있으면 관리형을 우선, 구축 도구는 온프레미스나 커스터마이즈가 필요할 때.

**환경 간 호환성**

환경에 따라 못 쓰는 기능이 일부 있지만(외부 로드 밸런서 연계, 동적 영구 볼륨 프로비저닝 등), 기본 동작은 어디서나 동일하다. CNCF의 **쿠버네티스 적합성 인증 프로그램(Certified Kubernetes Conformance Program)** 을 각 환경이 준수하기 때문. 이 프로그램은 클러스터 기능 동작의 **일관성과 이식성 보장**이 목적이며, 각 벤더는 이를 먼저 만족시킨 뒤 플랫폼 특성을 살려 기능을 확장한다.

## 3.2 로컬 쿠버네티스

### 3.2.1 미니큐브 (Minikube)

- 쿠버네티스 SIG-Cluster-Lifecycle 분과회에서 개발.
- **단일 노드** 구성 → 여러 대가 필요한 기능은 사용 불가.
- 하이퍼바이저 필요 (OS별 지원 드라이버)
  - macOS: Docker / hyperkit / VirtualBox / Parallels / VMware Fusion / Podman
  - Linux: Docker / VirtualBox / Podman / KVM / 베어메탈(systemd-based)
  - Windows: Docker / VirtualBox / Hyper-V
- 드라이버에 맞춰 호스트가 될 VM·컨테이너를 자동 생성하고 그 위에 쿠버네티스를 설치.

```bash
# 설치 (macOS + hyperkit)
$ brew install hyperkit
$ brew install minikube

# 클러스터 기동 (버전 지정 가능)
$ minikube start --driver=hyperkit --kubernetes-version v1.18.15

# 상태 확인 / 컨텍스트 전환 / 노드 확인
$ minikube status
$ kubectl config use-context minikube
$ kubectl get nodes

# 삭제
$ minikube delete
```

- `minikube tunnel` 로 ClusterIP 서비스 연결, Addon 기능으로 Istio 등 설치 가능.

### 3.2.2 Docker Desktop for Mac / Windows

- DockerCon EU 17에서 쿠버네티스 지원 발표. 버전 **18.06.0 CE**부터 로컬 사용 가능.
- Preferences → Kubernetes 활성화 (배포에 약 5분). 좌측 하단이 `Docker Running`, `Kubernetes running`이면 성공.
- `Show system containers (advanced)` 를 켜면 컨트롤 플레인 구성 요소가 컨테이너로 뜨는 걸 확인 가능.

```bash
$ kubectl config use-context docker-desktop
$ kubectl get nodes
```

### 3.2.3 kind (Kubernetes in Docker)

- 쿠버네티스 자체 개발을 위한 도구. SIG-Testing 분과회에서 개발.
- **도커 컨테이너 자체를 노드로 사용** → 로컬에서 멀티 노드 클러스터를 만들려면 현재 가장 좋은 선택.
- 노드 이미지는 Docker Hub의 `kindest` Organization에서 관리.

```yaml
# kind.yaml — 마스터 3대 + 워커 3대
apiVersion: kind.x-k8s.io/v1alpha4
kind: Cluster
nodes:
- role: control-plane
  image: kindest/node:v1.18.15
- role: control-plane
  image: kindest/node:v1.18.15
- role: control-plane
  image: kindest/node:v1.18.15
- role: worker
  image: kindest/node:v1.18.15
- role: worker
  image: kindest/node:v1.18.15
- role: worker
  image: kindest/node:v1.18.15
```

```bash
$ brew install kind
$ kind create cluster --config kind.yaml --name kindcluster   # Docker 환경 기동 필수
$ kubectl config use-context kind-kindcluster
$ kind delete cluster --name kindcluster
```

- 노드 대수만큼 컨테이너가 뜨고, 마스터 이중화용 **HAProxy** 컨테이너도 함께 생성됨.
- 내부적으로 **kubeadm**을 사용하며, `kubeadmConfigPatches` / `kubeadmConfigPatchesJson6902` 로 설정 패치 가능 → 알파 클러스터 생성 시 FeatureGates 활성화에 활용.
- `extraPortMapping` 등 로컬↔컨테이너 통신 설정도 자주 쓰임.

> **column: FeatureGates**
> 쿠버네티스 기능을 활성화/비활성화하는 방법. 베타 이상은 기본값으로 활성화되지만, **알파 기능은 명시적으로 활성화해야 한다.** FeatureGates를 확인하는 것만으로 어떤 신기능이 추가됐는지 어느 정도 파악할 수 있다.

## 3.3 쿠버네티스 구축 도구

### 3.3.1 서비스 수준 목표 (SLO)

SIG-Scalability가 정의한 SLI/SLO.

- **API 응답 시간**
  - 단일 객체 변경 API: 지난 5분간 99%가 1초 이내
  - 비스트리밍 API: 지난 5분간 99%가 아래 시간 이내
    - 특정 리소스 1초 / 네임스페이스 전체 5초 / 클러스터 전체 30초
- **파드 기동 시간**: 지난 5분간 99%가 5초 이내 (이미지 다운로드·Init Container 시간 제외)

**SLO를 충족하는 클러스터 최대 사이즈**

| 항목 | 네임스페이스 단위 상한 | 클러스터 전체 상한 |
|---|---|---|
| 노드 수 | – | 5,000 노드 이하 |
| 총 파드 수 | 3,000 파드 이하 | 150,000 파드 이하 |
| 1 노드당 파드 수 | – | 110 파드 또는 (코어 수 × 10) 중 낮은 쪽 |
| 서비스 수 | 5,000 이하 | 10,000 이하 |

- 관리형 서비스는 파드 네트워크 구성 제약 때문에 파드 수 제한이 다를 수 있음.
- 관리형은 마스터 스케일 업이 자동이지만, 구축 도구를 쓰면 마스터 인스턴스 사이즈를 직접 정해야 한다.

### 3.3.2 큐브어드민 (kubeadm)

쿠버네티스 공식 구축 도구. 1.13이 릴리스된 **2018년 12월 GA**.

```bash
# [모든 노드] 패키지 설치 + 커널 파라미터
$ sudo apt install -y kubelet=1.18.15-00 kubeadm=1.18.15-00 kubectl=1.18.15-00 docker.io
$ sudo apt-mark hold kubelet kubeadm kubectl docker.io
$ cat << EOF | sudo tee /etc/sysctl.d/k8s.conf
net.bridge.bridge-nf-call-ip6tables = 1
net.bridge.bridge-nf-call-iptables = 1
net.ipv4.ip_forward = 1
EOF
$ sudo sysctl --system

# [마스터] 초기화
$ sudo kubeadm init \
  --kubernetes-version=1.18.15 \
  --pod-network-cidr=172.31.0.0/16

# [마스터] 인증 파일 복사
$ mkdir -p $HOME/.kube
$ sudo cp -i /etc/kubernetes/admin.conf $HOME/.kube/config
$ sudo chown $(id -u):$(id -g) $HOME/.kube/config

# [워커] init 출력에 나온 명령어 실행
$ sudo kubeadm join <master-ip>:6443 --token ... --discovery-token-ca-cert-hash sha256:...
```

**주의**

- `--pod-network-cidr` 는 파드 네트워크용(플라넬 사용 전제) 설정.
- **swap이 비활성화되어 있어야 함**. 임시로는 `sudo swapoff -a`, 영구적으로는 `/etc/fstab` 의 swap 행을 `#` 주석 처리.

### 3.3.3 플라넬 (Flannel)

- 도커 컨테이너에 할당되는 IP는 호스트 외부에서 보이지 않는 **내부 IP** → 노드가 다르면 파드 간 통신 불가.
- 멀티 노드 클러스터가 되려면 각 호스트의 내부 네트워크 접속성 확보가 필수.
- 플라넬은 노드 사이 네트워크에 **가상 터널(오버레이 네트워크)** 을 구성해 파드 간 통신(파드 네트워크)을 구현.

```bash
$ kubectl apply -f \
  https://raw.githubusercontent.com/coreos/flannel/master/Documentation/kube-flannel.yml
```

- 파드 네트워크 구현 방법은 플라넬 외에도 여러 가지가 있다.

### 3.3.4 랜처 (Rancher)

Rancher Labs가 개발하는 오픈 소스 컨테이너 플랫폼. 1.X는 여러 오케스트레이션 도구를 지원했지만 **2.0(2018년 5월 정식 출시)부터 쿠버네티스 중심**.

주요 기능 (2.3 기준)

- 여러 클러스터의 통합 관리
- 다양한 플랫폼에 클러스터 배포 (AWS, OpenStack, VMware 등)
- 기존 클러스터를 랜처로 관리 (클러스터 임포트)
- 멀티 클러스터 앱(Multi-cluster App)
- 중앙 집중적 인증, 모니터링, 웹 UI
- 풍부한 애플리케이션 카탈로그, Istio 연계

```bash
$ sudo docker run -d --restart=unless-stopped -p 80:80 -p 443:443 rancher/rancher:v2.3.5
```

- 구조: 중앙 랜처 서버 → 클라우드 프로바이더 API를 사용해 클러스터 구축·관리.
- 실제 서비스 환경에서는 **DB 이중화와 랜처 서버 HA 구성**을 고려해야 한다.

### 3.3.5 / 3.3.6 그 외

- **구축 도구**: kubespray(Ansible), kube-aws(CloudFormation), kops(Terraform·CFN 형식 출력), OpenStack Magnum(Heat)
- **엔터프라이즈 솔루션**: Red Hat OpenShift, VMware Enterprise PKS, IBM Cloud Private, VMware Tanzu

## 3.4 퍼블릭 클라우드 관리형 쿠버네티스 서비스

영구 볼륨, 로드 밸런서 연계 등을 쉽게 쓸 수 있도록 기능을 제공한다.

### 3.4.1 GKE (Google Kubernetes Engine)

가장 먼저 출시된 관리형 서비스. **2015년 8월 GA**. Borg의 노하우 기반.

**주요 기능**

- 릴리스 채널, 노드 자동 업데이트 / 자동 복구(Node Auto Repair) / 노드 자동 프로비저닝 → 클러스터 운용 부하를 크게 낮춤
- **선점형 인스턴스(Preemptible Instance)**: 가동 시간 24시간 제한의 저비용 인스턴스를 노드로 사용 가능. 비용 절감되지만 노드가 정지될 수 있음 → 컨테이너 설정을 잘 해두면 자동 복구 가능. 전부 선점형이면 24시간 후 전 노드가 멈출 수 있으므로 **preemptible-killer** 같은 걸로 랜덤·점진 교체 검토.
- **노드 풀(NodePool)**: 클러스터 내부 노드에 레이블을 부여해 그룹핑. 'vCPU 많은 노드', '메모리 많은 노드' 식으로 나눠 스케줄링 시 배포 제약 조건으로 활용, 워크로드 분리에도 사용. 현재는 GKE 외 다른 관리형 서비스도 제공.
- GCP 통합: Cloud Logging(구 Stackdriver) 기본 연계, 고가용 HTTP LB(Ingress), GPU 사용 가능

```bash
$ curl https://sdk.cloud.google.com | bash
$ gcloud init

# 사용 가능한 버전 확인 (asia-northeast3 = 서울 리전)
$ gcloud container get-server-config --zone asia-northeast3-a

# 클러스터 생성
$ gcloud container clusters create k8s \
  --cluster-version 1.18.16-gke.2100 \
  --zone asia-northeast3-a \
  --num-nodes 3

# 인증 정보 재취득 (~/.kube/config 에 자동 저장)
$ gcloud container clusters get-credentials k8s --zone asia-northeast3-a

# 삭제
$ gcloud container clusters delete k8s --zone asia-northeast3-a
```

- `Kubernetes Engine API is not enabled` 에러 → 에러 메시지 마지막 URL에서 API 활성화.
- IAM 사용자에게 클러스터 관리자 권한 부여는 `clusterrolebinding` 으로 설정 (인증/인가는 13장).
- 구글 클라우드 콘솔 대시보드로 GUI 관리 가능.

### 3.4.2 AKS (Azure Kubernetes Service)

Microsoft Azure의 관리형 서비스. **2018년 6월 GA**.

**주요 기능**

- Azure Active Directory ↔ 쿠버네티스 RBAC 연계
- 리소스 부족 시 **Virtual Kubelet**으로 Azure Container Instances(ACI)에 **버스팅(bursting)**. 클러스터를 스케일 아웃하는 게 아니라 ACI로 넘기므로 파드를 몇 초 안에 기동, 버스팅 전까지는 비용 미발생.

```bash
$ brew install azure-cli && az login

$ az aks get-versions -l koreasouth
$ az group create --name k8srg --location koreasouth
$ az ad sp create-for-rbac --skip-assignment --name myAKSClusterServicePrincipal

$ az aks create --name k8s \
  --kubernetes-version 1.18.14 \
  --node-count 3 \
  --resource-group k8srg \
  --generate-ssh-keys \
  --service-principal <appId> --client-secret <password>

$ az aks get-credentials --name k8s --resource-group k8srg
$ az aks browse --name k8s --resource-group k8srg   # 대시보드
$ az aks delete --name k8s --resource-group k8srg
```

- 리소스 그룹을 먼저 만든 뒤 그 그룹으로 클러스터를 생성하는 흐름.

### 3.4.3 EKS (Elastic Kubernetes Service)

AWS re:Invent 2017 발표, **2018년 6월 GA**.

**주요 기능**

- **IAM ↔ 쿠버네티스 사용자 연결** → IAM 기반 권한 관리
- **파드 네트워크가 AWS VPC 서브넷과 직접 연결** → 가상 머신에서 컨테이너로 직접 통신 가능
- CloudWatch Logs / CloudTrail 연계 로깅
- 노드는 보통 AWS 제공 AMI로 만든 EC2. Packer 설정·스크립트로 커스텀 AMI도 가능.
- 운용 부하를 줄이려면 **Managed Nodegroups** 또는 **EKS on Fargate**.
- (집필 시점) 클러스터 내부 DNS, CNI, Ingress Controller 등 구성 요소는 관리되지 않으므로 주의.

```bash
# AWS CLI + CloudFormation 방식은 커스터마이즈는 좋지만 복잡 → eksctl 사용
$ curl --silent --location \
  "https://github.com/weaveworks/eksctl/releases/latest/download/eksctl_$(uname -s)_amd64.tar.gz" | tar xz -C /tmp
$ sudo mv /tmp/eksctl /usr/local/bin

$ eksctl create cluster \
  --name k8s \
  --version 1.18 \
  --region ap-northeast-2 \
  --nodes 3 \
  --managed

$ eksctl utils write-kubeconfig --cluster k8s
$ eksctl delete cluster --name k8s --region ap-northeast-2
```

- eksctl은 Amazon과 Weaveworks가 개발한 오픈 소스. 명령어 하나로 클러스터 기동.
- eksctl 없이 생성하는 문서, EKS/AWS 향후 로드맵 문서도 GitHub에 공개되어 있음.

## 3.6 정리

- **로컬 쿠버네티스**: 물리 머신 한 대에 구축하여 사용
- **쿠버네티스 구축 도구**: 도구로 온프레미스/클라우드에 클러스터를 구축하여 사용
- **관리형 쿠버네티스 서비스**: 퍼블릭 클라우드의 관리형 서비스로 제공하는 클러스터 사용

플랫폼 종류(퍼블릭/프라이빗 클라우드)와 환경적 측면(개발/스테이징/서비스), 용도에 맞게 선택한다.

인증 프로그램을 통과한 환경이라면 동작 일관성은 보장되지만 환경별 기능 차이는 있을 수 있다. 따라서 **개발/스테이징/서비스 환경은 가능하면 같은 환경**에서 운용하고, **최소한 스테이징과 서비스 환경은 반드시 같은 환경**이어야 한다.
