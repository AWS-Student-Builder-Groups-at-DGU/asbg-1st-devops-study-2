## 4.2 쿠버네티스 기초

쿠버네티스 클러스터는 **마스터**와 **노드**로 구성됩니다.

- **쿠버네티스 마스터**: API 엔드포인트 제공, 컨테이너 스케줄링, 스케일링을 담당
- **쿠버네티스 노드**: 도커 호스트에 해당하며 실제로 컨테이너를 기동

클러스터를 관리하려면 kubectl과 매니페스트 파일로 마스터에 **리소스**를 등록합니다.

- 매니페스트는 YAML 또는 JSON으로 작성하며, 가독성 때문에 보통 YAML을 사용
- 확장자는 `.yaml`, `.yml`, `.json`
- 쿠버네티스 API는 RESTful API이므로 kubectl 없이 curl이나 각 언어의 HTTP 라이브러리로 직접 호출하는 것도 가능

## 4.3 쿠버네티스와 리소스

리소스는 크게 다섯 가지 카테고리로 분류됩니다. 리소스 등록은 비동기로 처리됩니다.

| 카테고리 | 개요 |
|---|---|
| 워크로드 API | 컨테이너 실행에 관련된 리소스 |
| 서비스 API | 컨테이너를 외부에 공개하는 엔드포인트를 제공 |
| 컨피그 & 스토리지 API | 설정, 기밀 정보, 영구 볼륨 관련 |
| 클러스터 API | 보안이나 쿼터 등 클러스터 자체 동작을 정의 |
| 메타데이터 API | 클러스터 내부의 다른 리소스를 제어 |

이 중 애플리케이션 개발자가 주로 쓰는 것은 **워크로드 / 서비스 / 컨피그 & 스토리지** 세 가지입니다.

### 4.3.1 워크로드 API (5장)

클러스터 위에서 컨테이너를 기동하기 위한 리소스. 사용자가 직접 관리하는 것은 8종.

- 파드(Pod)
- 레플리케이션 컨트롤러(ReplicationController)
- 레플리카셋(ReplicaSet)
- 디플로이먼트(Deployment)
- 데몬셋(DaemonSet)
- 스테이트풀셋(StatefulSet)
- 잡(Job)
- 크론잡(CronJob)

### 4.3.2 서비스 API (6장)

서비스 디스커버리와 외부 접속용 엔드포인트를 제공. 서비스와 인그레스 두 종류.

- 서비스
  - ClusterIP
  - ExternalIP (ClusterIP의 한 종류)
  - NodePort
  - LoadBalancer
  - Headless(None)
  - ExternalName
  - None-Selector
- 인그레스

> ExternalIP와 None-Selector는 엄밀히는 타입이 아니지만 책에서는 타입으로 소개합니다.

### 4.3.3 컨피그 & 스토리지 API (7장)

설정값과 기밀 데이터를 컨테이너에 넘기거나 영구 볼륨을 제공.

- 시크릿(Secret)
- 컨피그맵(ConfigMap)
- 영구 볼륨 클레임(PersistentVolumeClaim)

시크릿과 컨피그맵은 모두 키 밸류 구조이며, 저장할 데이터가 기밀인지 일반 설정인지로 구분합니다.

### 4.3.4 클러스터 API (8장)

- 노드(Node)
- 네임스페이스(Namespace)
- 영구 볼륨(PersistentVolume)
- 리소스 쿼터(ResourceQuota)
- 서비스 어카운트(ServiceAccount)
- 롤(Role) / 클러스터 롤(ClusterRole)
- 롤바인딩(RoleBinding) / 클러스터롤바인딩(ClusterRoleBinding)
- 네트워크 정책(NetworkPolicy)

### 4.3.5 메타데이터 API (8장)

클러스터 내부의 다른 리소스 동작을 제어하는 리소스. 예를 들어 HPA는 디플로이먼트를 조작해 레플리카 수를 바꿔 오토 스케일링을 구현합니다.

- LimitRange
- HorizontalPodAutoscaler(HPA)
- PodDisruptionBudget(PDB)
- 커스텀 리소스 데피니션(CustomResourceDefinition)

## 4.4 네임스페이스로 가상적인 클러스터 분리

네임스페이스는 클러스터를 가상으로 분리하는 기능입니다. 완전한 분리는 아니라서 용도는 제한적이지만, 하나의 클러스터를 여러 팀이 쓰거나 환경별로 구분할 때 사용합니다.

기본 생성되는 네 가지 네임스페이스:

| 이름 | 용도 |
|---|---|
| `kube-system` | 클러스터 구성 요소와 애드온이 배포되는 네임스페이스 |
| `kube-public` | 모든 사용자가 사용할 수 있는 컨피그맵 등을 배치 |
| `kube-node-lease` | 노드 하트비트(Lease 리소스)가 저장되는 전용 네임스페이스 |
| `default` | 기본 네임스페이스 |

관리형 서비스나 구축 도구로 만든 클러스터는 대부분 **RBAC**(13장)이 기본 활성화되어 있습니다. RBAC은 클러스터 조작 권한을 네임스페이스별로 구분할 수 있고, 네트워크 정책과 함께 쓰면 네임스페이스 간 통신까지 제어할 수 있습니다.

### 네임스페이스 분리 기준에 대한 저자 의견

권한 분리 관점에서 마이크로서비스를 개발하는 팀 단위로 나누는 것이 좋습니다. 다만 서비스/스테이징/개발 환경은 네임스페이스가 아니라 **클러스터별로 나누는 것**을 권장합니다.

- 클러스터 업그레이드 시 모든 환경에서 동시에 장애가 날 수 있음
- `prd-ns1` / `stg-ns1` 같은 명명 규칙을 쓰면 매니페스트 재사용성이 떨어짐. 클러스터를 나누면 각 환경에서 같은 네임스페이스 이름을 써서 매니페스트를 그대로 재사용 가능
- 서비스 이름 해석 시 `SERVICE.prd-ns1.svc.cluster.local`처럼 다른 목적지로 통신하게 됨

### 4.5.1 인증 정보와 컨텍스트(config)

kubectl은 **kubeconfig**(기본 위치 `~/.kube/config`)의 정보를 사용해 마스터에 접속합니다. kubeconfig도 매니페스트와 동일한 형식입니다.

```yaml
apiVersion: v1
kind: Config
preferences: {}
clusters: # 접속 대상 클러스터
  - name: sample-cluster
    cluster:
      server: https://localhost:6443
users: # 인증 정보
  - name: sample-user
    user:
      client-certificate-data: LS0tLS1CRUdJTi...
      client-key-data: LS0tLS1CRUdJTi...
contexts: # 접속 대상과 인증 정보 조합
  - name: sample-context
    context:
      cluster: sample-cluster
      namespace: default
      user: sample-user
current-context: sample-context
```

설정은 `clusters` / `users` / `contexts` 세 가지이며 모두 배열이라 여러 대상을 등록할 수 있습니다. 사용자 인증에는 X.509 클라이언트 인증서, 토큰, 패스워드, 웹훅 등을 쓸 수 있습니다.

> 그림 4-4: 컨텍스트/사용자/클러스터의 관계

<img width="1672" height="941" alt="image" src="https://github.com/user-attachments/assets/2a680a28-38f3-4d81-9203-3350b3f9caf4" />


kubeconfig는 직접 편집해도 되고 kubectl 명령어로 바꿔도 됩니다. 명령어로 변경하면 파일 내용이 자동 갱신됩니다.

```bash
# 클러스터(prd-cluster) 정의 추가, 변경
kubectl config set-cluster prd-cluster \
  --server=https://localhost:6443

# 인증 정보 정의 추가, 변경
kubectl config set-credentials admin-user \
  --client-certificate=./sample.crt \
  --client-key=./sample.key \
  --embed-certs=true

# 컨텍스트 정의(클러스터/인증 정보/네임스페이스) 추가, 변경
kubectl config set-context prd-admin \
  --cluster=prd-cluster \
  --user=admin-user \
  --namespace=default
```

컨텍스트를 전환하면 여러 환경을 여러 권한으로 조작할 수 있습니다.

```bash
# 컨텍스트 목록 표시
kubectl config get-contexts

# 컨텍스트 전환
kubectl config use-context prd-admin

# 현재 컨텍스트 표시
kubectl config current-context

# 명령어 실행마다 컨텍스트 지정
kubectl --context prd-admin get pod
```

### 4.5.2 kubectx / kubens를 사용한 전환

클러스터나 네임스페이스가 많으면 `kubectl config use-context`나 `kubectl --namespace`는 비효율적입니다. kubectx와 kubens는 자동 완성을 제공해 전환이 훨씬 편합니다.

```bash
# 컨텍스트 전환 (kubectl config use-context docker-desktop과 동일)
kubectx docker-desktop

# 바로 전 컨텍스트로 전환
kubectx -

# 컨텍스트 삭제
kubectx -d prd-admin

# 네임스페이스 전환
# kubectl config set-context docker-desktop --namespace=default 와 동일
kubens default
```

### 4.5.3 매니페스트와 리소스 생성/삭제/갱신

```yaml
# sample-pod.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-pod
spec:
  containers:
    - name: nginx-container
      image: nginx:1.16
```

```bash
# 리소스 생성
kubectl apply -f sample-pod.yaml

# 리소스 삭제(삭제 완료 대기)
kubectl delete -f sample-pod.yaml --wait

# 리소스 즉시 강제 삭제
kubectl delete -f sample-pod.yaml --grace-period 0 --force
```

강제 삭제 시 `--grace-period 0`은 정지까지의 유예 기간을 0으로 만듭니다. 1.8 이후부터는 `--force`만 줘도 자동으로 붙습니다. 비슷한 `--now` 옵션은 `--grace-period 1`과 동일해서 바로 삭제되지 않을 수 있으니 주의해야 합니다. (Graceful Period는 11장)

업데이트는 `kubectl apply`를 사용합니다. 변경 부분이 있으면 적용하고, 없으면 적용하지 않으며, 리소스가 없으면 `create`처럼 신규 생성합니다.

```bash
# 변경 사항이 있을 경우
$ kubectl apply -f sample-pod.yaml
pod/sample-pod configured

# 변경 사항이 없을 경우
$ kubectl apply -f sample-pod.yaml
pod/sample-pod unchanged

# 리소스가 존재하지 않을 경우
$ kubectl apply -f sample-pod.yaml
pod/sample-pod created
```

기동 중인 파드 이미지 확인:

```bash
kubectl get pod sample-pod \
  -o jsonpath="{.spec.containers[?(@.name == 'nginx-container')].image}"
```

> 한번 기록된 리소스의 필드 대부분은 업데이트로 변경할 수 있지만, 생성 후 변경할 수 없는 필드도 있습니다.

### 4.5.4 리소스 생성에도 kubectl apply를 사용해야 하는 이유

**첫 번째**, 생성은 `create`, 업데이트는 `apply`라는 구분이 불필요합니다. 스크립트나 CI/CD에 포함될 것을 생각하면 조건 분기는 하지 않는 편이 좋습니다.

**두 번째**, `create`와 `apply`를 섞어 쓰면 `apply` 실행 시 변경 사항을 검출하지 못하는 경우가 생깁니다. `apply`의 변경 사항은 아래 세 가지에서 산출됩니다.

| 기준 | 역할 |
|---|---|
| 이전에 적용한 매니페스트 | 삭제된 필드 산출에 사용 |
| 현재 클러스터에 등록된 리소스 상태 | 추가/변경 필드 산출에 사용 |
| 이번에 적용할 매니페스트 | 추가/변경/삭제 판단 기준 |

'이전에 적용한 매니페스트'는 `kubectl create --save-config`나 `kubectl apply`로 리소스를 생성/변경했을 때 `metadata.annotations.kubectl.kubernetes.io/last-applied-configuration`에 원라이너 JSON으로 저장됩니다. `--save-config` 없이 `create`만 쓴 경우에는 저장되지 않습니다.

그래서 특정 필드를 **삭제**하고 싶을 때 변경 사항이 산출되지 않아 의도대로 반영되지 않는 필드가 생깁니다. 따라서 리소스 생성도 항상 `apply`를 쓰는 것이 좋습니다.

```bash
# kubectl create로 생성한 뒤 apply한 경우의 경고
$ kubectl apply -f sample-pod.yaml
Warning: kubectl apply should be used on resource created by either
kubectl create --save-config or kubectl apply
pod/sample-pod configured
```

### 4.5.5 Server-side apply (1.18 Beta2)

kubectl 외에도 다양한 시스템 구성 요소가 리소스 필드를 자동으로 수정할 수 있습니다. 기존 방식은 변경 사항 산출을 클라이언트(kubectl)에서 계산해 패치 요청을 보내기 때문에(Client-side apply), 여러 사용자나 구성 요소가 동시에 같은 필드를 바꾸면 **경합**이 발생합니다.

이를 해결하려고 두 가지가 도입되었습니다.

- 필드를 변경한 구성 요소(kubectl이나 구성 요소 이름)를 기록하는 기능
- 서버 측에서 변경 사항을 계산하는 기능

예를 들어 `kubectl set image`는 매니페스트 파일을 쓰지 않고 서버 측 정보를 직접 수정합니다. 매니페스트는 그대로이므로, 이후 `kubectl apply`로 매니페스트를 다시 적용하면 이미지가 원래대로 돌아가는 예상치 못한 변경이 발생합니다. 사용자가 존재하는 필드를 수정한 뒤 매니페스트를 재적용해서, 운영 중이던 다른 필드 변경이 덮어씌워지는 경우도 자주 있습니다.

> 그림 4-7: 충돌하는 상황

#### Server-side apply 실습

서버 측은 1.18부터 기본 활성화되어 있지만 클라이언트 측은 기본값이 아닙니다. `--server-side` 옵션으로 활성화합니다.

```bash
# 앞서 변경한 sample-pod.yaml을 기존 내용으로 복원
cp -av sample-pod.yaml{.old,}

# Server-side apply를 활성화하여 매니페스트 생성
$ kubectl apply -f sample-pod.yaml --server-side
pod/sample-pod serverside-applied

# 이미지 변경
$ kubectl set image pod sample-pod nginx-container=nginx:1.17
pod/sample-pod image updated

# Server-side apply를 활성화하여 매니페스트 적용
$ kubectl apply -f sample-pod.yaml --server-side
error: Apply failed with 1 conflict: conflict with "kubectl" using v1: .spec.
containers[name="nginx-container"].image

# 충돌(conflict)을 무시하고 강제로 매니페스트 적용
$ kubectl apply -f sample-pod.yaml --server-side --force-conflicts
pod/sample-pod serverside-applied
```

Server-side apply는 충돌 **감지**만 하므로, 실제 충돌이 나면 별도로 내용을 해결해야 합니다.

구조는 필드를 관리하는 구성 요소인 **manager**로 구현됩니다. `metadata.managedFields`에 manager와 그 manager가 관리하는 필드가 저장됩니다.

```yaml
# kubectl get pod sample-pod -o yaml (일부 발췌)
metadata:
  managedFields:
    - apiVersion: v1
      fieldsType: FieldsV1
      fieldsV1:
        f:spec:
          f:containers:
            k:{"name":"nginx-container"}:
              f:image: {}
              f:name: {}
      manager: kubectl
      operation: Apply
    - manager: calico
      operation: Update
    - manager: kubelet
      operation: Update
```

Server-side apply를 쓰면 Client-side apply의 `kubectl.kubernetes.io/last-applied-configuration` 어노테이션은 존재하지 않습니다.

manager 이름은 기본값이 `kubectl`입니다. 'CI/CD에서 쓰는 kubectl'과 '개발자가 콘솔에서 쓰는 kubectl'이 구별되지 않으면 예기치 않은 충돌이 발생하므로, `--field-manager`로 이름을 바꿀 수 있습니다.

```bash
# Manager 이름을 변경하고 변경 내용 적용 (CI 도구에서 실행한다고 가정)
$ kubectl apply -f sample-pod.yaml --server-side --field-manager ci-tool
pod/sample-pod serverside-applied

# 이미지 변경 적용 (개발자 콘솔에서 실행, --field-manager는 기본 kubectl)
$ kubectl apply -f sample-pod.yaml --server-side
error: Apply failed with 1 conflict: conflict with "ci-tool": .spec.
containers[name="nginx-container"].image
```

> 서버 측에서 변경 사항을 산출하므로 curl 등 HTTP 클라이언트로 리소스 조작 요청을 보내기도 쉬워집니다.

### 4.5.6 파드 재기동

디플로이먼트 등의 리소스와 연결된 모든 파드를 재기동할 수 있습니다(rollout restart). 파드 기동 시 처리를 재실행하고 싶거나 시크릿에서 참조되는 환경 변수를 바꾸고 싶을 때 유용합니다. 리소스와 연결되지 않은 **단독 파드에는 사용할 수 없습니다.**

```bash
# Deployment 리소스의 모든 파드 재기동
$ kubectl rollout restart deployment sample-deployment
deployment.apps/sample-deployment restarted

# 파드는 재기동 안 됨
$ kubectl rollout restart pod sample-pod
error: pods "sample-pod" restarting is not supported
```

### 4.5.7 generateName으로 임의의 이름을 가진 리소스 생성

`metadata.name` 대신 `metadata.generateName`을 지정하면 접두사 뒤에 난수가 붙은 이름이 자동 생성됩니다.

```yaml
# sample-generatename.yaml
apiVersion: v1
kind: Pod
metadata:
  generateName: sample-generatename-
spec:
  containers:
    - name: nginx-container
      image: nginx:1.16
```

```bash
$ kubectl create -f sample-generatename.yaml
pod/sample-generatename-n2jpz created

$ kubectl create -f sample-generatename.yaml
pod/sample-generatename-6km7c created

$ kubectl get pods
NAME                        READY   STATUS    RESTARTS   AGE
sample-generatename-6km7c   1/1     Running   0          86s
sample-generatename-n2jpz   1/1     Running   0          92s
```

> `generateName`은 `kubectl apply`에서는 사용할 수 없으므로 주의해야 합니다. (`resource name may not be empty` 에러)

### 4.5.8 리소스 상태 체크와 대기(wait)

kubectl 명령어를 연속 실행할 때, 앞 작업의 리소스가 의도한 상태가 된 뒤 다음 명령어를 실행해야 하는 경우가 있습니다. 이때 `kubectl wait`를 씁니다. `--for`에 지정한 상태가 될 때까지 최대 `--timeout` 시간(기본 30초)만큼 대기합니다.

```bash
# sample-pod가 Ready 상태가 될 때까지 대기
$ kubectl wait --for=condition=Ready pod/sample-pod
pod/sample-pod condition met

# 모든 파드가 PodScheduled 상태가 될 때까지 대기
$ kubectl wait --for=condition=PodScheduled pod --all

# 모든 파드가 삭제될 때까지 파드마다 최대 5초씩 대기
$ kubectl wait --for=delete pod --all --timeout=5s
timed out waiting for the condition on pods/sample-pod

# 삭제 완료를 기다리지 않고 곧바로 wait 실행
$ kubectl delete pod --all --wait=false
$ kubectl wait --for=delete pod --all
pod/sample-pod condition met
```

매니페스트 파일로 대상 리소스를 지정할 수도 있습니다.

```bash
kubectl wait --for=condition=Ready -f sample-pod.yaml
```

주의할 점:

- 하나의 매니페스트에 여러 리소스가 있으면 **모든** 리소스가 지정 상태가 될 때까지 대기합니다. 리소스 종류마다 지정 가능한 상태가 달라서 의도치 않게 계속 기다릴 수 있습니다.
- 특정 리소스만 대상으로 하려면 레이블과 `--selector` / `-l` 옵션으로 제어해야 합니다.

### 4.5.9 매니페스트 파일 설계

#### 하나의 매니페스트 파일에 여러 리소스를 정의

여러 리소스를 `---`로 구분해 한 파일에 정의할 수 있습니다.

```yaml
# sample-multi-resource-manifest.yaml
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: order1-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
        - name: nginx-container
          image: nginx:1.16
---
apiVersion: v1
kind: Service
metadata:
  name: order2-service
spec:
  type: LoadBalancer
  ports:
    - name: "http-port"
      protocol: "TCP"
      port: 8080
      targetPort: 80
  selector:
    app: sample-app
```

```bash
$ kubectl apply -f sample-multi-resource-manifest.yaml
deployment.apps/order1-deployment created
service/order2-service created
```

- 위에서부터 정의된 순서대로 적용됩니다.
- 일부 리소스 정의에 문법 에러가 있으면 **그 이후에 정의된 리소스는 적용되지 않습니다.**

일반적인 사용 사례는 '파드를 기동하는 워크로드 리소스'와 '외부에 공개하는 서비스 리소스'를 한 파일로 통합하는 방법입니다. 실행 순서를 정확히 지켜야 하거나 리소스 간 결합도를 높이고 싶다면 한 파일이 좋습니다. 다만 컨피그맵이나 시크릿처럼 여러 리소스에서 공통으로 쓰이는 것은 별도 매니페스트로 분리하는 편이 좋습니다.

#### 여러 매니페스트 파일을 동시에 적용

디렉터리를 지정하면 그 안의 매니페스트를 한 번에 적용합니다. 파일명 순으로 적용되므로 순서를 제어하려면 파일명 앞에 인덱스 번호를 붙입니다.

```bash
$ ls -R ./dir
innerdir        sample-pod1.yaml  sample-pod2.yaml

./dir/innerdir:
sample-pod3.yaml

# 디렉터리 지정
$ kubectl apply -f ./dir
pod/sample-pod1 created
pod/sample-pod2 created

# 재귀적으로 적용
$ kubectl apply -f ./dir -R
pod/sample-pod3 created
pod/sample-pod1 created
pod/sample-pod2 created
```

| 방식 | 문법 에러 발생 시 |
|---|---|
| 한 파일에 여러 리소스 | 이후에 정의된 리소스가 전부 적용 안 됨 |
| 디렉터리로 여러 파일 | 문제 있는 파일 이후의 리소스만 적용 안 되고, 다른 파일의 리소스는 적용됨 |

#### 매니페스트 파일 설계 방침

쿠버네티스 서비스 개발은 마이크로서비스 아키텍처와 친화적입니다. 규모나 요구 사항에 따라 아래 세 패턴 중 골라 쓰면 됩니다.

**패턴 1. 시스템 전체를 한 디렉터리로 통합** (그림 4-8)

규모가 크지 않을 때. 파일 하나를 적용하면 특정 마이크로서비스만, 디렉터리를 지정하면 시스템 전체를 업데이트할 수 있습니다.

```text
./whole-system
  microservice-A.yaml  (Deployment + Service)
  microservice-B.yaml  (Deployment + Service)
  microservice-C.yaml  (Deployment + Service)
  ...
```

**패턴 2. 서브 시스템이나 부서별로 디렉터리 분리** (그림 4-9)

한 디렉터리로 통합이 어려울 정도로 거대하거나, 내부 정책상 그룹핑이 필요할 때.

```text
./whole-system
  ./whole-system/subsystem-A
    microservice-A.yaml  (Deployment + Service)
    microservice-B.yaml  (Deployment + Service)
    ...
```

**패턴 3. 마이크로서비스별 디렉터리 + 리소스 종류별 파일** (그림 4-10)

가독성이 높아지는 대신 적용 순서 제어가 어렵다는 단점이 있습니다.

```text
./microservice-A        ./microservice-B
  deployment.yaml         deployment.yaml
  service.yaml            service.yaml
```

팀이나 조직 구성에 맞춰 디렉터리를 나누면 각 팀에서 변경 가능한 범위(권한)를 세밀하게 설정할 수 있다는 장점도 있습니다. 실제로 조직도와 매니페스트 관리 구조, 마이크로서비스 아키텍처 구조가 비슷해지는 경우가 많은데, 이를 **콘웨이의 법칙(Conway's law)** 이라고 합니다. 시스템이나 소프트웨어는 그것을 개발한 조직과 비슷한 구조를 가진다는 원칙입니다.

### 4.5.10 어노테이션과 레이블

각 리소스에 부여하는 메타데이터입니다. 둘 다 리소스 관리에 쓰이지만 용도가 다릅니다.

| 명칭 | 개요 |
|---|---|
| 어노테이션 | 시스템 구성 요소가 사용하는 메타데이터 |
| 레이블 | 리소스 관리에 사용하는 메타데이터 |

둘 다 `[접두사/]키: 값` 구성입니다. 접두사는 옵션이며 지정할 경우 DNS 서브 도메인 형식이어야 합니다.

| 구성 부분 | 문자 수 제한 |
|---|---|
| 접두사 | 253자 |
| 키 이름 | 63자 |
| 값 | 63자 |

#### 어노테이션

`metadata.annotations`에 설정하는 단순한 키 밸류입니다. 그 값으로 어떤 처리를 하는 시스템 구성 요소가 없으면 아무 일도 일어나지 않습니다. 의미 없는 메모 용도로도 쓸 수 있고, 값에 수치를 쓸 때는 큰따옴표로 묶어야 합니다.

```yaml
# sample-annotations.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-annotation
  annotations:
    annotation1: val1
    annotation2: "200"
spec:
  containers:
    - name: nginx-container
      image: nginx:1.16
```

```bash
# 어노테이션 부여
kubectl annotate pods sample-annotations annotation3=val3

# 덮어 쓰기 허용
kubectl annotate pods sample-annotations annotation3=val3-new --overwrite

# 확인
kubectl get pod sample-annotations -o json | jq .metadata.annotations

# 삭제
kubectl annotate pods sample-annotations annotation3-
```

어노테이션의 주요 용도 세 가지:

**1. 시스템 구성 요소를 위한 데이터 저장**

앞서 나온 `kubectl.kubernetes.io/last-applied-configuration`이 대표적입니다. 이 유형은 사용자가 매니페스트에 쓰는 것이 아니라 시스템 구성 요소가 자동으로 부여합니다. 디플로이먼트의 `deployment.kubernetes.io/revision`, 실행 명령어 내용이 저장되는 `kubernetes.io/change-cause` 등도 있습니다.

**2. 모든 환경에서 사용할 수 없는 설정**

GKE/AKS/EKS 등 환경 고유의 확장 기능은 어노테이션으로 제어합니다.

| 환경 | 예시 |
|---|---|
| GKE | `cloud.google.com/load-balancer-type: "Internal"` (내부 엔드포인트) |
| EKS | `service.beta.kubernetes.io/aws-load-balancer-internal: 0.0.0.0/0` |
| EKS | `service.beta.kubernetes.io/aws-load-balancer-type: "nlb"` (CLB/NLB 선택) |

쿠버네티스는 개방적이고 중립적인 오픈 소스이므로, 모든 환경에서 쓸 수 없는 설정은 어노테이션으로 빼두는 구조입니다.

**3. 정식으로 통합되기 전의 기능 설정**

스토리지클래스나 초기화 컨테이너(Init Container)도 이전에는 어노테이션으로 설정해야 했습니다.

#### 레이블

`metadata.labels`에 설정하며, 리소스를 **구분하기 위한 정보**입니다.

```yaml
# sample-label.yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-label
  labels:
    label1: val1
    label2: val2
spec:
  containers:
    - name: nginx-container
      image: nginx:1.16
```

```bash
# 레이블 부여
kubectl label pods sample-label label3=val3

# 덮어 쓰기 허용
kubectl label pods sample-label label3=val3-new --overwrite

# 확인
kubectl get pod sample-label -o json | jq .metadata.labels

# 삭제
kubectl label pods sample-label label3-
```

컨테이너는 프로세스 하나에 가까운 아주 작은 리소스이고 파드도 마찬가지입니다. 쿠버네티스는 이런 작은 리소스를 대량으로 다루기 때문에, 동일한 레이블로 그룹핑해서 처리하거나 어떤 처리의 조건으로 사용합니다.

**개발자가 사용하는 레이블** (그림 4-11)

`-l` 옵션으로 필터링합니다.

```bash
# label1=val1과 label2 레이블을 가진 파드 표시
kubectl get pods -l label1=val1,label2

# 지정한 레이블을 컬럼으로 함께 표시 (필터링은 안 함)
kubectl get pods -L label1

# 두 옵션 동시 사용
kubectl get pods -l label1 -L label2

# 모든 레이블 표시
kubectl get pods --show-labels
```

- `-l label1`: 해당 레이블이 있는지 필터링
- `-l label1=val1`: 레이블 값이 일치하는지 필터링
- `-l label1,label2`: 콤마로 여러 레이블 필터링

**시스템이 사용하는 레이블** (그림 4-12)

레이블 자체는 단순한 키 밸류라서, 실수로 잘못 지정하면 값이 충돌해 예상치 못한 문제가 생깁니다.

- **ReplicaSet**: 레이블에 부여된 파드 수를 계산해 레플리카 수를 관리합니다. 대상 파드가 레플리카 수보다 많으면 하나를 삭제하고, 적으면 새로 생성합니다. 조건에 일치하는 파드를 별도로 생성하면 이미 기동 중인 파드가 정지될 수 있습니다.
- **Service(LoadBalancer)**: 외부 요청을 전송할 목적지 파드를 레이블 기준으로 결정합니다. 레이블을 여러 개 지정할 수 있어 조건을 유연하게 걸 수 있지만, 실수로 지정하면 다른 파드에 트래픽이 흘러갑니다.

처음부터 레이블 지정 정책을 정해두는 것이 좋습니다. 최소한 아래 정도는 미리 정해두기를 권합니다.

- 프로젝트
- 애플리케이션 종류
- 애플리케이션 버전
- 환경

에코시스템 공통화를 위해 쿠버네티스가 권장하는 레이블 키:

| 레이블 키 이름 | 개요 |
|---|---|
| `app.kubernetes.io/name` | 애플리케이션 이름 |
| `app.kubernetes.io/version` | 애플리케이션 버전 |
| `app.kubernetes.io/component` | 애플리케이션 내 구성 요소 |
| `app.kubernetes.io/part-of` | 애플리케이션이 전체적으로 구성하는 시스템 이름 |
| `app.kubernetes.io/instance` | 애플리케이션이나 시스템을 식별하는 인스턴스명 |
| `app.kubernetes.io/managed-by` | 이 애플리케이션을 관리하는 데 사용되는 도구 |

### 4.5.11 Prune을 사용한 리소스 삭제: --prune 옵션 (1.18 Alpha)

실제 운용에서 kubectl을 수동 실행하는 일은 거의 없습니다. 휴먼 에러가 나기 쉽고, 사람이 파악할 수 있는 리소스 수에 한계가 있기 때문입니다. 해결책 중 하나는 매니페스트를 깃 저장소에서 관리하고 변경 시 자동으로 `kubectl apply`를 실행하는 방식입니다(그림 4-13).

문제는 **매니페스트에서 삭제된 리소스**입니다. 이를 자동으로 지우려면 삭제된 리소스를 감지하는 구조가 필요한데, 그것이 `--prune` 옵션입니다(그림 4-14).

```bash
# 초기 생성
$ kubectl apply -f ./prune-sample --prune -l system=a
pod/sample-pod1 created
pod/sample-pod2 created

# 파일 삭제
$ rm prune-sample/sample-pod1.yaml

# 같은 명령어로 업데이트
$ kubectl apply -f ./prune-sample --prune -l system=a
pod/sample-pod2 unchanged
pod/sample-pod1 pruned
```

Prune은 삭제된 파일에 기술된 리소스를 지우는 것처럼 보이지만, 실제로는 **레이블과 일치하는 전체 리소스 목록에서 apply로 읽어들인 매니페스트에 포함되지 않는 리소스를 모두 삭제**하는 구조입니다.

주의할 점:

- 레이블 대신 `--all` 옵션도 있지만, 클러스터에 배포된 모든 리소스의 매니페스트를 읽어들이지 않으면 읽히지 않은 리소스가 전부 삭제됩니다. 클러스터의 거의 모든 리소스가 날아갈 수 있어 매우 위험합니다.
- 기본적으로 레이블을 지정해서 사용해야 합니다.
- 정확히는 Prune 대상이 되는 리소스 조건으로 어노테이션에 `kubectl.kubernetes.io/last-applied-configuration`이 포함되어 있어야 합니다.
- `dir1`과 `dir2` 양쪽에 같은 레이블 리소스가 있을 때, `kubectl apply -f ./dir1 --prune -l system=a`를 실행하면 `dir2`의 리소스가 삭제됩니다(그림 4-15). 디렉터리 구성과 레이블을 정확히 설계해야 합니다.
- v1.18 시점 알파 상태이며 향후 사양이 바뀔 수 있습니다. 운영 중인 인프라에서는 특히 조심해야 합니다.

### 4.5.13 리소스 일부 정보 업데이트: set

매니페스트 파일을 수정하지 않고 특정 설정값만 바꿉니다. 변경 가능한 설정값은 `env`, `image`, `resources`, `selector`, `serviceaccount`, `subject`입니다.

```bash
# 서식: kubectl set image 리소스 종류 리소스명 컨테이너명=컨테이너 이미지:태그
$ kubectl set image pod sample-pod nginx-container=nginx:1.16

$ kubectl describe pod sample-pod
    Image:    nginx:1.16
```

> `set`으로 설정을 바꿔도 로컬 매니페스트는 갱신되지 않습니다. 매니페스트 내용과 실제 리소스 상태가 어긋나므로 남용하지 않는 것이 좋습니다.

### 4.5.14 로컬 매니페스트와 등록 정보 비교: diff

```bash
$ kubectl set image pod sample-pod nginx-container=nginx:1.15
pod/sample-pod image updated

$ kubectl diff -f sample-pod.yaml
@@ -85,7 +85,7 @@
   spec:

-    - image: nginx:1.15

       name: nginx-container
```

종료 코드는 차이가 있으면 **1**, 없으면 **0**을 반환합니다.

### 4.5.16 리소스 정보 가져오기: get

인수에 '리소스 종류'와 '리소스명(옵션)'을 지정합니다.

```bash
kubectl get pods
kubectl get pods sample-pod

# 레이블 필터링과 표시
kubectl get pods -l label1=val1,label2 --show-labels

# 더 상세히 (IP, NODE 컬럼 추가)
kubectl get pods -o wide
```

`--output` / `-o` 옵션으로 다양한 형식 출력이 가능합니다.

```bash
# YAML 형식
kubectl get pods -o yaml
kubectl get pods -o yaml sample-pod

# Custom Columns: 원하는 항목만 표 형식으로
kubectl get pods -o custom-columns="NAME:{.metadata.name},NodeIP:{.status.hostIP}"

# JSON Path: 특정 값 하나를 조사할 때 (셸 스크립트에서 자주 사용)
kubectl get pods sample-pod -o jsonpath="{.metadata.name}"

# 배열에서 조건에 맞는 요소만 필터링
kubectl get pod sample-pod \
  -o jsonpath="{.spec.containers[?(@.name == 'nginx-container')].image}"

# Go Template: 반복문, 조건문 등 제어 구문까지 사용 가능
kubectl get pods -o go-template="{{range .items}}{{.metadata.name}}: \
{{range .spec.containers}}{{.image}}{{end}} {{end}}"
```

> alias를 걸어두면 편합니다. 예: `alias kpod='kubectl get pods -o custom-columns="..."'`

`all`을 지정하면 all 카테고리에 속하는 리소스 목록을 한 번에 가져옵니다. 다만 시크릿, 컨피그맵, 인그레스 등 자주 쓰는데도 표시되지 않는 리소스가 있습니다.

```bash
kubectl get all

# 모든 리소스 목록을 가져오기
kubectl get $(kubectl api-resources --namespaced=true --verbs=list -o name \
  | tr '\n' ',' | sed -e 's|,$||g')
```

`--watch` 옵션으로 상태 변화를 계속 출력할 수 있습니다. 디플로이먼트나 레플리카셋의 레플리카 수 변화 추이를 볼 때 유용합니다.

```bash
kubectl get pods --watch

# 어떤 처리가 되었는지 이벤트(ADDED/MODIFIED/DELETED)까지 함께 표시
kubectl get pods --watch --output-watch-events
```

### 4.5.17 리소스 상세 정보 가져오기: describe

`get`으로 볼 수 있는 정보 외에 리소스 관련 **이벤트** 등 더 상세한 정보를 확인합니다. 파드를 지정하면 Events 항목 아래에 볼륨 셋업이나 이미지 다운로드 상태 등 컨테이너 라이프사이클 정보가 표시됩니다.

```bash
kubectl describe pod sample-pod
kubectl describe node gke-k8s-default-xxxxxxxx-377p
```

노드를 지정하면 리소스 사용 현황, 여유 리소스, 기동 중인 파드 리소스 사용량이 표시됩니다.

### 4.5.18 실제 리소스 사용량 확인: top

`describe`로 보이는 값은 쿠버네티스가 파드에 **확보한** 값입니다. 컨테이너가 **실제로** 쓰고 있는 양은 `kubectl top`으로 확인합니다. 노드와 파드 단위로 볼 수 있습니다.

> `top` 명령어는 **metrics-server** 라는 추가 구성 요소를 사용합니다. 일반적인 환경이면 배포되어 있지만, 없으면 수동으로 배포해야 합니다.

```bash
# 노드별 사용량과 사용률
kubectl top node

# 파드별 사용량
kubectl -n kube-system top pod

# 파드 내 컨테이너별 사용량
kubectl -n kube-system top pod --containers
```

### 4.5.19 컨테이너에서 명령어 실행: exec

파드 내부 컨테이너에서 명령어를 실행합니다. `/bin/bash` 등 셸을 실행하면 컨테이너에 로그인한 것 같은 상태가 됩니다.

```bash
# 파드 내부 컨테이너에서 /bin/ls 실행
$ kubectl exec -it sample-pod -- /bin/ls
bin  dev  home  lib64  mnt  proc  run  srv  tmp  var
boot etc  lib   media  opt  root  sbin sys  usr
```

- `-t`: 가상 터미널 생성
- `-i`: 표준 입출력 패스스루
- 둘을 함께 쓰고 `/bin/sh`를 기동하면 SSH로 로그인한 것과 비슷한 상태가 됩니다.
- 예전에는 `--`를 생략해도 됐지만 지금은 **필수**입니다.

### 4.5.21 로컬 머신에서 파드로 포트 포워딩: port-forward

디버깅 용도로 JMX 클라이언트에서 컨테이너의 자바 애플리케이션 서버에 붙거나, DB 클라이언트에서 컨테이너의 MySQL에 접속해야 할 때가 있습니다. 이때 로컬 머신에서 특정 파드로 트래픽을 전송합니다(그림 4-16).

```bash
$ kubectl apply -f sample-pod.yaml
pod/sample-pod created

# localhost:8888 에서 파드의 80/TCP 포트로 전송 (종료는 Ctrl + C)
$ kubectl port-forward sample-pod 8888:80
Forwarding from 127.0.0.1:8888 -> 80
Forwarding from [::1]:8888 -> 80

# 다른 터미널에서 접속 확인
$ curl -I localhost:8888
HTTP/1.1 200 OK
Server: nginx/1.16.1
```

실행 중에는 로컬 머신 브라우저에서도 접속할 수 있습니다.

파드명이 아니라 디플로이먼트나 서비스 리소스에도 포트 포워딩을 걸 수 있습니다. 다만 통신이 여러 파드로 **분산되지 않고**, `port-forward`를 실행할 때 선택된 파드 하나로만 전송됩니다. 실행 중 통신 가능한 파드는 항상 같은 파드 하나뿐입니다(그림 4-17).

### 로그 확인 도구: stern

여러 컨테이너의 로그를 색으로 구분해 시각화해주며, 하나의 콘솔에서 시계열로 표시합니다(그림 4-18).

```bash
# 맥 운영체제
brew install stern

# 리눅스 (버전 1.11.0 예시)
VERSION=1.11.0
sudo curl -L https://github.com/wercker/stern/releases/download/${VERSION}/stern_linux_amd64 \
  -o /usr/local/bin/stern
sudo chmod 755 /usr/local/bin/stern
```

파드명을 **부분 일치**로 검색하면 일치하는 파드가 전부 출력됩니다. 예를 들어 `sample-deployment`라는 디플로이먼트가 만드는 파드명은 `sample-deployment-7bb5fc6bc6-27p95`처럼 '디플로이먼트 이름 + 해시값 + 난수' 구성이므로, `stern sample-deployment-`로 실행하면 그 디플로이먼트가 생성한 전체 파드의 로그를 볼 수 있습니다.

`kubectl logs`로 할 수 있는 모든 작업이 가능하고, 추가로 다음 기능을 제공합니다.

- 각 컨테이너 로그를 시계열로 표시
- 타임스탬프 표시 (`--timestamps`)
- 특정 레이블로 지정한 파드 로그만 표시 (`--selector`)
- 예외 처리할 로그를 정규 표현식으로 지정 (`--exclude`)

| `modify-secret` | Base64 디코드된 상태로 시크릿을 edit |
| `konfig` | kubeconfig를 병합 |
| `view-serviceaccount-kubeconfig` | 특정 ServiceAccount의 kubeconfig를 생성 |
| `rolesum` | ServiceAccount나 Group에 할당된 RBAC 설정값을 행렬로 시각화 |
| `who-can` | 지정한 권한을 가진 ServiceAccount나 사용자를 표시 |

### 4.5.26 kubectl에서 디버깅

kubectl은 마스터의 API와 통신하므로, 에러가 나면 API 통신이나 kubectl 설정에 문제가 있는 경우가 대부분입니다. `-v` 옵션으로 로그 레벨을 지정하면 실행 내용을 상세히 볼 수 있습니다. HTTP Request/Response 내용까지 보려면 `-v=6` 이상으로 설정합니다.

```bash
kubectl -v=6 get pod
```

**파드가 기동하지 않는 경우**

| 방법 | 유용한 상황 |
|---|---|
| `kubectl logs` | 애플리케이션에 문제가 있을 때 |
| `kubectl describe`의 Events 항목 | 쿠버네티스 설정이나 리소스 설정에 문제가 있을 때 |
| `kubectl run`으로 실제 컨테이너 셸 확인 | 컨테이너 환경이나 애플리케이션에 문제가 있을 때 |

`describe`의 에러 메시지로 판별 가능한 원인:

- 리소스 부족으로 스케줄링이 불가능
- 스케줄링 정책에 해당하는 노드가 존재하지 않음
- 볼륨 마운트 실패

애플리케이션이 정지하면 파드도 정지해서 `exec`로 셸을 실행할 수 없습니다. 그럴 때는 ENTRYPOINT를 덮어써서 일시적으로 컨테이너를 기동시켜 확인합니다.

```bash
# nginx 이미지로 웹 서버가 아닌 셸을 기동 (종료 후 파드는 삭제됨)
kubectl run --image=nginx:1.16 --restart=Never --rm -it sample-debug \
  --command -- /bin/sh
```

### 4.5.27 kubectl의 기타 팁

**alias 생성**

```bash
# kubectl 명령어를 k로 사용
$ alias k='kubectl'

# 리소스 종류도 약어 사용 가능 (pods -> po)
$ k get po
NAME          READY   STATUS    RESTARTS   AGE
sample-pod    1/1     Running   2          2d1h
```

더 많은 alias를 한 번에 만들어주는 **kubectl-aliases** 도 있습니다.

**kube-ps1**

bash나 zsh 프롬프트에 현재 작업 중인 클러스터와 네임스페이스를 표시합니다. 여러 클러스터나 네임스페이스를 오갈 때 실수를 줄일 수 있습니다.

```bash
# 맥 운영체제 설치
brew update
brew install kube-ps1

# ~/.zshrc 또는 ~/.bashrc 에 추가
source "/usr/local/opt/kube-ps1/share/kube-ps1.sh"
PS1='$(kube_ps1)'$PS1
```

```bash
# 표시 기능 활성화 / 비활성화
kubeon
kubeoff
```

활성화하면 프롬프트가 아래처럼 바뀝니다.

```text
(⎈ |gke_GCP_PROJECT_asia-northeast3-a_k8s:default) $ kubectl ...
```

## 정리

- 클러스터 조작은 전부 마스터 API를 거치며, kubectl은 그 API를 감싼 CLI
- 리소스는 워크로드 / 서비스 / 컨피그 & 스토리지 / 클러스터 / 메타데이터 5개 카테고리
- 네임스페이스는 가상 분리이며 완전한 격리가 아니므로 RBAC, 네트워크 정책과 함께 사용
- 환경 분리는 네임스페이스보다 클러스터 단위 권장
- 생성이든 업데이트든 `kubectl apply` 하나로 통일
- 여러 주체가 같은 필드를 건드리면 Server-side apply로 충돌을 감지
- `kubectl wait`로 다음 명령 전 리소스 상태를 보장
- 매니페스트 설계는 통합 / 서브 시스템 분리 / 마이크로서비스별 분리 세 패턴 중 선택
- 어노테이션은 시스템 구성 요소용 메타데이터, 레이블은 리소스를 구분하고 그룹핑하는 메타데이터
- 레이블은 ReplicaSet과 Service의 동작 조건이 되므로 지정 정책을 미리 정해둘 것
- 조회 계열 명령어: `get`(목록, 출력 형식), `describe`(이벤트 포함 상세), `top`(실제 사용량), `diff`(로컬과 클러스터 차이)
- 디버깅은 `logs` / `describe`의 Events / `run`으로 셸 확인, 통신 문제는 `-v=6` 이상

> 더 자세한 내용은 `kubectl get --help`처럼 명령어 뒤에 `--help`를 붙이면 예제와 함께 출력됩니다.
