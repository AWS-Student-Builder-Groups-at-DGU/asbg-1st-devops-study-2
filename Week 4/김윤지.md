### 4.1.2 쿠버네티스(GKE) 클러스터 생성

```bash
# GKE에서 사용 가능한 쿠버네티스 버전 확인
gcloud container get-server-config --zone asia-northeast3-a
# → channels(RAPID/REGULAR/STABLE)별 defaultVersion,
#   validMasterVersions, validNodeVersions 목록이 출력된다

# GKE 클러스터 'k8s' 생성
$ gcloud container clusters create k8s \
  --cluster-version 1.18.16-gke.2100 \  # validMasterVersions에 있는 버전 지정
  --zone asia-northeast3-a \            # 존 설정
  --num-nodes 3 \                       # 노드 수
  --machine-type n1-standard-4 \        # 인스턴스 유형 지정
  --enable-network-policy \             # 네트워크 정책 기능 활성화
  --enable-vertical-pod-autoscaling     # VerticalPodAutoscaler 활성화

# GKE 클러스터 'k8s'에 접속하는 인증 정보를 다시 가져오는 방법
$ gcloud container clusters get-credentials k8s --zone asia-northeast3-a
Fetching cluster endpoint and auth data.
kubeconfig entry generated for k8s.
```

```bash
  --zone asia-northeast3-a \
  --workload-metadata=GKE_METADATA
```

## 4.2 쿠버네티스 기초

쿠버네티스는 **쿠버네티스 마스터**와 **쿠버네티스 노드**로 구성된다

- **마스터**: API 엔드포인트 제공, 컨테이너 스케줄링, 컨테이너 스케일링 등을 담당하는 노드
- **노드**: 이른바 도커 호스트에 해당하며 실제로 컨테이너를 기동시키는 노드

클러스터를 관리하려면 CLI 도구인 kubectl과 YAML/JSON 형식의 **매니페스트 파일**로 마스터에 '리소스'를 등록해야 한다. 매니페스트는 가독성 때문에 보통 YAML로 작성하며 확장자
.yaml / .yml / .json으로 구분된다.

kubectl은 매니페스트 정보를 바탕으로 마스터의 API에 요청을 보낸다. 쿠버네티스 API는 일반적으로 **RESTful API**로 구현되어 있으므로, kubectl을 쓰지 않고 각종 프로그래밍 언어의 REST 라이브러리나 `curl` 같은 명령어 도구로 직접 API를 호출해 관리할 수도 있다.

```bash
kubectl create -f sample.yaml
```

## 4.3 쿠버네티스와 리소스

쿠버네티스가 다루는 리소스는 다섯 가지 카테고리로 분류된다

쿠버네티스는 이러한 리소스 등록을 **비동기로** 처리한다 (등록 즉시 완료되는건 x)

| 종류                           | 개요                                                    |
| ------------------------------ | ------------------------------------------------------- |
| 워크로드 API 카테고리          | 컨테이너 실행에 관련된 리소스                           |
| 서비스 API 카테고리            | 컨테이너를 외부에 공개하는 엔드포인트를 제공하는 리소스 |
| 컨피그 & 스토리지 API 카테고리 | 설정/기밀 정보/영구 볼륨 등에 관련된 리소스             |
| 클러스터 API 카테고리          | 보안이나 쿼터 등에 관련된 리소스                        |
| 메타데이터 API 카테고리        | 클러스터 내부의 다른 리소스를 관리하기 위한 리소스      |

이 중 애플리케이션 개발자가 주로 사용하는 카테고리는 **워크로드 / 서비스 / 컨피그 & 스토리지
3종류**

### 4.3.1 워크로드 API 카테고리

클러스터 위에서 컨테이너를 기동하기 위해 사용되는 리소스, 사용자가 직접 관리하는 것은 8가지

- 파드(Pod)
- 레플리케이션 컨트롤러(ReplicationController)
- 레플리카셋(ReplicaSet)
- 디플로이먼트(Deployment)
- 데몬셋(DaemonSet)
- 스테이트풀셋(StatefulSet)
- 잡(Job)
- 크론잡(CronJob)

### 4.3.2 서비스 API 카테고리

컨테이너의 서비스 디스커버리와, 클러스터 외부에서도 접속 가능한 엔드포인트를 제공하는 리소스
사용자가 직접 관리하는 것은 **서비스**와 **인그레스** 2종류

서비스에는 엔드포인트 제공 방식이 다른 여러 타입이 있음

- 서비스
  - ClusterIP
  - ExternalIP (ClusterIP의 한 종류)
  - NodePort
  - LoadBalancer
  - Headless(None)
  - ExternalName
  - None-Selector
- 인그레스

### 4.3.3 컨피그 & 스토리지 API 카테고리

설정과 기밀 데이터를 컨테이너에 담거나 영구 볼륨을 제공하는 리소스, 시크릿과 컨피그맵은 모두 key-value 형태이며, **저장할 데이터가 기밀인지 일반 설정인지에 따라 구분됨.** 영구 볼륨
클레임은 컨테이너에서 영구 볼륨을 요청할 때 사용함

- 시크릿(Secret)
- 컨피그맵(ConfigMap)
- 영구 볼륨 클레임(PersistentVolumeClaim)

### 4.3.4 클러스터 API 카테고리

클러스터 자체 동작을 정의하는 리소스, 보안 관련 설정이나 정책, 클러스터 관리성을 향상시키는 기능을 위한 리소스 등이 있다

- 노드(Node)
- 네임스페이스(Namespace)
- 영구 볼륨(PersistentVolume)
- 리소스 쿼터(ResourceQuota)
- 서비스 어카운트(ServiceAccount)
- 롤(Role)
- 클러스터 롤(ClusterRole)
- 롤바인딩(RoleBinding)
- 클러스터롤바인딩(ClusterRoleBinding)
- 네트워크 정책(NetworkPolicy)

### 4.3.5 메타데이터 API 카테고리

클러스터 내부의 **다른 리소스의 동작을 제어**하기 위한 리소스. 예를 들어 HPA는 디플로이먼트
리소스를 조작해 레플리카 수를 변경함으로써 오토 스케일링을 구현한다.

- LimitRange
- HorizontalPodAutoscaler(HPA)
- PodDisruptionBudget(PDB)
- 커스텀 리소스 데피니션(CustomResourceDefinition)

## 4.4 네임스페이스로 가상적인 클러스터 분리

**네임스페이스(NameSpace)** 는 가상적인 클러스터 분리 기능이다. 완전한 분리 개념이 아니라
용도는 제한되지만, 하나의 클러스터를 여러 팀이 쓰거나 서비스/스테이징/개발 환경으로 구분할 때 사용할 수 있다.

**[기본 설정에서 생성되는 네임스페이스 네 가지]**

- **kube-system:** 클러스터 구성 요소와 애드온이 배포될 네임스페이스(대시보드 등)
- **kube-public:** 모든 사용자가 사용할 수 있는 컨피그맵 등을 배치하는 네임스페이스
- **kube-node-lease:** 노드 하트비트 정보(Lease 리소스)가 저장되는 전용 네임스페이스.
  클러스터 관리자 이외에는 신경 쓰지 않아도 된다.
- **default:** 기본 네임스페이스. 사용자가 임의의 리소스를 등록하는 데 쓴다.

목적에 따라 임의의 네임스페이스를 만들 수 있지만, **하나의 클러스터를 여러 목적의 공용으로
쓰지 않고 시스템이 복잡하지 않다면 기본 네임스페이스를 그대로 써도 된다.**

관리형 서비스나 구축 도구로 만든 대부분의 클러스터는 **RBAC**가 기본값으로 활성화되어 있고,
일부 환경에서는 **네트워크 정책**도 쓸 수 있다. RBAC는 클러스터 조작 권한을 네임스페이스별로
구분하고, 네트워크 정책과 함께 쓰면 네임스페이스 간 통신을 제어할 수 있다(그림 4-2).
**네임스페이스만으로는 높은 분리성을 확보하기 어렵지만 RBAC나 네트워크 정책을 쓰면 분리성을 높일 수 있다.**

- 권한 분리 관점에서 **마이크로서비스를 개발하는 팀마다** 네임스페이스를 분리하는 것이 좋다.
- 서비스/스테이징/개발 환경은 네임스페이스가 아니라 **클러스터별로** 나눠야 한다.
  - 클러스터 업그레이드 시 동시에 모든 환경에서 장애가 발생할 가능성이 있다.
  - 네임스페이스 명명 규칙이 `prd-ns1`/`stg-ns1`처럼 되면 **매니페스트 재사용성이 현저하게 저하된다.** 클러스터를 분리하면 각 환경에서 같은 네임스페이스 이름을 쓸 수 있어 완전히 같은 매니페스트를 재사용할 수 있다.
  - 서비스 이름 해석 시 `SERVICE.prd-ns1.svc.cluster.local` 등 다른 목적지로 통신해야 한다.

## 4.5 커맨드 라인 인터페이스(CLI) 도구 kubectl

클러스터 조작은 모두 마스터의 API를 통해 이루어진다. API에 직접 요청을 보내거나 클라이언트 라이브러리를 쓸 수도 있지만, **수동으로 조작하는 경우에는 `kubectl`을 쓰는 것이 일반적**

### 4.5.1 인증 정보와 컨텍스트(config)

kubectl이 마스터와 통신할 때는 접속 대상 서버 정보와 인증 정보가 필요하다. kubectl은
**kubeconfig**(기본 위치 `~/.kube/config`)의 정보를 사용해 접속한다. kubeconfig도 매니페스트와 동일한 형식으로 작성된다.

쿠버네티스 마스터에 접속하기 위한 인증 정보 예제(kubeconfig)

```yaml
apiVersion: v1
kind: Config
preferences: {}
clusters: # 접속 대상 클러스터
  - name: sample-cluster
    cluster:
      server: <https://localhost:6443>
users: # 인증 정보
  - name: sample-user
    user:
      client-certificate-data: LS0tLS1CRUdJTi...
      client-key-data: LS0tLS1CRUdJTi...
contexts: # 접속 대상과 인증 정보 조합
  - name: sample-context
    context:
      cluster: sample-cluster
      namespace: default
      user: sample-user
current-context: sample-context
```

설정이 이루어지는 부분은 **clusters / users / contexts** 세 가지이며, 모두 배열이므로 여러
대상을 등록할 수 있다. clusters에는 접속 대상 클러스터 정보, users에는 인증 정보를 정의한다.
사용자 인증에는 X.509 클라이언트 인증서 / 토큰 / 패스워드 / 웹훅 등 다양한 방식을 쓸 수 있다. contexts에는 cluster와 user, 네임스페이스를 지정한 것을 정의한다.

kubeconfig는 직접 편집해도 되지만 kubectl 명령어로 바꾸면 파일이 자동으로 갱신된다.

```bash
# 클러스터(prd-cluster) 정의를 추가, 변경
$ kubectl config set-cluster prd-cluster \
  --server=https://localhost:6443

# 인증 정보 정의를 추가, 변경
$ kubectl config set-credentials admin-user \
  --client-certificate=./sample.crt \
  --client-key=./sample.key \
  --embed-certs=true

# 컨텍스트 정의(클러스터/인증 정보/네임스페이스 정의)를 추가, 변경
$ kubectl config set-context prd-admin \
  --cluster=prd-cluster \
  --user=admin-user \
  --namespace=default
```

kubectl은 **컨텍스트(current-context)를 전환하여** 여러 환경을 여러 권한으로 조작할 수 있도록 설계되어 있다.

```bash
# 컨텍스트 목록 표시
$ kubectl config get-contexts
CURRENT   NAME             CLUSTER          AUTHINFO         NAMESPACE
*         docker-desktop   docker-desktop   docker-desktop
          prd-admin        prd-cluster      admin-user       default

# 컨텍스트 전환
$ kubectl config use-context prd-admin
Switched to context "prd-admin".
```

### 4.5.3 리소스 생성/삭제/갱신 (create / get / delete / apply)

sample-pod.yaml

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-pod
spec:
  containers:
    - name: nginx-container
      image: nginx:1.16
```

```bash
# 생성 - 이미 있으면 AlreadyExists 에러
$ kubectl create -f sample-pod.yaml
pod/sample-pod created

# 확인
$ kubectl get pods

# 삭제 - 없으면 NotFound 에러
$ kubectl delete -f sample-pod.yaml
$ kubectl delete pod sample-pod
$ kubectl delete pod --all

# 삭제 완료까지 대기
$ kubectl delete -f sample-pod.yaml --wait

# 즉시 강제 삭제(정상 종료 처리를 기다리지 않음)
$ kubectl delete -f sample-pod.yaml --grace-period 0 --force
```

`apply`는 매니페스트에 정의된 상태와 실제 상태의 차이만 반영함 (선언형 갱신)

```bash
# 변경 전 매니페스트를 백업해 차이를 확인해 보자
$ cp -av sample-pod.yaml{,.old}
# (여기서 image를 nginx:1.16 → nginx:1.17 등으로 수정)
$ diff sample-pod.yaml.old sample-pod.yaml

# apply — 상황에 따라 created / configured / unchanged 로 출력이 달라진다
$ kubectl apply -f sample-pod.yaml
pod/sample-pod configured

# 특정 필드만 뽑아 실제로 바뀌었는지 확인
$ kubectl get pod sample-pod \
  -o jsonpath="{.spec.containers[?(@.name=='nginx-container')].image}"
```

`create`와 `apply`의 관계에서 핵심은 **`kubectl.kubernetes.io/last-applied-configuration` 어노테이션**이다. `apply`는 이전에 적용한 매니페스트를 이 어노테이션에 저장해 두고, <이전 매니페스트 / 현재 매니페스트 / 실제 리소스> 세 가지를 비교하는 **three-way merge**로 차이를 계산한다. 그래서 매니페스트에서 필드를 **삭제**한 경우에도 그 필드를 지울 수 있다.

반면 `create`로 만든 리소스에는 이 어노테이션이 없으므로 이후 `apply`가 예상과 다르게
동작할 수 있다 → **처음부터 `apply`로 일관되게 관리하는 것이 권장됨**

### 4.5.5 Server-side apply

기존 apply는 클라이언트(kubectl)가 병합을 계산했는데, Server-side apply는 **서버(마스터)가** 병합을 수행하고, 어떤 필드를 어떤 도구가 관리하는지를 `metadata.managedFields`에 기록한다.

```bash
# 원래 매니페스트로 되돌려 두고 시작
$ cp -av sample-pod.yaml{.old,}

$ kubectl apply -f sample-pod.yaml --server-side

# 다른 방법(kubectl set)으로 이미지를 바꿔 필드 소유자를 바꿔 본다
$ kubectl set image pod sample-pod nginx-container=nginx:1.17

# 다시 server-side apply → 필드 소유자가 다르므로 conflict 에러
$ kubectl apply -f sample-pod.yaml --server-side

# 강제로 소유권을 가져오기
$ kubectl apply -f sample-pod.yaml --server-side --force-conflicts

# 어떤 도구가 어떤 필드를 관리하는지 확인
$ kubectl get pod sample-pod -o yaml   # metadata.managedFields 확인

# 필드 관리자 이름을 지정(CI 파이프라인 등에서 유용)
$ kubectl apply -f sample-pod.yaml --server-side --field-manager ci-tool
```
