## 4.2 쿠버네티스 기초 구조

| 구성 | 역할 |
|---|---|
| 쿠버네티스 마스터 | API 엔드포인트 제공, 스케줄링, 스케일링 담당 |
| 쿠버네티스 노드 | 도커 호스트에 해당. 실제 컨테이너 기동 |
<img width="315" height="425" alt="image" src="https://github.com/user-attachments/assets/76ac2c19-b797-493a-ab79-a9380f7ea314" />

- 클러스터 관리 = kubectl과 매니페스트(YAML/JSON)로 작성된 파일을 이용해 마스터에 리소스 등록(API로 요청)
- 쿠버네티스 API는 RESTful → kubectl 없이 curl/클라이언트 라이브러리로도 조작 가능
- 매니페스트는 가독성 때문에 보통 YAML 사용

## 4.3 리소스 카테고리 (5종)

| 카테고리 | 개요 |
|---|---|
| 워크로드 API | 컨테이너 실행 관련 | 
| 서비스 API | 컨테이너를 외부에 공개하는 엔드포인트 |
| 컨피그 & 스토리지 API | 설정/기밀 정보/영구 볼륨 |
| 클러스터 API | 보안·쿼터 등 클러스터 자체 동작 |
| 메타데이터 API | 클러스터 내부의 다른 리소스를 제어 |

개발자가 이중 주로 사용하는 리소스 카테고리는 워크로드/ 서비스/ 컨피그 & 스토리지 세 종류라고 한다
### 각 API 카테고리에 속하는 리소스(내부적으로 사용되는 리소스는 제외)
1. **워크로드(8종)**
- Pod, ReplicationController, ReplicaSet, Deployment, DaemonSet, StatefulSet, Job, CronJob
2.  **서비스**: 
- Service(ClusterIP / ExternalIP / NodePort / LoadBalancer / Headless(None) / ExternalName / None-Selector), Ingress
  - ExternalIP·None-Selector는 엄밀히는 type이 아니지만 책에서는 타입으로 소개
3. **컨피그 & 스토리지**: 
- Secret, ConfigMap, PersistentVolumeClaim
  - Secret/ConfigMap 모두 키-밸류 구조. 기밀 여부로 구분
3. **클러스터**: 
- Node, Namespace, PersistentVolume, ResourceQuota, ServiceAccount, Role, ClusterRole, RoleBinding, ClusterRoleBinding, NetworkPolicy
4. **메타데이터**: 
- LimitRange, HorizontalPodAutoscaler(HPA), PodDisruptionBudget(PDB), CustomResourceDefinition(CRD)
  - 예: HPA는 Deployment의 replicas를 조작해 오토 스케일링 구현

## 4.4 네임스페이스
쿠버네티스에는 **네임스페이스(Namespace)** 라고 불리는 가상적인 클러스터 분리 기능이 있다.

- **완전한 분리 개념이 아니기 때문에 용도는 제한된다**
- 주로 쓰이는 경우
  - 하나의 클러스터를 여러 팀이 나눠 쓸 때
  - 서비스 환경 / 스테이징 환경 / 개발 환경을 구분할 때

- 기본 생성되는 4개:kube-system, kube-public, kube-node-lease, default

| 네임스페이스 | 용도 |
|---|---|
| kube-system | 클러스터 구성 요소·애드온 배포 (대시보드 등) |
| kube-public | 모든 사용자가 공용으로 쓰는 ConfigMap 등 |
| kube-node-lease | 노드 하트비트(Lease 리소스) 저장 전용 |
| default | 기본 네임스페이스 |

<img width="476" height="398" alt="image" src="https://github.com/user-attachments/assets/85297f13-6ff8-4906-8f99-ba4ef714791a" />

### 네임스페이스만으로는 부족하다 — RBAC / 네트워크 정책

관리형 서비스나 구축 도구로 만든 대부분의 클러스터는 **RBAC(Role-Based Access Control)이 기본값으로 활성화**되어 있고, 일부 환경에서는 네트워크 정책도 사용할 수 있다. 

- **RBAC** → 클러스터 조작에 대한 **권한**을 네임스페이스별로 구분
- **네트워크 정책** → 네임스페이스 간 **통신**을 제어

### 네임스페이스 분리 범위
- 마이크로서비스를 개발하는 팀마다 분리
- 서비스/스테이징/개발환경은 네임스페이스가 아닌 클러스터별로 나눠야함

1. **클러스터 업그레이드 시 동시에 모든 환경에서 장애가 발생할 가능성이 있다.**
2. **매니페스트 재사용성이 현저히 저하된다.**
   - 네임스페이스 명명 규칙이 `prd-ns1` / `stg-ns1`처럼 되어버림
   - 클러스터를 분리하면 각 환경에서 **같은 네임스페이스 이름을 쓸 수 있어 완전히 동일한 매니페스트를 재사용**할 수 있다
3. **서비스 이름 해석 시 목적지가 달라진다.**
   - `SERVICE.prd-ns1.svc.cluster.local` 처럼 환경마다 다른 FQDN으로 통신해야 함

## 4.5 kubectl 요약
앞서 쿠버네티스에서 클러스터 조작은 모두 마스터의 API로 이루어짐
-> curl, 클라이언트 라이브러리를 사용하여 클러스터를 조작할 수 있지만 kubectl을 사용하는것이 일반적이다

### 인증 정보와 컨텍스트 (kubeconfig)
- kubectl이 쿠버네티스 마스터와 통신하기 위해서는 대상의 서버 정보, 인증 정보등이 필요하며 리를 kubeconfig에 있는 정보를 사용하여 접속한다. kubeconfig또한 yaml같은 메니페스트와 동일한 형식으로 작성된다.
### kubeconfig 파일의 항목과 역할
<img width="451" height="224" alt="image" src="https://github.com/user-attachments/assets/b5124b9d-bc3a-4c58-bf35-d3d96164dcd8" />

|항목|역할|
|---|---|
|cluster|접속대상 클러스터 정보 정의|
|user|인증정보 정의|
|contexts|cluster, user, 네임스페이스를 지정한 것을 정의|

이 세가지 설정은 모두 배열로 되어있어 여러 대상 등록 가능


### 리소스 생성/삭제/갱신 명령어
| 명령어 | 동작 |
|---|---|
| `kubectl create -f x.yaml` | 파드 생성, 이미 있으면 AlreadyExists 에러 |
| `kubectl delete -f x.yaml` | 파드 삭제, 없으면 NotFound 에러. `kubectl delete pod NAME`, `--all`도 가능 |
| `kubectl apply -f x.yaml` | 변경 있으면 configured, 없으면 unchanged, 없으면 created |


### 이때 생성에도 create가 아닌 apply를 쓰는것이 좋음
1. 생성=create / 갱신=apply 라는 구분을 할 필요가 없어짐
2. create와 apply를 섞으면 **변경 사항 산출이 깨짐**

apply의 변경 사항은 세 가지를 비교해 산출:
- **추가/변경 필드** = 현재 클러스터 리소스 상태 ↔ 이번 매니페스트
- **삭제 필드** = 이전에 적용한 매니페스트 ↔ 이번 매니페스트



### 정리
- 상세는 `kubectl <command> --help` (예제까지 출력됨)
