## 2.1 쿠버네티스란?

- **쿠버네티스(Kubernetes, k8s)** = 컨테이너화된 애플리케이션의 **배포·확장·관리를 자동화**하기 위한 플랫폼(컨테이너 오케스트레이션 엔진).
- 배경: 도커(Docker) 같은 컨테이너 런타임은 **단독으로는 여러 호스트를 통합 관리할 수 없음** → 일정 규모 이상의 서비스 환경을 구축하려면 오케스트레이션 엔진이 필요.
- 경쟁 기술: 도커 스웜(Docker Swarm), 아파치 메소스(Apache Mesos) 등이 있으나, 현재는 **쿠버네티스가 사실상 표준(de facto standard)**.
- 쿠버네티스는 도커 외에도 **containerd, CRI-O** 등 다양한 컨테이너 런타임을 CRI(Container Runtime Interface)를 통해 지원.
- 핵심 용어
    - **노드(Node)**: 컨테이너가 실제로 기동되는 물리/가상 머신
    - **마스터(Master, 컨트롤 플레인)**: 노드들을 관리하는 주체

---

## 2.2 쿠버네티스의 역사

- 구글이 내부적으로 사용하던 컨테이너 클러스터 관리 도구 **Borg**의 아이디어를 계승해 만든 오픈소스 프로젝트.
- **2014년 6월** 공개, **2015년 7월 v1.0** 발표와 함께 **CNCF(Cloud Native Computing Foundation)** 산하(리눅스 재단 소속)로 이관.
- CNCF는 프로젝트 성숙도를 3단계로 분류: **Sandbox → Incubating → Graduated**. 쿠버네티스는 최상위 단계인 **Graduated**.
- 관리형 쿠버네티스 서비스 등장 흐름
    - 2014.11 – Google **GKE**(Google Kubernetes Engine) 최초 출시
    - 2017.02 – Microsoft **AKS**(Azure Kubernetes Service, 2018.06 GA)
    - 2017.11 – AWS **EKS**(Elastic Kubernetes Service, 2018.06 GA)
    → 3대 퍼블릭 클라우드 모두 관리형 서비스를 갖추며 표준 지위 확립.

## 2.3 쿠버네티스를 사용하면 무엇을 할 수 있을까?

컨테이너 하나만으로는 어려운 아래와 같은 일들을 쿠버네티스가 **자동화·선언적으로** 해결해준다.

| 기능 | 요약 |
| --- | --- |
| 여러 노드 관리 | 다수의 쿠버네티스 노드를 클러스터로 통합 관리 |
| 컨테이너 스케줄링 | 애플리케이션 특성/노드 리소스에 맞춰 배치 위치 자동 결정 |
| 롤링 업데이트 | 무중단으로 애플리케이션 버전 교체 |
| 스케일링/오토스케일링 | 부하에 따라 레플리카 수 자동 증감 |
| 컨테이너 모니터링 | 프로세스 상태 지속 감시 |
| 자동화된 복구(Self-healing) | 장애 발생 시 자동 재배포 |
| 로드밸런싱 | 여러 레플리카에 트래픽 분산 |
| 데이터 관리 | 설정/시크릿/영구 데이터 관리 |
| 워크로드 관리 | 다양한 워크로드 유형(배치, 상시 실행 등) 지원 |
| 로그 관리 | 컨테이너 로그 수집/전달 체계 |
| 선언적 코드를 사용한 관리(IaC) | 매니페스트(YAML/JSON)로 원하는 상태 정의 |
| 에코시스템 연계·확장 | CRD/오퍼레이터 등으로 기능 확장 |

### 2.3.1 선언적 코드를 사용한 관리 (Infrastructure as Code)

- 쿠버네티스는 **YAML/JSON 형식의 선언적 매니페스트**를 통해 "원하는 상태(Desired State)"를 정의하고, 실제 상태를 그에 맞춰 자동으로 수렴시킨다.
- 예시 매니페스트(Deployment)의 핵심 필드: `apiVersion`, `kind`, `metadata`, `spec.selector`, `spec.template` 등.
- 기존 방식(AWS CloudFormation, OpenStack Heat 등)과 유사한 IaC 개념을 컨테이너 워크로드에 적용한 것.

### 2.3.2 스케일링/오토스케일링

- 동일한 컨테이너 이미지 기반의 **레플리카(Replica)**를 여러 개 배포해 부하 분산·다중화 구현.
- 부하에 따라 레플리카 수를 **자동으로 늘리거나 줄이는 오토스케일링** 지원.

### 2.3.3 스케줄링

- 컨테이너를 어떤 노드에 배포할지 결정하는 단계.
- **어피니티(Affinity) / 안티 어피니티(Anti-Affinity)** 기능으로 워크로드 특성이나 노드 성능 기준 배치 제어 가능 (예: 디스크 I/O가 많은 컨테이너 → 디스크 성능 좋은 노드).
- 클라우드(GCP/AWS 등) 환경에서는 **가용 영역(Availability Zone)** 정보를 활용해 멀티 AZ 분산 배치 가능.
- 별도 지정이 없으면 CPU/메모리 등 **여유 리소스 상태 기준으로 자동 스케줄링** → 사용자가 직접 배치 위치를 관리할 필요 없음.
- 클러스터 오토스케일러 등을 통해 **노드 자체도 자동으로 추가/삭제** 가능 (리소스 관리).

### 2.3.5 자동화된 복구 (Self-healing)

- 컨테이너 프로세스를 표준적으로 모니터링하고, 정지가 감지되면 자동으로 재배포.
- 노드 장애·축출 시에도 서비스 영향 없이 자동 복구.
- 프로세스 감시 외에 **HTTP/TCP 체크, 셸 스크립트 기반 헬스체크**로 정상 여부 판단 가능 (→ 이후 챕터의 Liveness/Readiness Probe로 이어짐).

### 2.3.6 로드밸런싱과 서비스 디스커버리

- **서비스(Service)** / **인그레스(Ingress)** 리소스로 로드밸런싱 기능 제공.
- 조건에 맞는 컨테이너 그룹으로 라우팅되는 엔드포인트를 할당하고, 컨테이너 확장/장애/롤링 업데이트 시 **자동 등록·해제** 처리.
- 마이크로서비스 아키텍처에서 서비스 간 상호 참조를 쉽게 해주는 **서비스 디스커버리** 기능도 함께 제공.

### 2.3.7 데이터 관리

- 클러스터 상태 저장에 **etcd**(분산 key-value 스토어)를 사용, 이중화 구성 가능.
- 설정 파일·인증 정보 등을 저장하는 구조도 별도로 존재 (→ 이후 챕터의 **ConfigMap / Secret**으로 이어짐).

### 에코시스템 연계 예시

쿠버네티스는 독립 플랫폼으로도, 다양한 미들웨어/도구와 연계해서도 사용 가능. 책에서 언급된 예:
Ansible, Apache Ignite, Fluentd(td-agent), GitLab, Jenkins, OpenStack, Prometheus, Spark, Spinnaker, Kubeflow, Rook, Vitess 등.

---

## 2.4 정리

- 컨테이너를 서비스 환경에서 운영하려면 컨테이너와 그 주변 리소스를 관리하는 복잡한 기능이 필요한데, 쿠버네티스는 이를 **사전에 구현된 자동화 기능**으로 제공한다.
- 과거에는 CloudFormation, 로드밸런서 수동 구성, 자체 배포 스크립트 등으로 직접 구현해야 했던 것을, 쿠버네티스는 **컨테이너의 이동성·경량성**을 살려 빠른 개발과 배포 자동화로 실현.
- 자체 배포 스크립트 등도 쿠버네티스·에코시스템에서 **공통으로 재사용 가능**하다는 것이 큰 장점.
