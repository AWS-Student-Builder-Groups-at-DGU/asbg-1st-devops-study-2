## 2.1 쿠버네티스란

컨테이너화된 애플리케이션의 **배포, 확장, 운영을 자동화하는 플랫폼**입니다.
즉, 컨테이너 오케스트레이션 엔진에 해당합니다.

### 도커 단독 사용의 한계
| 항목 | 도커 단독 | 쿠버네티스 |
|:---|:---|:---|
| 관리 대상 | 도커가 설치된 단일 호스트 | 여러 노드로 구성된 클러스터 |
| 중앙 통합 관리 | 불가 | 가능 |
| 일정 규모 이상 서비스 환경 | 구축 난이도 높음 | 표준적인 구성 방식 |

> [!NOTE]
> 오케스트레이션 엔진에는 도커 스웜, 아파치 메소스도 있으나
> 현재 서비스 환경에서 가장 많이 쓰이는 것은 쿠버네티스이며 사실상 표준으로 자리잡았습니다.

### 구성 용어
| 용어 | 설명 |
|:---|:---|
| 쿠버네티스 노드 | 실제 컨테이너가 기동되는 물리 머신 또는 가상 머신 |
| 쿠버네티스 마스터 | 노드를 관리하고 제어하는 컨트롤 플레인 |
| 컨테이너 런타임 | 도커 외에 containerd, cri-o 등 선택 가능 |

<br>

## 2.2 쿠버네티스의 역사

구글 내부의 컨테이너 클러스터 관리 도구 **Borg**에서 아이디어를 얻어 만들어진 오픈 소스입니다.

### 타임라인
| 시점 | 내용 |
|:---|:---|
| 2014.06 | 오픈 소스로 공개 |
| 2014.11 | GCP가 GKE(구 Google Container Engine) 제공 시작 |
| 2015.07 | v1.0 도달, 리눅스 재단 산하 CNCF로 이관 |
| 2015.08 | GKE GA |
| 2017.02 | Azure Container Service(구 AKS) 출시 |
| 2017.11 | AWS EKS 출시 |
| 2018.06 | AKS, EKS GA |

### CNCF 프로젝트 성숙도
높은 순서대로 다음과 같이 분류되며, 쿠버네티스는 **Graduated** 단계입니다.

| 단계 | 의미 |
|:---|:---|
| Graduated | 품질, 프로젝트 활성도, 운영 프로세스 명확성까지 성숙도를 인정받은 상태 |
| Incubating | 성장 중인 프로젝트 |
| Sandbox | 초기 단계 프로젝트 |

> [!TIP]
> Graduated가 "졸업"을 뜻하지만 CNCF 호스팅이 종료된다는 의미는 아닙니다.

사실상 표준이 된 배경에는 주요 클라우드 사업자가 모두 **관리형 쿠버네티스 서비스**를 제공한다는 점이 크게 작용했습니다.

<br>

## 2.3 쿠버네티스로 할 수 있는 것

컨테이너는 "애플리케이션을 실행하도록 빌드된 이미지를 기반으로 기동된 워크로드"입니다.
도커만으로도 배포는 쉽지만, 실제 서비스 환경에서는 다음 과제가 함께 발생합니다.

<details>
<summary><b>컨테이너 운영에서 고려해야 하는 과제 목록</b></summary>

- 여러 노드 관리
- 컨테이너 스케줄링
- 롤링 업데이트
- 스케일링 / 오토 스케일링
- 컨테이너 모니터링
- 자동화된 복구
- 서비스 디스커버리
- 로드 밸런싱
- 데이터 관리
- 워크로드 관리
- 로그 관리
- 선언적 코드를 사용한 관리
- 에코시스템 연계 및 확장

</details>

쿠버네티스는 위 과제를 자동화하거나 간단한 오퍼레이션으로 해결합니다.

<br>

### 2.3.1 선언적 코드를 사용한 관리 (IaC)

YAML 또는 JSON으로 작성한 **매니페스트**를 통해 컨테이너와 주변 리소스를 관리합니다.
가상화 시대의 AWS CloudFormation, OpenStack Heat와 같은 계보에 있습니다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
        - name: nginx-container
          image: nginx:1.16
```

<br>

### 2.3.2 스케일링 / 오토 스케일링

동일한 이미지를 기반으로 여러 **레플리카**를 배포해 부하 분산과 다중화 구조를 만듭니다.
부하에 따라 레플리카 수를 자동으로 늘리거나 줄이는 오토 스케일링도 지원합니다.

### 2.3.3 스케줄링

컨테이너를 어떤 노드에 배치할지 결정하는 단계입니다.

| 기능 | 활용 예 |
|:---|:---|
| Affinity | 디스크 I/O가 많은 컨테이너를 SSD 노드에 배치 |
| Anti-Affinity | 동일 역할 컨테이너를 서로 다른 노드에 분산 |
| 가용 영역 정보 | GCP, AWS, OpenStack 환경에서 멀티존 분산 배치 |

### 2.3.4 리소스 관리

배치 지정이 없으면 노드의 **CPU와 메모리 여유 상태**에 따라 자동 스케줄링됩니다.
사용자가 배치 위치를 직접 관리할 필요가 없고, 리소스 사용 상태에 따라 클러스터 오토 스케일링으로 노드 자체를 추가하거나 삭제할 수도 있습니다.

### 2.3.5 자동화된 복구 (Self-healing)

다중화(fault tolerant) 관점의 핵심 기능입니다.

| 상황 | 동작 |
|:---|:---|
| 컨테이너 프로세스 정지 | 스케줄링을 다시 실행해 자동 재배포 |
| 노드 장애 또는 축출 | 해당 노드의 컨테이너가 사라져도 서비스 영향 없이 복구 |

복구 조건은 프로세스 모니터링 외에 **HTTP / TCP 헬스 체크**나 셸 스크립트 실행 결과로도 설정할 수 있습니다.

### 2.3.6 로드 밸런싱과 서비스 디스커버리

여러 대로 구성된 애플리케이션을 하나의 엔드포인트로 노출합니다.
쿠버네티스는 **Service**와 **Ingress**로 로드 밸런서 기능을 제공하며,
사전에 정의한 조건과 일치하는 컨테이너 그룹에 라우팅합니다.

자동으로 처리되는 작업
- 확장 시 엔드포인트에 컨테이너 자동 등록 및 삭제
- 장애 컨테이너 분리
- 롤링 업데이트 시 필요한 사전 분리 작업

마이크로서비스 아키텍처에서는 각 서비스가 서로를 참조해야 하므로,
서비스 디스커버리를 통해 복수의 매니페스트로 정의된 시스템 전체를 쉽게 연계할 수 있습니다.

### 에코시스템 연계

쿠버네티스는 단독 플랫폼으로도 쓰이지만 외부 미들웨어 연계가 활발합니다.

| 미들웨어 | 용도 |
|:---|:---|
| Ansible | 쿠버네티스에 컨테이너 배포 |
| Apache Ignite | 서비스 디스커버리를 사용한 클러스터 생성과 스케일링 |
| Fluentd | 컨테이너 로그 전송 |
| GitLab | CI/CD 도구 통합 |
| Jenkins | Job 실행 시 실행용 컨테이너 배포 |
| OpenStack | 클라우드 사업자와 연계한 클러스터 구축 |
| Prometheus | 모니터링 |
| Spark | Job을 네이티브로 실행 (YARN 대체) |
| Spinnaker | 컨테이너 배포 |
| Kubeflow | ML 플랫폼 배포 |
| Rook | 분산 파일 시스템 배포 |
| Vitess | MySQL 클러스터 배포 |

또한 자체 기능을 추가하거나 쿠버네티스를 프레임워크로 삼아 자체 플랫폼을 구현할 수도 있습니다.

<br>

## 2.4 정리

| 구분 | 기존 가상 머신 기반 | 쿠버네티스 기반 |
|:---|:---|:---|
| 자동 배포 | CloudFormation 등으로 개별 구성 | 매니페스트 기반 선언적 배포 |
| 로드 밸런싱 | 구조를 직접 설계 | Service, Ingress로 제공 |
| 업데이트 | 구조를 계속 수정 | 롤링 업데이트 표준 지원 |
| 복구 | 별도 구성 필요 | Self-healing 기본 제공 |

컨테이너 운영에는 복잡한 주변 기능이 필요하지만, 쿠버네티스는 이를 사전 개발된 자동화 기능으로 제공합니다.
직접 만든 배포 스크립트를 쿠버네티스와 주변 에코시스템에서 공통으로 재사용할 수 있다는 점도 큰 장점입니다.
