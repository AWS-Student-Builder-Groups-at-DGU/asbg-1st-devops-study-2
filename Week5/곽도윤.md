## 5.1 워크로드 API 카테고리 개요

4장에서 본 다섯 카테고리 중 **워크로드 API**를 다루는 장. 사용자가 직접 쓰는 리소스는 8가지다.

파드 / 레플리케이션 컨트롤러 / 레플리카셋 / 디플로이먼트 / 데몬셋 / 스테이트풀셋 / 잡 / 크론잡

**파드를 최소 단위로 하고 그것을 관리하는 상위 리소스가 있는 부모-자식 관계**로 되어 있다.

```
Tier 3           Tier 2                    Tier 1
                 레플리케이션 컨트롤러  →  파드
디플로이먼트  →  레플리카셋           →  파드
                 데몬셋                →  파드
                 스테이트풀셋           →  파드
크론잡        →  잡                    →  파드
```

## 5.2 파드

워크로드 리소스의 **최소 단위**. 한 개 이상의 컨테이너로 구성되며, 같은 파드에 포함된 컨테이너끼리는 네트워크적으로 격리되어 있지 않고 **IP 주소를 공유**한다. 따라서 파드 내부 컨테이너는 서로 `localhost`로 통신할 수 있다.

대부분은 1파드 1컨테이너지만, 메인 컨테이너를 지원하는 서브 컨테이너(프록시, 로컬 캐시, SSL 종단 등)를 함께 두기도 한다. 다만 **nginx + redis처럼 메인 성격의 컨테이너를 한 파드에 묶는 구성은 비권장** — 개별 파드의 이동이 어려워지고 복잡해진다.

### 5.2.1 파드 디자인 패턴

| 종류                       | 개요                            |
| -------------------------- | ------------------------------- |
| 사이드카(sidecar) 패턴     | 메인 컨테이너에 기능을 추가     |
| 앰배서더(ambassador) 패턴  | 외부 시스템과의 통신을 중계     |
| 어댑터(adapter) 패턴       | 외부 접속을 위한 인터페이스 제공 |

- **사이드카**: 설정 변경 감지 후 리로드 / 깃 저장소↔로컬 스토리지 동기화 / 로그를 오브젝트 스토리지로 전송. 파드가 데이터 영역을 공유할 수 있어서 대부분 **데이터·설정 관련** 패턴이다.
- **앰배서더**: 메인 컨테이너는 목적지로 항상 `localhost`만 지정하고, 실제 라우팅은 앰배서더가 담당 → **결합도가 낮아진다.** 단일 DB 개발 환경과 샤딩된 서비스 환경을 애플리케이션 변경 없이 쓸 수 있다.
- **어댑터**: 데이터 형식 변환. 프로메테우스처럼 정해진 형식으로 메트릭을 수집해야 할 때 미들웨어 출력을 변환해 준다.

> 세 패턴이 구분되어 있지만, 메인을 보조하는 서브 컨테이너를 통틀어 **사이드카**라고 부르는 경우도 많다.

### 5.2.2 파드 생성

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: sample-pod
spec:
  containers:
    - name: nginx-container
      image: nginx:1.16
```

```bash
$ kubectl apply -f sample-pod.yaml
$ kubectl get pods                # READY 1/1 이면 정상
$ kubectl get pods --output wide  # IP, NODE까지 표시
```

### 5.2.3 두 개의 컨테이너를 포함한 파드

컨테이너 2개면 `READY 2/2`로 표시된다. 단, **같은 포트를 바인드하면 하나는 뜨지 않는다.**

```bash
$ kubectl get pods
NAME               READY  STATUS  RESTARTS  AGE
sample-2pod-fail   1/2    Error   1         18s

$ kubectl logs sample-2pod-fail -c nginx-container-113
nginx: [emerg] bind() to 0.0.0.0:80 failed (98: Address already in use)
```

파드는 네트워크 네임스페이스를 공유하므로 **VM 한 대에서 80/TCP를 두 프로세스가 못 쓰는 것과 같다**고 보면 된다.

### 5.2.4 컨테이너 로그인과 명령어 실행

SSH 로그인이 아니라 **가상 터미널 생성(`-t`) + 표준입력 패스스루(`-i`)** 로 셸을 실행하는 것.

```bash
$ kubectl exec -it sample-pod -- /bin/bash
$ kubectl exec -it sample-pod -- ls
$ kubectl exec -it sample-2pod -c nginx-container -- ls   # 멀티 컨테이너는 -c로 지정
$ kubectl exec -it sample-pod -- /bin/bash -c "ls | grep lib"  # 파이프는 -c로 감싼다
```

### 5.2.5 ENTRYPOINT/CMD와 command/args

도커와 쿠버네티스의 용어가 다르다. **`CMD`가 `command`에 해당하지 않는다는 점에 주의.**

| 도커         | 쿠버네티스                     |
| ------------ | ------------------------------ |
| `ENTRYPOINT` | `spec.containers[].command`    |
| `CMD`        | `spec.containers[].args`       |

```yaml
containers:
  - name: nginx-container
    image: nginx:1.16
    command: ["/bin/sleep"]   # ENTRYPOINT 대체
    args: ["3600"]            # CMD 대체
```

### 5.2.6 파드명 제한

RFC 1123 호스트명 규약을 따른다.

- 영문 소문자와 숫자
- 기호는 `-`, `.` 만
- 시작과 끝은 영숫자

→ **언더바(`_`) 사용 불가.** `sample_podname_fail`은 `DNS-1123 subdomain` 검증 에러로 생성 실패.

### 5.2.7 호스트의 네트워크 구성을 사용한 파드 기동

`spec.hostNetwork: true` → 노드의 네트워크 구성(IP·DNS·hosts)을 그대로 상속받아 호스트에서 프로세스를 기동한 것과 같아진다.

```yaml
spec:
  hostNetwork: true
```

기본적으로 파드 대역과 노드 대역은 다르고(예: `10.0.0.0/14` vs `10.178.0.0/16`) 서로 통신할 수 없다.

**노드 IP를 쓰기 때문에 포트 번호 충돌 위험이 있어 기본적으로 사용하지 않는다.** 외부 공개는 6장의 NodePort 서비스 등으로 해결 가능한지 먼저 검토하고, 엣지 환경이나 호스트 네트워크를 감시·제어하는 특수한 애플리케이션에만 쓰자.

### 5.2.8 파드 DNS 설정과 서비스 디스커버리

`spec.dnsPolicy`에 설정한다.

| 설정값                       | 개요                                                        |
| ---------------------------- | ----------------------------------------------------------- |
| **ClusterFirst**(기본값)     | 클러스터 내부 DNS에 질의, 해석 실패 시 업스트림 DNS로       |
| **None**                     | 파드 정의 내에서 `dnsConfig`로 정적 설정                     |
| **Default**                  | 노드의 `/etc/resolv.conf`를 상속                             |
| **ClusterFirstWithHostNet**  | ClusterFirst와 같은 동작(`hostNetwork` 사용 시)              |

```yaml
spec:
  dnsPolicy: None
  dnsConfig:
    nameservers: ["8.8.8.8", "8.8.4.4"]
    searches: ["example.com"]
    options:
      - name: ndots
        value: "5"
```

- **`dnsPolicy`의 기본값은 `Default`가 아니라 `ClusterFirst`다.** 이름 때문에 헷갈리기 쉽다.
- `None` / `Default`로 설정하면 **클러스터 내부 DNS를 쓰는 서비스 디스커버리를 할 수 없게 된다.**
- `hostNetwork: true`면 기본값 `ClusterFirst`가 **무시되고** 노드의 네트워크 설정이 사용되므로, 내부 DNS를 쓰려면 `ClusterFirstWithHostNet`을 **명시**해야 한다.

### 5.2.9 정적 호스트명 해석: /etc/hosts

리눅스는 DNS보다 `/etc/hosts`를 먼저 본다. `spec.hostAliases`로 파드 내 **모든 컨테이너**의 `/etc/hosts`에 항목을 추가할 수 있다.

```yaml
spec:
  hostAliases:
    - ip: 8.8.8.8
      hostnames:
        - google-dns
        - google-public-dns
```

### 5.2.10 작업 디렉터리 설정

도커 파일의 `WORKDIR`을 따르지만 `spec.containers[].workingDir`로 덮어쓸 수 있다. 볼륨으로 마운트한 스크립트 디렉터리로 이동한 뒤 실행하고 싶을 때 쓴다.

## 5.3 레플리카셋 / 레플리케이션 컨트롤러

파드의 레플리카를 생성하고 **지정한 파드 수를 유지**하는 리소스.

원래 이름이 레플리케이션 컨트롤러였고 이후 레플리카셋으로 바뀌면서 일부 기능이 추가됐다. **레플리케이션 컨트롤러는 사용하지 않는 추세이므로 레플리카셋을 쓴다.**

### 5.3.1 레플리카셋 생성

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: sample-rs
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:              # 복제할 파드 정의(Pod Template)
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
        - name: nginx-container
          image: nginx:1.16
```

파드 이름은 **`레플리카셋이름-임의의문자열`** 로 명명되고, 여러 노드에 흩어져 생성되어 노드 장애 영향을 최소화한다.

### 5.3.2 파드 정지와 자동화된 복구

파드를 삭제해도 즉시 새 파드가 생성되고, 노드 장애 시에도 다른 노드에서 파드를 기동해 레플리카 수를 유지한다. 쿠버네티스 핵심 콘셉트 중 하나인 **자동화된 복구(self-healing)**.

```bash
$ kubectl describe replicaset sample-rs   # Events에서 SuccessfulCreate 이력 확인
```

### 5.3.3 레플리카셋과 레이블 ★

레플리카셋은 파드를 **소유**하는 게 아니라 **특정 레이블을 가진 파드 수를 계산하는 형태**로 모니터링한다. 부족하면 `spec.template`으로 생성하고, 많으면 레이블이 일치하는 파드 중 하나를 삭제한다.

여기서 함정이 두 개 나온다.

**① `spec.selector` ≠ `spec.template.metadata.labels`**

```bash
$ kubectl apply -f sample-rs-fail.yaml
The ReplicaSet "sample-rs-fail" is invalid: spec.template.metadata.labels:
`selector` does not match template `labels`
```

에러로 막힌다. 만약 막히지 않았다면 카운트가 안 되니 **파드를 무한히 계속 생성**했을 것이다.

**② 레플리카셋 밖에서 같은 레이블의 파드를 생성하면?**

레플리카셋이 그것도 자기 레플리카로 세서 **초과분(4개 중 1개)을 정지시킨다.** 예제에서는 마지막에 생성된 파드가 삭제되지만 **상황에 따라 기존 파드가 삭제될 수도 있다.**

→ 동작이 익숙해질 때까지 **레이블은 유니크하게** 붙이고, 여러 레이블을 조합해 규칙을 정하자.

```yaml
labels:
  env: dev
  codename: system_a
  role: web-front
```

### 5.3.4 레플리카셋과 스케일링

```bash
# ① 매니페스트 수정 후 apply — IaC 구현을 위해서라도 이 방법을 쓰자
$ kubectl apply -f sample-rs.yaml

# ② scale 명령어
$ kubectl scale replicaset sample-rs --replicas 5
```

`kubectl scale`은 레플리카셋 외에 **레플리케이션 컨트롤러 / 디플로이먼트 / 스테이트풀셋 / 잡 / 크론잡**에도 쓸 수 있다.

### 5.3.5 일치성 기준 조건과 집합성 기준 조건

| 조건                      | 개요                                                       |
| ------------------------- | ---------------------------------------------------------- |
| 일치성 기준(equality-based) | `=`, `!=` 조건 지정                                        |
| 집합성 기준(set-based)      | `=`, `!=` + `in`, `notin`, `exists` 집합 조건 지정 가능     |

- 레플리케이션 컨트롤러는 일치성 기준만 → 레플리카셋은 집합성 기준까지 지원해 더 유연하다.
- 예: `app=sample-app` / `env in [development, staging]`
- 레플리카셋뿐 아니라 **스케줄링**에서도 쓰이며, 스케줄링에서는 수치 비교도 가능하다.
- 자세한 문법은 12장 `matchExpressions` 절에서 다룬다.

## 5.4 디플로이먼트

여러 레플리카셋을 관리해 **롤링 업데이트 / 롤백**을 구현하는 리소스. `디플로이먼트 → 레플리카셋 → 파드` 관계다.

**롤링 업데이트 동작 순서**

1. 신규 레플리카셋을 생성
2. 신규 레플리카셋의 레플리카 수를 단계적으로 늘림
3. 이전 레플리카셋의 레플리카 수를 단계적으로 줄임
4. (2, 3 반복)
5. **이전 레플리카셋은 레플리카 수를 0으로 유지** ← 롤백의 근거

신규 파드의 기동/헬스 체크 통과를 확인하며 전환된다. **쿠버네티스에서 가장 권장하는 컨테이너 기동 방법**으로, 파드 하나만 띄우더라도 디플로이먼트를 쓰는 게 좋다.

- 파드로만 배포 → 장애 시 자동으로 다시 생성되지 않음
- 레플리카셋으로만 배포 → 롤링 업데이트를 쓸 수 없음

### 5.4.1 디플로이먼트 생성

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-deployment
spec:
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
        - name: nginx-container
          image: nginx:1.16
```

```bash
$ kubectl apply -f sample-deployment.yaml --record
$ kubectl set image deployment sample-deployment nginx-container=nginx:1.17 --record
$ kubectl rollout status deployment sample-deployment
```

이력은 각 레플리카셋의 어노테이션에 저장된다.

- `metadata.annotations["kubernetes.io/change-cause"]` — 실행한 명령어
- `metadata.annotations["deployment.kubernetes.io/revision"]` — 수정 버전 번호

업데이트 후 `kubectl get replicasets`를 보면 **신규 RS(3/3/3)와 이전 RS(0/0/0)** 가 함께 남아 있다.

> 서비스 환경 운영에서 `kubectl rollout`을 쓰는 경우가 거의 없어서 `--record` 옵션도 많이 쓰지는 않는다.

### 5.4.2 디플로이먼트 업데이트(레플리카셋이 생성되는) 조건 ★

**'변경'에 레플리카 수 변경은 포함되지 않는다.** `spec.template`이 바뀌어야 신규 레플리카셋이 생성되고 롤링 업데이트가 실행된다.

구현 원리는 `spec.template` 아래 내용의 **해시값(pod-template-hash)** 을 계산해 레이블로 관리하는 것이다.

```yaml
selector:
  matchLabels:
    app: sample-app
    pod-template-hash: 5988b689cb
```

→ 이미지를 이전 버전으로 되돌려 **해시값이 같아지면 신규 RS를 만들지 않고 기존 RS를 재사용**한다.

### 5.4.3 변경 롤백

롤백의 실체는 **사용 중인 레플리카셋의 전환**이다. 이전 RS가 레플리카 0으로 남아 있으니 그 수를 다시 늘리는 것뿐.

```bash
$ kubectl rollout history deployment sample-deployment
$ kubectl rollout history deployment sample-deployment --revision 1
$ kubectl rollout undo deployment sample-deployment --to-revision 1
$ kubectl rollout undo deployment sample-deployment   # 기본 0 = 바로 이전 버전
```

`CHANGE-CAUSE`는 `--record`를 안 썼으면 `<none>`으로 뜬다.

> 실제 환경에서 롤백 기능을 쓰는 경우는 많지 않다. CI/CD 파이프라인에서는 `kubectl rollout`보다 **이전 매니페스트를 다시 `kubectl apply`** 하는 쪽이 호환성 면에서 낫다. `spec.template`이 같은 내용으로 돌아가면 `pod-template-hash`도 같아져서 결국 기존 레플리카셋의 파드가 기동된다.

### 5.4.4 디플로이먼트 변경 일시 중지

```bash
$ kubectl rollout pause deployment sample-deployment
$ kubectl rollout resume deployment sample-deployment
```

pause 상태에서는 `set image` 등을 해도 즉시 반영되지 않고 대기 상태가 되며, **롤백도 되지 않는다**(resume 먼저 하라는 에러).

### 5.4.5 디플로이먼트 업데이트 전략

`spec.strategy.type`의 기본값이 `RollingUpdate`다.

**Recreate**

모든 파드를 한 번 삭제하고 다시 생성한다. `type` 외에 지정할 파라미터가 없다.

- 이전 RS 레플리카 → 0(리소스 반환) → 신규 RS 생성 → 레플리카 증가
- ❌ 몇 초간 파드가 전혀 없는 구간이 생겨 **다운타임 발생**
- ✅ 추가 리소스를 쓰지 않고 전환이 빠름

**RollingUpdate**

| 파라미터          | 개요                                     | 기본값 |
| ----------------- | ---------------------------------------- | ------ |
| `maxUnavailable`  | 업데이트 중 동시에 정지 가능한 최대 파드 수 | 25%    |
| `maxSurge`        | 업데이트 중 동시에 생성 가능한 최대 파드 수 | 25%    |

```yaml
spec:
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
```

- `maxUnavailable=0 / maxSurge=1` → **먼저 늘리고** 파드를 이동(추가 리소스 필요, 무중단)
- `maxUnavailable=1 / maxSurge=0` → **먼저 줄이고** 파드를 이동(추가 리소스 불필요)
- 백분율 지정 가능. **둘 다 0으로 설정할 수는 없다.**

### 5.4.6 상세 업데이트 파라미터

모두 `spec` 바로 아래에 설정한다.

| 파라미터                  | 개요                                                                     |
| ------------------------- | ------------------------------------------------------------------------ |
| `minReadySeconds`         | 파드가 Ready가 된 뒤 기동 완료(다음 파드 교체 가능)로 판단하기까지의 최소 시간(초) |
| `revisionHistoryLimit`    | 유지할 레플리카셋 수 = **롤백 가능한 이력 수**                             |
| `progressDeadlineSeconds` | 업데이트 처리 타임아웃(초). 경과하면 **자동 롤백**                          |

### 5.4.7 디플로이먼트 스케일링

레플리카셋과 동일하다.

```bash
$ kubectl apply -f sample-deployment.yaml
$ kubectl scale deployment sample-deployment --replicas=5
```

### 5.4.8 매니페스트를 사용하지 않고 디플로이먼트 생성

```bash
$ kubectl create deployment sample-deployment-by-cli --image nginx:1.16
```

기본 레이블 `app: sample-deployment-by-cli`와 `pod-template-hash`가 부여된다. 이미지 확인 등 간단한 작업 용도로는 쓸 만하지만 **서비스 환경에서는 매니페스트를 사용하자.**

## 정리 — 헷갈리기 쉬운 지점

1. `ENTRYPOINT` → `command`, **`CMD` → `args`**. 이름 매핑이 직관과 어긋난다.
2. `dnsPolicy` 기본값은 `Default`가 아니라 **`ClusterFirst`**.
3. `hostNetwork: true`면 `ClusterFirst`가 무시된다 → `ClusterFirstWithHostNet` 명시 필요.
4. 레플리카셋은 파드를 소유하는 게 아니라 **레이블로 센다.** 밖에서 만든 동일 레이블 파드가 삭제될 수 있다.
5. 디플로이먼트에서 **레플리카 수 변경은 롤링 업데이트를 유발하지 않는다.** `spec.template` 변경만 유발한다.
6. **롤백 = 레플리카셋 전환.** 이전 RS가 replicas=0으로 남아 있어서 가능한 것.
7. `maxUnavailable`과 `maxSurge`를 동시에 0으로 둘 수 없다.
8. pause 상태에서는 업데이트도 롤백도 반영되지 않는다.
