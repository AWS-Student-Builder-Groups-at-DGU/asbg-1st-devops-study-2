# Kubernetes 10주차 스터디정리 (Day 13 ~ 15)

### 파드 배치 흐름

```
Pod 생성 요청
  ├─ spec.nodeName 있음 → 해당 노드의 kubelet이 실행 (1, 2절)
  └─ spec.nodeName 없음 → scheduler가 후보 노드를 거름
        ├─ taint / toleration (3절)
        ├─ nodeSelector, required affinity (4, 5절)
        └─ preferred affinity 점수 합산 후 선택 (5절)
```

실습 환경은 kind 클러스터(control-plane 1개, worker 2개)다. 노드 이름은 `cka-cluster3-control-plane`, `cka-cluster3-worker`, `cka-cluster3-worker2`이고, 다른 환경에서는 `kubectl get nodes`로 확인해서 바꿔 쓴다.

## 1. 스케줄러와 kubelet

### 파드 생성 흐름

`kubectl run nginx --image=nginx`를 실행하면 API 서버가 요청을 받아 etcd에 Pod를 저장한다. 이 시점의 Pod에는 실행할 노드가 비어 있다. scheduler가 이 Pod에 맞는 노드를 골라 기록하고, 그 노드의 kubelet이 컨테이너 런타임으로 컨테이너를 띄운다.

`pod/nginx created`는 API에 객체가 저장됐다는 응답이다. 컨테이너 실행 여부는 STATUS로 따로 확인한다.

| 구성 요소 | 역할 |
| --- | --- |
| API 서버 | 요청 수신, 상태 저장·조회 |
| scheduler | 노드가 비어 있는 Pod에 실행 노드 지정 |
| kubelet | 자기 노드에 배정된 Pod 실행, 상태 보고 |

### scheduler 중지 실습

scheduler도 `kube-system`의 Pod로 실행된다. kind 노드는 Docker 컨테이너라서 SSH 대신 `docker exec`로 들어간다.

```bash
docker exec -it cka-cluster3-control-plane bash   # control-plane 노드 컨테이너로 진입
cd /etc/kubernetes/manifests                      # kubelet이 감시하는 매니페스트 폴더
mv kube-scheduler.yaml /tmp/                      # 폴더 밖으로 옮기면 scheduler Pod 종료
```

이 상태에서 다른 터미널로 nginx를 만들면 `created` 응답 후 STATUS가 `Pending`에 머문다. `kubectl describe pod nginx`의 Node 항목은 비어 있고 오류 이벤트도 남지 않는다. 노드를 고르는 scheduler가 없으니 실패 이벤트를 기록할 주체도 없다.

기존에 실행 중이던 Pod는 계속 동작한다. 영향을 받는 건 새로 노드를 배정받아야 하는 Pod다. 파일을 되돌리면 scheduler가 다시 뜨고, 대기하던 nginx도 노드를 배정받아 Running이 된다.

```bash
mv /tmp/kube-scheduler.yaml /etc/kubernetes/manifests/   # 원위치 후 scheduler 재시작
```

백업 파일은 폴더 밖에 둔다. kubelet은 확장자를 구분하지 않고, 점으로 시작하지 않는 파일을 모두 읽는다. `kube-scheduler.yaml.bak`을 같은 폴더에 두면 이 파일도 Pod로 읽힌다.

자원 부족, taint, label 조건으로도 Pod가 Pending이 된다. 이 실습은 원인을 직접 만들었기 때문에 scheduler 중지로 판단할 수 있었다.

## 2. 스케줄러를 거치지 않는 파드

### Static Pod

kubelet은 노드의 정해진 폴더를 계속 감시한다. 폴더에 Pod YAML이 생기면 Pod를 띄우고, 파일을 수정하면 다시 만들고, 파일을 지우면 Pod도 내린다. 이 과정에는 API 서버와 scheduler가 끼지 않는다. 1절에서 파일을 옮겼을 때 scheduler가 내려간 것도 같은 동작이다.

kind control-plane의 폴더에는 파일 네 개가 있다.

```
/etc/kubernetes/manifests
├─ etcd.yaml
├─ kube-apiserver.yaml
├─ kube-controller-manager.yaml
└─ kube-scheduler.yaml
```

폴더 경로는 kubelet 설정의 `staticPodPath`로 정한다. kubeadm 계열이 위 경로를 기본으로 쓰고, 다른 설치 방식은 다를 수 있다. API에 보이는 Static Pod는 kubelet이 등록한 사본이라서 수정이나 삭제는 노드의 원본 파일에서 한다.

`kube-system`의 Pod 중 CoreDNS는 Deployment, kube-proxy와 kindnet은 DaemonSet이 관리한다. 일반 앱 YAML도 이 폴더에 넣으면 Static Pod로 실행된다.

### nodeName 지정

scheduler는 `spec.nodeName`이 비어 있는 Pod만 처리한다. 처음부터 노드 이름을 적어서 만들면 scheduler가 그 Pod를 건너뛴다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx
spec:
  nodeName: cka-cluster3-worker   # containers와 같은 들여쓰기
  containers:
    - name: nginx
      image: nginx
```

```bash
kubectl delete pod nginx            # 배정된 Pod의 nodeName은 수정 불가, 삭제 후 재생성
kubectl apply -f pod.yaml           # scheduler를 내린 상태에서 생성
kubectl get pods -o wide            # NODE 열 = cka-cluster3-worker
```

scheduler를 내린 상태에서도 nginx는 지정한 worker에서 Running이 됐다. 실습 후에는 scheduler 파일을 원위치하고 READY가 `0/1`에서 `1/1`로 바뀌는지 확인한다.

| 항목 | Static Pod | nodeName 지정 Pod |
| --- | --- | --- |
| 생성 위치 | 노드의 로컬 폴더 | API 서버 (kubectl apply) |
| scheduler | 거치지 않음 | 거치지 않음 |
| 실행 | 해당 노드의 kubelet | 지정한 노드의 kubelet |
| 삭제 | 노드에서 파일 제거 | kubectl delete |

nodeName으로 만든 Pod도 노드 이름이 틀리거나 자원이 부족하면 실행에 실패한다. API로 만든 일반 Pod라서 Static Pod와는 관리 방식이 다르다.

## 3. Taint와 Toleration

### taint 설정과 해제

GPU와 큰 메모리를 단 worker가 있다고 할 때, 일반 웹 Pod가 먼저 자리를 차지하면 AI 작업이 들어갈 자원이 부족해진다. 이럴 때 노드에 taint를 건다.

```bash
kubectl taint node cka-cluster3-worker gpu=true:NoSchedule     # key=value:effect
kubectl describe node cka-cluster3-worker | grep Taints         # 적용 확인 (T 대문자)
kubectl taint node cka-cluster3-worker gpu=true:NoSchedule-    # 끝에 - 를 붙이면 제거
```

### Toleration 작성

taint가 걸린 노드에 들어가려면 Pod의 `spec.tolerations`에 같은 조건을 적는다. Pod label에 `gpu=true`를 붙여도 toleration으로 인정되지 않는다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: redis
spec:
  containers:
    - name: redis
      image: redis
  tolerations:              # containers와 같은 들여쓰기
    - key: "gpu"
      operator: "Equal"     # key, value, effect 모두 일치
      value: "true"         # 따옴표 없으면 YAML이 불리언으로 해석
      effect: "NoSchedule"
```

`operator`에는 `Equal`과 `Exists`를 쓴다. `Exists`는 value를 생략하고 key만 비교한다. `In`, `NotIn`은 affinity 쪽 연산자다.

### Effect 종류

| effect | 새로 배치할 Pod | 해당 노드에서 실행 중인 Pod |
| --- | --- | --- |
| `NoSchedule` | toleration 없으면 배치 안 함 | 유지 |
| `PreferNoSchedule` | 가능하면 다른 노드 선택 | 유지 |
| `NoExecute` | toleration 없으면 배치 안 함 | toleration 없으면 퇴거 |

`PreferNoSchedule`은 다른 후보가 없으면 그 노드에도 배치한다. 노드에 taint가 여러 개면 Pod는 강제 효과가 있는 taint를 모두 견뎌야 들어갈 수 있다.

### 실습: 두 worker에 taint 적용

두 worker에 `gpu=true:NoSchedule`을 걸고 toleration 없는 nginx를 만들었다.

```bash
kubectl run nginx --image=nginx
kubectl describe pod nginx      # Events 확인
```

nginx는 Pending이었고 Events 내용은 다음과 같다.

```
0/3 nodes are available:
  1개 노드  → control-plane 기본 taint를 견디지 못함
  2개 노드  → gpu=true taint를 견디지 못함
preemption 효과 없음
```

control-plane에는 일반 Pod를 막는 taint가 기본으로 있어서 후보 노드가 없다. 다른 Pod를 밀어내도 nginx에 toleration이 생기지 않기 때문에 preemption도 소용없다.

위 toleration을 넣은 redis를 만들자 redis는 worker1에서 Running이 되고 nginx는 Pending으로 남았다. worker2의 taint를 지우자 nginx를 다시 만들지 않았는데도 worker2에 배치됐다. scheduler는 Pending 상태의 Pod를 노드 상태가 바뀔 때 다시 평가한다.

| 단계 | nginx (toleration 없음) | redis (toleration 있음) |
| --- | --- | --- |
| 두 worker에 taint | Pending | 생성 전 |
| redis 생성 | Pending | worker1에서 Running |
| worker2 taint 제거 | worker2에서 Running | 유지 |

두 worker에 같은 taint가 걸려 있었으니 redis는 worker2로 갈 수도 있었다. toleration은 taint가 걸린 노드에 들어갈 자격만 준다. taint 없는 노드가 따로 있으면 toleration을 가진 Pod도 그 노드에 배치될 수 있다.

## 4. nodeSelector

### 노드 label과 nodeSelector

3절의 toleration만으로는 Pod를 특정 노드에 묶을 수 없다. nodeSelector는 노드 label을 기준으로 Pod가 갈 노드를 제한한다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-new
spec:
  containers:
    - name: nginx
      image: nginx
  nodeSelector:            # containers와 같은 들여쓰기
    gpu: "false"           # 노드 label과 비교, 값은 문자열
```

```bash
kubectl apply -f new-nginx.yaml
kubectl get nodes --show-labels                  # 노드 label 확인
kubectl label node cka-cluster3-worker gpu=false # 조건에 맞는 label 추가
kubectl get pods -o wide                         # 해당 worker에 배치
```

### 실습: label 추가 전후

label을 붙이기 전에는 Pending이었다. Events에는 control-plane taint 1개와 `node affinity/selector` 불일치 2개가 찍혔다. scheduler는 nodeSelector와 node affinity 불일치를 같은 메시지로 보여 준다.

영상 중간에 노드 label을 지운 상태에서 nginx-new가 Running으로 보이는 장면이 있었다. label을 지우기 전에 떠 있던 Pod였고, 삭제 후 다시 만들자 Pending이 됐다. nodeSelector는 배치 시점에만 검사하고, 실행 중인 Pod는 label이 바뀌어도 그대로 둔다.

nodeSelector에 key를 여러 개 적으면 모두 일치해야 한다(AND). "ssd 또는 hdd", "특정 값 제외", "맞으면 우선" 같은 조건은 표현하지 못하고, 이 부분은 node affinity로 쓴다.

## 5. Node Affinity

### required와 preferred

두 속성 이름은 앞부분(배치 시점)과 뒷부분(실행 중)으로 나뉜다.

```
requiredDuringScheduling   IgnoredDuringExecution
└ 배치할 때 반드시 일치      └ 실행 중 label 변경은 무시

preferredDuringScheduling  IgnoredDuringExecution
└ 배치할 때 일치하면 우선    └ 실행 중 label 변경은 무시
```

| 항목 | required | preferred |
| --- | --- | --- |
| 일치하는 노드가 없을 때 | Pending | 다른 노드에 배치 |
| 사용 예 | SSD 노드에서만 실행할 작업 | SSD를 선호하지만 다른 노드도 허용하는 작업 |

preferred를 써도 자원이 부족하거나 견딜 수 없는 taint만 남으면 Pending이 된다.

### 실습 1: required

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: redis-required
spec:
  containers:
    - name: redis
      image: redis
  affinity:
    nodeAffinity:                                   # 빠뜨리면 unknown field 오류
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
          - matchExpressions:
              - key: disktype
                operator: In
                values:
                  - ssd
```

처음에는 `disktype` label을 가진 노드가 없어서 Pending이었다. `kubectl label node cka-cluster3-worker disktype=ssd`로 label을 붙이자 대기하던 Pod가 그 worker에서 Running이 됐다. 영상에서는 `nodeAffinity` 계층을 빠뜨려 `unknown field` 오류가 한 번 났다. `nodeAffinity`는 `affinity` 아래에 둔다.

### 실습 2: preferred와 weight

preferred는 구조가 달라서 `weight`와 `preference`를 넣는다.

```yaml
  affinity:
    nodeAffinity:
      preferredDuringSchedulingIgnoredDuringExecution:
        - weight: 1                 # 1~100, 일치한 조건의 weight를 노드 점수에 합산
          preference:
            matchExpressions:
              - key: disktype
                operator: In
                values:
                  - sdd             # 일부러 어떤 노드에도 없는 값
```

일치하는 노드가 없었는데도 ContainerCreating을 거쳐 Running이 됐다. 같은 조건을 required로 썼다면 Pending이었다. `weight`는 점수 계산에 쓰이고 검사 순서와는 관계없다. 일치한 preferred 조건들의 weight가 합산되고, 100을 줘도 필수 조건이 되지는 않는다.

### 실습 3: 실행 중 label 삭제

```bash
kubectl label node cka-cluster3-worker disktype-   # key 삭제
kubectl get pods -o wide                           # 기존 Pod는 Running 유지
```

`IgnoredDuringExecution`에 해당하는 동작이다. 새로 만드는 Pod는 바뀐 label을 기준으로 검사한다.

### 실습 4: Exists 연산자

`operator`를 `Exists`로 바꾸고 `values`를 지운다. 노드에는 값이 빈 label을 붙인다.

```bash
kubectl label node cka-cluster3-worker disktype=   # key 있음, 값은 빈 문자열
```

새 Pod는 이 worker에 배치됐다. `Exists`는 key 존재 여부만 확인한다. `disktype-`는 key를 지우고 `disktype=`는 빈 값으로 key를 만들어서, `Exists` 판정 결과가 반대로 나온다.

| 노드 label | `In [ssd]` | `Exists` |
| --- | --- | --- |
| `disktype=ssd` | 통과 | 통과 |
| `disktype=hdd` | 탈락 | 통과 |
| `disktype=` | 탈락 | 통과 |
| `disktype` 없음 | 탈락 | 탈락 |

### 연산자와 조건 결합

| 연산자 | 조건 |
| --- | --- |
| `In` | 값 목록 중 하나와 일치 |
| `NotIn` | 값 목록에 없음 |
| `Exists` | key 존재 |
| `DoesNotExist` | key 없음 |
| `Gt`, `Lt` | label 값을 정수로 비교 |

같은 term 안의 여러 `matchExpressions`는 AND, 여러 `nodeSelectorTerms`는 OR로 묶인다. affinity에는 `Equal`이 없어서 값 하나를 비교할 때도 `In`에 값 하나를 넣는다.

## 6. 전용 노드 구성

영상 마지막 도식은 노드 세 개와 Pod 세 개로 구성된다. green 노드에는 `color=green` taint와 `gpu=false` label, blue 노드에는 `color=blue` taint, 세 번째 노드에는 taint 없이 `gpu=true` label이 있다. green Pod의 배치 가능 노드는 다음과 같다.

| green Pod 설정 | green 노드 | blue 노드 | 세 번째 노드 |
| --- | --- | --- | --- |
| toleration만 | 가능 | taint로 불가 | **가능** |
| toleration + required affinity `gpu=false` | 가능 | 불가 | label 불일치로 불가 |

toleration만 있으면 green Pod가 taint 없는 세 번째 노드로 갈 수 있다. affinity만 있으면 green 노드의 taint를 통과하지 못한다.

| 설정 | 거는 위치 | 막는 상황 |
| --- | --- | --- |
| taint + toleration | 노드에 taint, Pod에 toleration | 자격 없는 Pod의 진입 |
| required affinity + 노드 label | Pod에 affinity, 노드에 label | 전용 Pod의 다른 노드 배치 |

taint와 label은 같은 `gpu` 키를 써도 별개 필드라서 노드에 각각 붙인다. GPU, AI/ML, 데이터 웨어하우징 노드처럼 특정 작업만 받을 노드에 이 조합을 쓴다.

## 7. Pending 진단 순서

```bash
kubectl get pods -o wide                   # 1. NODE가 비어 있으면 배치 단계 문제
kubectl describe pod <Pod>                 # 2. Events의 실패 이유
kubectl get nodes --show-labels            # 3. Pod가 요구한 label이 노드에 있는지
kubectl describe node <노드> | grep Taints  # 4. 견디지 못하는 taint
kubectl get pods -n kube-system            # 5. 이벤트가 없으면 scheduler 상태
```

| Events 메시지 | 확인할 곳 |
| --- | --- |
| `untolerated taint` | 노드 taint와 Pod toleration의 key/value/effect |
| `didn't match Pod's node affinity/selector` | nodeSelector, required affinity와 노드 label의 철자·값 |
| `Insufficient cpu/memory` | 요청 자원과 노드 여유 |
| 이벤트 없음 + NODE 비어 있음 | scheduler 실행 여부 |

`0/3 nodes are available`은 조건을 모두 통과한 후보 노드가 0개라는 뜻이다.

## 8. Label, Annotation, Namespace

### Deployment의 label 위치

Deployment YAML에는 label이 세 곳에 나온다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: demo
  labels:
    env: demo          # Deployment 자신의 label
spec:
  selector:
    matchLabels:
      env: demo        # 관리할 Pod를 찾는 조건
  template:
    metadata:
      labels:
        env: demo      # 생성할 Pod의 label, selector와 일치해야 함
    spec:
      containers:
        - name: nginx
          image: nginx
```

`metadata.labels`에만 붙인 label은 Pod로 전달되지 않는다. Pod에 붙는 label은 `template` 쪽에 적고, `selector`가 그 label로 Pod를 찾는다.

### selector로 조회

실습에서는 nginx에 `tier=frontend`, `type=app1`을, redis에 `tier=backend`를 붙였다. Pod 하나에 label을 여러 개 붙일 수 있다.

```bash
kubectl get pods --show-labels               # label 전체 보기
kubectl get pods --selector=tier=frontend    # nginx
kubectl get pods -l tier=backend             # redis (-l은 --selector 축약)
kubectl get pods -l 'env in (dev,prod)'      # 값 여러 개 중 하나
```

`--selector`는 조회 필터라서 Pod 배치에는 영향이 없다. 4절의 nodeSelector와 이름이 비슷하니 구분한다.

nginx YAML에 label을 추가해 `apply`했을 때 `the object has been modified` 충돌이 났고, 영상에서는 `--force`로 다시 적용했다. label 변경에 원래 force가 필요하지는 않다. 서버에서 받은 YAML에 오래된 메타데이터가 남아 있으면 이 충돌이 나므로, 최신 객체와 비교한 뒤 적용한다.

### annotation과 namespace

| 구분 | 용도 | selector 조회 |
| --- | --- | --- |
| label | 분류, 대상 선택 | 가능 |
| annotation | 도구용 기록, 설명 | 불가 |
| namespace | 이름과 관리 범위 구분 | `-n`으로 범위 지정 |

`kubectl edit pod nginx`로 열면 `last-applied-configuration` annotation이 보인다. 마지막 `apply` 내용을 기록하는 용도이고, 변경 이력 전체나 롤백 기능은 없다. namespace를 나눠도 통신과 권한은 자동으로 막히지 않는다(Day 10). label은 namespace와 상관없이 붙인다.
