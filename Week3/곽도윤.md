# 3장. 쿠버네티스 환경 구축 — 스터디 정리

> 대상: 《쿠버네티스 완벽 가이드》(마사야 아오야마, 길벗) 3장
> 범위: 3.1 ~ 3.6 (p.35~61)

3장은 **"쿠버네티스 클러스터를 어떤 방식으로 준비할 것인가"**를 다루는 장입니다. 실습 명령어가 많지만, 핵심은 **세 가지 구축 방식의 특징과 용도 차이**를 이해하는 것입니다.

---

## 3.1 쿠버네티스 환경의 종류

쿠버네티스 클러스터를 구성하는 방법은 크게 3가지로 나뉩니다.

| 방식 | 설명 | 적합한 용도 |
|---|---|---|
| **로컬 쿠버네티스** | 한 대의 머신에 구축 | 개인 테스트·개발 (이중화 없음 → 서비스 환경 부적합) |
| **쿠버네티스 구축 도구** | 온프레미스/클라우드에 도구로 클러스터 구축 | 세밀한 커스터마이즈가 필요한 스테이징/서비스 환경 |
| **관리형 쿠버네티스 서비스** | 퍼블릭 클라우드가 제공하는 클러스터 사용 | 운영 부담을 최소화하고 싶은 스테이징/서비스 환경 |

- 이 세 방식으로 만들어진 환경은 CNCF의 **Certified Kubernetes Conformance Program** 인증을 받으므로, 기본 동작은 어떤 환경에서도 동일하게 보장됨(이식성).
- 책의 4장 이후 실습은 기본적으로 **GKE 기준**으로 설명하되, 대부분 기능은 다른 환경에서도 동일하게 동작.

## 3.2 로컬 쿠버네티스

한 대의 머신에서 손쉽게 테스트할 수 있는 방식(이중화 없음, 일부 기능 제한).

### 3.2.1 미니큐브(Minikube)
- 하이퍼바이저(Hyperkit/VirtualBox/HyperV 등) 위에 **가상머신 1대**를 만들고 그 안에 쿠버네티스를 설치.
- `minikube start --driver=... --kubernetes-version=...` 형태로 기동, `kubectl`로 조작.
- SIG-cluster-lifecycle 분과회에서 관리하는 공식 로컬 툴.

### 3.2.2 Docker Desktop for Mac/Windows
- 도커가 자체적으로 쿠버네티스 지원을 내장 (Docker Desktop 설정에서 활성화).
- 별도 버전 지정이 어려운 점이 단점.

### 3.2.3 kind (Kubernetes IN Docker)
- 쿠버네티스 **SIG-testing** 분과회가 만든, 쿠버네티스 자체 개발/테스트용 도구.
- 도커 컨테이너 하나하나를 쿠버네티스 "노드"로 사용 → **멀티 노드 클러스터**를 로컬에서도 구성 가능(미니큐브/Docker Desktop과의 차별점).
- YAML 설정 파일로 마스터/워커 노드 수를 지정해 클러스터 구성.

### 3.2.4 로컬 쿠버네티스 정리 (비교)

| 항목 | 미니큐브 | Docker Desktop | kind |
|---|---|---|---|
| 버전 선택 | 가능 | 불가 | 가능 |
| 멀티 클러스터 | 가능 | 불가 | 가능 |
| 멀티 노드 | 불가 | 불가 | **가능** |
| 기능성 | 중간 | 낮음 | 높음 |
| 단순성 | 높음 | 높음 | 중간 |

(그 외 microk8s, k3s 등도 언급)

## 3.3 쿠버네티스 구축 도구

온프레미스/클라우드 인프라 위에 **직접 클러스터를 구축**하는 방식.

### 3.3.1 쿠버네티스 서비스 수준 목표(SLO)
- SIG-scalability 분과회가 정의한 클러스터 확장성 지표(SLI/SLO).
- 대표 상한 값(참고용): **노드 수 ≤ 5,000**, **클러스터 내 총 파드 ≤ 150,000**, **노드당 파드 수 ≤ 110**.
- 관리형 서비스는 이 한도가 환경별로 다를 수 있음(네트워크 구성 제약 등).

### 3.3.2 큐브어드민(kubeadm)
- 쿠버네티스 **공식 구축 도구** (1.13 릴리스, 2018년 12월 GA).
- 여러 대의 리눅스 머신에 도커/kubelet 등을 설치 → `kubeadm init`으로 마스터 초기화 → 워커 노드를 `kubeadm join`으로 합류시키는 흐름.
- 노드 간 파드 통신(파드 네트워크)을 위해 **CNI 플러그인**(예: **플라넬(Flannel)**, 오버레이 네트워크 방식)을 별도로 배포해야 함.
- kind 내부적으로도 kubeadm을 사용해 클러스터를 구성함 (3.2.3과 연결).

### 3.3.3 파드 네트워크 구성 (플라넬 등)
- 멀티 노드 클러스터가 되려면 각 호스트 간 **내부 네트워크(파드 네트워크) 연결성**이 필요.
- 플라넬은 노드 간 **가상 터널(오버레이 네트워크)**을 구성해 파드 간 통신을 구현하는 대표적인 방법 중 하나 (그 외에도 Calico, Weave 등 여러 CNI 구현체가 존재).

### 3.3.4 랜처(Rancher)
- Rancher Labs가 개발하는 **엔터프라이즈 컨테이너 관리 플랫폼** (2.0부터 쿠버네티스 중심으로 전환, 2018년 5월 정식 출시).
- 랜처 서버를 띄우고, 웹 UI를 통해 **여러 클러스터를 통합 관리**.
- 주요 기능: 기존 클러스터 임포트, 멀티 클러스터 앱 배포, 중앙 인증, 애플리케이션 카탈로그, Istio 연계 등.

### 3.3.5 그 외 구축 도구
- Ansible 기반의 Kubespray, 클라우드 포메이션/테라폼으로 IaC 방식 구축, OpenStack Magnum(Heat 기반) 등.

### 3.3.6 그 외 엔터프라이즈 솔루션
- 온프레미스 대상: **Red Hat OpenShift Container Platform**, **VMware Enterprise PKS**(현 Tanzu), **IBM Cloud Private** 등.
- 국내 사례로 피보탈 컨테이너 서비스(PKS) 등이 언급됨.

## 3.4 퍼블릭 클라우드 관리형 쿠버네티스 서비스

운영 부담(마스터 관리, 업그레이드 등)을 클라우드에 맡기는 방식.

### 3.4.1 GKE (Google Kubernetes Engine)
- **가장 먼저 등장한 관리형 서비스**. 구글의 Borg 운영 노하우 반영.
- 릴리스 채널 기반 자동 업데이트, 노드 자동 복구/자동 프로비저닝 등 운영 부담을 낮추는 기능 다수.
- **선점형 인스턴스(Preemptible VM)**를 노드로 활용해 비용 절감 가능 -> 단, 최대 24시간 후 강제 종료.
- GCP의 다른 서비스(Cloud Logging/Stackdriver 등)와 통합 가능.

### 3.4.2 AKS (Azure Kubernetes Service)
- 마이크로소프트 애저의 관리형 서비스.
- Azure AD와 연계한 RBAC, 리소스 부족 시 **Virtual Kubelet + ACI로 버스팅**해 파드를 컨테이너 인스턴스로 순간 확장하는 기능이 특징.

### 3.4.3 EKS (Elastic Kubernetes Service)
- AWS의 관리형 서비스.
- GKE/AKS와 유사하게 클러스터 인증 정보를 CLI로 가져와 kubectl로 조작하는 흐름.

> 세 서비스 모두 **Certified Kubernetes** 인증을 받아 기본 동작은 호환되지만, 세부 운영 기능(자동 확장 방식, 노드 관리 등)에는 클라우드별 차이가 있음.

## 3.5 쿠버네티스 플레이그라운드 (Play with Kubernetes)

- 도커가 제공하는 **웹 기반 임시 쿠버네티스 테스트 환경**.
- 설치 없이 브라우저에서 최대 5개 인스턴스로 kubeadm 기반 클러스터를 몇 분 안에 구성 가능.
- 단, **사용 시간 제한(최대 4시간)**과 기능 제한이 있어 정식 학습/개발용이 아닌 **빠른 테스트 용도**로 적합.

## 3.6 정리

- 쿠버네티스 환경 구축 방식은 크게 **로컬 쿠버네티스 / 구축 도구 / 관리형 서비스** 3가지.
- 선택 기준: 플랫폼(퍼블릭/프라이빗 클라우드 등)과 환경 목적(개발/스테이징/서비스)에 따라 적절히 선택.
- 인증 프로그램을 통과한 환경이라면 기본 동작의 일관성은 보장되지만, 세부 기능 차이가 있을 수 있으므로 **개발/스테이징/서비스 환경은 가능한 한 동일한 환경으로 운용**하는 것이 권장됨(최소한 스테이징=서비스 환경 일치는 필수).
- 다음 장(4장)부터는 이렇게 구축한 클러스터를 사용해 쿠버네티스의 개념과 기능을 본격적으로 설명.
