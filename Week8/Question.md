## 문제 1. 명령형과 선언형의 차이

쿠버네티스에 리소스를 만드는 방식에는 **명령형(Imperative)** 과 **선언형(Declarative)** 두 가지가 있습니다.

1. 두 방식의 차이를 설명하세요.
2. 각각 주로 어떤 상황에서 쓰이나요?
3. 강사는 왜 "둘 다 알아야 한다"고 했을까요?

<details>
<summary>모범 답안</summary>

**1. 차이**

| | 명령형 (Imperative) | 선언형 (Declarative) |
| --- | --- | --- |
| 방식 | 명령을 직접 내림 | 원하는 상태를 파일에 정의 |
| 예시 | `kubectl run nginx --image=nginx` | `kubectl apply -f pod.yaml` |
| 관점 | **"어떻게" 할지**를 지시 | **"무엇을" 원하는지**를 선언 |
| 기록 | 남지 않음 | 파일로 남아 버전 관리 가능 |

명령형은 "이걸 해라, 저걸 실행해라" 하고 지시하는 방식이다. 선언형은 설정 파일에 **원하는 상태(desired state)** 를 적어두고 쿠버네티스가 그 상태를 만들도록 맡긴다.

**2. 사용 상황**

- **명령형**: 트러블슈팅, 클러스터에 문제가 생겼을 때 빠르게 확인, 로컬에서 테스트할 때
- **선언형**: 프로덕션 배포, CI/CD 파이프라인, GitOps

**3. 둘 다 알아야 하는 이유**

실무에서 둘 다 쓰기 때문이다. 운영 중 장애가 났을 때 YAML 파일을 열어 수정하고 apply할 여유가 없다. `kubectl get pods`, `kubectl describe` 같은 명령형이 훨씬 빠르다.

반대로 프로덕션 배포는 반드시 선언형이어야 한다. **파일로 남아야 Git에 올리고, 리뷰하고, 롤백할 수 있기 때문**이다. 명령형으로 배포하면 지금 클러스터가 왜 이 상태인지 아무도 모르게 된다.

</details>

## 문제 2. 컨테이너를 왜 파드로 감싸는가

쿠버네티스에서는 컨테이너를 단독으로 실행할 수 없고 반드시 **파드**로 감싸야 합니다.

1. 왜 컨테이너를 그대로 쓰지 않고 파드라는 개념을 한 겹 더 두었을까요?
2. 파드 안에 컨테이너를 여러 개 넣는 경우는 어떤 경우인가요?
3. `READY 1/1` 과 `READY 2/1` 은 각각 무슨 뜻인가요?

<details>
<summary>모범 답안</summary>

**1. 파드가 필요한 이유**

강사의 비유대로 **파드는 양막(sack), 컨테이너는 아기**다. 뱃속의 아기를 보호하려면 양막이 필요하듯, 컨테이너를 쿠버네티스에서 관리하려면 감싸는 단위가 필요하다.

기술적으로는 **같은 파드 안의 컨테이너들이 네트워크와 리소스를 공유**하게 만들기 위해서다. 같은 파드의 컨테이너는 **동일한 IP를 갖고 localhost로 통신**할 수 있고, 볼륨 같은 데이터 영역도 공유한다. 컨테이너 단위로 관리하면 "이 둘은 항상 같은 노드에서 함께 떠야 한다"를 표현할 방법이 없다.

그래서 **파드가 쿠버네티스에서 가장 작은 배포 단위**가 된다.

**2. 멀티 컨테이너 파드**

대부분은 파드당 컨테이너 하나가 이상적이다. 여러 개를 넣는 건 **메인 컨테이너를 보조하는 역할**일 때다.

- 헬퍼 컨테이너
- 모니터링 에이전트
- init 컨테이너 (메인보다 먼저 실행되어 준비 작업)
- 로그 수집, 설정 동기화 등

반대로 **nginx와 redis처럼 각각이 메인인 컨테이너를 한 파드에 넣는 건 권장하지 않는다.** 개별 파드의 이동과 스케일링이 어려워지기 때문이다.

**3. READY 표기**

- `1/1` — 컨테이너 1개 중 1개가 실행 중 (정상)
- `2/1` — 컨테이너가 2개인데 1개만 실행 중 (문제 있음)

앞이 **전체 컨테이너 수**, 뒤가 **준비된 컨테이너 수**다. `0/1` 이면 컨테이너가 1개인데 하나도 준비되지 않은 상태로, ImagePullBackOff 같은 문제를 의심해야 한다.

</details>

## 문제 3. create와 apply의 차이

`kubectl create -f` 와 `kubectl apply -f` 는 둘 다 리소스를 만듭니다.

1. 두 명령의 차이는 무엇인가요?
2. 이미 존재하는 리소스에 각각을 실행하면 어떻게 되나요?
3. 강의에서 강사가 주로 `apply`를 쓴 이유는 무엇일까요?

<details>
<summary>모범 답안</summary>

**1~2. 차이와 동작**

| | `create` | `apply` |
| --- | --- | --- |
| 역할 | **생성 전용** | **생성 또는 업데이트** |
| 리소스가 없을 때 | 생성 | 생성 |
| 리소스가 있을 때 | **에러** (`already exists`) | 변경된 부분만 **업데이트** |

`create`로 이미 있는 파드를 만들려고 하면 이런 에러가 난다.

```
Error from server (AlreadyExists): pods "nginx-pod" already exists
```

**3. apply를 쓰는 이유**

`apply`가 **선언형 사상에 더 맞기 때문**이다. 선언형은 "내가 원하는 최종 상태는 이것이다"를 말하는 방식인데, `apply`는 현재 상태와 비교해서 **차이만 반영**한다. 리소스가 있든 없든 같은 명령을 쓸 수 있으니 CI/CD에서도 안전하다.

`create`는 "새로 만들어라"라는 명령형에 가깝다. 이미 있으면 실패하므로 파이프라인에서 쓰기 불편하다.

</details>

## 문제 4. ReplicaSet과 Deployment의 차이

Deployment를 만들면 내부적으로 ReplicaSet이 생성됩니다.

1. ReplicaSet만으로도 파드 개수는 유지되는데, 왜 Deployment라는 계층을 하나 더 두었을까요?
2. 두 방식의 업데이트 동작 차이를 설명하세요.
3. 이 차이가 실제 서비스에서 왜 중요한가요?

<details>
<summary>모범 답안</summary>

**1. Deployment를 둔 이유**

ReplicaSet은 **"개수 유지"** 만 담당한다. Deployment는 거기에 **"버전 관리와 배포 전략"** 을 얹은 상위 리소스다.

```
Deployment  →  ReplicaSet  →  Pod
 (배포 전략)    (개수 유지)     (실행)
```

역할을 계층으로 분리해두면, 새 버전을 배포할 때 **새 ReplicaSet을 만들고 기존 것을 남겨둘 수 있다.** 이전 ReplicaSet이 남아 있기 때문에 **롤백이 가능**해진다.

**2. 업데이트 동작 차이**

- **ReplicaSet만 사용**: 변경 적용 시 **모든 파드를 한꺼번에 재생성**한다. 그 사이 서비스가 끊긴다
- **Deployment 사용**: **롤링 업데이트**로 파드를 하나씩 순차 교체한다. 교체 중인 파드의 트래픽은 나머지 파드가 받으므로 **다운타임이 없다**

**3. 실제 서비스에서의 중요성**

nginx처럼 가벼운 앱은 재생성이 몇 초라 체감이 적을 수 있다. 하지만 **은행 앱이나 주식 거래 시스템**이라면 이야기가 다르다. 강사 표현대로 **시간이 곧 돈이라 1밀리초의 다운타임도 허용되지 않는다.**

그래서 실무에서는 파드나 ReplicaSet을 직접 만들지 않고 **처음부터 Deployment로 시작**하는 것이 원칙이다.

</details>

## 문제 5. 서비스가 왜 필요한가

파드끼리는 서비스 없이도 IP로 직접 통신할 수 있습니다.

1. 그럼에도 서비스를 반드시 써야 하는 이유는 무엇인가요?
2. 서비스가 "느슨한 결합(loosely coupled)"을 만든다는 말은 무슨 뜻인가요?
3. Endpoints란 무엇이며, 파드가 재시작되면 어떻게 되나요?

<details>
<summary>모범 답안</summary>

**1. 서비스가 필요한 이유 — 파드 IP는 고정이 아니다**

파드마다 IP가 할당되지만 **파드가 재시작되면 IP가 바뀐다.** 강의에서도 파드를 지웠다가 다시 조회하니 `10.244.1.2` 에서 `10.244.2.3` 으로 바뀌는 것을 확인했다.

그래서 프론트엔드가 백엔드를, 백엔드가 DB를 IP로 직접 부르는 구조는 유지될 수 없다. 서비스는 **변하지 않는 이름과 가상 IP**를 제공해 이 문제를 해결한다.

추가로 서비스는 **여러 파드에 트래픽을 분산(로드 밸런싱)** 하는 역할도 한다.

**2. 느슨한 결합의 의미**

호출하는 쪽이 **상대방의 실제 위치를 몰라도 되는 상태**를 말한다.

백엔드 파드는 프론트엔드 파드가 몇 개인지, 어느 노드에 있는지, IP가 뭔지 알 필요가 없다. 그냥 **서비스 이름만 부르면** 된다. 뒤에서 파드가 늘어나든 줄어들든 옮겨가든 호출하는 코드는 바뀌지 않는다.

반대로 IP를 하드코딩하면 **강하게 결합(tightly coupled)** 되어, 파드가 재시작될 때마다 호출하는 쪽도 고쳐야 한다.

**3. Endpoints**

Endpoints는 **서비스가 트래픽을 전달하는 실제 파드들의 IP 목록**이다. `kubectl get endpoints` 로 조회하면 `kubectl get pods -o wide` 의 파드 IP와 정확히 일치한다.

**파드가 재시작되어 IP가 바뀌면 Endpoints도 자동으로 갱신된다.** 사용자는 서비스 이름만 쓰고, IP 변동은 쿠버네티스가 알아서 처리한다.

참고로 **Endpoints가 비어 있다면 셀렉터와 파드 라벨이 일치하지 않는다는 신호**다. 서비스는 만들어졌는데 접속이 안 될 때 가장 먼저 확인할 지점이다.

</details>

## 문제 6. nodePort, port, targetPort의 차이

NodePort 서비스에는 포트가 세 개 등장합니다.

1. 각각이 **누구를 위한 포트**인지 설명하세요.
2. 세 포트가 모두 같은 값이어도 되나요? 모두 달라도 되나요?
3. `targetPort`를 생략하면 어떻게 되나요?

<details>
<summary>모범 답안</summary>

**1. 각 포트의 주인**

| 포트 | 누구를 위한 것인가 | 범위 |
| --- | --- | --- |
| **nodePort** | **클러스터 외부 사용자**. 브라우저로 `노드IP:30080` 접근 | 30000~32767 |
| **port** | **클러스터 내부의 다른 파드/서비스**. 서비스 이름으로 호출할 때 쓰는 포트 | 자유 |
| **targetPort** | **애플리케이션 컨테이너**가 실제로 리스닝하는 포트. 외부 노출 안 됨 | 자유 |

트래픽 흐름으로 보면 이렇다.

```
외부 사용자 → nodePort(30080) → port(8080) → targetPort(80) → 컨테이너
내부 파드   →                    port(8080) → targetPort(80) → 컨테이너
```

**2. 값의 자유도**

- **모두 같아도 된다.** 강의 예제에서도 port와 targetPort를 둘 다 80으로 썼다
- **모두 달라도 된다.** 다만 nodePort만은 **30000~32767 범위**를 지켜야 한다. 벗어나면 에러가 난다

```
Invalid value: 300001: provided port is not in the valid range. The range is 30000-32767
```

**3. targetPort 생략 시**

**`port`와 같은 값으로 설정된다.** 예를 들어 `port: 80` 만 쓰고 targetPort를 생략하면 targetPort도 80이 된다.

**추가로 알아둘 점**: nodePort 역시 생략할 수 있다. 그러면 쿠버네티스가 범위 내에서 **임의로 할당**한다. `kubectl expose` 명령으로 서비스를 만들면 nodePort를 지정할 수 없어 임의 할당되는 것도 같은 이유다.

</details>

## 보너스. 라벨과 셀렉터는 왜 존재하는가

지금까지 배운 리소스들(ReplicaSet, Deployment, Service)은 모두 **셀렉터로 대상 파드를 찾습니다.**

쿠버네티스는 왜 "이 ReplicaSet은 이 파드들을 소유한다"처럼 직접 연결하지 않고, **라벨이라는 간접적인 방식**을 택했을까요?

<details>
<summary>모범 답안</summary>

**핵심은 느슨한 결합과 유연성이다.**

만약 소유권으로 직접 연결했다면:

- ReplicaSet이 만든 파드는 **그 ReplicaSet만** 관리할 수 있다 (ReplicationController의 한계가 바로 이것)
- 서비스도 특정 Deployment에만 붙일 수 있어, 여러 Deployment의 파드를 한 서비스로 묶을 수 없다
- 파드를 다른 컨트롤러로 옮기려면 지우고 다시 만들어야 한다

라벨 방식이면 이런 게 가능해진다.

- **같은 라벨을 가진 파드라면 누가 만들었든 관리 대상**이 된다
- 하나의 서비스가 **여러 Deployment의 파드**를 동시에 가리킬 수 있다 (블루/그린 배포 등)
- 라벨만 바꾸면 **파드를 컨트롤러 관리에서 빼낼 수 있다** (장애 파드를 살려둔 채 디버깅하는 기법)
- `app=web`, `tier=frontend`, `env=prod` 처럼 **여러 기준으로 동시에 그룹핑**할 수 있다

즉 라벨은 단순한 태그가 아니라 **쿠버네티스에서 리소스들이 서로를 찾는 유일한 방법**이며, 이 간접성 덕분에 구성 요소를 자유롭게 조합하고 교체할 수 있다.

반대로 이 때문에 **라벨 오타 하나로 서비스 Endpoints가 비는** 일이 흔히 생긴다. 셀렉터와 라벨이 일치하는지 확인하는 습관이 중요한 이유다.

</details>
