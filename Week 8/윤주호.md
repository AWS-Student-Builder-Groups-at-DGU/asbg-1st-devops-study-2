
# Day 7 

## 1. 쿠버네티스와 통신하는 구조

사용자는 마스터(컨트롤 플레인) 노드의 **API 서버**와 통신한다. 통신 수단은 `kubectl` 같은 클라이언트 유틸리티이며, 관리형 서비스라면 클라우드 콘솔을 쓸 수도 있다. CKA 시리즈에서는 `kubectl`을 주로 사용한다.

```
사용자 → kubectl → API 서버 (컨트롤 플레인) → 워커 노드에 Pod 생성
```

## 2. Pod를 만드는 두 가지 방식

### 명령형 (Imperative)

- "이것을 해라"라고 **직접 지시**하는 방식
- 예: `kubectl run nginx --image=nginx`
- 쓰이는 곳: 트러블슈팅, 로컬/개발 환경, 빠른 확인
- 장점: 빠르다 

### 선언형 (Declarative)

- 설정 파일(YAML 또는 JSON)에 **원하는 상태(desired state)** 를 정의하고 `kubectl create` / `apply` 로 적용
- 쓰이는 곳: 운영 배포, CI/CD, GitOps
- 장점: 버전 관리·재현성



## 3. 쿠버네티스 YAML의 4가지 최상위 필드

모든 쿠버네티스 매니페스트는 아래 4개를 가진다.

| 필드 | 설명 |
|---|---|
| `apiVersion` | 오브젝트가 속한 API 버전 (예: `v1`, `apps/v1`) |
| `kind` | 오브젝트 종류 (예: `Pod`, `Deployment`, `Service`) |
| `metadata` | 이름, 라벨 등 오브젝트 식별 정보 |
| `spec` | 원하는 상태 상세 정의 (컨테이너, 이미지, 포트 등) |


## 4. metadata와 labels

- `metadata`, `spec` 내부에는 **쿠버네티스가 지원하는 필드만** 넣을 수 있다
- `labels` 내부에는 **원하는 어떤 키-값 쌍이든** 넣을 수 있다 (`env: demo`, `type: frontend` 등)

**라벨의 역할**: 리소스를 그룹화한다. 수백 개 Pod 중 프론트엔드 애플리케이션에 속한 Pod만 골라내는 식으로 쓰이며, ReplicaSet의 `selector`, Service의 `selector`가 모두 이 라벨을 기준으로 동작한다.

## 5. Pod 상태 읽기

```
NAME        READY   STATUS    RESTARTS   AGE
nginx-pod   1/1     Running   0          10s
```

- `READY 1/1` = Pod 안의 컨테이너 총 1개 중 1개가 실행 중
- Pod 안에는 여러 컨테이너가 있을 수 있다 (헬퍼 컨테이너, init 컨테이너 등) → `1/2`, `2/2` 처럼 표시됨
- STATUS는 `ContainerCreating` → `Running` 순으로 진행된다


## 6. dry-run으로 YAML 생성하기

간단한 YAML은 손으로 쓸 수 있지만 수백 줄이 되면 비현실적이다. 명령형 명령어에 `--dry-run=client -o yaml` 을 붙이면 적용 없이 YAML만 출력되며, `>` 로 파일에 저장해 수정해서 쓰면 된다.

- `--dry-run=client` : 실제로 적용하지 않고 결과만 시뮬레이션
- `-o yaml` / `-o json` : 출력 포맷 지정

# Day 8 — ReplicationController / ReplicaSet / Deployment

## 1. 왜 컨트롤러가 필요한가

단일 Pod만 띄워두면 그 Pod가 crash 되는 순간 사용자는 아무 응답도 받지 못한다. 오케스트레이션 시스템이라면 다음이 보장되어야 한다.

1. **Auto-heal** — Pod가 죽으면 자동으로 새 Pod를 띄움
2. **고가용성(HA)** — 동일한 Pod를 여러 개(replica) 실행
3. **로드 밸런싱** — 트래픽을 단일 Pod가 아니라 컨트롤러로 보내고, 컨트롤러가 정상(healthy)인 Pod로 분산
4. **스케일링** — 트래픽 증가 시 복제본 수를 늘려 대응

## 2. Replication Controller

- Controller Manager가 관리하는 컨트롤러 중 하나
- **컨트롤러 = 리소스가 항상 원하는 상태로 유지되도록 모니터링하는 존재**. 노드, 네임스페이스, Pod 등 모든 리소스에 대한 컨트롤러가 존재한다
- `replicas` 에 지정한 수만큼 Pod를 **항상** 유지한다. 1개 죽으면 1개, 2개 죽으면 2개를 띄운다
- 여러 노드에 걸쳐 Pod를 배치할 수 있다

### 스케일링과 노드 추가

복제본 수를 2 → 3으로 올리면 새 Pod가 뜬다. 노드의 CPU·메모리·스토리지가 부족해지는 지점까지 트래픽이 늘면 **새 노드를 추가**하고 그 노드에 Pod를 배치한다. 

## 3. spec.template 구조

Replication Controller/ReplicaSet은 Pod를 "만들어내는" 존재이므로, 어떤 Pod를 만들지에 대한 정보가 필요하다. 그 정보가 `spec.template` 에 들어간다.

```yaml
spec:                  # ① 컨트롤러의 spec
  replicas: 3
  template:
    metadata:          # ② Pod의 metadata
      labels:
        env: demo
    spec:              # ③ Pod의 spec
      containers:
        - name: nginx-container
          image: nginx
```

- Pod YAML에서 `apiVersion`, `kind` 두 줄만 빼고 `metadata` + `spec` 을 그대로 `template` 아래에 넣는 형태
- **`metadata`가 2개, `spec`이 2개**가 되는데, 하나는 컨트롤러의 것이고 하나는 template 내부 Pod의 것이다.

## 4. Replication Controller vs ReplicaSet

| 항목 | ReplicationController | ReplicaSet |
|---|---|---|
| 위상 | 레거시(구 버전) | 최신 버전 (**권장**) |
| `apiVersion` | `v1` | `apps/v1` |
| `selector` | 없음 | `selector.matchLabels` 필수 |
| 관리 범위 | 자신이 생성한 Pod만 관리 | `matchLabels`로 **기존에 있던 Pod까지** 관리 가능 |

ReplicaSet의 핵심 차이는 `selector.matchLabels` 다. 지정한 라벨을 가진 Pod라면 ReplicaSet이 직접 만들지 않은 Pod여도 자기 관리 대상으로 편입한다.


## 5. Deployment

### 계층 구조

```
Deployment → ReplicaSet → Pod
```

사용자는 Deployment를 만들고, Deployment가 ReplicaSet을 만들고, ReplicaSet이 Pod를 관리한다. `kubectl get all` 로 이 구조를 한 번에 볼 수 있다.

### Deployment가 추가로 제공하는 것 — 롤링 업데이트

ReplicaSet만 쓸 때 이미지를 1.1 → 1.2 로 바꾸면 **모든 Pod가 한 번에 재생성**되어 다운타임이 발생한다.

금융 기관이나 주식 거래 앱처럼 1밀리초의 다운타임도 허용되지 않는 환경에서는 곤란하다. Deployment는 **롤링 업데이트** 방식으로 동작한다.

1. Pod 하나를 업데이트하는 동안 트래픽은 나머지 Pod가 처리
2. 새 Pod가 준비되면 로드밸런서/ReplicaSet에 추가되어 트래픽을 받기 시작
3. 순차적으로 다음 Pod를 교체 → **다운타임 없이** 전체 배포 완료

### 롤백 (Revision)

- `rollout history` 로 리비전 이력 확인 (리비전 1 = 최초 생성, 이후 변경마다 증가)
- `rollout undo` 로 직전 리비전으로 되돌릴 수 있다
- 롤백 자체도 새 리비전으로 기록된다

## 6. 복제본 수를 바꾸는 3가지 방법

| 방법 | 명령 | 특징 |
|---|---|---|
| YAML 수정 후 재적용 | `kubectl apply -f rs.yaml` | 파일과 클러스터 상태가 일치 (GitOps 친화적) |
| 라이브 오브젝트 수정 | `kubectl edit rs <name>` | 즉시 반영. VI 단축키 필요. **로컬 YAML은 변경 안 됨** |
| 명령형 scale | `kubectl scale --replicas=10 rs/<name>` | 가장 빠름 |

# Day 9 — Service

## 1. 왜 Service가 필요한가

### 문제 1 — 외부 노출

Deployment로 Pod를 띄워도 그 Pod는 **클러스터 내부에서만** 접근 가능하다. 프론트엔드 애플리케이션이라면 외부 사용자가 접근할 수 있어야 한다.

### 문제 2 — Pod IP는 고정이 아니다

모든 Pod에는 전용 IP가 할당되지만, **Pod가 재시작되는 즉시 IP가 바뀐다.**

```
kubectl describe pod  →  IP: 10.244.1.2
kubectl delete pod
kubectl describe pod  →  IP: 10.244.2.3   (변경됨)
```

따라서 IP로 Pod를 참조하는 방식은 쓸 수 없다. 클러스터 수명 주기 동안 **변하지 않는 무언가**가 필요하다.

### 문제 3 — 계층 간 통신

프론트엔드 Pod ↔ 백엔드 Pod ↔ 데이터베이스/외부 데이터 소스가 서로 통신해야 한다.

### 결론

Service가 이 모든 것을 해결한다. Service는 애플리케이션을 **느슨하게 결합(loosely coupled)** 시키고, Pod가 특정 포트에서 수신 대기하며 지정한 대상에게만 접근 가능하도록 보장한다.

## 2. Service의 4가지 타입

| 타입 | 용도 | 외부 노출 |
|---|---|---|
| **ClusterIP** | 클러스터 내부 통신 (기본값) | ✕ |
| **NodePort** | 노드의 특정 포트로 외부 노출 | ○ (30000~32767) |
| **LoadBalancer** | 클라우드 로드밸런서를 통한 외부 노출 | ○ |
| **ExternalName** | 외부 DNS 이름으로 매핑 | - |

## 3. NodePort

### 세 가지 포트의 차이 — 가장 중요한 개념

```
외부 사용자 ──[nodePort: 30001]──> Service ──[port: 80]──> Pod [targetPort: 80]
```

| 필드 | 의미 | 누가 사용하나 |
|---|---|---|
| `nodePort` | **외부에 노출되는 포트** | 브라우저/로컬 시스템 등 클러스터 외부 사용자 |
| `port` | **클러스터 내부 서비스 포트** | 같은 클러스터의 다른 Pod/서비스 (예: 백엔드 → 프론트엔드) |
| `targetPort` | **Pod(컨테이너)가 실제 수신 대기하는 포트** | Service가 트래픽을 전달하는 목적지. 외부에 노출되지 않음 |

- `nodePort` 범위: **30000 ~ 32767** (이 범위를 벗어나면 `Invalid value` 에러)
- 아무것도 지정하지 않으면 기본 포트 80을 사용

### 접근 방법

`<노드 IP>:<nodePort>` 로 접근한다. 여러 노드·여러 Pod가 있어도 Service가 **라운드 로빈** 방식으로 트래픽을 내부 분산한다.

### Service의 selector

Service가 어떤 Pod를 노출할지는 `selector`에 지정한 라벨로 결정된다.

```yaml
spec:
  selector:
    env: demo      # ReplicaSet과 달리 matchLabels를 쓰지 않는다
```

**ReplicaSet은 `selector.matchLabels`, Service는 `selector` 아래 라벨을 직접** 쓴다. 

대상 Pod의 라벨은 `kubectl get pods --show-labels` 로 확인한다.

### kind 클러스터에서의 추가 작업

kind 클러스터는 **NodePort를 호스트 외부로 노출하지 않는다.** 그래서 `kind.yaml`의 control-plane 역할에 `extraPortMappings`를 추가해 컨테이너 포트 30001을 호스트 포트 30001로 매핑해야 한다.

kind는 **기존 클러스터를 수정할 수 없으므로 클러스터를 삭제하고 재생성**해야 한다. 재생성 후에는 `localhost:30001` 로 접근할 수 있다.

## 4. ClusterIP

- **기본 서비스 타입** (`type` 필드를 생략하면 ClusterIP로 생성됨)
- 클러스터 **내부 전용**이므로 `EXTERNAL-IP`가 없다
- 다른 Pod/서비스가 **서비스 이름 또는 ClusterIP**로 대상 Pod에 접근할 수 있게 해준다 → Pod IP가 바뀌어도 영향 없음
- `nodePort` 필드가 필요 없고 `port` / `targetPort` 만 지정
- 클러스터 생성 시 `kubernetes` 라는 이름의 기본 ClusterIP 서비스가 자동으로 만들어져 있다

### Endpoints

**엔드포인트 = 서비스가 트래픽을 보내는 Pod들의 IP 목록**

```bash
kubectl get endpoints    # 또는 kubectl get ep
```

- `kubectl get pods -o wide` 로 본 Pod IP들과 정확히 일치한다
- **Pod가 재시작되어 새 IP가 할당되면 엔드포인트도 자동으로 갱신된다**
- 같은 Deployment를 대상으로 NodePort 서비스와 ClusterIP 서비스를 각각 만들면, 두 서비스의 엔드포인트는 동일하다

## 5. LoadBalancer

### 왜 필요한가

Pod마다 IP가 다르고 그마저 계속 바뀐다. 3개 노드 정도면 몰라도 **50개 노드에 분산된 애플리케이션이라면 사용자에게 50개의 IP를 줄 수는 없다.**

사용자에게 필요한 것은 `myapp.com` 같은 **하나의 URL**이다. 로드밸런서가 모든 Pod를 백엔드에 두고, 사용자는 로드밸런서 URL 하나로만 접근하며, 로드밸런서가 알고리즘에 따라 트래픽을 분산한다.

<img width="1069" height="562" alt="image" src="https://github.com/user-attachments/assets/b20cdeca-ebf1-48e1-8575-4a7bd7a5f1ee" />


### 쿠버네티스에서의 동작

- AWS / Azure / GCP 같은 클라우드 제공업체 환경에서 **외부 로드밸런서를 프로비저닝**한 뒤, `type: LoadBalancer` 서비스를 만들면 그 로드밸런서를 참조한다
- 로드밸런서가 없으면 `EXTERNAL-IP`가 `<pending>` 상태로 남고, 랜덤 NodePort가 할당되어 **NodePort처럼 동작**한다
- kind에서 시뮬레이션하려면 `cloud-provider-kind` 바이너리를 별도로 설치해야 한다

## 6. ExternalName

- 라벨 selector 대신 **실제 DNS 이름에 매핑**하는 타입
- 예: 데이터베이스가 특정 DNS에서 수신 대기 중일 때, 그 DNS를 `externalName`으로 지정
- 클러스터 내부 서비스가 그 이름을 참조해 외부 리소스에 접근할 수 있다
- 이름 그대로의 의미라 직관적이다
