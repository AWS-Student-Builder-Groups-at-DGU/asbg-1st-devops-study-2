## Day 7. Pod와 YAML 기초

### 1. 전체 흐름
사용자는 `kubectl` 같은 클라이언트로 컨트롤 플레인의 API 서버에 요청을 보냅니다. API 서버는 요청을 받아 리소스를 생성, 수정, 삭제, 조회하고, 생성된 Pod는 워커 노드 중 하나에 배치되어 실행됩니다.

```
User → kubectl → API Server (Control Plane) → Worker Node 위에 Pod 생성
```

### 2. Pod란
Pod는 쿠버네티스에서 배포할 수 있는 가장 작은 단위이며, 하나 이상의 컨테이너를 감싸는 묶음입니다.

**컨테이너를 Pod로 감싸는 이유**
- **자원 공유**: 같은 Pod 안의 컨테이너는 네트워크(같은 IP, 포트 공간)를 공유해 `localhost`로 통신하고, 볼륨도 함께 마운트할 수 있습니다. 예를 들어 앱 컨테이너가 로그를 쓰면 옆의 사이드카 컨테이너가 같은 볼륨에서 읽어 전송하는 구조가 가능합니다.
- **스케줄링, 생명주기 단위**: Pod 안의 컨테이너는 항상 같은 노드에 함께 배치되고 함께 생성, 삭제됩니다.
- **IP 부여 단위**: IP는 컨테이너가 아니라 Pod에 부여됩니다. Docker처럼 호스트 포트 매핑을 신경 쓰지 않고 각 Pod가 독립된 호스트처럼 통신합니다. 내부적으로는 pause 컨테이너가 네트워크 공간을 잡고 나머지 컨테이너가 여기에 붙습니다.
- **런타임 추상화**: 쿠버네티스는 Pod 단위로 관리하고 실제 실행은 containerd, CRI-O 등 런타임에 맡기므로 런타임 교체가 자유롭습니다.

실무에서는 대부분 Pod 하나에 컨테이너 하나를 넣지만, 헬퍼 컨테이너나 init 컨테이너(본 컨테이너 실행 전에 준비 작업만 하고 종료)를 함께 쓰는 경우도 있습니다.

### 3. Pod 생성 방식

<img width="1964" height="1056" alt="image" src="https://github.com/user-attachments/assets/8725b56c-70d7-4a66-8862-9fb8fc71a363" />

| 방식 | 설명 | 주 사용처 |
|---|---|---|
| 명령형 (Imperative) | `kubectl run`처럼 명령어로 "이것을 실행하라"고 직접 지시 | 트러블슈팅, 로컬 테스트, 빠른 확인 |
| 선언형 (Declarative) | 설정 파일(YAML/JSON)에 원하는 상태를 정의하고 `create` / `apply`로 적용 | 운영 배포, CI/CD, GitOps |

두 방식 모두 실무와 시험에서 사용하므로 둘 다 익숙해져야 합니다. JSON도 지원하지만 실제로는 거의 YAML을 사용합니다.

### 4. 명령형으로 Pod 생성
```bash
kubectl run nginx-pod --image=nginx      # 태그 생략 시 latest
kubectl get pods
```
- 상태는 `ContainerCreating` → `Running` 순으로 바뀝니다.
- `READY 1/1`은 Pod 안 컨테이너 1개 중 1개가 준비되었다는 뜻입니다. 컨테이너가 2개라면 `1/2`, `2/2`처럼 표시됩니다.

### 5. YAML 문법
YAML은 간결하고 직관적이라 쿠버네티스뿐 아니라 Docker Compose, Prometheus 등에서도 설정 언어로 널리 쓰입니다.

- 확장자는 `.yaml`, `.yml` 모두 같습니다.
- `#`으로 주석을 작성합니다.
- JSON의 중괄호 대신 **들여쓰기와 공백**으로 구조를 표현합니다. 공백 2칸을 권장하고 탭은 권장하지 않습니다.
- 문자열은 따옴표 없이 써도 됩니다.
- 문자열, 정수, 딕셔너리, 리스트 등을 지원합니다.

```yaml
# 딕셔너리
employee:
  name: minhyeong
  age: 25

# 리스트 (-로 표현) 와 중첩
employees:
- name: a
  age: 25
  address:
  - old address
  - new address
- name: b
  age: 30
```
들여쓰기가 한 칸이라도 어긋나면 하위 필드가 아니라 별도 필드로 인식되어 구조가 깨집니다.

### 6. 쿠버네티스 YAML 최상위 필드

| 필드 | 역할 | 예시 |
|---|---|---|
| `apiVersion` | 오브젝트 생성에 사용할 API 버전 | Pod, Service: `v1` / ReplicaSet, Deployment: `apps/v1` |
| `kind` | 생성할 오브젝트 종류 (대소문자 구분) | `Pod`, `ReplicaSet`, `Deployment`, `Service` |
| `metadata` | 오브젝트 식별 정보 | `name`, `labels` |
| `spec` | 오브젝트의 원하는 상태 | 컨테이너, 이미지, 포트, replicas 등 |

- 필드 이름과 값 모두 대소문자를 구분합니다.
- 지원 버전은 `kubectl explain <리소스>`로 확인합니다. 출력의 `GROUP`이 있으면 `그룹/버전` 형식으로 씁니다.
- `metadata`, `spec`에는 정해진 필드만 쓸 수 있지만, `labels` 안에는 원하는 key-value를 자유롭게 넣을 수 있습니다.

### 7. Pod YAML 예시
```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    env: demo
    type: frontend
spec:
  containers:            # 리스트
  - name: nginx-container
    image: nginx
    ports:               # containers 안의 하위 리스트
    - containerPort: 80
```

```bash
kubectl create -f pod.yaml
kubectl apply -f pod.yaml
```
- `create`: 생성만 가능하며 이미 있으면 에러가 납니다.
- `apply`: 없으면 생성하고 있으면 업데이트합니다. `create`로 만든 오브젝트에 처음 `apply`하면 last-applied-configuration annotation이 없다는 경고가 나오지만 무시해도 됩니다.

### 8. 트러블슈팅 실습
이미지 이름을 일부러 틀리게 바꿔 적용하면 `READY 0/1`, 상태 `ImagePullBackOff`가 됩니다.

```bash
kubectl describe pod nginx-pod
```
Events 항목에서 이미지 pull 실패 원인을 확인할 수 있습니다. 이미지 이름이나 태그가 틀렸거나, 비공개 이미지에 대한 권한이 없는 경우입니다.

**수정 방법**
1. YAML을 고치고 `kubectl apply -f pod.yaml`
2. 라이브 오브젝트를 직접 수정: `kubectl edit pod nginx-pod` (vi 편집기에서 수정 후 `:wq`, 저장 즉시 반영)

`kubectl edit`는 클러스터의 라이브 오브젝트만 바꾸며 로컬 YAML 파일은 그대로입니다.

### 9. 기타 명령어
```bash
kubectl exec -it nginx-pod -- sh        # 컨테이너 내부 셸 접속
kubectl delete pod nginx-pod
kubectl describe pod nginx-pod          # 상태, 노드, 이미지, 라벨, 이벤트 등 전체 정보
kubectl get pods nginx-pod --show-labels
kubectl get pods -o wide                # IP, 실행 노드 추가 표시
kubectl get nodes -o wide               # OS 이미지, 커널 버전, 컨테이너 런타임, 외부 IP
```
라벨은 여러 리소스를 그룹으로 묶는 데 쓰입니다. 예를 들어 Pod가 수백 개일 때 frontend 라벨이 붙은 것만 조회할 수 있습니다.

### 10. YAML 자동 생성 (dry run)
필드가 많아지면 YAML을 직접 작성하기 번거로우므로 명령형 명령어로 뼈대를 뽑아 수정해서 씁니다.

```bash
kubectl run nginx --image=nginx --dry-run=client -o yaml > pod-new.yaml
kubectl run nginx --image=nginx --dry-run=client -o json > pod-new.json
```
- `--dry-run=client`: 실제로 적용하지 않고 결과만 보여줍니다.
- 생성된 파일에서 `creationTimestamp`, `status` 같은 불필요한 필드는 지우고 라벨 등을 수정해 사용합니다.

### 11. 시험 팁
시험 환경에는 VS Code가 없고 터미널만 있으므로 vi 편집기 사용에 익숙해져야 합니다.

## Day 8. ReplicationController, ReplicaSet, Deployment

### 1. 왜 필요한가
Pod 하나만 띄워두면 Pod가 죽었을 때 사용자는 응답을 받지 못합니다. Docker 컨테이너를 단독으로 실행할 때와 같은 문제입니다. 오케스트레이션 시스템은 이를 자동으로 복구해야 하며, 이 역할을 컨트롤러가 합니다.

컨트롤러는 Controller Manager가 관리하며, 리소스가 원하는 상태를 유지하도록 계속 감시합니다. 노드, 네임스페이스 등 리소스마다 컨트롤러가 있고, Pod 복제본을 관리하는 것이 ReplicationController와 ReplicaSet입니다.

### 2. 복제 컨트롤러가 하는 일

<img width="2844" height="1396" alt="image" src="https://github.com/user-attachments/assets/bff4b7ee-da5f-483f-aaf1-75e21481c227" />

- **자동 복구**: replicas에 지정한 개수를 항상 유지합니다. 3개 중 1개가 죽으면 1개를, 2개가 죽으면 2개를 새로 만듭니다. replicas가 1이어도 Pod가 죽으면 새로 만듭니다.
- **고가용성, 부하 분산**: 동일한 Pod 여러 개로 트래픽을 나눠 처리합니다.
- **수동 스케일링**: 트래픽이 늘면 replicas를 늘립니다. 노드 자원(CPU, 메모리, 스토리지)이 부족하면 노드를 추가하며, 컨트롤러는 여러 노드에 걸쳐 Pod를 관리할 수 있습니다.

자동 스케일링(HPA, VPA)은 이후 영상에서 다룹니다.

### 3. ReplicationController
```yaml
apiVersion: v1
kind: ReplicationController
metadata:
  name: nginx-rc
  labels:
    env: demo
spec:
  replicas: 3
  template:                  # 새 Pod를 만들 때 사용할 설계도
    metadata:
      labels:
        env: demo
    spec:
      containers:
      - name: nginx-container
        image: nginx
        ports:
        - containerPort: 80
```
- Pod가 죽었을 때 어떤 이미지, 포트로 새로 만들지 알아야 하므로 `template`에 Pod의 metadata와 spec을 넣습니다. 기존 Pod YAML에서 `apiVersion`, `kind`를 뺀 나머지를 그대로 옮긴다고 생각하면 됩니다.
- metadata와 spec이 두 번씩 나옵니다. **바깥쪽은 RC 자신의 것, template 안쪽은 Pod의 것**입니다.
- 생성된 Pod 이름은 `RC이름-랜덤문자열` 형식입니다.

```bash
kubectl explain rc
kubectl apply -f rc.yaml
kubectl get rc
kubectl describe pod <pod이름>     # Controlled By 항목에서 관리 주체 확인
```

### 4. ReplicaSet
| 구분 | ReplicationController | ReplicaSet |
|---|---|---|
| 상태 | 레거시 | 권장 |
| apiVersion | `v1` | `apps/v1` |
| 관리 대상 | 자신이 만든 Pod만 | `selector`로 기존 Pod도 선택해 관리 |

```yaml
apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: nginx-rs
  labels:
    env: demo
spec:
  replicas: 3
  selector:
    matchLabels:
      env: demo
  template:
    metadata:
      labels:
        env: demo
    spec:
      containers:
      - name: nginx-container
        image: nginx
        ports:
        - containerPort: 80
```
`apiVersion: v1`으로 적용하면 `no matches for kind "ReplicaSet" in version "v1"` 에러가 납니다. `kubectl explain rs`를 보면 GROUP이 `apps`이므로 `apps/v1`로 써야 합니다.

### 5. selector와 matchLabels의 동작
- `selector`는 "어떤 Pod를 관리할지" 고르는 조건입니다.
- `matchLabels`는 그 조건을 쓰는 방법 중 하나로, 라벨이 정확히 일치하는 Pod를 고릅니다. 이 외에 `matchExpressions`(In, NotIn, Exists 등 조건식)도 쓸 수 있습니다.
- ReplicaSet이 라벨을 붙이는 것이 아니라, 새 Pod를 만들 때 **template의 labels**가 Pod에 붙습니다.
- ReplicaSet은 selector에 맞는 Pod 수를 계속 세면서 replicas보다 적으면 template으로 새로 만들고, 많으면 삭제합니다.
- 따라서 **selector와 template labels는 반드시 일치**해야 합니다. 다르면 생성 시 에러가 납니다.
- 이미 떠 있던 Pod라도 라벨이 selector와 맞고 다른 컨트롤러 소속이 아니면 편입됩니다. 실습에서 RC가 만든 Pod 3개를 RC 삭제 후 ReplicaSet이 그대로 가져간 것이 이 경우입니다.

**동작 예시**
- replicas 3인 상태에서 Pod 하나를 직접 삭제하면 → 새 Pod를 하나 만들어 3개 유지 (이름과 IP는 달라짐)
- 같은 라벨의 Pod를 따로 하나 더 만들면 → 4개로 세어지므로 하나를 삭제해 3개 유지

### 6. replicas 변경 방법 세 가지
```bash
# 1. YAML 수정 후 적용
kubectl apply -f rs.yaml

# 2. 라이브 오브젝트 직접 수정 (저장 즉시 반영)
kubectl edit rs nginx-rs

# 3. 명령형
kubectl scale --replicas=10 rs/nginx-rs
```
- `kubectl edit`로 열리는 라이브 오브젝트에는 `last-applied-configuration` annotation, `creationTimestamp`, `resourceVersion`, `uid` 등 직접 쓰지 않은 필드가 추가로 보입니다.
- vi에서 `Shift + A`는 줄 끝으로 이동하면서 입력 모드로 들어가는 단축키입니다.
- 명령어가 기억나지 않으면 `kubectl scale --help`의 예제를 복사해 쓰면 됩니다.

### 7. Deployment

<img width="2008" height="1480" alt="image" src="https://github.com/user-attachments/assets/1b706d60-aba5-43d7-87cd-54c50f0abeff" />

**구조**
```
Deployment → ReplicaSet → Pod
```
사용자가 Deployment를 만들면 Deployment가 ReplicaSet을 만들고, ReplicaSet이 Pod를 만들고 개수를 유지합니다.

**ReplicaSet만으로 부족한 이유**
ReplicaSet은 "개수 유지"만 합니다. template의 이미지를 바꿔도 이미 떠 있는 Pod는 그대로 두고, 이후 새로 생성되는 Pod에만 새 template이 적용됩니다. 즉 버전 업데이트를 하려면 기존 Pod를 직접 지워야 하고, 그 과정에서 다운타임이 생깁니다. 은행, 증권 같은 서비스에서는 짧은 중단도 허용되지 않습니다.

**롤링 업데이트 원리**
1. 이미지를 바꾸면 Deployment는 기존 ReplicaSet을 수정하지 않고 **새 template으로 새 ReplicaSet을 하나 더 만듭니다**.
2. 새 ReplicaSet의 replicas를 조금씩 늘리고, 기존 ReplicaSet의 replicas를 조금씩 줄입니다.
3. 업데이트 중에도 항상 일부 Pod가 트래픽을 처리하므로 무중단 배포가 됩니다.
4. 끝나면 새 ReplicaSet은 원래 개수, 기존 ReplicaSet은 replicas 0으로 남습니다.

한 번에 얼마나 교체할지는 다음 값으로 조절합니다.

| 필드 | 의미 | 기본값 |
|---|---|---|
| `maxSurge` | 업데이트 중 replicas보다 추가로 띄울 수 있는 Pod 수 | 25% |
| `maxUnavailable` | 업데이트 중 사용 불가 상태가 되어도 되는 Pod 수 | 25% |

**롤백 원리**
기존 ReplicaSet이 삭제되지 않고 replicas 0으로 남아 있으므로, `rollout undo`를 하면 기존 ReplicaSet을 다시 늘리고 새 것을 줄이는 방식으로 빠르게 되돌립니다. 롤백도 새 리비전으로 기록됩니다.

### 8. Deployment 실습
ReplicaSet YAML에서 `kind`만 `Deployment`로 바꾸면 됩니다 (`apiVersion`은 `apps/v1` 동일).

```bash
kubectl apply -f deploy.yaml
kubectl get deploy
kubectl get rs
kubectl get all        # Deployment, ReplicaSet, Pod, Service 전체 조회
```
`get all`에 보이는 `kubernetes` Service는 클러스터 생성 시 기본으로 만들어지는 것입니다.

**이미지 변경과 롤백**
```bash
kubectl set image deploy/nginx-deploy nginx-container=nginx:1.9.1
kubectl describe deploy nginx-deploy        # Image 항목 확인
kubectl get rs                              # ReplicaSet 2개 확인

kubectl rollout history deploy/nginx-deploy # 리비전 목록
kubectl rollout undo deploy/nginx-deploy    # 직전 상태로 롤백
kubectl rollout undo deploy/nginx-deploy --to-revision=1   # 특정 리비전으로
kubectl rollout status deploy/nginx-deploy
kubectl rollout restart deploy/nginx-deploy
```
`set image`도 라이브 오브젝트만 바꾸므로 로컬 YAML의 이미지는 그대로입니다.

**YAML 자동 생성**
```bash
kubectl create deploy nginx-new --image=nginx --dry-run=client -o yaml > deploy.yaml
```
`--image`를 빼면 `required flag(s) "image" not set` 에러가 납니다. 생성된 파일에는 replicas 1(기본값), selector의 matchLabels, template 등이 들어 있습니다.

### 9. 시험 팁
시험은 시간 싸움이므로 같은 작업이라도 가장 빠른 방법을 선택합니다. 명령어를 알면 명령형으로, vi에 익숙하면 `edit`로, 둘 다 어려우면 공식 Quick Reference나 `--help` 예제를 복사해 씁니다.

## Day 9. Service

### 1. 왜 필요한가

<img width="2904" height="608" alt="image" src="https://github.com/user-attachments/assets/385cdd93-9a23-429d-8c08-de8f4e313a3b" />

Deployment의 Pod들은 그대로는 외부에 노출되지 않고 클러스터 내부에서만 접근할 수 있습니다. 또한 Pod IP는 재시작할 때마다 바뀌므로 Pod IP로 직접 통신할 수 없습니다.

```
User → Service → Frontend Pods → Service → Backend Pods → Service → External Data Source
```
Service는 Pod들을 라벨로 묶어 **고정된 이름과 IP**를 제공하고, 외부 노출과 내부 통신을 담당합니다. 이를 통해 각 계층이 느슨하게 결합되고, 지정한 포트와 대상으로만 접근이 허용됩니다.

### 2. Service 타입

| 타입 | 용도 | 외부 접근 |
|---|---|---|
| ClusterIP | 클러스터 내부 통신 (기본값) | 불가 |
| NodePort | 노드의 특정 포트로 외부 노출 | `노드IP:nodePort` |
| LoadBalancer | 클라우드 외부 로드밸런서와 연결 | LB 주소 |
| ExternalName | 외부 DNS 이름에 매핑 | 해당 없음 |

### 3. 포트 구분

<img width="1888" height="1124" alt="image" src="https://github.com/user-attachments/assets/ec921ac5-0042-40d1-ad89-f1d43525dd3a" />

| 필드 | 의미 | 사용 주체 |
|---|---|---|
| `nodePort` | 노드에 열리는 포트 (30000 ~ 32767) | 클러스터 외부 사용자 |
| `port` | Service 자체의 포트 | 클러스터 내부의 다른 Pod |
| `targetPort` | Pod 안 애플리케이션이 리스닝하는 포트 | Service가 Pod로 전달할 때 |

```
외부 사용자 → 노드IP:30001 (nodePort) → Service:80 (port) → Pod:80 (targetPort)
```
- `targetPort`를 생략하면 `port`와 같은 값이 쓰입니다.
- 외부 사용자는 `nodePort`로, 백엔드 Pod 같은 내부 클라이언트는 `port`로 접근합니다.
- Pod가 여러 노드에 흩어져 있어도 Service가 뒤의 Pod들로 트래픽을 분산합니다.

### 4. NodePort
```yaml
apiVersion: v1
kind: Service
metadata:
  name: nodeport-svc
  labels:
    env: demo
spec:
  type: NodePort
  ports:
  - nodePort: 30001
    port: 80
    targetPort: 80
  selector:
    env: demo            # 대상 Pod의 라벨
```
```bash
kubectl explain svc
kubectl apply -f nodeport.yaml
kubectl get svc
kubectl describe svc nodeport-svc
```

**실습 중 만난 에러**
| 에러 원인 | 해결 |
|---|---|
| selector 안에 `matchLabels` 사용 | Service는 라벨을 바로 작성 (ReplicaSet, Deployment와 다름) |
| `type: nodePort` | 대소문자 구분, `NodePort`로 작성 |
| `nodePort: 300001` | 범위(30000 ~ 32767) 밖, `30001`로 수정 |

접근 주소는 Pod IP가 아니라 **노드 IP**입니다. Pod가 떠 있는 노드는 `kubectl get pods -o wide`나 `describe pod`의 Node 항목에서 확인합니다.

### 5. kind 클러스터 포트 매핑
kind는 노드가 Docker 컨테이너로 떠 있어서 NodePort가 호스트에 자동으로 노출되지 않습니다. 그래서 노드 IP로 접근해도 응답이 없습니다. 클러스터 설정에 `extraPortMappings`를 추가하고 클러스터를 새로 만들어야 합니다 (기존 클러스터는 변경 불가).

```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
  extraPortMappings:
  - containerPort: 30001
    hostPort: 30001
- role: worker
- role: worker
```
```bash
kind delete cluster --name <기존클러스터>
kind create cluster --config kind.yaml --name cka-cluster3
kubectl apply -f ../day08/deploy.yaml
kubectl apply -f nodeport.yaml
curl localhost:30001         # Welcome to nginx 확인
```
시험 환경이나 온프레미스, 클라우드 클러스터에서는 이 작업 없이 `노드IP:nodePort`로 바로 접근됩니다. kind는 포트 매핑 때문에 `localhost`로 접근하는 것이 차이점입니다.

### 6. ClusterIP

<img width="2440" height="1200" alt="image" src="https://github.com/user-attachments/assets/43489a02-05aa-46bf-8d5c-c78c038ddc51" />

Pod를 삭제하면 새로 생긴 Pod의 IP가 달라지는 것을 `describe`로 확인할 수 있습니다. 프론트엔드, 백엔드, DB 간 통신은 이렇게 바뀌는 IP 대신 ClusterIP Service의 이름이나 IP로 해야 합니다.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: cluster-svc
  labels:
    env: demo
spec:
  ports:                 # type 생략 시 ClusterIP
  - port: 80
    targetPort: 80
  selector:
    env: demo
```
- `type` 기본값이 ClusterIP이므로 생략해도 됩니다.
- 외부 노출이 없으므로 `nodePort`는 필요 없고, EXTERNAL-IP도 없습니다.
- ClusterIP는 특정 포트에 고정된 개념이 아니라 Service에 지정한 `port`로 동작합니다. 기본 `kubernetes` Service는 443 포트를 사용합니다.

### 7. Endpoints
Endpoints는 Service가 실제로 트래픽을 전달하는 **Pod IP 목록**입니다.

```bash
kubectl describe svc cluster-svc
kubectl get endpoints        # 또는 get ep
kubectl get pods -o wide     # Pod IP와 비교
```
- Pod가 재시작되어 IP가 바뀌면 Endpoints도 자동 갱신됩니다.
- NodePort와 ClusterIP Service가 같은 Deployment를 가리키면 selector가 같으므로 두 Service의 Endpoints도 같습니다.

### 8. LoadBalancer

<img width="2164" height="1080" alt="image" src="https://github.com/user-attachments/assets/9a766227-712a-4c4a-bb17-c65e0281ca97" />

Pod가 수십 개 노드에 분산되어 있으면 사용자에게 노드 IP를 모두 알려줄 수 없습니다. 사용자는 `myapp.com` 같은 단일 주소를 원하므로, 로드밸런서가 요청을 받아 알고리즘에 따라 뒤의 Pod들로 분산합니다.

AWS, Azure, GCP 등 클라우드 환경에서는 외부 로드밸런서가 프로비저닝되고, 쿠버네티스에서 `type: LoadBalancer` Service로 연결합니다.

```yaml
spec:
  type: LoadBalancer
  ports:
  - port: 80
    targetPort: 80
  selector:
    env: demo
```
- 외부 로드밸런서가 없는 환경에서는 EXTERNAL-IP가 `<pending>`으로 남고, 랜덤 NodePort가 할당되어 NodePort처럼 동작합니다.
- kind에서는 `cloud-provider-kind`를 설치하면 로드밸런서를 흉내 낼 수 있습니다 (영상에서는 생략).

### 9. ExternalName
라벨 selector로 Pod를 고르지 않고 외부 DNS 이름에 매핑합니다. 예를 들어 외부 DB 주소를 Service 이름으로 등록해두면 클러스터 내부 서비스는 그 이름으로 외부 리소스를 참조할 수 있습니다.

```yaml
spec:
  type: ExternalName
  externalName: db.example.com
```

### 10. 명령형으로 Service 생성
```bash
kubectl expose deployment nginx-deploy --port=80 --target-port=80
kubectl expose deployment nginx-deploy --type=NodePort --port=80 --target-port=80
```
YAML을 직접 쓰지 않아도 되므로 시험에서 시간을 아낄 수 있습니다.


## 헷갈리기 쉬운 포인트 정리

| 항목 | 내용 |
|---|---|
| apiVersion | Pod, Service는 `v1`, ReplicaSet, Deployment는 `apps/v1` |
| selector 형식 | ReplicaSet, Deployment는 `matchLabels` 사용, Service는 라벨을 바로 작성 |
| template labels | ReplicaSet, Deployment의 selector와 반드시 일치 |
| 라이브 수정 | `edit`, `set image`, `scale`은 로컬 YAML에 반영되지 않음 |
| create vs apply | create는 생성만, apply는 생성과 업데이트 |
| ReplicaSet 이미지 변경 | 기존 Pod는 교체되지 않음, 롤링 업데이트는 Deployment가 담당 |
| NodePort 접근 | Pod IP가 아니라 노드 IP 사용 |
| targetPort 생략 | port와 같은 값 |
| type 생략 | ClusterIP |
