## Day 7 : Pod & YAML 기초

### Pod 생성 방식

- **Imperative(명령형)**: `kubectl run <pod-name> --image=<image>` 처럼 명령어로 즉시 실행
    - 예: `kubectl run nginx-pod --image=nginx`
    - 트러블슈팅이나 로컬 테스트에 적합
- **Declarative(선언형)**: YAML/JSON 설정 파일에 원하는 상태(desired state)를 정의하고 `kubectl apply -f` 또는 `kubectl create -f`로 적용
    - 운영(Production), CI/CD, GitOps에서 주로 사용

### YAML 기본 문법

- 주석은 `#`
- 들여쓰기는 공백(스페이스) 사용, 탭은 비권장
- 데이터 타입: 문자열, 숫자, 딕셔너리(중첩 가능), 리스트( 사용)
- 확장자는 `.yml`, `.yaml` 둘 다 동일하게 사용 가능

### Pod YAML 구조 (최상위 4개 필드)

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    env: demo
    type: frontend
spec:
  containers:
    - name: nginx-container
      image: nginx
      ports:
        - containerPort: 80
```

- 대소문자 구분(case-sensitive) 주의 (`apiVersion`, `Pod`, `metadata`, `spec` 등)
- `kubectl explain <object>` 명령으로 지원되는 apiVersion 확인 가능
- `metadata.labels`는 임의의 key-value 지정 가능 (그룹핑/필터링 용도)

### 주요 명령어

- `kubectl get pods` : Pod 상태 확인 (READY 컬럼: n/n = 컨테이너 개수)
- `kubectl get pods -o wide` : Pod의 IP, 실행 노드 등 확장 정보
- `kubectl get pods --show-labels` : 라벨 확인
- `kubectl describe pod <name>` : 상세 정보 및 이벤트(에러) 로그 확인
- `kubectl edit pod <name>` : 실행 중인 객체를 직접 수정 (vi 에디터 사용)
- `kubectl exec -it <pod> -- sh` : 컨테이너 내부 접속
- `kubectl delete pod <name>` : Pod 삭제
- `kubectl run <name> --image=<image> --dry-run=client -o yaml > pod.yaml` : dry-run으로 YAML 자동 생성 (JSON도 가능: `o json`)

### 트러블슈팅 예시

- 잘못된 이미지 태그 → `ImagePullBackOff` 에러 → `kubectl describe pod`로 원인 확인 → YAML 수정 후 재적용 또는 `kubectl edit`으로 직접 수정

## Day 8 : ReplicationController, ReplicaSet, Deployment

### 배경

- 단일 Pod만 운영 시 장애 발생하면 서비스 중단됨 → 고가용성을 위해 여러 개의 동일 Pod(레플리카)를 관리하는 오브젝트 필요

### ReplicationController (RC) - 레거시

```yaml
apiVersion: v1
kind: ReplicationController
metadata:
  name: nginx-rc
  labels:
    env: demo
spec:
  replicas: 3
  template:
    metadata:
      labels:
        env: demo
    spec:
      containers:
        - name: nginx-container
          image: nginx
          ports:
            - containerPort: 80
```

- `spec.template` 안에 Pod의 metadata/spec을 그대로 정의
- `spec.replicas`로 원하는 Pod 개수 지정
- 지정된 replica 수 유지(자동 복구), 수요 증가 시 replica를 늘려 수동 스케일링 가능

### ReplicaSet (RS) - RC의 신버전

- apiVersion이 다름: `apps/v1` (RC는 `v1`)
- RC와 차이점: **selector.matchLabels** 필드로 기존에 이미 떠 있는 Pod까지 관리 가능

```yaml
spec:
  replicas: 3
  selector:
    matchLabels:
      env: demo
  template:
    ...
```

- 복제본 개수 변경 방법 3가지:
    1. YAML 수정 후 `kubectl apply -f`
    2. `kubectl edit rs <name>` (live object 직접 수정)
    3. `kubectl scale --replicas=<n> rs/<name>` (imperative)

### Deployment

- **Deployment → ReplicaSet → Pod** 순으로 관리 (Deployment가 RS를 생성/관리)
- RS/RC와 달리 **롤링 업데이트(rolling update)** 지원 → 무중단 배포 가능
- apiVersion: `apps/v1`, kind: `Deployment`
- 주요 명령어:
    - `kubectl set image deploy/<name> <container>=<image>:<tag>` : 이미지 업데이트(롤링 업데이트 트리거)
    - `kubectl rollout history deploy/<name>` : 배포 히스토리 확인
    - `kubectl rollout undo deploy/<name>` : 이전 리비전으로 롤백
    - `kubectl get all` : 클러스터 내 전체 리소스(Deployment/RS/Pod/Service) 확인
    - `kubectl create deploy <name> --image=<image> --dry-run=client -o yaml > deploy.yaml` : YAML 자동 생성

## Day 9 : Services & 클러스터 네트워킹

### Service가 필요한 이유

- Pod의 IP는 재시작 시마다 변경됨(비정적) → 고정된 접근 지점 필요
- Deployment 자체는 외부에 노출되지 않음 → Service로 노출

### Service 종류

1. **NodePort**
    - 외부에서 접근 가능한 포트를 노드에 오픈 (범위: 30000~32767)
    - 3가지 포트 개념:
        - `port`: 클러스터 내부에서 다른 서비스가 접근하는 포트
        - `targetPort`: 실제 Pod(컨테이너)가 리스닝하는 포트
        - `nodePort`: 외부에서 접근하는 포트
    
    ```yaml
    apiVersion: v1
    kind: Service
    metadata:
      name: nodeport-svc
      labels:
        env: demo
    spec:
      type: NodePort
      selector:
        env: demo
      ports:
        - port: 80
          targetPort: 80
          nodePort: 30001
    ```
    
    - `selector`로 어떤 Pod(라벨 기준)를 대상으로 할지 지정
    - kind 클러스터 사용 시 포트를 호스트에 매핑하려면 클러스터 생성 시 `extraPortMappings` 설정 필요
2. **ClusterIP** (기본값)
    - 클러스터 내부 통신 전용 (외부 노출 없음)
    - Pod 간 통신(front-end ↔ back-end 등) 시 사용
    - `type` 필드를 생략해도 기본값이 ClusterIP
    
    ```yaml
    spec:
      selector:
        env: demo
      ports:
        - port: 80
          targetPort: 80
    ```
    
3. **LoadBalancer**
    - 클라우드 제공자(AWS/Azure/GCP)의 외부 로드밸런서와 연동
    - 로컬(kind 등) 환경에서는 외부 IP가 할당되지 않고 NodePort처럼 동작
    
    ```yaml
    spec:
      type: LoadBalancer
      ports:
        - port: 80
    ```
    
4. **ExternalName**
    - 특정 DNS 이름으로 매핑 (예: 외부 데이터베이스 주소 등 내부 서비스가 참조)

### 주요 명령어

- `kubectl get svc` / `kubectl describe svc <name>`
- `kubectl get endpoints` (`kubectl get ep`) : 서비스에 연결된 실제 Pod IP 목록 확인
- `kubectl expose deployment <name> --port=<port> --target-port=<port>` : imperative 방식으로 서비스 생성
- alias 설정 팁: `.bash_profile`에 `alias k='kubectl'` 추가 + bash completion 설정으로 작업 속도 향상
