## 1. 개요

### 요약

> 쿠버네티스에서 애플리케이션을 안정적으로 운영하고 외부와 원활하게 통신하기 위해서는 '서비스(Service)'라는 개념을 이해하는 것이 필수적이다. 서비스는 파드(Pod)들의 집합에 접근할 수 있는 고유한 IP 주소와 DNS 이름을 제공하며, 파드의 동적인 특성에도 불구하고 안정적인 접근을 보장한다.
>
> 쿠버네티스 서비스의 다양한 종류와 각각의 특징, 그리고 이를 활용하는 방법을 정리하고, 이를 통해 쿠버네티스 환경에서 애플리케이션의 가용성과 접근성을 높이는 방법을 명확하게 이해한다.

## k8s 서비스의 필요성

### 파드의 동적인 특성과 서비스의 역할

- 쿠버네티스의 파드 = 애플리케이션을 실행하는 가장 작은 단위
  - but 파드는 언제든지 생성되거나 삭제될 수 있으며, 재시작될 때마다 IP 주소가 변경됨 (동적임)
  - 이처럼 파드의 IP 주소가 고정되지 않기 때문에, 다른 파드나 외부 사용자가 파드에 직접 접근하는 것은 매우 어려움
- → 이 문제를 해결하기 위해 쿠버네티스는 '서비스(Service)'라는 추상화 계층을 제공한다.
  - 서비스는 파드들의 집합에 대한 고유한 `IP 주소`와 `DNS 이름`을 부여하여, 파드의 동적인 변화와 상관없이 안정적인 접근 지점을 제공한다.
  - 이를 통해 애플리케이션은 **내부적으로** 파드 간 `통신`을 원활하게 하고, **외부에서는** 애플리케이션에 쉽게 `접근`할 수 있게 된다.

## 서비스의 핵심 기능

- **안정적인 접근**: 파드의 IP가 변경되어도 서비스의 IP는 고정되어 있어 안정적인 접근을 보장한다.
- **로드 밸런싱**: 여러 개의 파드에 걸쳐 들어오는 트래픽을 분산시켜 애플리케이션의 가용성과 성능을 높인다.
- **애플리케이션 디스커버리**: 다른 서비스나 파드가 특정 애플리케이션을 찾고 통신할 수 있도록 DNS 이름 또는 IP 주소를 제공한다.
- **느슨한 결합(Loosely Coupled)**: 서비스는 백엔드 파드의 구현 세부 사항을 추상화하여, 파드의 변경이 서비스 자체에 미치는 영향을 최소화한다.

## 쿠버네티스 서비스의 종류

쿠버네티스는 다양한 네트워크 환경과 요구사항에 맞춰 여러 종류의 서비스를 제공한다. 각 서비스 타입은 외부 노출 방식과 접근 범위에서 차이를 보인다.

### ClusterIP

- **기본적인 내부 통신용 서비스**이다.
- 클러스터 내부에서만 접근 가능한 가상 IP 주소를 할당받는다.
- 기본적으로 서비스 타입으로 지정되지 않으면 ClusterIP로 설정된다. (default)
- **주요 용도**:
  - 프론트엔드 파드가 백엔드 파드와 통신해야 할 때 사용된다.
  - 파드의 IP 주소가 동적으로 변경되는 문제를 해결하고, 안정적인 통신 채널을 제공한다.
  - 예를 들어, Nginx 프론트엔드 파드와 Node.js 백엔드 파드가 서로 통신할 때 ClusterIP 서비스를 통해 백엔드 파드에 접근한다.
- **작동 방식**:
  - ClusterIP 서비스는 특정 파드 그룹(셀렉터로 지정된)의 IP 주소와 포트를 내부적으로 관리한다.
  - 다른 파드에서 ClusterIP 서비스의 IP나 서비스 이름으로 접근하면, 서비스는 해당 요청을 백엔드 파드 중 하나로 전달한다.
  - 파드가 재시작되어 IP가 변경되어도, 서비스의 엔드포인트(Endpoint) 정보가 자동으로 업데이트되어 계속해서 정상적으로 통신할 수 있다.
- **YAML 설정 예시**:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-clusterip-service
spec:
  type: ClusterIP # 명시적으로 지정 or 생략 가능 (기본값이므로)
  selector:
    app: my-app # 해당 레이블을 가진 파드들을 대상으로 함
  ports:
    - protocol: TCP
      port: 80 # 서비스가 노출될 포트
      targetPort: 8080 # 파드가 실제로 리스닝하는 포트
```

## NodePort

- **클러스터 외부에서 접근 가능하게 하는 서비스**이다.
- 각 노드(Node)의 특정 포트(NodePort)를 통해 서비스에 접근할 수 있게 한다.
- ClusterIP 서비스의 기능을 포함하며, 추가적으로 노드 포트를 외부에 노출시킨다.
- **NodePort 범위**: 기본적으로 30,000번부터 32,767번 사이의 포트가 사용된다.
- **주요 용도**:
  - 개발 및 테스트 환경에서 애플리케이션을 외부에서 간단하게 테스트할 때 유용하다.
  - 클라우드 환경이 아닌 곳에서 외부 접근이 필요할 때 사용될 수 있다.
- **작동 방식**:
  - 외부 사용자는 `노드IP:NodePort` 형식으로 서비스에 접근한다.
  - 이 요청은 해당 노드의 NodePort로 전달되고, 서비스는 이를 내부적으로 파드가 리스닝하는 TargetPort로 포워딩한다.
  - 트래픽은 여러 파드에 걸쳐 라운드 로빈(Round Robin) 방식으로 분산된다.
- **포트 종류**:
  - **Target Port**: 애플리케이션 파드가 실제로 리스닝하고 있는 포트이다.
  - **Port**: 서비스가 클러스터 내부에서 노출하는 포트이며, 다른 서비스들이 이 포트를 통해 접근한다.
  - **NodePort**: 서비스가 외부에서 접근할 수 있도록 노출하는 포트이다.
- **YAML 설정 예시**:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-nodeport-service
spec:
  type: NodePort
  selector:
    app: my-app
  ports:
    - protocol: TCP
      port: 80 # 서비스 내부 포트
      targetPort: 8080 # 파드 리스닝 포트
      nodePort: 30001 # 외부 노출 포트 (범위 내에서 지정)
```

,

- `kind` **클러스터에서의 제약**: `kind`와 같은 로컬 쿠버네티스 환경에서는 NodePort 서비스가 기본적으로 외부로 노출되지 않는다.
  - 이를 해결하기 위해 클러스터 생성 시 포트 매핑 설정을 추가해야 한다.
  - 예시: `kind create cluster --config=kind.yaml` 명령 시 `kind.yaml` 파일에 다음과 같은 포트 매핑 설정을 추가한다.

```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
    extraPortMappings:
      - containerPort: 30001 # 파드 컨테이너 포트
        hostPort: 30001 # 호스트 머신 포트
```

### LoadBalancer

- **클라우드 환경에서 외부 로드 밸런서를 프로비저닝하여 서비스를 노출**한다.
- 클라우드 제공업체(AWS, Azure, GCP 등)의 로드 밸런서 기능을 활용한다.
- **주요 용도**:
  - 프로덕션 환경에서 애플리케이션을 안정적으로 외부에 노출하고 트래픽을 분산할 때 사용된다.
  - 단일 진입점(Single Entry Point)을 제공하여 사용자가 복잡한 IP 주소 대신 간단한 URL이나 DNS로 접근할 수 있게 한다.
- **작동 방식**:
  - `type: LoadBalancer`로 설정하면, 쿠버네티스는 클라우드 제공업체의 API를 호출하여 외부 로드 밸런서를 생성한다.
  - 이 로드 밸런서는 서비스의 ClusterIP와 NodePort를 모두 포함하며, 외부에서 접근 가능한 고유한 외부 IP 주소(External IP)를 할당받는다.
  - 사용자는 이 외부 IP 주소나 로드 밸런서의 DNS 이름을 통해 서비스에 접근한다.
  - 로드 밸런서는 내부적으로 트래픽을 여러 파드로 분산시킨다.
- `kind` **클러스터에서의 제약**: `kind`와 같은 로컬 환경에서는 기본적으로 외부 로드 밸런서가 프로비저닝되지 않는다.
  - 따라서 `type: LoadBalancer`로 설정해도 외부 IP가 할당되지 않고, NodePort 서비스처럼 동작한다.
  - `kind`에서 로드 밸런서 기능을 사용하려면 별도의 Cloud Controller Manager를 설치하거나 포트 매핑 설정을 해야 한다.
- **YAML 설정 예시**:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: my-loadbalancer-service
spec:
  type: LoadBalancer # 로드 밸런서 타입으로 지정
  selector:
    app: my-app
  ports:
    - protocol: TCP
      port: 80 # 외부에서 접근할 포트
      targetPort: 8080
```

## ExternalName

- **외부의 DNS 이름을 쿠버네티스 서비스로 매핑**하는 데 사용된다.
- 실제 파드를 생성하거나 IP 주소를 할당받는 것이 아니라, 외부 서비스의 DNS 이름을 내부 서비스 이름처럼 사용할 수 있게 한다.
- **주요 용도**:
  - 쿠버네티스 클러스터 외부의 데이터베이스나 다른 외부 서비스에 접근해야 할 때 유용하다.
  - 예를 들어, 클러스터 외부의 MySQL 데이터베이스를 서비스 이름 `my-db.example.com`으로 접근하고 싶을 때 사용한다.
- **작동 방식**:
  - `type: ExternalName`으로 설정하고 `externalName` 필드에 외부 서비스의 DNS 이름을 지정한다.
  - 클러스터 내부의 다른 파드들이 이 ExternalName 서비스를 참조하면, 해당 DNS 이름으로 요청이 전달된다.
- **YAML 설정 예시**:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: external-db-service
spec:
  type: ExternalName
  externalName: my-external-database.example.com # 외부 서비스의 DNS 이름
```

## 서비스 생성 및 관리

### 선언적(Declarative) 방식: YAML 파일 사용

- 쿠버네티스에서 리소스를 관리하는 가장 일반적이고 권장되는 방식이다.
- 애플리케이션의 원하는 상태를 YAML 파일로 정의하고, `kubectl apply` 명령어로 클러스터에 적용한다.
- **YAML 파일의 기본 구조**:
  - `apiVersion`: 쿠버네티스 API 버전 (예: `v1`)
  - `kind`: 생성할 리소스의 종류 (예: `Service`, `Pod`, `Deployment`)
  - `metadata`: 리소스의 이름, 레이블 등 메타데이터 정보
  - `spec`: 리소스의 구체적인 설정 내용 (타입, 셀렉터, 포트 등)
- **서비스 YAML 예시 (NodePort)**:

```yaml
apiVersion: v1
kind: Service
metadata:
  name: nginx-service # 서비스 이름
  labels:
    env: demo # 서비스 레이블
spec:
  type: NodePort # 서비스 타입
  selector:
    app: nginx # 이 레이블을 가진 파드들을 대상으로 함
  ports:
    - protocol: TCP
      port: 80 # 서비스 포트
      targetPort: 80 # 파드 컨테이너 포트
      nodePort: 30001 # 노드 포트 (외부 노출)
```

### 명령형(Imperative) 방식: `kubectl expose` 명령어

- YAML 파일을 작성하지 않고 직접 명령줄에서 서비스를 생성하는 방식이다.
- 간단한 서비스 생성 시 시간을 절약할 수 있다.
- **기본 명령어**: `kubectl expose <resource_type> <resource_name> --port=<service_port> --target-port=<container_port> --type=<service_type>`
- **예시**: Nginx 디플로이먼트를 NodePort 타입의 서비스로 노출하기

```bash
kubectl expose deployment nginx-deploy --port=80 --target-port=80 --type=NodePort --name=nginx-nodeport-svc
```

- **장점**: 빠르게 서비스를 생성하고 테스트할 수 있다.
- **단점**: 복잡한 설정이나 프로덕션 환경에서는 YAML 파일을 사용하는 것이 더 명확하고 관리하기 용이하다.

### 서비스 생성 후 확인

- 생성된 서비스 목록을 확인한다: `kubectl get svc` 또는 `kubectl get services`
- 서비스의 상세 정보를 확인한다: `kubectl describe service <service_name>`
  - 이를 통해 서비스 타입, 할당된 IP 주소, 포트 정보, 엔드포인트(Endpoint) 등을 확인할 수 있다.
- **엔드포인트(Endpoint)**: 서비스가 실제로 트래픽을 전달할 대상 파드들의 IP 주소와 포트 목록이다.
  - 파드가 생성되거나 삭제되면 엔드포인트 정보는 자동으로 업데이트된다.

## 고급 서비스 개념 및 활용

### ReplicaSet과 Deployment

- **ReplicaSet**: 지정된 수만큼의 파드 복제본을 항상 유지하도록 관리하는 쿠버네티스 오브젝트이다.
  - 파드 장애 시 자동으로 새로운 파드를 생성하여 애플리케이션의 가용성을 높인다.
  - 파드 수를 조절하여 애플리케이션의 확장성(Scaling)을 지원한다.
  - 레거시 버전인 Replication Controller보다 더 발전된 기능을 제공하며, 셀렉터(Selector)를 통해 기존 파드도 관리할 수 있다.
- **Deployment**: ReplicaSet을 관리하며, 애플리케이션의 배포, 업데이트, 롤백을 더 정교하게 제어할 수 있게 해준다.
  - **롤링 업데이트(Rolling Update)**: 애플리케이션을 업데이트할 때, 기존 파드를 점진적으로 새 버전의 파드로 교체하여 서비스 중단 시간을 최소화한다.
  - **롤백(Rollback)**: 업데이트 과정에서 문제가 발생하거나 이전 버전으로 돌아가야 할 때, 이전 상태로 쉽게 복구할 수 있다.
  - Deployment는 ReplicaSet을 생성하고, ReplicaSet은 Pod를 관리하는 계층 구조를 가진다.
- **YAML 설정 예시 (Deployment)**:

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: nginx-deployment
spec:
  replicas: 3 # 원하는 파드 복제본 수
  selector:
    matchLabels:
      app: nginx # 이 레이블을 가진 파드들을 관리
  template: # 파드 템플릿 정의
    metadata:
      labels:
        app: nginx
    spec:
      containers:
        - name: nginx
          image: nginx:latest # 사용할 컨테이너 이미지
          ports:
            - containerPort: 80
```

### 서비스와 함께 사용하기

- 서비스는 ReplicaSet이나 Deployment와 함께 사용될 때 그 진가를 발휘한다.
- Deployment는 여러 버전의 파드를 관리하고, 서비스는 이 파드들의 집합에 대한 안정적인 접근 지점을 제공한다.
- 예를 들어, Deployment를 통해 Nginx 애플리케이션을 업데이트할 때, 서비스는 계속해서 이전 버전의 파드 또는 새 버전의 파드로 트래픽을 라우팅하여 사용자 경험을 유지한다.
- `kubectl get all` 명령어를 사용하면 Deployment, ReplicaSet, Service, Pod 등 클러스터의 주요 리소스들을 한눈에 확인할 수 있다.

### 명령줄 도구 활용

- `kubectl run`: 간단한 파드를 생성할 때 사용된다.
  - `-dry-run=client -o yaml` 옵션을 사용하면, 실제 생성 없이 YAML 형식의 정의를 출력하여 YAML 파일 생성에 활용할 수 있다.
- `kubectl edit`: 실행 중인 서비스나 다른 리소스의 설정을 직접 수정할 때 사용된다.
- `kubectl scale`: Deployment나 ReplicaSet의 복제본 수를 즉시 변경할 때 사용된다.
- `kubectl rollout`: Deployment의 업데이트 및 롤백을 관리하는 명령어이다.
  - `kubectl rollout history deploy <deployment_name>`: 배포 기록을 확인한다.
  - `kubectl rollout undo deploy <deployment_name>`: 이전 버전으로 롤백한다.
- `kubectl exec`: 실행 중인 파드 내부의 컨테이너에 접속하여 명령을 실행할 때 사용된다.
- `kubectl logs`: 파드 컨테이너의 로그를 확인할 때 사용된다.
