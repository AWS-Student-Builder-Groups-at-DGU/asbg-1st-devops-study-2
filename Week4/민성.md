『쿠버네티스 완벽 가이드』 4주차 정리 — 민성

3장에서 쿠버네티스 환경을 골랐다면, 4장은 그 클러스터를 실제로 조작하는 방법을 다룬다. 쿠버네티스가 다루는 리소스에는 어떤 종류가 있고, 그것을 매니페스트와 kubectl로 어떻게 관리하는지가 핵심이다. 이 책 전체에서 가장 실용적인 장이라 두고두고 참고하게 된다.

## 4.1 이 책을 읽기 위한 준비

### kubectl 설치와 셸 자동 완성
kubectl에는 셸 자동 완성 기능이 있어 bash나 zsh 환경에 맞게 설정할 수 있다.

```bash
# 현재 셸에만 적용
source <(kubectl completion bash)
source <(kubectl completion zsh)

# 다음 로그인 시에도 유지
echo 'source <(kubectl completion bash)' >> ~/.bashrc
echo 'source <(kubectl completion zsh)' >> ~/.zshrc
```

### GKE 클러스터 생성
이 책의 실습은 기본적으로 GKE 클러스터를 사용한다.

```bash
# 사용 가능한 쿠버네티스 버전 확인
gcloud container get-server-config --zone asia-northeast3-a

# 버전과 클라이언트 확인
kubectl version

# 클러스터 삭제
gcloud container clusters delete k8s --zone asia-northeast3-a
```

GCP에는 300달러 크레딧의 무료 등급이 있어 처음에는 이것으로 테스트해도 좋다. 다만 노드로 쓰이는 GCE는 종량 과금 단가가 비싼 편이라, 사용 후 불필요한 클러스터는 삭제해 두는 것이 좋다.

최신 버전 기능을 테스트할 때는 3장에서 소개한 kind로 구축한 클러스터를 사용한다.

```bash
kind create cluster --name kind-alpha-cluster --config kind-alpha.yaml
```

### 참고: GKE 워크로드 아이덴티티
GKE에서 기동 중인 컨테이너가 GCP 서비스를 사용할 때 유연하게 권한을 부여하는 기능이다. 쿠버네티스의 서비스 어카운트(KSA)와 GCP의 서비스 어카운트(GSA)를 연결해서, 해당 KSA를 쓰는 파드가 GCP 서비스에 접속할 때 연결된 GSA 권한이 자동으로 부여되는 구조다.

## 4.2 쿠버네티스 기초

쿠버네티스는 마스터와 노드로 구성된다.

- 쿠버네티스 마스터: API 엔드포인트 제공, 컨테이너 스케줄링, 스케일링 등을 담당
- 쿠버네티스 노드: 도커 호스트에 해당하며 실제로 컨테이너를 기동하는 노드

클러스터를 관리하려면 CLI 도구인 kubectl과 YAML 또는 JSON으로 작성된 매니페스트 파일로 마스터에 리소스를 등록해야 한다. 매니페스트는 가독성을 고려해 YAML로 작성하는 것이 일반적이며 확장자는 .yaml, .yml, .json으로 구분된다.

중요한 점은 kubectl이 매니페스트 정보를 바탕으로 마스터의 API에 요청을 보낸다는 것이다. 쿠버네티스 API는 RESTful API로 구현되어 있어서, kubectl 없이도 각종 언어의 RESTful API 라이브러리나 curl로 직접 API를 호출해 관리할 수 있다.

```
매니페스트 작성 → kubectl create -f sample.yaml → 마스터 API → 노드에 컨테이너 기동
```

## 4.3 쿠버네티스와 리소스

쿠버네티스가 다루는 리소스는 다섯 가지 카테고리로 분류된다. 리소스 등록은 비동기로 처리된다.

| 종류 | 개요 |
| --- | --- |
| 워크로드 API 카테고리 | 컨테이너 실행에 관련된 리소스 |
| 서비스 API 카테고리 | 컨테이너를 외부에 공개하는 엔드포인트를 제공하는 리소스 |
| 컨피그 & 스토리지 API 카테고리 | 설정, 기밀 정보, 영구 볼륨 등에 관련된 리소스 |
| 클러스터 API 카테고리 | 보안이나 쿼터 등에 관련된 리소스 |
| 메타데이터 API 카테고리 | 클러스터 내부의 다른 리소스를 관리하기 위한 리소스 |

이 중 애플리케이션 개발자가 주로 사용하는 것은 워크로드, 서비스, 컨피그 & 스토리지 세 가지다.

### 4.3.1 워크로드 API 카테고리 (5장에서 상세)
클러스터 위에서 컨테이너를 기동하기 위한 리소스. 사용자가 직접 관리하는 것은 여덟 종류다.

파드(Pod), 레플리케이션 컨트롤러(ReplicationController), 레플리카셋(ReplicaSet), 디플로이먼트(Deployment), 데몬셋(DaemonSet), 스테이트풀셋(StatefulSet), 잡(Job), 크론잡(CronJob)

### 4.3.2 서비스 API 카테고리 (6장에서 상세)
컨테이너의 서비스 디스커버리와 클러스터 외부 접속용 엔드포인트를 제공하는 리소스. 크게 서비스와 인그레스 두 종류다.

서비스 타입
- ClusterIP
- ExternalIP (ClusterIP의 한 종류)
- NodePort
- LoadBalancer
- Headless (None)
- ExternalName
- None-Selector

인그레스(Ingress)

참고로 ExternalIP 서비스와 None-Selector 서비스는 엄밀히 말하면 타입은 아니지만 이 책에서는 하나의 타입으로 소개한다.

### 4.3.3 컨피그 & 스토리지 API 카테고리 (7장에서 상세)
설정과 기밀 데이터를 컨테이너에 담거나 영구 볼륨을 제공하는 리소스.

- 시크릿(Secret): 기밀 데이터를 키-밸류로 저장
- 컨피그맵(ConfigMap): 일반 설정 정보를 키-밸류로 저장
- 영구 볼륨 클레임(PersistentVolumeClaim): 컨테이너에서 영구 볼륨을 요청할 때 사용

시크릿과 컨피그맵은 데이터 구조가 같고, 저장할 데이터가 기밀인지 일반 설정인지에 따라 구분된다.

### 4.3.4 클러스터 API 카테고리 (8장에서 상세)
클러스터 자체의 동작을 정의하는 리소스. 보안 설정이나 정책, 클러스터 관리성 향상을 위한 리소스들이다.

노드(Node), 네임스페이스(Namespace), 영구 볼륨(PersistentVolume), 리소스 쿼터(ResourceQuota), 서비스 어카운트(ServiceAccount), 롤(Role), 클러스터 롤(ClusterRole), 롤바인딩(RoleBinding), 클러스터롤바인딩(ClusterRoleBinding), 네트워크 정책(NetworkPolicy)

### 4.3.5 메타데이터 API 카테고리 (8장에서 상세)
클러스터 내부의 다른 리소스 동작을 제어하기 위한 리소스.

LimitRange, HorizontalPodAutoscaler(HPA), PodDisruptionBudget(PDB), 커스텀 리소스 데피니션(CustomResourceDefinition)

예를 들어 HPA는 디플로이먼트 리소스를 조작해 레플리카 수를 변경함으로써 오토 스케일링을 구현한다.

## 4.4 네임스페이스로 가상적인 클러스터 분리

네임스페이스는 가상적인 클러스터 분리 기능이다. 완전한 분리 개념은 아니라서 용도가 제한되지만, 하나의 클러스터를 여러 팀이 사용하거나 서비스/스테이징/개발 환경으로 구분할 때 쓸 수 있다.

기본으로 생성되는 네 가지 네임스페이스
- kube-system: 클러스터 구성 요소와 애드온이 배포되는 네임스페이스
- kube-public: 모든 사용자가 사용할 수 있는 컨피그맵 등을 배치
- kube-node-lease: 노드 하트비트 정보(Lease 리소스)가 저장되는 전용 네임스페이스
- default: 기본 네임스페이스

시스템이 복잡하지 않으면 기본 네임스페이스를 그대로 써도 된다.

### 네임스페이스와 RBAC
관리형 서비스나 구축 도구로 만든 클러스터는 대부분 RBAC(Role-Based Access Control)가 기본 활성화되어 있다. RBAC는 클러스터 조작 권한을 네임스페이스별로 구분할 수 있고, 네트워크 정책과 함께 쓰면 네임스페이스 간 통신도 제어할 수 있다. 네임스페이스만으로는 높은 분리성을 확보하기 어렵지만 RBAC나 네트워크 정책을 더하면 분리성을 높일 수 있다.

### 네임스페이스 분리 범위에 대한 저자 의견
권한 분리 관점에서 마이크로서비스를 개발하는 팀마다 분리하는 것이 좋다. 다만 서비스/스테이징/개발 환경은 네임스페이스가 아니라 클러스터별로 나눠야 한다는 것이 저자의 입장이며, 이유는 세 가지다.

1. 클러스터 업그레이드 시 동시에 모든 환경에서 장애가 발생할 가능성이 있다
2. 네임스페이스 명명 규칙이 prd-ns1, stg-ns1처럼 되면 매니페스트 재사용성이 현저히 떨어진다. 클러스터를 분리하면 각 환경에서 같은 네임스페이스 이름을 쓸 수 있어 완전히 같은 매니페스트를 재사용할 수 있다
3. 서비스 이름 해석 시 SERVICE.prd-ns1.svc.cluster.local처럼 다른 목적지에 통신해야 한다
