## 5.5 데몬셋

**레플리카셋의 특수 형태. 각 노드에 파드를 하나씩 배치한다.**

<img width="293" height="213" alt="image" src="https://github.com/user-attachments/assets/a09bba10-b8fd-4dac-842a-a5cdf8db46dc" />


| | 레플리카셋 | 데몬셋 |
|---|---|---|
| 배치 | 총 N개를 리소스 상황에 맞게 | 모든 노드에 1개씩 |
| replicas | 지정 가능 | **지정 불가** (필드 없음) |
| 노드당 파드 | 균등하지 않음 | 정확히 1개 (2개 불가) |
| 노드 추가 시 | 그대로 | 새 노드에 자동 기동 |

- 특정 노드를 제외하려면 `nodeSelector` / 노드 안티어피니티 (12장)
- **용도**: 모든 노드에서 반드시 동작해야 하는 프로세스 — 로그 수집(Fluentd), 노드 모니터링(Datadog)

```yaml
apiVersion: apps/v1
kind: DaemonSet          # replicas 항목 없음
spec:
  selector:
    matchLabels: { app: sample-app }
  template: ...
```

### 업데이트 전략 (기본값 `RollingUpdate`)

**OnDelete**
- 매니페스트를 바꿔도 기존 파드는 그대로. 다른 이유로 재생성될 때 새 정의 적용
- 데몬셋은 모니터링/로그 전송 용도가 많아 임의 시점 수동 업데이트를 하도록 되어 있음
- 방치하면 **이전 버전이 장기간 계속 사용**됨
- 수동 업데이트는 `kubectl delete pod`로 하나씩 → 자동 복구
- `type` 외에 지정 가능한 항목 없음

**RollingUpdate**
- 한 노드에 같은 파드를 여러 개 못 만들므로 **`maxSurge` 사용 불가**, `maxUnavailable`만 지정
- `maxUnavailable` 기본값 **1**, **0으로 지정 불가**

```yaml
updateStrategy:
  type: RollingUpdate
  rollingUpdate:
    maxUnavailable: 2     # 두 개씩 동시에 업데이트
```

## 5.6 스테이트풀셋

**레플리카셋의 특수 형태. DB 등 스테이트풀 워크로드용.**

### 레플리카셋과의 차이 2가지

1. **파드명에 숫자 인덱스** — `sample-statefulset-0, -1, ..., -N` → **파드명이 바뀌지 않는다**
2. **데이터를 영구 저장하는 구조** — 재기동 시 같은 디스크를 사용하여 재생성

### 생성 — volumeClaimTemplates

`spec.volumeClaimTemplates`로 **각 파드마다 영구 볼륨 클레임(PVC)을 자동 생성**한다. 클러스터 외부 네트워크로 제공되는 영구 볼륨을 붙이므로, 파드를 재기동하거나 다른 노드로 옮겨도 **같은 데이터를 보유한 채** 컨테이너가 재생성된다.

```yaml
apiVersion: apps/v1
kind: StatefulSet
spec:
  serviceName: sample-statefulset
  replicas: 3
  template:
    spec:
      containers:
      - name: nginx-container
        image: nginx:1.16
        volumeMounts:
        - { name: www, mountPath: /usr/share/nginx/html }
  volumeClaimTemplates:
  - metadata: { name: www }
    spec:
      accessModes: [ReadWriteOnce]
      resources:
        requests: { storage: 1G }
```

생성되는 PVC 이름: `www-sample-statefulset-0` 형태.

### 스케일링 — 순서가 핵심

`kubectl apply` / `kubectl scale` 사용법은 같지만, **한 번에 하나씩만** 생성·삭제하므로 시간이 더 걸린다.


 **스케일 아웃** 인덱스 **작은 것부터** `0 → 1 → 2`. 이전 파드가 **Ready 된 후** 다음 생성 (최초 생성 시에도 동일) 

<img width="387" height="166" alt="image" src="https://github.com/user-attachments/assets/e2576969-81b0-40e5-b96a-c3d1cbe0106c" />


 **스케일 인**  인덱스 **큰 것부터** `2 → 1 → 0` 

<img width="368" height="160" alt="image" src="https://github.com/user-attachments/assets/39da11bd-0bc3-4792-bddd-e534dfb73b40" />


→ 레플리카셋은 파드가 **무작위로 삭제**되어 특정 파드가 마스터인 앱에 부적합. 스테이트풀셋은 **0번이 항상 먼저 생성되고 가장 늦게 삭제**되므로 **0번을 마스터로 쓰는 이중화 구조에 적합**.

### podManagementPolicy

| 값 | 동작 |
|---|---|
| `OrderedReady` (기본) | 하나씩, 이전 파드 Ready 후 다음 생성 |
| `Parallel` | 레플리카셋처럼 병렬 동시 기동 |

### 업데이트 전략 (기본값 `RollingUpdate`)

**OnDelete** — 매니페스트를 바꿔도 기존 파드 유지. **영속성 영역을 가진 DB나 클러스터에서 수동 업데이트**하고 싶을 때 사용. `type` 외 지정 항목 없음.

**RollingUpdate** — 영속성 데이터가 있으므로 제약이 많다.
- 추가 파드를 만들어 롤링 업데이트 **불가** (maxSurge 없음)
- **`maxUnavailable`도 지정 불가** → 파드마다 Ready 확인하며 하나씩
- `podManagementPolicy: Parallel`이어도 **업데이트는 순차적**

**partition** — 부분 업데이트

```yaml
updateStrategy:
  type: RollingUpdate
  rollingUpdate:
    partition: 3        # 인덱스 3 이상만 업데이트 대상
```
<img width="451" height="196" alt="image" src="https://github.com/user-attachments/assets/a85dd402-073d-40b2-b3a8-14e9cdea3fa3" />


replicas=5, partition=3에서 이미지 수정 시:
```
0, 1, 2  →  업데이트 안 됨
4 → 3    →  이 순서로(인덱스 큰 것부터) 하나씩 업데이트
```
이후 `partition: 3 → 1`로 바꾸면 `2 → 1`이 순서대로 업데이트된다.

- 전체에 영향 없이 **부분 적용 후 확인** → 안전한 업데이트
- OnDelete와 달리 **수동 재기동해도 partition보다 작은 인덱스는 업데이트되지 않는다**

### 영구 볼륨 데이터 유지 확인

컨테이너에 `/dev/sdb` 같은 별도 디스크가 마운트되어 있다. 파일을 만든 뒤 **파드를 삭제하거나(`kubectl delete pod`) 컨테이너 프로세스를 죽여도(`kill 1`) 복구 후 파일이 유실되지 않는다.** 복구 후 **IP는 바뀌지만 파드명은 그대로**.

### 삭제 시 주의 — PVC는 자동으로 안 지워진다

- 스테이트풀셋을 삭제해도 **영구 볼륨은 해제되지 않는다** → 데이터 백업 시간을 주기 위해서
- 반대로, PVC를 남긴 채 같은 스테이트풀셋을 다시 만들면 **기존 데이터 그대로** 기동된다 (스케일 인 후 다시 늘린 경우도 동일)
- **비용 발생** — 관리형은 종량 과금, 온프레미스도 디스크 점유. 삭제 후엔 PVC도 정리할 것

```bash
$ kubectl delete persistentvolumeclaims www-sample-statefulset-{0..2}
```

- PVC를 지워도 PV가 안 지워질 수 있는데, 이는 **PV의 ClaimPolicy** 때문 (7장)

## 5.7 잡

**컨테이너를 사용해 한 번만 실행되는 리소스.** 정확히는 **N개를 병렬로 실행하며 지정한 횟수의 정상 종료를 보장**한다.

### 레플리카셋과의 차이

**'파드가 정지되는 것을 전제로 만들어졌는가'** 가 핵심.

| | 레플리카셋 | 잡 |
|---|---|---|
| 파드 정지 | 예상치 못한 **에러** | **정상 종료**되는 작업 |
| 정상 종료 횟수 | 셀 수 없음 | 셈 (COMPLETIONS 표시) |

**용도**: rsync, 오브젝트 스토리지 업로드 등 **배치 처리**. 레플리카셋으로는 성공 횟수를 셀 수 없으므로 배치엔 잡을 적극 사용할 것.

```yaml
apiVersion: batch/v1
kind: Job
spec:
  completions: 1
  parallelism: 1
  backoffLimit: 10
  template:
    spec:
      containers:
      - { name: tools-container, image: amsy810/tools:v2.0, command: ["sleep"], args: ["60"] }
      restartPolicy: Never
```

- 레이블/셀렉터는 쿠버네티스가 **유니크한 uuid를 자동 생성**하므로 명시적 지정은 **비추천**
- 잡도 결국 **파드를 생성하는 리소스**

### restartPolicy — `Never` 또는 `OnFailure`만 가능

| 값 | 장애 시 |
|---|---|
| `Never` | **신규 파드 생성** (기존 파드는 Error로 남음) |
| `OnFailure` | **동일 파드 재사용**, RESTARTS 카운터 증가. 노드/파드 IP 유지되지만 볼륨을 안 붙였다면 데이터는 유실 |


### 병렬 실행 파라미터

| 파라미터 | 의미 | 나중에 변경 |
|---|---|---|
| `completions` | 성공 횟수 | **불가** |
| `parallelism` | 병렬 수 | 가능 |
| `backoffLimit` | 실패 허용 횟수 | 가능 |


#### 워크로드별 설정 (M, N, P는 임의의 수)

| 워크로드 | completions | parallelism | backoffLimit |
|---|---|---|---|
| 1회만 실행하는 태스크 | 1 | 1 | 0 |
| N개 병렬 태스크 | M | N | P |
| 한 개씩 실행하는 작업 큐 | 미지정 | 1 | P |
| N개 병렬 작업 큐 | 미지정 | N | P |

**One Shot Task** — `1/1/0`
"1 병렬 / 성공 1회면 종료 / 실패 0회 허용" ⇒ **성공 여부와 무관하게 반드시 1회만 실행**.

**Multi Task** — 예) `completions=5, parallelism=3`
5회 정상 종료할 때까지 3개씩 병렬 실행.
- 남은 성공 횟수가 2면 파드도 **2개만** 생성된다. "3개 돌려서 먼저 성공하는 걸 쓴다"는 식으로 **동작하지 않음**
- `parallelism ≥ completions`면 **completions 개수만큼만** 생성 (3/5 → 파드 3개)

**Multi WorkQueue** — `completions` 미지정 + `parallelism: N`
- 병렬 수만큼 실행하다 **하나라도 정상 종료하면 이후 파드를 생성하지 않는다**
- 이미 실행 중인 나머지는 **강제 정지되지 않고** 끝까지 동작
- **전제**: 진행 관리용 **메시지 큐가 별도로 필요**. 파드 앱은 큐에서 반복해 데이터를 가져오고, **큐가 비면 정상 종료**하도록 구현
- 큐에 계속 데이터가 들어오면 **크론잡과 조합**. 메시지 양에 따라 병렬 수를 늘리면 **자동 스케일**도 가능

**Single WorkQueue** — `completions` 미지정 + `parallelism: 1`

#### COMPLETIONS 출력 차이

```
Multi Task        3/5         # 5개 성공 필요, 3개 완료
Multi WorkQueue   0/1 of 3    # 3개 병렬 중 1개만 성공하면 되는데 아직 0개
```

#### 파라미터 변경

```bash
# completions → 실패
The Job "..." is invalid: spec.completions: Invalid value: 2: field is immutable

# parallelism → 성공
$ kubectl patch job sample-single-workqueue-job -p '{"spec": {"parallelism": 2}}'
```
→ Single WorkQueue를 나중에 **Multi WorkQueue로 변경 가능**.

### 일정 기간 후 잡 삭제 [1.18 Alpha]

잡은 종료 후에도 삭제되지 않고 남는다. `spec.ttlSecondsAfterFinished: 30` → 종료 30초 후 자동 삭제.

## 5.8 크론잡

**스케줄된 시간에 잡을 생성**하는 리소스. 1.4까지는 ScheduledJob이라는 이름이었다.

크론잡과 잡의 관계는 **디플로이먼트-레플리카셋 관계와 비슷**한 3계층 구조:

<img width="495" height="202" alt="image" src="https://github.com/user-attachments/assets/8575a910-0fb8-4a86-8488-776924727d13" />


```
크론잡  →  잡  →  파드
```

```yaml
apiVersion: batch/v1beta1
kind: CronJob
spec:
  schedule: "*/1 * * * *"           # Cron 형식
  concurrencyPolicy: Allow
  startingDeadlineSeconds: 30
  successfulJobsHistoryLimit: 5
  failedJobsHistoryLimit: 3
  suspend: false
  jobTemplate:
    spec: { completions: 1, parallelism: 1, backoffLimit: 0, template: ... }
```

생성되는 잡 이름은 `sample-cronjob-<타임스탬프>` 형태.

### suspend — 일시 정지

`spec.suspend: true`면 **스케줄 대상에서 제외**된다 (기본 false). 점검 시 사용.

```bash
$ kubectl patch cronjob sample-cronjob -p '{"spec":{"suspend":true}}'
```

### 임의 시점 실행

```bash
$ kubectl create job sample-job-from-cronjob --from cronjob/sample-cronjob
```

### concurrencyPolicy — 동시 실행 제어

잡이 의도한 간격 안에 정상 종료하면 문제없지만, **이전 잡이 아직 실행 중일 때**의 정책.

| 정책 | 개요 |
|---|---|
| `Allow` (기본값) | 제한 없음. 이전 잡 상태와 무관하게 계속 생성 |
| `Forbid` | 이전 잡이 안 끝났으면 다음 잡을 실행하지 않음 |
| `Replace` | 이전 잡을 취소하고 새 잡 시작 (= **이전 잡의 레플리카 수를 0으로 변경**해 파드 삭제) |

### startingDeadlineSeconds — 실행 시작 기한

마스터가 일시 정지되는 등으로 시작이 지연될 때, **허용할 지연 시간(초)**.
- ex) 매시 00분 잡을 "00~05분에만 실행 가능"으로 → **300**
- **기본값은 아무리 늦어져도 잡을 생성**한다

### HistoryLimit — 잡 이력

| 설정 항목 | 개요 | 기본값 |
|---|---|---|
| `successfulJobsHistoryLimit` | 성공한 잡 저장 개수 | 3 |
| `failedJobsHistoryLimit` | 실패한 잡 저장 개수 | 3 |

- 잡이 남아 있다 = 파드도 `Completed`/`Error`로 남아 있어 **`kubectl logs`로 로그 확인 가능**
- **0으로 설정하면 종료 즉시 삭제**
- 실제 운영에서는 컨테이너 로그를 **외부 로그 시스템**으로 수집하는 것을 추천 (16장)
- 단, Kubernetes Dashboard로 젠킨스처럼 UI에서 결과를 보려면 **HistoryLimit을 크게** 설정

## 5.9 정리

**기본적으로 파드나 레플리카셋을 생성할 때는 처음부터 디플로이먼트를 통해 생성하는 것이 좋다.**

### 표 5-8 리소스 사용 방법

| 리소스 | 사용 방법 |
|---|---|
| 파드 | 디버깅이나 확인 용도 |
| 레플리케이션 컨트롤러 | 추천하지 않음, 레플리카셋 사용 |
| 레플리카셋 | 파드 스케일링 관리 / 기본적으로 디플로이먼트를 통해 사용 |
| 디플로이먼트 | 스케일링할 워크로드 |
| 데몬셋 | 각 노드에 파드 하나씩 배포 |
| 스테이트풀셋 | 영속성 데이터 등 상태를 가진 워크로드 |
| 잡 | 작업 큐/태스크 등 컨테이너 종료가 필요한 워크로드 |
| 크론잡 | 정기적으로 잡을 생성 |

### 리소스 관계

```
Tier 1          Tier 2                  Tier 3
 파드   ←──  레플리케이션 컨트롤러
 파드   ←──  레플리카셋          ←──  디플로이먼트
 파드   ←──  데몬셋
 파드   ←──  스테이트풀셋
 파드   ←──  잡                  ←──  크론잡
                                  ────→ 상위 리소스
```
