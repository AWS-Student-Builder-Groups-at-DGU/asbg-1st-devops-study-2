# 6장. 서비스 API 카테고리

『쿠버네티스 완벽 가이드』 6주차 정리 — 민성

5장에서 컨테이너를 기동하는 워크로드 리소스를 봤다면, 6장은 그 컨테이너에 접속할 수 있는 엔드포인트를 제공하는 서비스 API 카테고리를 다룬다. 클러스터 내부 통신부터 외부 공개까지, 네트워크와 관련된 내용이 대부분이다.

---

## 6.1 서비스 API 카테고리 개요

서비스 API 카테고리로 분류된 리소스는 클러스터상의 컨테이너에 대한 엔드포인트를 제공하거나, 레이블과 일치하는 컨테이너의 디스커버리에 사용된다. 사용자가 직접 사용하는 것은 두 종류다.

L4 로드 밸런싱을 제공하는 서비스 리소스
L7 로드 밸런싱을 제공하는 인그레스 리소스

서비스는 제공 목적에 따라 일곱 가지 타입을 가진다.

- ClusterIP
- ExternalIP (ClusterIP의 한 종류)
- NodePort
- LoadBalancer
- Headless (None)
- ExternalName
- None-Selector

ExternalIP 서비스와 None-Selector 서비스는 정확히 말하면 서비스 타입은 아니지만, 이 책에서는 타입 중 하나로 설명한다.

## 6.2 쿠버네티스 클러스터 네트워크와 서비스

### 파드 네트워크 복습

파드 내부에는 여러 컨테이너가 존재할 수 있는데, 같은 파드 내에 있는 컨테이너는 동일한 IP 주소를 할당받는다. 따라서 같은 파드의 컨테이너와 통신하려면 localhost로, 다른 파드에 있는 컨테이너와 통신하려면 파드의 IP 주소로 통신한다.

### 클러스터 내부 네트워크

쿠버네티스 클러스터는 생성하면 노드상에 파드를 위한 내부 네트워크가 자동으로 구성된다. 내부 네트워크 구성은 사용할 CNI(Container Network Interface)라는 플러그형 모듈 구현에 따라 다르지만, 기본적으로 노드별로 다른 네트워크 세그먼트를 구성하고 노드 간의 트래픽은 VXLAN이나 L2 Routing 등의 기술을 사용하여 전송함으로써 노드 간 통신이 가능하게 구성한다.

노드별 네트워크 세그먼트는 클러스터 전체에 할당된 네트워크 세그먼트를 자동으로 분할해 할당하므로 사용자가 설정하지 않아도 된다.

### 서비스를 쓰는 이유

내부 네트워크가 자동으로 구성되기 때문에 파드는 서비스를 사용하지 않고도 파드 간 통신이 가능하다. 그러나 서비스를 사용하면 두 가지 큰 장점을 얻을 수 있다.

파드에 트래픽 로드 밸런싱
서비스 디스커버리와 클러스터 내부 DNS

이 기능은 모든 서비스 종류에서 사용할 수 있다.

### 6.2.1 파드에 트래픽 로드 밸런싱

서비스는 셀렉터 조건에 맞는 파드들에 트래픽을 분산시킨다.

```bash
kubectl get services sample-clusterip
# NAME              TYPE       CLUSTER-IP     EXTERNAL-IP  PORT(S)    AGE
# sample-clusterip  ClusterIP  10.3.251.192   <none>       8080/TCP   3h

kubectl describe service sample-clusterip
# Selector:   app=sample-app
# IP:         10.3.251.192
# Port:       http-port  8080/TCP
# TargetPort: 80/TCP
# Endpoints:  10.0.0.34:80,10.0.1.26:80,10.0.2.124:80
```

Endpoints 항목에서 트래픽의 목적지 IP 주소와 포트를 확인할 수 있다. 셀렉터 조건에 따라 선택된 파드의 IP가 여기에 등록된다.

Endpoints 항목에 아무것도 표시되지 않을 경우 셀렉터 조건이 맞지 않을 가능성이 있다. 파드에 레이블이 정확히 설정되었는지, 레이블 값이 셀렉터 조건과 동일한지 확인해야 한다.

로드 밸런싱 동작은 임시 파드를 띄워서 확인할 수 있다.

```bash
kubectl run --image=amsy810/tools:v2.0 --restart=Never --rm -i testpod \
  --command -- curl -s http://10.3.251.192:8080
# Host=10.3.251.192 Path=/ From=sample-deployment-7c67dd9675-x4x97 ClientIP=10.0.2.144
```

여러 번 실행하면 비슷한 빈도로 세 개의 파드명이 표시된다.

### 6.2.2 서비스 디스커버리와 클러스터 내부 DNS

서비스명으로 이름 해석을 할 수 있다. IP 주소를 수동으로 관리하거나 애플리케이션 설정 파일에 IP를 하드코딩하면 이식성이 떨어지므로, 최대한 서비스명을 사용해 이름 해석을 하도록 한다.

정방향과 역방향 모두 DNS 질의가 가능하다.

```bash
# 역방향 질의
dig -x 10.3.251.192
# 192.251.3.10.in-addr.arpa. 30 IN PTR sample-clusterip.default.svc.cluster.local.
```

컨테이너 내부의 resolv.conf에는 다음과 같은 search 지시자가 들어 있다.

```
nameserver 10.3.240.10
search default.svc.cluster.local svc.cluster.local cluster.local ...
options ndots:5
```

이 때문에 짧은 이름으로도 질의가 가능하다.

### DNS SRV 레코드를 사용한 서비스 디스커버리

SRV 레코드를 사용하면 포트명과 프로토콜을 사용하여 서비스를 제공하는 포트 번호를 포함한 엔드포인트를 DNS로 해석할 수 있다. 레코드 형식은 다음과 같으며, 서비스의 포트명과 프로토콜에는 접두사에 언더바가 붙는다는 점에 주의해야 한다.

```
_서비스의_포트명._프로토콜.서비스명.네임스페이스명.svc.cluster.local
```

## 6.3 ClusterIP 서비스

클러스터 내부에서만 접속 가능한 가상 IP를 할당하는 가장 기본적인 서비스 타입이다.

```yaml
apiVersion: v1
kind: Service
metadata:
  name: sample-clusterip
spec:
  type: ClusterIP
  ports:
  - name: "http-port"
    protocol: "TCP"
    port: 8080
    targetPort: 80
  selector:
    app: sample-app
```

port는 서비스가 수신할 포트, targetPort는 목적지 컨테이너의 포트다.

---

## 6.4 ExternalIP 서비스

특정 쿠버네티스 노드 IP 주소와 포트에서 수신한 트래픽을 컨테이너로 전송하는 형태로 외부와 통신할 수 있도록 하는 서비스다. 특별한 이유가 없는 경우에는 ExternalIP 서비스 대신 NodePort 서비스를 사용하는 것을 검토해보는 게 좋다.

```yaml
spec:
  type: ClusterIP        # type 자체는 ClusterIP다
  externalIPs:
  - 10.178.0.61
  - 10.178.0.62
  ports:
  - name: "http-port"
    protocol: "TCP"
    port: 8080
    targetPort: 80
  selector:
    app: sample-app
```

주의할 점은 type을 ExternalIP로 지정하는 것이 아니라는 것이다. type 자체는 ClusterIP이고, spec.externalIPs에 노드 IP를 나열한다. 또 ExternalIP에 사용하는 IP는 모든 쿠버네티스 노드의 IP를 넣을 필요가 없다.

---

## 6.5 NodePort 서비스

모든 노드의 특정 포트에서 수신한 트래픽을 컨테이너로 전송하는 서비스다. ExternalIP와 달리 일부 노드가 아니라 전체 노드에서 수신한다.

### 포트 충돌 주의

같은 NodePort 번호를 사용하는 서비스를 여러 개 만들면 에러가 발생한다.

```
The Service is invalid value: 30080: provided port is already allocated
```

쿠버네티스 노드에서 30080/TCP 포트로 복수의 Listen 상태를 가질 수 없기 때문이다. 당연한 결과지만 실수하기 쉬운 부분이다.

---

## 6.6 LoadBalancer 서비스

클러스터 외부의 로드 밸런서를 사용하는 서비스로, 실제 서비스 환경에서 외부 공개할 때 가장 많이 쓰인다.

```yaml
spec:
  type: LoadBalancer
  ports:
  - name: "http-port"
    protocol: "TCP"
    port: 8080
    targetPort: 80
    nodePort: 30082
  selector:
    app: sample-app
```

포트 설정이 세 단계로 구성된다.

| 설정 항목 | 의미 |
| --- | --- |
| spec.ports[].port | 로드 밸런서에 할당되는 가상 IP와 ClusterIP에서 수신할 포트 번호 |
| spec.ports[].nodePort | 모든 쿠버네티스 노드에서 수신할 포트 번호 |
| spec.ports[].targetPort | 목적지 컨테이너에서 수신할 포트 번호 |

type: LoadBalancer를 사용할 때는 NodePort도 자동으로 할당되므로 nodePort 지정도 가능하다.

Docker Desktop for Mac/Windows에서는 LoadBalancer 서비스를 생성하면 localhost(127.0.0.1)의 IP 주소를 사용하여 접속할 수 있게 한다. 따라서 같은 포트 번호를 사용하여 여러 LoadBalancer 서비스를 생성할 수 없으므로 주의해야 한다.

또 GKE에서 서비스를 생성한 상태로 클러스터를 삭제한 경우 GCLB의 과금이 계속 발생하므로, 잊지 말고 서비스를 삭제해야 한다. 보안 관점에서도 불필요한 서비스는 최대한 삭제하도록 한다.

## 6.7 Headless 서비스

ClusterIP가 할당되지 않고, DNS 라운드 로빈으로 파드 IP 주소를 직접 반환하는 서비스다. 로드 밸런서를 거치지 않고 파드에 직접 접속하고 싶을 때 사용한다.

```bash
dig sample-headless.default.svc.cluster.local
# ANSWER SECTION:
# sample-headless.default.svc.cluster.local. 30 IN A 10.0.2.50
# sample-headless.default.svc.cluster.local. 30 IN A 10.0.0.35
# sample-headless.default.svc.cluster.local. 30 IN A 10.0.1.41
```

### 파드 단위 이름 해석

일반적으로는 클러스터 내부 DNS에서 개별 파드명으로 이름 해석을 할 수 없다. 서비스를 생성할 때 ClusterIP 등 여러 파드에 대해 엔드포인트가 할당되어 그 엔드포인트의 이름 해석은 제공되지만, 개별 파드명으로는 불가능하다.

그런데 스테이트풀셋이 헤드리스 서비스를 사용하고, 서비스의 metadata.name이 스테이트풀셋의 spec.serviceName과 같은 경우에는 추가로 파드 단위의 이름 해석을 할 수 있다.

```
파드명.서비스명.네임스페이스명.svc.cluster.local
```

```bash
dig sample-statefulset-headless-0.sample-headless.default.svc.cluster.local
# ANSWER SECTION:
# sample-statefulset-headless-0.sample-headless.default.svc.cluster.local. 30 IN A 10.0.1.41
```

이 기능이 데이터베이스처럼 각 파드를 개별적으로 지정해야 하는 스테이트풀 워크로드에서 중요하다.

---

## 6.8 ExternalName 서비스

클러스터 내부에서 외부 도메인을 참조할 때 쓰는 서비스다. CNAME 레코드를 반환하는 형태로, 외부 서비스를 클러스터 내부 이름처럼 부를 수 있게 해준다. 외부 서비스를 내부로 전환할 때 매니페스트 변경 없이 전환할 수 있다는 장점이 있다.

---

## 6.9 None-Selector 서비스

셀렉터를 지정하지 않고 엔드포인트를 직접 수동으로 등록하는 서비스다. 클러스터 외부의 특정 IP를 서비스처럼 다루고 싶을 때 사용한다.

---

## 6.10 ~ 6.11 인그레스

서비스가 L4 로드 밸런싱이라면, 인그레스는 L7 로드 밸런싱을 제공한다. 호스트명이나 URL 경로에 따라 다른 서비스로 트래픽을 분기할 수 있다.

### 인그레스 컨트롤러

인그레스는 규칙을 정의하는 리소스일 뿐이고, 실제 처리는 인그레스 컨트롤러가 담당한다. 대표적인 구현이 Nginx 인그레스 컨트롤러다.

```
LoadBalancer Service (ingress-endpoint)
        ↓
Deployment (nginx-ingress-controller)
        ↓
Service service-a / service-b / default-http-backend
        ↓
Deployment service-a / service-b / default-http-backend
```

클러스터 외부로부터의 통신을 확보하기 위해 Nginx 인그레스 컨트롤러의 파드에 로드 밸런서 서비스(NodePort 등에서도 가능)를 생성해야 한다.

```bash
kubectl apply -f https://raw.githubusercontent.com/kubernetes/ingress-nginx/controller-v0.44.0/deploy/static/provider/cloud/deploy.yaml
```

커스텀하여 사용하는 경우에는 패키지 관리 툴 헬름(Helm)을 사용하여 인그레스 컨트롤러를 설치하는 것도 검토해볼 만하다.

### 인그레스 리소스 생성을 위한 사전 준비

인그레스는 먼저 생성된 서비스를 백엔드로 전송하는 구조로 되어 있어 서비스를 먼저 생성해야 한다. 백엔드에서 사용하는 서비스는 type: NodePort를 지정한다. 인그레스 리소스에서 필요한 것은 서비스 리소스뿐이다.

### 최신 기능

IngressClass 리소스에 의한 Ingress 분리
pathType에 의한 경로 지정
호스트 이름에서 와일드카드 매칭

IngressClass 지정은 어노테이션에 의한 지정이 아니라 IngressClass 리소스와 인그레스 리소스의 spec.ingressClassName에서 지정하는 방법으로 대체될 예정이다.

지금까지 인그레스 리소스에 경로를 지정한 경우 처리는 각각의 인그레스 컨트롤러 구현에 따라 달랐지만, pathType으로 설정할 수 있게 되었다.

| pathType | 개요 |
| --- | --- |
| ImplementationSpecific (기본값) | 구현에 따라 처리가 다름 |
| Exact | URL 경로와의 완전 일치가 조건 |
| Prefix | URL 경로에 대해 슬래시를 기준으로 분리할 때 전방 일치가 조건 |

## 6.12 정리

이 장에서는 컨테이너에 접속하기 위한 엔드포인트를 제공하는 서비스와 인그레스 리소스를 다뤘다.

| 종류 | 특징 |
| --- | --- |
| ClusterIP | 클러스터 내부에서만 접속 가능한 가상 IP |
| ExternalIP | 특정 노드의 IP와 포트로 수신 |
| NodePort | 모든 노드의 특정 포트로 수신 |
| LoadBalancer | 클러스터 외부 로드 밸런서 사용, 실서비스 공개용 |
| Headless | ClusterIP 없이 DNS 라운드 로빈으로 파드 IP 반환 |
| ExternalName | 외부 도메인을 CNAME으로 참조 |
| None-Selector | 엔드포인트를 수동으로 등록 |
| Ingress | L7 로드 밸런싱, 호스트나 경로 기반 라우팅 |

다음 7장에서는 설정 파일이나 기밀 정보, 영구 볼륨을 제공하는 컨피그 & 스토리지 API 카테고리를 다룬다.

서비스는 바뀌는 파드 앞에 고정된 접근점을 만들어주는 리소스이며, 어디까지 노출할지에 따라 ClusterIP에서 LoadBalancer까지 타입이 나뉘고, 경로 기반 분기가 필요하면 인그레스를 쓴다.

---

## 정리하며 (개별연구와 연결)

이번 장은 개별연구에서 다룬 내용과 가장 많이 겹쳤다.

6.2에서 설명하는 CNI와 노드별 네트워크 세그먼트 자동 분할이 바로 Cilium의 cluster-pool IPAM이 하는 일이다. 교재는 "사용자가 설정하지 않아도 된다"고만 하는데, 실제로 Cilium은 자체 IPAM으로 10.0.0.0/8을 나눠 쓰기 때문에 kubectl get nodes에서 보이는 PodCIDR과 실제 할당 대역이 달라진다.

노드 간 트래픽을 VXLAN이나 L2 Routing으로 전송한다는 부분도 그대로 이어진다. 개별연구에서 routing-mode를 tunnel(VXLAN)에서 native로 바꿔본 것이 교재의 이 두 방식을 직접 실험한 셈이다.

서비스 디스커버리와 resolv.conf의 search 지시자는 앞서 네임스페이스 간 통신을 정리할 때 나왔던 내용이고, 헤드리스 서비스에서 파드 단위 이름 해석이 가능한 조건은 스테이트풀셋과 묶여 있어서 5장 내용과도 연결된다.
