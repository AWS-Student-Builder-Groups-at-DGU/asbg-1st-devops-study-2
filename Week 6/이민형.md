# 5.5 데몬셋 (DaemonSet)

## 개념
- 레플리카셋의 특수한 형태. 각 노드에 파드를 **하나씩** 배치하는 리소스
- 레플리카셋은 N개의 파드를 노드 리소스 상황에 맞게 배치하므로 노드별 파드 수가 다를 수 있고 모든 노드에 배치된다는 보장도 없음
- 데몬셋은 레플리카 수를 지정할 수 없고, 한 노드에 두 개의 파드를 배치할 수도 없음
- 특정 노드에 배치하고 싶지 않다면 nodeSelector나 노드 안티어피니티로 예외 처리 가능
- 노드를 늘리면 새 노드에서도 자동으로 파드가 기동됨

<img width="1693" height="929" alt="image" src="https://github.com/user-attachments/assets/f4a37aaa-cd0b-4578-96ae-57488b28cd57" />

## 주요 용도
모든 노드에서 반드시 동작해야 하는 프로세스
- 로그 수집 에이전트 (Fluentd)
- 노드 상태 / 리소스 모니터링 에이전트 (Datadog)

## 매니페스트
`kind: DaemonSet`으로 지정. 레플리카셋과 달리 `replicas` 항목이 없음.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: sample-ds
spec:
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
      - name: nginx-container
        image: nginx:1.16
```

## 업데이트 전략
`spec.updateStrategy.type`으로 지정. 기본값은 RollingUpdate.

| 전략 | 동작 | 특징 |
|---|---|---|
| OnDelete | 매니페스트 변경 시 즉시 업데이트하지 않고, 파드가 다른 이유로 재생성될 때 새 정의로 생성 | 모니터링 / 로그 전송처럼 업데이트 시점을 수동으로 제어하고 싶을 때. type 외 지정 항목 없음 |
| RollingUpdate | 디플로이먼트와 동일하게 즉시 파드 업데이트 | 한 노드에 파드를 여러 개 둘 수 없으므로 maxSurge 설정 불가. maxUnavailable만 지정 (기본값 1, 0 불가) |

- OnDelete에서 임의 시점에 업데이트하려면 `kubectl delete pod`로 파드를 수동 정지하고 자동 복구로 새 파드가 생성되게 함
- OnDelete는 이전 버전이 장기간 유지될 수 있다는 점에 주의

```yaml
spec:
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 2
```

# 5.6 스테이트풀셋 (StatefulSet)

## 개념
- 레플리카셋의 특수한 형태. 데이터베이스 등 스테이트풀한 워크로드용 리소스
- 레플리카셋과의 차이
  - 파드명 접미사가 숫자 인덱스 (`sample-statefulset-0`, `-1`, ... `-N`)
  - 파드명이 바뀌지 않음
  - 데이터를 영구적으로 저장하는 구조 (영구 볼륨 사용 시 파드 재기동 후에도 같은 디스크 사용)

## 영구 볼륨 연결
- `spec.volumeClaimTemplates`로 각 파드에 영구 볼륨 클레임(PVC)을 설정
- 파드 재기동이나 다른 노드로 이동 시에도 같은 데이터를 유지한 채 컨테이너가 재생성됨
- 영구 볼륨은 하나의 파드가 소유할 수도, 종류에 따라 여러 파드가 공유할 수도 있음
- 스테이트풀셋이 볼륨 리소스를 생성하여 영구 볼륨을 확보하는 구조

```yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: sample-statefulset
spec:
  serviceName: sample-statefulset
  replicas: 3
  selector:
    matchLabels:
      app: sample-app
  template:
    metadata:
      labels:
        app: sample-app
    spec:
      containers:
      - name: nginx-container
        image: nginx:1.16
        volumeMounts:
        - name: www
          mountPath: /usr/share/nginx/html
  volumeClaimTemplates:
  - metadata:
      name: www
    spec:
      accessModes:
      - ReadWriteOnce
      resources:
        requests:
          storage: 1G
```

## 스케일링
`kubectl apply -f` 또는 `kubectl scale`로 스케일링. 레플리카셋이나 데몬셋과 달리 기본적으로 파드를 **한 번에 하나씩** 생성 / 삭제하므로 시간이 조금 걸림.

- 스케일 아웃: 인덱스가 가장 작은 것부터 생성. 이전 파드가 Ready가 된 후 다음 파드 생성 (0 → 1 → 2). 최초 생성 시에도 동일
- 스케일 인: 인덱스가 가장 큰 파드(가장 최근 생성)부터 삭제 (2 → 1 → 0)
- 레플리카셋은 파드를 무작위로 삭제하므로 특정 파드가 마스터인 애플리케이션에 부적합. 스테이트풀셋은 0번 파드가 항상 먼저 생성되고 가장 늦게 삭제되므로 0번을 마스터 노드로 쓰는 이중화 구조에 적합

## 라이프사이클 (podManagementPolicy)
- 기본값 `OrderedReady`: 파드를 하나씩 생성하고 Ready가 되면 다음 파드 생성
- `Parallel`: 레플리카셋처럼 여러 파드를 병렬로 동시에 기동

<img width="1448" height="1086" alt="image" src="https://github.com/user-attachments/assets/c505ed34-f72c-46d0-a3de-bd7382d25fa7" />

```yaml
spec:
  podManagementPolicy: Parallel
```

## 업데이트 전략
데몬셋과 동일하게 OnDelete와 RollingUpdate 중 선택. 기본값은 RollingUpdate.

### OnDelete
- 매니페스트 수정 후에도 기존 파드는 업데이트되지 않고, 파드가 다른 이유로 재생성될 때 새 설정으로 생성
- 영속 영역을 가진 데이터베이스 / 클러스터에서 수동 업데이트를 원할 때 많이 사용

### RollingUpdate
- 영속 데이터가 있으므로 디플로이먼트처럼 추가 파드를 생성하는 롤링 업데이트 불가
- maxUnavailable도 지정 불가. 파드마다 Ready 확인 후 하나씩 업데이트
- podManagementPolicy가 Parallel이어도 업데이트는 하나씩 순차 진행
- `partition` 설정 가능
  - 전체 파드 중 어느 인덱스부터 업데이트할지 지정
  - partition 값 이상의 인덱스만 업데이트, 그보다 작은 인덱스는 업데이트 안 됨
  - 전체에 영향 없이 부분 적용 후 확인할 수 있어 안전한 업데이트 가능
  - OnDelete와 달리 수동 재기동해도 partition보다 작은 인덱스는 업데이트되지 않음
  - 업데이트 순서는 인덱스 큰 것부터 (partition=3, replicas=5이면 4 → 3 순서)

<img width="1402" height="1122" alt="image" src="https://github.com/user-attachments/assets/c43eb97f-377a-4b85-88eb-5617818e6b20" />

```yaml
spec:
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      partition: 3
```

## 영구 볼륨 데이터 유지
- 파드 삭제(`kubectl delete pod`), 컨테이너 프로세스 정지 등으로 파드가 재생성되어도 영구 볼륨의 파일은 유실되지 않음
- 복구 후 IP는 변경되지만 파드명은 그대로 유지

## 스테이트풀셋 삭제와 영구 볼륨
- 스테이트풀셋을 삭제해도 확보한 영구 볼륨은 함께 해제되지 않음 (데이터 백업 시간을 주기 위함)
- 영구 볼륨을 해제하지 않고 스테이트풀셋을 다시 생성하면 기존 데이터가 그대로 유지된 채 파드 기동. 스케일 인으로 레플리카 수를 줄인 경우도 동일
- 볼륨이 남아 있으면 관리형 서비스는 과금, 온프레미스는 디스크 공간이 점유되므로 삭제 후 PVC도 해제 필요
- PVC를 삭제해도 PV의 ReclaimPolicy 설정에 따라 PV가 남는 경우가 있음 (7장 참고)

# 5.7 잡 (Job)

## 개념
- 컨테이너를 사용하여 한 번만 실행되는 리소스
- 정확히는 **N개의 병렬로 실행하면서 지정한 횟수의 컨테이너 실행(정상 종료)을 보장**하는 리소스

<img width="1693" height="929" alt="image" src="https://github.com/user-attachments/assets/f5f1392a-0569-42d1-b171-bd3c8146f7ff" />

## 레플리카셋과의 차이점
| 구분 | 레플리카셋 | 잡 |
|---|---|---|
| 파드 정지 | 예상치 못한 에러로 간주 | 정상 종료되는 것을 전제로 설계 |
| 적합한 워크로드 | 계속 떠 있어야 하는 서비스 | 종료가 목적인 작업 |

- 잡이 적합한 예: 특정 서버와의 rsync, S3 등 오브젝트 스토리지에 파일 업로드
- 레플리카셋 등에서는 정상 종료 횟수를 셀 수 없으므로 배치 처리라면 잡을 사용

## 매니페스트
- `apiVersion: batch/v1`, `kind: Job`
- 레이블과 셀렉터를 명시적으로 지정할 수 있으나, 쿠버네티스가 유니크한 uuid를 자동 생성하므로 **명시 지정은 비권장**
- `kubectl get`으로 확인 시 READY가 아닌 **정상 종료한 파드 수(COMPLETIONS)**를 표시

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: sample-job
spec:
  completions: 1
  parallelism: 1
  backoffLimit: 10
  template:
    spec:
      containers:
      - name: tools-container
        image: amsy810/tools:v2.0
        command: ["sleep"]
        args: ["60"]
      restartPolicy: Never
```

## restartPolicy에 따른 동작 차이
`spec.template.spec.restartPolicy`에 OnFailure 또는 Never 중 하나를 반드시 지정.

| 값 | 동작 |
|---|---|
| Never | 파드에 장애 발생 시 **신규 파드**를 생성 |
| OnFailure | **동일 파드**를 다시 사용하여 잡을 재시작 (RESTARTS 카운터 증가) |

- OnFailure의 경우 파드가 기동하는 노드와 파드 IP는 변경되지 않음. 영구 볼륨이나 hostPath를 마운트하지 않았다면 데이터 자체는 유실됨
- Docker에서 `spec.containers[].command`로 지정한 프로그램은 PID 1로 실행됨. PID 1에서 sleep을 실행하면 SIGKILL이 전달되지 않아 프로세스를 정지시킬 수 없으므로, 셸에서 별도 프로세스를 시작하는 형태(`sh -c`)로 기동해야 함

## 병렬 실행 파라미터
| 파라미터 | 의미 | 도중 변경 |
|---|---|---|
| completions | 성공(정상 종료) 횟수 | 불가 (immutable) |
| parallelism | 병렬성 | 가능 |
| backoffLimit | 실패 허용 횟수 | 가능 |

기본값은 모두 1(backoffLimit은 6)이며, 변경은 매니페스트 수정 후 `kubectl apply` 또는 `kubectl patch`로 적용.

### 네 가지 전형적인 워크로드 패턴

| 워크로드 | completions | parallelism | backoffLimit |
|---|---|---|---|
| 1회만 실행하는 태스크 (One Shot Task) | 1 | 1 | 0 |
| N개 병렬로 실행시키는 태스크 (Multi Task) | M | N | P |
| 한 개씩 실행하는 작업 큐 (Single WorkQueue) | 미지정 | 1 | P |
| N개 병렬로 실행하는 작업 큐 (Multi WorkQueue) | 미지정 | N | P |

**One Shot Task**
- `completions=1 / parallelism=1 / backoffLimit=0`
- "한 개 병렬로 실행 / 성공 1회면 종료 / 실패 0회면 종료(실패 불허)" 조건이므로 성공 여부와 관계없이 반드시 1회만 실행

<img width="1672" height="941" alt="image" src="https://github.com/user-attachments/assets/de0edc34-a611-4426-af92-7742b8fb5e17" />

**Multi Task**
- 예: `completions=5 / parallelism=3` → 파드가 5회 정상 종료할 때까지 세 개 병렬로 실행
- 세 개 생성 후 세 개가 종료되면, 남은 두 개만 필요하므로 이후에는 세 개가 아닌 **두 개만** 생성됨
- "남은 성공 횟수가 2여도 3 병렬로 실행해서 먼저 성공하는 것이 나오면 종료" 방식으로는 동작하지 않음
- parallelism을 completions 이상으로 잡아도 파드는 completions 수만큼만 생성됨 (completions=3 / parallelism=5 → 파드 3개)

<img width="1672" height="941" alt="image" src="https://github.com/user-attachments/assets/548272c8-5b8d-410b-ae77-a4288cf4e845" />

**Multi WorkQueue**
- 개별 파드의 정상 종료 횟수가 아니라, **큰 처리 전체가 끝날 때까지** 몇 개 병렬로 계속 실행하고 싶을 때 사용
- completions를 지정하지 않고 parallelism만 지정
- parallelism 수만큼 파드를 실행하고, **그중 하나라도 정상 종료하면** 이후 파드를 생성하지 않음
- 이미 실행 중인 나머지 파드는 강제 정지되지 않고 개별 처리가 끝날 때까지 계속 동작
- 사용 전제
  - 처리 전체의 진행을 관리하는 메시지 큐가 필요
  - 파드 내 애플리케이션은 큐에서 반복적으로 데이터를 가져오는 처리를 구현
  - 큐가 빈 것을 확인하면 해당 파드가 정상 종료하도록 구현 → 전체 처리를 정지
  - 정상 종료 후 큐에 새 데이터가 들어오는 경우는 크론잡과 조합
  - 큐에 쌓인 메시지 양에 따라 병렬 수를 늘리면 자동 스케일도 가능

**Single WorkQueue**
- Multi WorkQueue 응용. completions 미지정 + parallelism=1
- 한 번 정상 종료할 때까지 한 개씩 실행하는 작업 큐
- completions는 immutable이지만 parallelism은 변경 가능하므로, Single → Multi WorkQueue로 나중에 전환 가능

### COMPLETIONS 출력 형식 차이
- 태스크형(Multi Task): `3/5` 형태로 출력
- 작업 큐형(Multi WorkQueue): `0/1 of 3` 형태로 출력. 세 개 병렬 실행 중 하나가 정상 종료하면 되지만 아직 하나도 종료되지 않았음을 의미

## 일정 기간 후 잡 삭제 (ttlSecondsAfterFinished)
- 잡은 종료 후에도 삭제되지 않고 계속 남음
- `spec.ttlSecondsAfterFinished`를 지정하면 잡 종료 후 일정 시간(초) 경과 후 자동 삭제

```yaml
spec:
  ttlSecondsAfterFinished: 30
```

## 매니페스트 없이 생성
`kubectl create job`으로 간단히 생성 가능하지만 상세 설정은 불가. 서비스 환경에서는 매니페스트 사용 권장.

```bash
kubectl create job sample-job-by-cli --image=amsy810/tools:v2.0 -- sleep 30

# 크론잡 기반으로 잡 생성
kubectl create job sample-job-from-cronjob --from cronjob/sample-cronjob
```

# 5.8 크론잡 (CronJob)

## 개념
- Cron과 같이 스케줄링된 시간에 **잡을 생성**하는 리소스
- 쿠버네티스 1.4까지는 ScheduledJob이라는 이름이었으나 CronJob으로 변경
- 크론잡 → 잡 → 파드의 **3계층 구조**. 디플로이먼트 → 레플리카셋 → 파드 관계와 유사

<img width="1182" height="1330" alt="image" src="https://github.com/user-attachments/assets/9e609b6e-13b2-4c10-b489-b5117d5483cc" />

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/a8e71aae-bc77-4b05-8b33-d1c8e0969175" />

```yaml
apiVersion: batch/v1beta1
kind: CronJob
metadata:
  name: sample-cronjob
spec:
  schedule: "*/1 * * * *"
  concurrencyPolicy: Allow
  startingDeadlineSeconds: 30
  successfulJobsHistoryLimit: 5
  failedJobsHistoryLimit: 3
  suspend: false
  jobTemplate:
    spec:
      completions: 1
      parallelism: 1
      backoffLimit: 0
      template:
        spec:
          containers:
          - name: tools-container
            image: amsy810/random-exit:v2.0
          restartPolicy: Never
```

## 일시 정지 (suspend)
- `spec.suspend: true`로 설정하면 스케줄 대상에서 제외 (기본값 false)
- 점검 등으로 잡 생성을 원치 않을 때 사용

```bash
kubectl patch cronjob sample-cronjob -p '{"spec":{"suspend":true}}'
```

## 임의 시점에 실행
정기 실행 외 시점에 잡을 생성하려면 `--from` 옵션 사용.

```bash
kubectl create job sample-job-from-cronjob --from cronjob/sample-cronjob
```

## 동시 실행 제어 (concurrencyPolicy)
잡 실행이 의도한 시간 간격 안에 정상 종료될 때는 명시하지 않아도 동시 실행되지 않음. 이전 잡이 아직 실행 중일 때의 정책을 지정.

| 정책 | 개요 |
|---|---|
| Allow (기본값) | 동시 실행에 대한 제한을 하지 않음 |
| Forbid | 이전 잡이 종료되지 않았을 경우 다음 잡을 실행하지 않음 |
| Replace | 이전 잡을 취소하고 새 잡을 시작 |

- Replace는 정확히는 **이전 잡의 레플리카 수를 0으로 변경**하여 연결된 파드를 삭제 처리

<img width="1536" height="1024" alt="image" src="https://github.com/user-attachments/assets/ff1d8833-97d0-465d-b032-acf160d56b2b" />

## 실행 시작 기한 제어 (startingDeadlineSeconds)
- 쿠버네티스 마스터가 지정 시간에 잡을 생성하므로, 마스터가 일시적으로 정지되면 시작 시간이 지연될 수 있음
- `spec.startingDeadlineSeconds`(초)로 지연을 허용할 시간을 지정
- 예: 매시 00분 시작 잡을 "00~05분에만 실행 가능"으로 하려면 300 지정
- 기본값에서는 시작 시간이 아무리 늦어져도 잡을 생성

<img width="1774" height="887" alt="image" src="https://github.com/user-attachments/assets/336e3006-a0b2-4071-a19d-218d1c4b3822" />

## 크론잡 이력 (History Limit)
| 설정 항목 | 개요 | 기본값 |
|---|---|---|
| spec.successfulJobsHistoryLimit | 성공한 잡을 저장하는 개수 | 3 |
| spec.failedJobsHistoryLimit | 실패한 잡을 저장하는 개수 | 3 |

- 잡이 남아 있다는 것은 연결된 파드도 Completed / Error 상태로 남아 있어 `kubectl logs`로 로그를 확인할 수 있다는 의미
- 두 값을 0으로 하면 잡 종료 시 즉시 삭제
- 실제 운영에서는 컨테이너 로그를 외부 로그 시스템으로 운영하는 것을 권장. 대시보드 등 UI로 결과를 확인하는 경우라면 HistoryLimit을 큰 값으로 두는 것이 좋음

<img width="1774" height="887" alt="image" src="https://github.com/user-attachments/assets/c22e3820-eea7-4ae6-b04e-b4b3b90cd87c" />

## 매니페스트 없이 생성
```bash
kubectl create cronjob sample-cronjob-by-cli \
  --image amsy810/random-exit:v2.0 \
  --schedule "*/1 * * * *" \
  --restart Never
```

# 5.9 정리

## 워크로드 API 리소스 사용 방법

| 리소스 종류 | 사용 방법 |
|---|---|
| 파드 | 디버깅이나 확인 용도로 사용 |
| 레플리케이션 컨트롤러 | 추천하지 않으며 대신 레플리카셋을 사용 |
| 레플리카셋 | 파드를 스케일링하여 관리. 기본적으로는 디플로이먼트를 통해 사용 |
| 디플로이먼트 | 스케일링할 워크로드에 사용 |
| 데몬셋 | 각 노드에 파드 하나씩 배포할 때 사용 |
| 스테이트풀셋 | 영속성 데이터 등의 상태를 가진 워크로드에 사용 |
| 잡 | 작업 큐나 태스크 등 컨테이너 종료가 필요한 워크로드에 사용 |
| 크론잡 | 정기적으로 잡을 생성하고 싶은 경우 사용 |

- 파드나 레플리카셋을 생성하는 경우 처음부터 **디플로이먼트를 통해** 생성하는 것이 좋음
