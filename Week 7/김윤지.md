> **요약)** 서비스 API 카테고리 = 파드에 트래픽을 로드 밸런싱하고, 파드를 찾을 수 있는 고정된 접속 창구(엔드포인트)를 제공하는 리소스
>
> → 파드는 뜰 때마다 IP가 바뀌므로, 서비스가 그 앞단에서 "변하지 않는 주소"를 붙여줌
> → ClusterIP(내부용) → ExternalIP/NodePort(간이 외부 공개) → LoadBalancer(정식 외부 공개) 순으로 접근 범위가 넓어짐

---

## 6.1 서비스 API 카테고리 개요

4장의 다섯 카테고리 중 **컨테이너를 외부에 공개하는 엔드포인트를 제공하는 리소스**가 서비스 API 카테고리. 목적에 따라 총 7가지 서비스 타입 + 인그레스로 구성됨

| 종류           | 개요                                          |
| -------------- | --------------------------------------------- |
| ClusterIP      | 클러스터 내부 전용 가상 IP                    |
| ExternalIP     | ClusterIP의 한 종류, 노드 IP로 직접 노출      |
| NodePort       | 모든 노드의 특정 포트로 노출                  |
| LoadBalancer   | 외부 로드 밸런서에 가상 IP 할당 (가장 실용적) |
| Headless(None) | 가상 IP 없이 파드 IP를 그대로 디스커버리      |
| ExternalName   | 클러스터 외부 이름으로 리다이렉트             |
| None-Selector  | 셀렉터 없이 수동으로 엔드포인트 지정          |
| 인그레스       | L7 로드 밸런싱을 제공하는 별도 리소스         |

cf. ExternalIP, None-Selector는 엄밀히는 별도 `type`이 아니지만(ExternalIP는 `type: ClusterIP` + `externalIPs` 필드 조합) 책에서는 서비스 타입 중 하나로 다룸

실제로 클러스터 외부와 통신할 때 자주 쓰는 **6.1~6.6 (ClusterIP, ExternalIP, NodePort, LoadBalancer)**

## 6.2 쿠버네티스 클러스터 네트워크와 서비스

파드 내부 컨테이너는 IP를 공유해 `localhost`로 통신하고, 다른 파드와는 파드 IP로 통신함(5장 복습). 클러스터는 생성 시 노드마다 다른 네트워크 세그먼트를 자동 구성(CNI 플러그인에 따라 방식 상이)하고, VXLAN, L2 Routing 등으로 노드 간 통신을 가능하게 함 → 이 내부 네트워크는 **서비스 없이도 파드 간 통신이 가능**

그럼에도 서비스를 쓰는 이유는 두 가지

- 파드에 트래픽 로드 밸런싱
- 서비스 디스커버리와 클러스터 내부 DNS

### 6.2.1 파드에 트래픽 로드 밸런싱

서비스는 `spec.selector`에 지정한 레이블과 일치하는 파드에 트래픽을 로드 밸런싱함. 생성하면 `Endpoints` 항목에 실제 로드밸런싱 대상 파드의 IP:포트 목록이 채워짐

주의) **Endpoints가 비어 있으면 대개 셀렉터 조건 불일치.** 파드 레이블과 서비스 셀렉터 값이 정확히 같은지부터 확인

- **여러 포트 할당**: http/https처럼 포트별로 ClusterIP가 다르면 불편하므로, 하나의 서비스에 여러 포트(`ports` 배열)를 등록할 수 있음
- **이름을 사용한 포트 참조**: 파드의 `containerPort`에 이름(`name: http`)을 붙여두면 서비스의 `targetPort`에서 숫자 대신 그 이름으로 참조 가능 → 파드마다 실제 포트 번호(80, 81 등)가 달라도 같은 이름이면 하나의 서비스로 묶임

### 6.2.2 클러스터 내부 DNS와 서비스 디스커버리

서비스 디스커버리 = 서비스에 속한 파드를 찾거나, 서비스명으로 엔드포인트를 알아내는 기능. 방식은 3가지

| 방식           | 설명                                                                               |
| -------------- | ---------------------------------------------------------------------------------- |
| 환경 변수      | 파드 기동 시 같은 네임스페이스 서비스가 `SERVICE_HOST` 등으로 주입됨               |
| DNS A 레코드   | `서비스명.네임스페이스명.svc.cluster.local` → ClusterIP로 정방향 해석              |
| DNS SRV 레코드 | `_포트명._프로토콜.서비스명.네임스페이스명.svc.cluster.local` → 포트까지 포함 해석 |

주의) **환경 변수 방식**은 도커 `--links`와 같은 형식으로 파드 생성 시점의 서비스만 등록됨. 파드가 뜬 _후에_ 생성/삭제된 서비스는 반영되지 않아 예기치 못한 장애로 이어질 수 있음 → `spec.enableServiceLinks: false`로 끌 수도 있음(기본값 true)

**DNS A 레코드 방식**이 추천됨: IP를 애플리케이션 설정에 직접 박으면 서비스 재생성마다 IP가 바뀔 때 설정을 고쳐야 해서 컨테이너를 immutable하게 유지할 수 없음. DNS명을 쓰면 그럴 필요가 없음

cf. 컨테이너 내부 `/etc/resolv.conf`의 `search` 옵션 덕분에 같은 네임스페이스면 서비스명만, 다른 네임스페이스면 `서비스명.네임스페이스명`까지만 써도 이름이 해석됨

**DNS SRV 레코드**는 포트명, 프로토콜까지 포함해 포트 번호까지 알려주는 방식. 정방향/역방향(`dig -x`) 질의 모두 가능

### 6.2.3 클러스터 내부 DNS와 클러스터 외부 DNS

파드가 `dnsPolicy`를 명시하지 않는 이상 모든 파드는 클러스터 내부 DNS를 사용함. 내부 DNS에는 `*.cluster.local` 레코드만 있으므로, 그 외 이름(외부 도메인)을 질의하면 **클러스터 외부 DNS로 재귀 질의**함

### 6.2.4 `1.18 Stable` 노드 로컬 DNS 캐시

대규모 클러스터에서 매번 클러스터 내부 DNS를 타면 성능이 떨어지므로, 각 노드 로컬에 DNS 캐시 서버를 두는 구조. 캐시 히트 시 노드 밖으로 나가지 않고 바로 응답(GKE는 `gcloud` 명령으로 활성화)

## 6.3 ClusterIP 서비스

> 쿠버네티스 클러스터 **내부에서만** 통신 가능한 가상 IP(Internal Network)를 할당하는, 가장 기본이 되는 서비스
>
> = **type: ClusterIP**

ClusterIP와의 통신은 각 노드에서 실행 중인 `kube-proxy`가 담당함(실제 동작은 Proxy-mode에 따라 다름). 쿠버네티스 API용 `kubernetes` 서비스도 기본적으로 ClusterIP로 생성되어 있음

**왜 필요한가?** 클러스터 외부에서 트래픽을 받을 필요가 없는 내부 로드 밸런서 용도. DB, 내부 API 서버처럼 외부 노출이 필요 없는 워크로드에 적합

### 6.3.1 ClusterIP 서비스 생성

| 설정 항목               | 개요                           |
| ----------------------- | ------------------------------ |
| spec.ports[].port       | ClusterIP에서 수신할 포트 번호 |
| spec.ports[].targetPort | 목적지 컨테이너 포트 번호      |

```yaml
# sample-clusterip.yaml
apiVersion: v1
kind: Service
metadata:
  name: sample-clusterip
spec:
  type: ClusterIP
  ports:
    - name: "http-port"
      protocol: "TCP"
      port: 8080 # 서비스가 수신할 포트
      targetPort: 80 # 파드(컨테이너)가 수신할 포트
  selector:
    app: sample-app # 이 레이블을 가진 파드로 로드 밸런싱
```

### 6.3.2 ClusterIP 가상 IP 정적 지정

기본은 서비스명으로 DNS 해석하는 게 바람직하지만, IP로 직접 지정해야 하면 `spec.clusterIP`로 고정 가능

주의) **서비스 생성 후에는 ClusterIP를 변경할 수 없음(immutable).** `kubectl apply`로 값을 바꿔도 `field is immutable` 에러가 남 → 바꾸려면 삭제 후 재생성해야 함

```yaml
spec:
  type: ClusterIP
  clusterIP: 10.3.251.194 # 실습 환경에 맞춰 IP 변경
```

## 6.4 ExternalIP 서비스

> 특정 쿠버네티스 **노드**의 IP 주소:포트에서 수신한 트래픽을 컨테이너로 전송하는 서비스
>
> = `type: ClusterIP` + `spec.externalIPs` 조합 (별도 `type: ExternalIP`가 있는 게 아님)

| 설정 항목                 | 개요                                        |
| ------------------------- | ------------------------------------------- |
| `spec.externalIPs`        | 쿠버네티스 노드 IP 주소                     |
| `spec.ports[].port`       | ExternalIP와 ClusterIP에서 수신할 포트 번호 |
| `spec.ports[].targetPort` | 목적지 컨테이너 포트 번호                   |

```yaml
# sample-externalip.yaml
apiVersion: v1
kind: Service
metadata:
  name: sample-externalip
spec:
  type: ClusterIP # type 자체는 ClusterIP
  externalIPs:
    - 10.178.0.61 # 실습 환경의 노드 IP로 변경
  ports:
    - name: "http-port"
      protocol: "TCP"
      port: 8080
      targetPort: 80
  selector:
    app: sample-app
```

`externalIPs`에 넣은 노드만 해당 포트를 Listen하므로, **넣지 않은 노드는 접속 불가**

주의) GKE는 GCE 인스턴스에 할당된 **Internal용 IP만 externalIPs에 사용 가능**하고, 글로벌 IP는 OS가 직접 인식하지 못해 쓸 수 없음. 책에서도 **"특별한 이유가 없으면 ExternalIP 대신 NodePort를 검토하라"**고 권장함 → 노드 IP를 수동으로 관리해야 하는 부담이 있기 때문

---

## 6.5 NodePort 서비스

> **모든** 쿠버네티스 노드의 IP 주소:포트에서 수신한 트래픽을 컨테이너로 전송하는 서비스
>
> = **type: NodePort**

ExternalIP와 비슷하지만, ExternalIP가 지정한 노드만 Listen하는 것과 달리 NodePort는 `0.0.0.0:포트`로 **모든 노드**가 Listen함. 도커 스웜의 "서비스를 Expose한 상태"와 유사한 동작

### 6.5.1 NodePort 서비스 생성

| 설정 항목                 | 개요                                  |
| ------------------------- | ------------------------------------- |
| `spec.ports[].port`       | ClusterIP에서 수신할 포트 번호        |
| `spec.ports[].targetPort` | 목적지 컨테이너 포트 번호             |
| `spec.ports[].nodePort`   | **모든** 노드 IP에서 수신할 포트 번호 |

```yaml
# sample-nodeport.yaml
apiVersion: v1
kind: Service
metadata:
  name: sample-nodeport
spec:
  type: NodePort
  ports:
    - name: "http-port"
      protocol: "TCP"
      port: 8080
      targetPort: 80
      nodePort: 30080 # 생략하면 빈 포트가 자동 할당됨
  selector:
    app: sample-app
```

NodePort도 내부적으로 ClusterIP가 자동 할당됨. 클러스터 외부에서는 임의의 노드 IP + `nodePort`로 접속 가능하고, 파드로의 트래픽 분산도 이루어짐

### 6.5.2 NodePort 주의점

- 사용 가능한 포트 범위는 대부분 환경에서 **30000~32767**(쿠버네티스 기본값). 범위 밖 지정 시 에러
- **여러 NodePort 서비스가 같은 포트를 쓸 수 없음** — 노드가 같은 포트에 두 개의 Listen 상태를 가질 수 없기 때문

---

## 6.6 LoadBalancer 서비스

> 서비스 환경에서 클러스터 **외부로부터 트래픽을 수신할 때 가장 실용적이고 사용하기 편리한** 서비스
>
> = **type: LoadBalancer**

쿠버네티스 클러스터 외부의 로드 밸런서에 외부 통신이 가능한 가상 IP를 할당함. GCP/AWS/Azure/OpenStack 등 클라우드 프로바이더가 지원(MetalLB 등으로 온프레미스에서도 사용 가능)

**왜 필요한가?** NodePort나 ExternalIP는 결국 하나의 노드 IP로 통신하므로 그 노드가 **단일 장애점(SPoF)**이 됨. LoadBalancer는 노드와 별도인 외부 로드 밸런서를 쓰므로 노드 장애가 발생해도 크게 문제되지 않음(장애 노드로는 자동으로 전송 중지). 단, 로드 밸런서가 장애를 감지하고 복적지에서 제외하기까지 시간이 걸려 일시적 중단이 발생할 수 있음

cf. Docker Desktop에서는 LoadBalancer 서비스를 만들면 `localhost` IP로 접속하게 해줌 → 같은 포트로 여러 LoadBalancer 서비스를 만들 수 없으니 주의

### 6.6.1 LoadBalancer 서비스 생성

| 설정 항목                 | 개요                                                       |
| ------------------------- | ---------------------------------------------------------- |
| `spec.ports[].port`       | 로드 밸런서에 할당되는 가상 IP와 ClusterIP에서 수신할 포트 |
| `spec.ports[].targetPort` | 목적지 컨테이너 포트 번호                                  |
| `spec.ports[].nodePort`   | 모든 노드 IP에서 수신할 포트 번호(자동 할당됨)             |

```yaml
# sample-lb.yaml
apiVersion: v1
kind: Service
metadata:
  name: sample-lb
spec:
  type: LoadBalancer
  ports:
    - name: "http-port"
      protocol: "TCP"
      port: 8080
      targetPort: 80
  selector:
    app: sample-app
```

생성 직후 `EXTERNAL-IP`가 `<pending>` 상태인 건 클라우드 프로바이더의 로드 밸런서 생성 처리가 백그라운드에서 진행 중이기 때문(보통 몇 초~수십 초). 완료되면 실제 외부 IP가 반환되는데, 이는 **GCE 인스턴스 IP가 아니라 GCLB(Google Cloud Load Balancing)에 할당된 가상 IP**

### 6.6.2 로드 밸런서에 할당되는 가상 IP 정적 지정

DNS 설정 등의 이유로 고정 IP가 필요하면 `spec.loadBalancerIP`로 지정 가능

주의) GKE는 **사용자가 임의의 IP를 함부로 지정할 수 없도록** 설계되어 있어서, 소유하지 않은 IP를 지정하면 `<pending>`에 멈춤. GCP라면 **VPC 네트워크 > 외부 IP 주소**에서 정적 주소를 먼저 예약해야 하고, 이때 주소 타입은 반드시 **'리전'**이어야 함('전역' 타입은 인그레스 전용)

```yaml
spec:
  type: LoadBalancer
  loadBalancerIP: xxx.xxx.xxx.xxx
```

### 6.6.3 로드 밸런서 방화벽 정책 설정

LoadBalancer 서비스는 기본적으로 **전 세계(0.0.0.0/0)에 공개**됨. `spec.loadBalancerSourceRanges`로 접속을 허가할 발신 측 네트워크를 지정하면 클라우드가 제공하는 방화벽 기능으로 제한 가능(GKE, EKS 지원)

cf. 접속 제어를 지원하지 않는 환경에서는 노드 측 `iptables`로 처리됨. 더 세밀한 제어가 필요하면 13장의 **NetworkPolicy**도 검토할 수 있지만, 확장성 저하나 레이턴시 영향이 있을 수 있어 가능하면 **로드 밸런서 쪽에서 제한하는 게 우선**

```yaml
spec:
  type: LoadBalancer
  loadBalancerSourceRanges:
    - 10.0.0.0/8
```

### 6.6.4 GKE와 클라우드 서비스에서 주의할 점

`type: LoadBalancer` 서비스를 생성하면 GKE에서는 **GCLB가 실제로 프로비저닝됨** → 불필요한 비용 발생 방지와 보안 관점에서 불필요한 서비스는 삭제 권장

주의) **서비스를 생성한 상태에서 GKE 클러스터 자체를 삭제하면 GCLB만 남아 과금이 계속 발생**할 수 있으므로, 서비스 삭제를 잊지 말 것
