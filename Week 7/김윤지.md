# Day 4. 쿠버네티스가 필요한 이유

![images/김윤지/image.png](/Week%207/images/김윤지/image.png)

쿠버네티스: 컨테이너 오케스트레이션의 필요성과 기본 개념

## 단순 컨테이너 환경의 문제점

VM 한 대 위에 컨테이너 서너 개를 띄운 소규모 서비스를 기준으로 본다.

- 애플리케이션이 여러 컨테이너로 구성될 때, 단일 가상 머신에서 운영하면 컨테이너 하나가 다운될 경우 사용자에게 직접적인 영향을 미친다.
- 이러한 문제를 해결하기 위해 운영팀이 직접 시스템에 접속하여 로그를 확인하고 문제를 해결해야 하는데, 이는 소규모 애플리케이션에서는 가능하지만, 24시간 운영이 필요한 경우나 전 세계 사용자를 대상으로 하는 서비스에서는 많은 인력과 비용이 발생한다.
- 수백, 수천 개의 컨테이너가 동시에 다운되는 대규모 장애 발생 시, 이를 관리하는 것은 매우 어렵고 생산성 저하를 초래한다.

컨테이너가 수백, 수천 개인 환경에서는

- 여러 컨테이너가 동시에 죽으면 사람이 순차 대응하는 속도로는 따라갈 수 없다
- 호스트 VM이 내려가면 그 위의 워크로드가 전부 같이 내려간다
- 애플리케이션 버전 업데이트 시에도 수많은 컨테이너를 수동으로 관리하는 것은 비효율적이며 자동화된 시스템이 필요하다.
- 외부 노출을 위해 로드밸런서와 라우팅 규칙을 직접 구성하고 계속 유지해야 한다
- 네트워킹, 리소스 관리, 보안, 고가용성, 장애 허용, 서비스 검색 등 컨테이너 오케스트레이션 시스템 없이는 해결하기 어려운 복잡한 문제들이 발생한다.

## 쿠버네티스의 역할

= 위 항목(컨테이너 환경의 복잡성)들을 해결(자동화)하는 컨테이너 오케스트레이션 도구

확장성, 로드 밸런싱, 오케스트레이션 등 다양한 측면을 최소한의 노력으로 관리할 수 있게 해줌

- 자동 복구: 죽은 파드를 감지해 다시 띄운다
- 스케일링: 부하에 따라 파드 수를 조절한다
- 로드밸런싱과 서비스 디스커버리
- 롤링 업데이트: 버전 교체를 순차적으로 수행한다
- 스케줄링과 리소스 관리: 어떤 노드에 얼마를 배치할지 결정한다

**하지만 쿠버네티스가 항상 정답은 아니며, 애플리케이션의 규모와 복잡성을 고려하여 도입 여부를 신중하게 결정해야 함**

- 컨테이너 두세 개짜리 앱에 클러스터를 붙이면 리소스와 비용, 운영 공수만 늘어난다
- EKS, AKS, GKE 같은 관리형 서비스를 써도 클러스터 유지보수, 업그레이드, 패치 계획, 워크로드 최적화는 여전히 사용자 몫이다
- 컨테이너화했다는 이유나 마이크로서비스라는 이유만으로 선택할 근거는 되지 않는다
- 소규모라면 Docker Compose, VM 위 단순 컨테이너 실행, VPS(DigitalOcean Droplet, AWS Lightsail) 수준으로 충분한 경우가 많다

## 용어 정리

| 용어                        | 의미                                               |
| --------------------------- | -------------------------------------------------- |
| 오케스트레이션              | 컨테이너의 배치, 복구, 확장을 자동으로 처리하는 것 |
| 고가용성 (HA)               | 구성 요소 일부가 죽어도 서비스가 계속 제공되는 것  |
| 장애 허용 (Fault Tolerance) | 장애 발생 상태에서도 동작을 유지하는 것            |
| 서비스 디스커버리           | IP를 몰라도 이름으로 대상을 찾아 통신하는 것       |
| 스케일링                    | 부하에 따라 인스턴스 수를 늘리고 줄이는 것         |

# Day 5. 쿠버네티스 아키텍처

컨트롤 플레인과 워커 노드의 컴포넌트가 각각 무슨 일을 하는지, 파드 생성 요청이 어떤 순서로 흐르는지 정리한다.

## Node

쿠버네티스에서 노드는 가상 머신(VM)을 의미하며, 컨테이너화된 애플리케이션이나 관리 컴포넌트를 실행하는 기본 단위이다. 쿠버네티스 클러스터는 하나 이상의 노드로 구성된다.

![images/김윤지/image 1.png](/Week%207/images/김윤지/image%201.png)

- 컨트롤 플레인/마스터 노드: 클러스터를 원활하게 운영하기 위한 다양한 관리 컴포넌트들을 호스팅하는 노드 (회사의 이사회처럼 실제 업무를 직접 수행하지는 않지만, 다른 팀이나 관리자에게 지시를 내려 회사를 운영하는 역할을 한다.)
  - **주요 컴포넌트**
    - API 서버 (API Server): 클라이언트의 모든 요청을 받는 중앙 관제탑 역할을 하며, 인증, 인가, 요청 유효성 검증 후 다른 컴포넌트와 통신한다.
    - 스케줄러 (Scheduler): API 서버로부터 받은 파드(Pod) 스케줄링 요청을 처리하며, CPU, 메모리 등 노드의 제약 조건을 고려하여 파드를 실행할 최적의 노드를 결정한다.
    - 컨트롤러 매니저 (Controller Manager): 노드 컨트롤러, 네임스페이스 컨트롤러, 디플로이먼트 컨트롤러 등 다양한 컨트롤러를 포함하며, 워크로드, 노드, 디플로이먼트 등이 항상 정상 상태를 유지하도록 모니터링하고 관리한다.
    - etcd: 클러스터의 모든 정보(상태, 노드, 파드, 설정 등)를 저장하는 키-값 데이터 저장소이다. API 서버만이 etcd에 접근하여 데이터를 읽고 쓸 수 있다.
- 워커 노드: 실제 애플리케이션 워크로드가 실행되는 노드, 컨테이너화된 애플리케이션은 이곳에서 파드(Pod) 형태로 실행된다.
  - 컴포넌트
    - kubelet: 컨트롤 플레인으로부터 명령을 받아 파드를 생성, 삭제하는 등 노드에서 실제 작업을 수행하는 에이전트이다.
    - kube-proxy: 노드 내 네트워킹을 담당하며, 파드 간 통신 및 서비스 통신을 가능하게 한다.

컨트롤 플레인은 직접 작업하지 않고 지시만 내린다. 실제 작업은 워커 노드에서 일어난다. 프로덕션 환경에서는 고가용성을 위해 컨트롤 플레인도 3대 이상 둔다.

## 쿠버네티스의 기본 배포 단위: 파드 (Pod)

- 컨테이너는 단독으로 실행할 수 없고 파드로 감싸야 한다
- 파드는 쿠버네티스에서 컨테이너를 실행하는 가장 작은 배포 단위이다.
- 보통 파드당 컨테이너 1개를 두지만, 헬퍼 컨테이너, 모니터링 에이전트, init 컨테이너가 함께 들어가기도 한다
- 같은 파드의 컨테이너는 네트워크와 스토리지 등 파드의 리소스를 공유한다

**컨트롤 플레인 컴포넌트**

| 컴포넌트                | 역할                                                                            |
| ----------------------- | ------------------------------------------------------------------------------- |
| kube-apiserver          | 클러스터의 유일한 진입점. 모든 요청을 인증, 인가, 검증하고 etcd 접근을 중계한다 |
| kube-scheduler          | 노드 미배정 파드를 감지해 제약 조건을 고려하여 배치할 노드를 결정한다           |
| kube-controller-manager | 현재 상태를 원하는 상태와 비교하여 일치하도록 관리한다                          |
| etcd                    | 클러스터 상태를 저장하는 키-값 저장소                                           |

**etcd가 키-값 저장소인 이유**

관계형 데이터베이스는 스키마가 고정돼 있다. 특정 레코드에만 필드를 하나 추가하려면 테이블 자체를 변경해야 한다. 클러스터 상태처럼 오브젝트마다 필요한 필드가 다른 데이터에는 맞지 않는다.

키-값 저장소는 스키마가 없고, 레코드마다 필요한 키와 값을 JSON 형태의 문서로 저장한다. 클러스터에 변경이 생기면 API 서버가 그 즉시 etcd에 반영하고, 조회 요청도 API 서버를 통해서만 이뤄진다.

**워커 노드 컴포넌트**

| kubelet    | API 서버의 지시를 받아 파드를 생성, 삭제하고 상태를 보고한다          |
| ---------- | --------------------------------------------------------------------- |
| kube-proxy | 파드 간, 서비스와 파드 간 통신을 가능하게 하는 네트워크 규칙을 만든다 |

**파드 생성 요청 흐름**

1. 사용자가 kubectl로 파드 생성을 요청한다
2. API 서버가 인증, 인가, 검증을 수행한다
3. API 서버가 etcd에 파드 정보를 기록하고 응답을 받는다
4. 스케줄러가 노드 미배정 파드를 발견하고 배치할 노드를 고르거나, 배정이 불가능하면 무한 대기한다 (Pending 상태)
5. API 서버가 해당 노드의 kubelet에 파드 생성을 지시한다
6. kubelet이 파드를 생성하고 결과를 API 서버에 보고한다
7. API 서버가 etcd를 갱신하고 사용자에게 최종 응답을 보낸다

모든 컴포넌트는 API 서버에만 정보를 전달하고, 판단과 지시는 API 서버가 한다.

**조회 요청 흐름**

- API 서버가 인증과 검증을 마친 뒤 etcd에서 값을 읽어 그대로 반환한다
- 실행 중인 노드에 직접 묻지 않는다
- 따라서 현재 파드의 정확한 상태를 알려면 etcd에 저장된 정보를 신뢰해야 한다

## 기억해둘 점

- API 서버가 먼저 연락하는 구조가 아니라, 스케줄러와 kubelet이 API 서버를 지켜보다가 자기 할 일을 가져가는 구조다
- 스케줄러가 죽으면 새 파드는 Pending 상태에서 멈춘다
- kubelet이 죽으면 해당 노드가 NotReady로 표시된다
- 컨트롤 플레인 컴포넌트는 상시 가용해야 한다. 특히 etcd가 죽으면 클러스터 상태를 읽고 쓸 수 없어 클러스터 자체가 마비된다

# Day 6. kind로 로컬 클러스터 구성

관리형 서비스 대신 로컬에 kind 클러스터를 만든다. EKS, AKS, GKE는 컨트롤 플레인에 접근할 수 없어 컴포넌트 단위 트러블슈팅을 연습하기 어렵다. CKA 시험 대비에는 로컬 환경이 필수다.

**kind란**

= Kubernetes IN Docker

도커 컨테이너 하나를 노드 하나로 취급해 로컬에 클러스터를 구성한다. minikube, k3s, k3d 등 대안이 있지만 설치가 단순하고 멀티 노드 구성이 쉬운 편이다.

**버전 기준**

| 항목       | 기준                           |
| ---------- | ------------------------------ |
| 사전 요구  | Docker (또는 Podman, nerdctl)  |
| Kubernetes | 시험 환경과 동일한 마이너 버전 |
| kubectl    | 클러스터와 같은 마이너 버전    |

시험에서 쓰는 Kubernetes 버전은 새 마이너 릴리스 후 몇 주 안에 갱신된다고 한다. 응시 전 CNCF 공식 시험 안내에서 확인한다. 노드 이미지의 SHA 고정 문자열은 kind 릴리스 노트에서 해당 버전 항목을 그대로 복사해 쓴다.

## 설치

### kind

```bash
brew install kind
kind --version
```

### kubectl

```bash
curl -LO "https://dl.k8s.io/release/$(curl -L -s https://dl.k8s.io/release/stable.txt)/bin/linux/amd64/kubectl"
sudo install -o root -g root -m 0755 kubectl /usr/local/bin/kubectl
kubectl version --client
```

## 단일 노드 클러스터

```bash
kind create cluster --image kindest/node:<버전> --name cka-cluster1
kubectl cluster-info --context kind-cka-cluster1
kubectl get nodes
```

- `-image`를 생략하면 kind가 지원하는 최신 버전으로 만들어진다. 노드가 하나만 나오고 컨트롤 플레인과 워커 역할이 한 노드에 섞여 있다.

## 멀티 노드 클러스터

`config.yaml`

```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker
```

```bash
kind create cluster --image kindest/node:<버전> --name cka-cluster2 --config config.yaml
kubectl get nodes
```

생성 과정은 노드 이미지 준비, 컨트롤 플레인 기동, CNI 설치, StorageClass 설치, 워커 노드 조인 순으로 진행된다. 조인 단계를 거쳐야 세 노드가 하나의 클러스터로 묶인다.

## 컨텍스트 전환

클러스터가 여러 개면 kubectl이 어느 쪽을 보는지 명시해야 한다.

```bash
kubectl config get-contexts
kubectl config use-context kind-cka-cluster1
kubectl config use-context kind-cka-cluster2
```

- 표시가 현재 컨텍스트다. kind가 만든 컨텍스트 이름은 `kind-<클러스터명>` 형식이다.

## 자주 쓰는 명령

```bash
kind get clusters
kind delete cluster --name cka-cluster1
docker ps
docker start $(docker ps -aq)
```

클러스터를 두 개 동시에 띄우면 메모리를 많이 쓴다. 실습에 쓰지 않는 쪽은 삭제해도 된다.

## 클러스터 생성 후 첫 확인 사항

클러스터의 기본 상태 파악

```bash
# 현재 컨텍스트 확인
kubectl cluster-info

# 노드 상태 확인
kubectl get nodes

# 컨트롤 플레인 컴포넌트 확인
kubectl get pods -n kube-system

# 네트워크 플러그인 (CNI) 확인
kubectl get pods -n kube-system | grep -E 'coredns|kindnet'
```
