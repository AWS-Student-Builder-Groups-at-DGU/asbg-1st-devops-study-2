
## DAY 4~6 요약


### 1. Container만으로 운영할 때 생기는 문제

**소규모 (VM 1대 + container 3~5개)**
- container 하나(프론트엔드/백엔드/DB)가 죽으면 실사용자에게 즉시 영향
- 대응 방식: 운영자가 VM에 SSH 접속 → container 로그 확인 → 수동 복구
- 담당자 1~2명으로 관리 가능 — **단, 업무 시간 내에만**

**시간대 문제**
- 글로벌 서비스는 24/7 지원 필요 → 모든 타임존을 커버할 인력 채용 → 인건비 폭증

**엔터프라이즈 규모 (container 수백~수천 개)**
- 8~10개 container가 동시에 죽는 다중 장애는 수동으로 대응 불가
- 프로덕션 outage는 디버깅·수정 가능 시간이 극히 짧고, 하루에 여러 번 발생할 수 있음
- **VM 자체가 죽으면 애플리케이션 전체가 중단** (단일 장애점)

### 2. 오케스트레이션 없이 직접 해결해야 하는 항목

| 영역 | 수동으로 해야 하는 일 |
|---|---|
| **배포(Deployment)** | 0.9 → 1.0 업데이트를 수백 개 container에 수동 적용 또는 자동화 직접 구축 |
| **네트워킹/노출** | 외부 Load Balancer 배치 + 라우팅 규칙 일일이 설정 (API만이면 API Gateway로 가능) |
| **리소스 관리** | CPU/메모리 할당과 스케줄링 직접 판단 |
| **보안** | 격리·접근 제어 직접 구성 |
| **고가용성(HA)** | 이중화 구성 직접 설계 |
| **내결함성** | 장애 감지·복구 로직 직접 작성 |
| **Service Discovery** | 서비스 간 주소 탐색 직접 관리 |

-> 이 모든 것을 처리해 주는 것이 Kubernetes (Scalability, Load Balancing, Orchestration).

- **소규모에 도입하면 리소스·비용 낭비** — container 1~2개짜리 To-Do 앱에 거대 오케스트레이션 시스템은 과잉

### 4. 쿠버네티스 아키텍처 기본 개념

**Node = 가상 머신(VM)**
컴포넌트나 워크로드를 실행하는 VM을 Kubernetes에서 Node라고 부른다.

| 구분 | 역할 |
|---|---|
| **Control Plane / Master Node** | 관리 컴포넌트 호스팅, 지시를 내림 |
| **Worker Node** | 실제 워크로드(container) 실행 |

> 프로덕션 HA 구성에서는 Control Plane도 보통 2개 이상(권장 3개) 둔다.

**Pod = Kubernetes에서 배포 가능한 가장 작은 단위**
- Kubernetes에서는 container를 그 자체로 단독 실행할 수 없다 → **Pod로 캡슐화해야 함**
- Pod 안에는 1개 이상의 container 가능. 
- Pod 내 container들은 **Pod의 리소스를 공유**

### 5. Control Plane 컴포넌트

| 컴포넌트 | 역할 |
|---|---|
| **API Server** | Control Plane의 **중심이자 클러스터의 기본 진입점(entry point)**. 외부의 모든 요청이 가장 먼저 도달하고, 클라이언트를 대신해 다른 컴포넌트와 상호작용 |
| **Scheduler** | 어떤 Pod를 어떤 Node에 올릴지 결정. Node의 CPU·가용 메모리·디스크 스토리지, request/limit 등 여러 제약 조건을 고려. **항상 Control Plane을 모니터링**하며 스케줄링 대기 중인 Pod를 탐지 |
| **Controller Manager** | 여러 controller의 집합(node controller, namespace controller, deployment controller 등). 모든 controller가 제대로 실행되는지 보장하고 워크로드·Node·Deployment가 항상 Up & Healthy한지 모니터링. **Pod가 죽으면 계속 재시작** |
| **etcd** | 클러스터의 모든 정보를 담는 **key-value 데이터 스토어** |

### 6. Worker Node 컴포넌트

| 컴포넌트 | 역할 |
|---|---|
| **kubelet** | **Node 레벨 에이전트.** API Server로부터 지시를 받아 수행 **Worker Node ↔ Control Plane 간 통신을 가능하게 함** <br> ex) API Server가 "이 Pod 삭제해" → kubelet이 삭제 실행 → "삭제됐다" 보고 → API Server가 etcd에 반영 |
| **kube-proxy** | **Node 내 통신 담당. Pod 간 통신(Pod to Pod)을 가능하게 함.|


### 7. End-to-End 흐름 — Pod 생성

<img width="955" height="735" alt="image" src="https://github.com/user-attachments/assets/5b3fb56f-1b21-4959-a3a2-0020c9327738" />



```
1.  User ──kubectl apply ~~ ──> API Server
2.  인증, 인가, 검증 
3.  API Server ──"pod 추가(pending)"──> etcd
4.  etcd ──"항목 생성 완료"──> API Server
5.  Scheduler: Control Plane을 모니터링 중 → 스케줄링 대기 Pod 발견
6.  Scheduler ──"Node에 스케줄링 요청"──> API Server
7.  API Server ──"Pod 스케줄링 요청 "──> Node A의 kubelet
8.  해당 Node에 Pod 스케줄링 및 생성
9. kubelet ──"Pod 생성 완료"──> API Server
10. API Server ──"pod 추가(running)"──> etcd
```

### 8. End-to-End 흐름 — Pod 조회

```
1. User ──kubectl get pods──> API Server
2. 인증, 인가, 검증
3. API Server ──조회──> etcd
4. API Server ──응답──> User
```

**클러스터를 직접 확인하지 않는다.** 모든 세부 정보가 etcd에 저장되어 있으므로 DB 내부만 보고 반환한다.
