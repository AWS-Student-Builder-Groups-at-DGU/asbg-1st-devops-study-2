# Day 4. 왜 쿠버네티스가 필요한가

컨테이너만으로 서비스를 운영할 때 생기는 문제와, 쿠버네티스가 그 문제를 어떻게 해결하는지 정리한다. 실습 없이 개념만 다룬다.

## 컨테이너만 쓸 때의 한계

VM 한 대에 컨테이너 몇 개를 띄운 작은 앱을 가정한다.

<img width="1744" height="800" alt="image" src="https://github.com/user-attachments/assets/8ab8e058-e1e2-4e10-a908-3a3f461fd2cc" />

- 컨테이너가 죽으면 사람이 SSH로 들어가 로그를 보고 직접 복구해야 한다
- 새벽이나 다른 시간대에 장애가 나면 24시간 대응 인력이 필요하다

<img width="2684" height="1488" alt="image" src="https://github.com/user-attachments/assets/afc54060-6c32-4a80-8070-37a7eb61f135" />

- 컨테이너가 수백 개인 환경에서 여러 개가 동시에 죽으면 수동 대응이 불가능하다
- VM 자체가 죽으면 앱 전체가 내려간다
- 버전 업그레이드를 수백 개 컨테이너에 수동으로 반복해야 한다
- 외부 노출을 위해 로드밸런서와 라우팅 규칙을 직접 구성해야 한다
- 네트워킹, 리소스 관리, 보안, 고가용성, 장애 허용, 서비스 디스커버리를 전부 사람이 챙겨야 한다

## 쿠버네티스가 해결하는 것

위 문제를 자동화하는 컨테이너 오케스트레이션 도구다.

- 자동 복구 (Self-healing)
- 스케일링
- 로드밸런싱
- 롤링 업데이트
- 서비스 디스커버리
- 리소스 관리와 스케줄링

## 쿠버네티스가 항상 정답은 아니다

<img width="1980" height="600" alt="image" src="https://github.com/user-attachments/assets/a89dd824-2248-4fdb-a414-3499658818ce" />

- 컨테이너 2개짜리 앱에 쿠버네티스를 쓰는 것은 리소스와 비용 낭비다
- EKS, AKS, GKE 같은 관리형 서비스를 써도 클러스터 유지보수, 업그레이드, 패치는 여전히 운영자 몫이다
- 마이크로서비스라고 무조건 쿠버네티스를 쓸 이유는 없다
- 작은 앱은 Docker Compose, VM 위 컨테이너, VPS(DigitalOcean Droplet, AWS Lightsail)로 충분한 경우가 많다

## 핵심 용어

| 용어 | 의미 |
|---|---|
| 오케스트레이션 | 컨테이너 여러 개를 자동으로 배치, 복구, 확장하는 것 |
| 고가용성 (HA) | 일부가 죽어도 서비스가 끊기지 않는 것 |
| 장애 허용 (Fault Tolerance) | 장애가 나도 계속 동작하는 것 |
| 서비스 디스커버리 | 컨테이너끼리 IP를 몰라도 이름으로 찾는 것 |
| 스케일링 | 부하에 따라 컨테이너 수를 늘리고 줄이는 것 |

# Day 5. 쿠버네티스 아키텍처

컨트롤 플레인과 워커 노드를 구성하는 컴포넌트, 그리고 파드가 생성될 때 요청이 흐르는 순서를 정리한다. kind 클러스터에서 컴포넌트를 직접 확인한다.

## 노드

노드는 VM 또는 물리 서버다. 역할에 따라 두 종류로 나뉜다.

- 컨트롤 플레인 노드: 클러스터를 관리하는 컴포넌트가 실행된다. 프로덕션에서는 고가용성을 위해 여러 대를 둔다
- 워커 노드: 실제 워크로드(파드)가 실행된다

## 파드

- 쿠버네티스에서 컨테이너는 단독으로 실행할 수 없고 반드시 파드로 감싸야 한다
- 파드는 쿠버네티스에서 배포 가능한 가장 작은 단위다
- 파드 하나에 보통 컨테이너 1개를 두지만 헬퍼 컨테이너, 모니터링 에이전트, init 컨테이너 등 여러 개를 둘 수 있다
- 같은 파드 안의 컨테이너는 네트워크와 스토리지를 공유한다

## 컨트롤 플레인 컴포넌트

<img width="2848" height="1684" alt="image" src="https://github.com/user-attachments/assets/93a40f1e-1446-4c7b-9698-d6c9950ca3db" />

| 컴포넌트 | 역할 |
|---|---|
| kube-apiserver | 클러스터의 유일한 진입점. 모든 요청을 받아 인증, 인가, 검증한다. etcd에 읽고 쓰는 유일한 컴포넌트 |
| kube-scheduler | 노드가 배정되지 않은 파드를 찾아 CPU, 메모리, requests/limits 등을 고려해 적합한 노드를 결정한다 |
| kube-controller-manager | 노드, 네임스페이스, 디플로이먼트 등 여러 컨트롤러의 묶음. 원하는 상태와 현재 상태를 비교해 차이를 맞춘다 |
| etcd | 클러스터의 모든 상태(노드, 파드, 설정, 시크릿)를 저장하는 키-값 저장소 |

## 워커 노드 컴포넌트

<img width="3032" height="1804" alt="image" src="https://github.com/user-attachments/assets/8e8396ba-79aa-4833-b95f-0f2f9121ff70" />

| 컴포넌트 | 역할 |
|---|---|
| kubelet | 각 노드에서 실행되는 에이전트. 파드를 실제로 생성, 삭제하고 상태를 API 서버에 보고한다 |
| kube-proxy | iptables 등 네트워크 규칙을 만들어 파드 간, 서비스와 파드 간 통신을 가능하게 한다 |

## 파드 생성 흐름

<img width="6572" height="2336" alt="image" src="https://github.com/user-attachments/assets/2c90b8d9-0e29-4b90-84df-be3d5923c124" />

1. 사용자가 kubectl로 파드 생성 요청
2. API 서버가 인증, 인가, 검증
3. API 서버가 etcd에 파드 정보 기록
4. 스케줄러가 노드 미배정 파드를 발견하고 노드를 선택해 API 서버에 알림
5. API 서버가 etcd에 노드 배정 기록
6. 해당 노드의 kubelet이 파드를 생성하고 API 서버에 보고
7. API 서버가 etcd를 갱신하고 사용자에게 응답

조회 요청(`kubectl get pods`)은 API 서버가 etcd만 읽어서 응답한다. 노드에 직접 묻지 않는다.

## 주의할 점

- API 서버는 다른 컴포넌트에 먼저 연락하지 않는다. 스케줄러와 kubelet이 API 서버를 watch하다가 자기 할 일이 생기면 가져가는 구조다
- 스케줄러가 죽으면 새 파드가 Pending 상태에 머무른다
- kubelet이 죽으면 해당 노드가 NotReady가 된다
- Cilium 같은 CNI는 kube-proxy를 대체하기도 한다. kind는 kindnet CNI와 kube-proxy를 함께 사용한다

# Day 6. kind로 로컬 쿠버네티스 클러스터 구성

관리형 서비스(EKS, AKS, GKE) 대신 로컬에 kind 클러스터를 구성한다. 관리형 서비스는 컨트롤 플레인에 접근할 수 없어 트러블슈팅 학습이 어렵다.

## 환경

| 항목 | 버전 |
|---|---|
| OS | Ubuntu 22.04 (VirtualBox) |
| Docker | 최신 stable |
| kind | v0.33.0 |
| Kubernetes | v1.35.8 (CKA 시험 환경과 동일) |
| kubectl | v1.35 |

시험 환경 버전은 새 마이너 릴리스 후 4~8주 안에 갱신되므로 응시 전 공식 FAQ에서 확인한다.

## kind란

<img width="1280" height="720" alt="image" src="https://github.com/user-attachments/assets/fd776502-a623-4a74-9291-f39a5352ebdd" />

Kubernetes IN Docker. 도커 컨테이너 하나를 노드 하나로 취급해 로컬에 클러스터를 만든다. minikube, k3s, k3d 등 대안이 있다.

## 설치

### kind

```bash
curl -Lo ./kind https://kind.sigs.k8s.io/dl/v0.33.0/kind-linux-amd64
chmod +x ./kind
sudo mv ./kind /usr/local/bin/kind
kind --version
```

### kubectl

클러스터와 마이너 버전을 맞춘다.

```bash
sudo apt-get update
sudo apt-get install -y apt-transport-https ca-certificates curl gpg
sudo mkdir -p -m 755 /etc/apt/keyrings
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.35/deb/Release.key | sudo gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo 'deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.35/deb/ /' | sudo tee /etc/apt/sources.list.d/kubernetes.list
sudo apt-get update
sudo apt-get install -y kubectl
kubectl version --client
```

## 단일 노드 클러스터

```bash
kind create cluster --image kindest/node:v1.35.8@sha256:07b2536e30b803ed61d1677a79df6115f798ce64c80f9e22f6ed45afd09323c0 --name cka-cluster1
kubectl cluster-info --context kind-cka-cluster1
kubectl get nodes
```

컨트롤 플레인과 워커가 노드 하나에 같이 있다. 학습용으로는 분리된 구성이 필요하다.

## 멀티 노드 클러스터

`config.yml`

```yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
- role: control-plane
- role: worker
- role: worker
```

```bash
kind create cluster --image kindest/node:v1.35.8@sha256:07b2536e30b803ed61d1677a79df6115f798ce64c80f9e22f6ed45afd09323c0 --name cka-cluster2 --config config.yml
kubectl get nodes
```

생성 과정: 노드 이미지 준비 → 컨트롤 플레인 시작 → CNI 설치 → StorageClass 설치 → 워커 노드 조인

## 컨텍스트 전환

클러스터가 여러 개일 때 kubectl이 바라보는 대상을 바꾼다.

```bash
kubectl config get-contexts
kubectl config use-context kind-cka-cluster1
kubectl config use-context kind-cka-cluster2
```

`*`가 현재 컨텍스트다. kind 클러스터의 컨텍스트 이름은 `kind-<클러스터명>` 형식이다.

## 시험 관련

- 모든 문제는 `kubectl config use-context <이름>`으로 시작한다. 문제에 명령이 주어지므로 복사해서 실행한다
- 컨텍스트를 바꾸지 않고 다음 문제를 풀면 올바르게 작업해도 채점되지 않는다
- 시험 중 접근 가능한 사이트: kubernetes.io/docs, kubernetes.io/blog 및 서브도메인
- kubernetes.io/docs에서 "cheat sheet"를 검색하면 주요 명령을 찾을 수 있다

## 유용한 명령

```bash
kind get clusters
docker ps
kind delete cluster --name cka-cluster1
```

## 참고

- VM 메모리가 8GB면 클러스터 두 개 동시 실행이 느릴 수 있다. cluster1을 삭제하고 cluster2만 유지해도 된다
- VM 재부팅 후 노드 컨테이너가 안 뜨면 `docker start $(docker ps -aq)`
